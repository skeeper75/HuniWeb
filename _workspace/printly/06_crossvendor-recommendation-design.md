# 06 · 크로스벤더 추천 설계 — 가능여부 먼저, 가격은 나중

> 작성: 2026-07-04 · 트리거 = 지니 질문 "여러 회사가 각자 가격으로 파는데 이걸 온톨로지화할 필요가
> 있나? 같은 상품군이라도 회사마다 옵션이 다른데 어떻게 추천하고, 추천 이유가 분명해야 하고,
> 옵션이 회사마다 겹치거나 충돌하면 어느 회사를 추천하나? 상품은 쪼갤 수 없는데."
> **이 문서 = 데이터를 더 채우기 전에 못 박는 추천 설계(keystone). §35 재사용·§36 후보.**
> 상태: ★핵심 모델 확정 · **정책 2건 = 지니 확정 대기**(§8).

---

## 0. 문제 (지니 질문 그대로)

- 후니·와우·레드가 **같은 상품군(예: 명함)**을 팔지만 **옵션군도 가격도 다르다.**
- 어떤 옵션은 한 회사에만 있다(홀로그램박=와우만·귀돌이=후니만 — 실데이터).
- 인쇄 한 건은 **쪼갤 수 없다**(후니에서 인쇄 + 레드에서 박 = 불가).
- 그럼 고객이 원한 옵션이 **회사마다 흩어져 있을 때** 어느 회사를 추천하나?
- 가격을 비교해서 고르라고? 그런데 가격 기준이 다르면?

---

## 1. 결론 3줄 (설계 원칙)

1. **가격 "값"은 온톨로지에 넣지 않는다.** 낡고, 회사 엔진이 권위(원칙3·§33 D-18).
   넣을 건 ① 가격 **경계**(어느 엔진·어느 입력축·어느 출력필드) ② 가격 **의미**(price_basis:
   도매/소매·부가세 포함여부·기본 제공물). 값은 질의 시점에 각 회사 엔진이 계산.
2. **온톨로지화해야 하는 건 "가능 여부"** — 회사별 옵션을 **브랜드-중립 상위 개념**에 걸어
   ("이 사양을 어느 회사가 만들 수 있나"를 그래프로 물을 수 있게). = §35 상위 온톨로지의 진짜 목적.
3. **추천 = 2단계**: ① **가능여부 하드 필터**(만들 수 있나?) → ② **가격/납기 랭킹**(되는 곳 중 어디가 나은가?).
   순서 역전 금지 — 가격이 싸도 **못 만들면 후보 아님.**

---

## 2. 왜 2단계인가 — "쪼갤 수 없다"가 전부

인쇄 한 건은 원자(atomic)다. 그래서 **"어느 회사가 이 사양 전체를 통째로 만드나"가 먼저**고,
가격은 그 다음이다. 옵션 가용성을 4경우로 정리(후니 스탠다드명함 vs 와우 일반명함 40073 실데이터):

| 경우 | 예시 | 판정 |
|---|---|---|
| **한 회사에만 있음** | 홀로그램박·형압·넘버링 = 와우만 / 귀돌이(모서리) = 후니만 | 그 옵션 원하면 **feasibility가 회사를 강제**(가격 안 봄) |
| **양쪽에 다 있음** | 양면4도·무광코팅·오시 | feasibility로 구분 안 됨 → **가격/납기로 랭킹** |
| **양쪽에 다 없음** | 원하는 특수 사양 미지원 | **아무도 못 만듦** → 근접 대안/되묻기 |
| **★충돌** | 홀로그램박(와우만) + 귀돌이(후니만)를 **동시에** | **한 회사로 불가**(쪼갤 수 없음) → §4 |

---

## 3. 온톨로지가 담는 것 (데이터 층) — 전부 §35 재사용

> search-before-mint 결과: **신규 엔티티 없음**. 기존 관계·노드 재사용 + 속성 1개 추가.

| 담는 것 | 어떻게(재사용) | 안 담는 것 |
|---|---|---|
| **옵션 가용성** | 각 회사 옵션 노드 → `instance_of`(X-1) → 상위 개념(U-4 PrintMethod·U-5 Color·U-6 Media·U-8 Finishing…). **feasibility 척추** | 옵션의 가격 값 |
| **가격 경계** | `quote_function`(E19) 회사별(후니=evaluate_price·와우=jobcost·레드=엔진). input_axes·output_field | 계산된 가격 값 |
| **가격 의미** | E19에 **신규 속성 `price_basis`**(retail/wholesale·vat_included·bundled_items) | — (값 아님·의미라서 안전) |
| **같은 상품군** | `same_family_as`(X-3·16쌍 확정) | — |
| **가격모델 상이** | `price_model_differs`(X-4·8쌍 확정·both_authority 한정자) | — |
| **생산 능력** | 라우팅 층 `capability_covers`(E22~E25·§35 routing) — feasibility의 상위 근거 | — |

★**유일한 델타 = E19에 `price_basis` 속성 추가**(엔티티 아님·속성). 나머지 전부 기존 폐쇄목록 23관계 재사용.

## 4. 추천 알고리즘 (절차 = recommendation_function · D-REC 경계)

> ★온톨로지에 넣지 않는다. 원칙2(3추론 분리): 선언=온톨로지·**절차=에이전트/엔진**.
> 온톨로지는 이 알고리즘이 읽는 **데이터**(가용성·경계·의미)만 제공.

```
입력: 고객 사양 = 상품군 + 원하는 옵션 집합 {o1, o2, …}  (각 oi = 상위개념 참조)

Stage A — 가능여부 하드 필터 (feasibility)
  각 회사 v에 대해:  covers(v) = { oi 를 v 가 instance_of 로 보유하는가 } 전부 참?
  feasible = { v | 원하는 옵션 전부 커버 }

Stage B — 분기
  ├ feasible ≥ 1 :  랭킹(feasible, 기준=§8 Q2 정책) → 1순위 추천 + 근거
  └ feasible = 0 :  ★충돌 처리
       - 각 옵션을 "어느 회사가 되는지" 역추적
       - "이 조합은 한 곳에서 불가. o1=와우만, o2=후니만" 명시(원칙4)
       - 되묻기: 어느 옵션을 포기/우선? → 완화 후 Stage A 재실행
       - (상품을 쪼개 두 회사에 넘기는 선택 = 기본 금지)
```

**충돌 시 절대 하지 않는 것**: 회사를 몰래 하나 고르고 원한 옵션을 조용히 버리기.
→ 반드시 **왜 한 곳에서 안 되는지**를 드러낸다(추천 이유 명확성 = 지니 요구).

---

## 5. 추천 이유는 그래프에서 자동으로 나온다

옵션-회사 연결(instance_of)이 있으면 이유 문장이 데이터에서 생성된다:

- "**후니 추천**: 원하신 옵션(양면·오시·무광코팅) **모두 가능** + 500매 17,500원"
- "**레드로 가셔야 함**: 홀로그램박은 **레드만** 됩니다(후니·와우 미지원)"
- "**이 조합은 한 곳에서 불가**: 홀로그램박=와우 / 귀돌이=후니. 하나를 빼시겠어요?"

= 원칙4(모든 제안은 node_id 근거·지어내기 차단)가 추천 이유를 자동 보증.

## 6. 가격 비교가 지금은 위험 (제 우려 = 실측 확정)

- 와우 devshop = **B2B 도매 API가**(일반명함 양면500 = 4,510원·부가세 별도·명함케이스 무료 포함).
- 후니 = **소매가**(스탠다드명함 500 대표사양 = 17,500원).
- → **4,510 vs 17,500을 "와우가 싸다"고 나란히 말하면 거짓.** 티어·부가세·포함물이 다르다.
- 그래서 가격을 **랭킹**에 쓰려면 먼저 `price_basis`를 정규화해야 한다(값이 아니라 "이 숫자가
  무슨 뜻인가"라서 온톨로지에 넣을 수 있고, 넣어야 함). §8 Q2 정책.

## 7. 데이터 채우기에 주는 함의 (우선순위 재정렬)

이 설계가 말해주는 것: **가격 값 수집보다 "옵션을 상위 개념에 거는 것(feasibility 척추)"이 최우선.**

- 지금까지: 와우 일반명함 6부류 채움 + 가격 샘플 확보(잘 됨).
- 다음 최우선: **각 회사 옵션 → instance_of → 상위 개념** 배선(현재 §35는 대표만·전 노드 GAP).
  이게 있어야 Stage A(가능여부 필터)가 실제로 돈다. 없으면 추천 불가.
- 가격은 경계만 배선(값=엔진). 랭킹은 price_basis 정규화 후.

## 8. 미확정 — 지니 확정 대기 (제안 기본값 표기)

| # | 결정 | 제안 기본값(권장) | 대안 |
|---|---|---|---|
| **Q1** | 옵션 충돌 시(한 회사로 불가) 기본 동작 | **충돌 알리고 고객이 선택**(투명·근거·되묻기) | ② 핵심옵션 기준 자동추천+빠진옵션 명시 · ③ 회사별 근접 사양 나란히 |
| **Q2** | 가격의 추천 역할(티어 상이) | **지금은 표시만·price_basis 라벨·정규화 후 랭킹 도입** | ② 바로 랭킹+경고 · ③ 정규화 규칙부터 설계 |
