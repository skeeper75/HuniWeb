> **⑤ 라이브 셀러어드민 실화면은 이 카드에서 확인하지 못했다.** 접속 주소·자격증명이 저장소 어디에도 없다(§6 U-1). 화면 근거가 필요한 진술은 전부 「미확인」으로 남겼다.

## [HARD] 이 문서를 읽는 전제

1. **엔터프라이즈 매뉴얼이 곧 셀러어드민 매뉴얼이다.** 주문 상태별로 문서가 하나씩 있고(`order/` 16문서), 그 문서가 그 화면에서 무엇을 누를 수 있는지를 정의한다.
2. **후니는 현재 PG 결제승인 심사 중이라 실주문이 한 건도 흐르지 않았다.** 아래에서 「관측되지 않음」은 **아직 실행되지 않았다**는 뜻이지 **구현되지 않았다**는 뜻이 아니다(`CARDS-N.md:11-13`).
3. **후니 주문의 상태는 후니가 올린다.** 「쇼핑몰 관리자에서 주문 상태를 손으로 바꾸지 마세요 — 취소 경계가 어긋납니다」(`sdk-guide-live-20260902.txt:968`, 같은 취지 `:925-928`, `:1403-1405`). 즉 **아래 동선의 상태 전이 버튼 대부분은 후니 실무진이 셀러어드민에서 누를 것이 아니다.** 이 문서는 「매뉴얼상 그 화면에서 무엇이 가능한가」를 적고, 후니 계약상 누르면 안 되는 자리를 그때마다 표시한다.

## 1. 일일 운영 동선

셀러어드민 주문관리는 **상태별로 메뉴가 하나씩** 있는 구조다(`order.mdx:8-23`). 그래서 하루 일과는 자연스럽게 「상태 목록을 위에서 아래로 훑는 것」이 된다.

### 1.1 아침 — 무엇을 여는가

| 순서 | 화면 | 무엇을 확인하나 | 근거 |
|---|---|---|---|
| ① | **전체주문 조회** `order/list` | 밤사이 들어온 전체 주문. 기간·주문상태·결제수단·주문접수 유형으로 좁힌다. 기간검색은 **최대 3개월** | `order/list.mdx:9`, `:30` |
| ② | **입금대기 주문** `order/deposit-wait` | 무통장 입금 확인 대상. **가상계좌·에스크로는 PG가 자동 처리**하므로 손댈 것이 없다 | `order/deposit-wait.mdx:11`, `:28-30` |
| ③ | **결제완료 주문** `order/pay-done` | 접수해야 할 신규 주문. **결제완료로 넘어온 지 1영업일 경과분은 「접수지연」으로 자동 집계**된다 | `order/pay-done.mdx:19` |
| ④ | **상품준비중 주문** `order/product-prepare` | 제작 중. **1영업일 경과분은 「발송지연」으로 자동 집계** | `order/product-prepare.mdx:19` |
| ⑤ | **배송준비중 주문** `order/delivery-prepare` | 출고 대기. 송장 입력 자리 | `order/delivery-prepare.mdx` |
| ⑥ | **배송보류 관리** `order/hold-delivery` | 보류 걸어둔 건. **보류 3영업일 경과분은 「배송보류 지연」으로 자동 집계** | `order/hold-delivery.mdx` (경고 블록) |

### 1.2 낮 — 상태를 넘긴다

매뉴얼이 정의하는 표준 진행은 한 방향이다.

```
입금대기 ──[입금확인 처리]──▶ 결제완료 ──[상품준비중]──▶ 상품준비중
   ──[배송준비중]──▶ 배송준비중 ──[배송중]──▶ 배송중
   ──[배송완료]──▶ 배송완료 ──[구매확정]──▶ 구매확정
```

각 화면에 **① 주문상태 선택 · ② 일괄처리 · ③ 다음 단계 버튼**이 공통으로 있다(`order/pay-done.mdx:27-35`, `order/product-prepare.mdx:27-35`, `order/delivery-prepare.mdx:28-39`, `order/delivery-ing.mdx:19-25`, `order/delivery-done.mdx:19-25`, `order/buy-confirm.mdx:16-22`). 즉 어느 상태 화면에서든 조작 방식이 같다.

- **건너뛰기·되돌리기가 열려 있다.** 「특정 시점에 관계없이 특정 상태의 앞 단계로 복귀가 가능하고, 특정 단계를 건너뛸 수도 있다」(`order/list.mdx:73-75`).
- **예외 둘.** 입금대기→결제완료(입금확인)는 **입금대기 목록에서만** 가능하다(`order/list.mdx:76-78`). 에스크로 결제(가상계좌·실시간계좌이체) 건은 **배송완료·구매확정으로 수동 이동 불가**(`order/list.mdx:11`, `:79`).

> **[HARD] 후니에서는 ②~⑦의 상태 전이 버튼을 누르지 않는다.** 후니 서버가 결제 웹훅을 받아 생산 진행에 맞춰 상태를 올리고 송장까지 등록한다(`sdk-guide-live-20260902.txt:755-759`, `:895-898`, `:1398-1400`). 사람이 먼저 누르면 취소 가능/불가 경계가 어긋난다(`:925-928`). 실무진이 셀러어드민에서 실제로 하는 일은 **읽기·응대·조회**이지 상태 운전이 아니다.

### 1.3 개별 건을 파고들 때 — 주문상세

주문번호를 클릭하면 주문상세로 간다(`order/list.mdx:130-132`). 여기가 담당자가 가장 오래 머무는 화면이다.

- **상단 요약** — 쇼핑몰·주문번호·처리 중인 CS 건수·업무메시지 건수(`order/list/detail.mdx:11`)
- **주문상품 정보** — 전체/클레임 상태별 조회, 운영자 직접 클레임 처리, 배송번호 클릭 시 수령자 정보로 이동, **택배사/송장번호 입력**(`order/list/detail.mdx:18-27`)
- **결제정보 / 결제수단** — 배송비 금액·할인혜택 금액 클릭 시 상세, 결제방법·결제일시(`:31-41`)
- **혜택지급내역 / 주문자 정보** — 적립 혜택, 주문자 휴대폰·이메일 변경, **주문자명 클릭 → CRM 창**, SMS 발송(`:45-55`)
- **수령자 정보** — 수령자명·연락처·주소 변경. **택배사/송장번호를 적용하기 전 단계에서만 변경 가능**(`:59-67`)
- **거래명세서 출력** — **배송번호 기준으로만** 출력된다(`:74-77`)
- **업무메시지 보기** — 운영자↔파트너사 담당자 사이의 메시지. **고객에게는 미노출**(`claim-order/message.mdx:11`). 처리 중 건이 있으면 주문리스트에 Flag 아이콘(`order/list/detail.mdx:83-88`)
- **CS 처리 보기** — 상품 상태 변경 정보와 처리 내역, CS 등록·관리(`:94-98`)

### 1.4 저녁 — 마감

- **거래명세서 출력**(주문리스트 ⑥ 또는 주문상세) — 배송번호 기준(`order/list.mdx:95-97`)
- **엑셀 생성·다운로드** — 주문리스트를 엑셀로. **다운로드 사유 입력 + 압축 비밀번호 설정이 강제**된다(개인정보 안전성 확보조치). AES-256 지원 압축 프로그램 권장(`order/list.mdx:139-147`)
- **그리드 컬럼 설정(톱니바퀴)** — 주문리스트에 어떤 항목을 어떤 순서로 볼지, 주문상세창을 어떻게 띄울지. **로그인한 관리자 계정별로 저장**되고 저장 버튼을 눌러야 반영된다(`order/list.mdx:105-110`)

### 2.1 자동 전이 두 개

사람이 누르지 않아도 넘어가는 자리가 둘 있다. 둘 다 **서비스관리 > 쇼핑몰 관리 > 주문처리기간 설정**에서 영업일 기준 1~30일로 지정한다.

| 자동 전이 | 설정 | 근거 |
|---|---|---|
| 배송중 → 배송완료 | 자동배송완료(국내배송) 기간 | `order/delivery-ing.mdx:26-30` |

후니에서 이 두 값을 어떻게 잡았는지는 **미확인**(§6 U-4).

## 3. ★ 후니 주문이 셀러어드민에 어떻게 보이는가

### 3.1 무엇이 실려 오는가 — 도착하는 필드가 이것뿐이다

샵바이 장바구니 항목 하나가 가질 수 있는 필드는 **여섯 개**다(`sdk-guide-live-20260902.txt:1203-1209`):

```
productNo       // 상품에 고정
optionNo        // 상품에 고정
orderCnt        // 수량(= 금액 ÷ 10)
baseProductNo   // 추가상품용
groupId         // 장바구니 그룹
optionInputs    // ★ 주문마다 다른 값을 넣을 수 있는 유일한 자리
```

그리고 후니가 `optionInputs`에 싣는 것은 **텍스트 옵션 두 칸**뿐이다(`:1300-1308`, 2026-08-27 판매중 226개 상품 전건 등록 완료):

| 라벨 | 값 | 성격 |
|---|---|---|
| `huni_order` | 사람이 읽는 **요약 한 줄** (문자열) | 「셀러어드민·주문서·고객 알림에 보이는 값」(`:1304`) |
| `huni_item` | `item_id` — 36자 UUID, **불변** | 기계가 읽는 키. 장바구니 화면·수량 변경·주문 등록이 전부 이 값으로 후니 기록을 찾는다(`:1305-1309`) |

**샵바이에 넣지 않는 것**: 서명 토큰(`huni_token` 라벨을 **일부러 만들지 않았다** — `:1310-1315`), 사양 JSON, 원고 파일 키, 편집기 프로젝트 ID, 금액 내역(`:1128-1136`). 이유는 「텍스트 옵션은 주문조회 응답으로 그대로 읽힌다」이다(`:1006-1007`, `:1164-1165`).

### 3.2 그래서 셀러어드민 주문 상세에 렌더되는 것

**셀러어드민에 후니 주문이 보이는 방식은 이 한 줄로 요약된다 — 「10원짜리 상품 × 수량 N」 + 텍스트 옵션 두 줄.**

| 항목 | 셀러어드민이 보여주는 값 | 실제 의미 |
|---|---|---|
| 상품명 | 샵바이 상품명 (후니 상품코드 `PRD_…`는 `productManagementCd`에 들어 있음, `:1293-1295`) | 그대로 |
| 판매가 | **10원** (판매중 226개 전 상품 일괄 변경 완료, `:1052-1054`) | 금액 표현용 단가 |
| 수량 | **금액 ÷ 10** (15,000원 주문 = 수량 1,500) | ★인쇄 수량이 **아니다**(`:1047-1051`) |
| 옵션 | 자동 생성 옵션 행 하나. 옵션명·옵션값이 상품명과 같고 옵션관리코드가 비어 있음 | 샵바이가 재고를 담으려고 만든 행. 후니는 옵션을 등록하지 않았다(`:1278-1286`) |
| 텍스트 옵션 `huni_order` | `명함 / 스노우250g / 200장` 같은 요약 한 줄 | **담당자가 주문을 알아보는 유일한 근거** |
| 텍스트 옵션 `huni_item` | `2b9aceca-edf5-4b8c-a682-0dec3f96af51` | 후니에 문의할 때 집어 보내는 키 |

가이드가 직접 적은 문장이 결론이다:

> 「요약이 없으면 담당자가 주문을 열어도 **"10원 × 1,500개" 만 보여서** 취소·환불·문의 응대를 할 수 없습니다」 (`:1425-1428`)

즉 **셀러어드민에서 후니 주문의 사양은 `huni_order` 한 줄이 전부다.** 용지·후가공·수량·원고는 샵바이에 없다. 사양의 원본은 후니 DB 한 곳뿐이다(`:1129`).

### 3.3 수량이 그대로 보이는 자리 — 담당자가 매일 보는 화면 포함

가이드가 「샵바이가 직접 내보내는 것」으로 정리한 표(`:1409-1415`):

| 무엇 | 누가 만드나 | 수량(=금액÷10)이 보이나 |
|---|---|---|
| 상품·장바구니·주문서·주문조회 화면 | 자사몰 | 아니오 — 통제 가능 |
| 거래명세표 | 자사몰 | 아니오 — 통제 가능 |
| 주문·결제·배송 알림(문자·알림톡·메일) | 샵바이 | **예 — 설정 필요** |
| 결제창(PG) | 샵바이 → PG | 금액은 정상, 상품명만 노출 |
| 현금영수증·세금계산서 | 샵바이 | **품목·수량 표기** |
| **셀러어드민 주문 화면·판매 통계** | 샵바이 | **예 — 담당자가 매일 봅니다** |

⇒ **운영 동선 전체가 「수량 1,500」을 매일 보는 조건에서 돌아간다.** 알림 템플릿의 `count`·`productNames`(「상품명(수량)」) 치환은 제거를 권고했으나 **수정 여부·시점은 미확정**이다(`:1416-1424`, 가이드 스스로 「★미확정」 표기).

### 3.4 ★ 3라벨 붕괴 — 「표지코팅 / 박가공 / 형압」이 전부 「디지털인쇄」

#### 관측된 사실 (확정)

M1이 라이브 위젯 `WGT_000288`(무선책자)의 `huni:change` 이벤트에서 캡처한 `summary`:

```json
"summary":[ …, {"label":"표지코팅","value":"디지털인쇄"},
                {"label":"박가공","value":"디지털인쇄"},
                {"label":"형압","value":"디지털인쇄"} ]
```

출처: `L0/M1/customer-journey.md:238-244`. 라이브 데모에서 재현됨(`L0/M1/progress.md:96`, lead 검산 `L0/LEAD-VERDICT-M.md:103`).

화면 자체는 정상이다 — 증거 스크린샷 `L0/M1/evidence-set-widget-live.png`에서 표지 구성원 아래 「표지코팅(표지코팅없음/무광라미네이팅/유광라미네이팅)」·「박가공(금유광·은유광·먹유광·동박·적박·청박·홀로그램박·프리즘박)」·「형압(형압(양각)/형압(음각))」 세 줄이 각각 제 선택지를 그리고 있다. **붕괴는 UI가 아니라 `summary` 배열에서 일어난다.**

#### 왜 「디지털인쇄」인가 — 값의 출처는 확정됐다

표지 구성원의 `procs[0]`이 필수공정 `PROC_000004`(디지털인쇄)다. 고객이 아무것도 고르지 않은 초기 상태에서도 state의 `members[].procs`에 이미 들어 있다:

```
WGT_000288 표지 구성원 procs[0] = {"v":"PROC_000004","t":"디지털인쇄","mand":true}
```
(라이브 실측 — `L0/M1/production-payload.md:123`)

세 후가공 컴포넌트가 **각자 선택된 공정을 표시하는 대신, 구성원의 선택 공정 목록 첫 항목(=필수공정)을 공통으로 집어 표시**하는 것으로 보인다. **다만 요약 생성 로직을 코드로 확인하지 않았다** — M1이 명시적으로 「원인 미확인」으로 남겼고(`customer-journey.md:247-249`), 이 카드에서도 코드를 열지 않았다(카드 [HARD] 「코드부터 열지 마라」).

#### 셀러어드민까지의 전파 경로 — 여기가 이 카드의 발견

```
위젯 summary 배열  ({label,value}[])
      │  ① el.submit() / huni:submit 결과에 실림           sdk:1228-1236
      ▼
POST /api/w/v1/cart/items  (토큰 → 후니 항목 보관소)
      │  ② 응답의 summary = 「사람이 읽는 요약 한 줄」(문자열)  sdk:1242-1243
      ▼
POST /cart  optionInputs[inputLabel="huni_order"].inputValue
      │  ③ ②의 문자열을 그대로 싣는다                        sdk:1251-1254
      ▼
샵바이 주문 원장  →  ★셀러어드민 주문 상세 · 주문조회 응답 · 고객 알림 문구
                                                         sdk:1223, :1304, :1425-1428
```

⇒ **후가공 라벨이 틀린 채로 담당자가 읽는 자리까지 그대로 간다.** 담당자에게는 그 한 줄이 사양의 전부이므로(§3.2), 「표지코팅=디지털인쇄」를 읽고 응대·취소·환불 판단을 하게 된다. M2가 같은 위험을 독립적으로 지목했다: 「담당자가 틀린 사양을 보고 응대. 취소·환불 판단이 어긋난다」(`L0/M2/interface-6.md:220`).

#### 확정 / 미확인 경계

| # | 진술 | 상태 | 근거 |
|---|---|---|---|
| 1 | 위젯 `summary` 배열에서 세 후가공 라벨의 value가 전부 「디지털인쇄」로 나온다 | **확정 · 재현됨** | `customer-journey.md:238-244` · lead 검산 `LEAD-VERDICT-M.md:103` |
| 2 | 그 값의 정체는 표지 구성원의 필수공정 `PROC_000004` | **확정(값 일치)** | `production-payload.md:123` |
| 3 | `summary`는 `huni_order` 텍스트 옵션으로 실려 셀러어드민 주문 상세에 렌더된다 | **계약상 확정** | `sdk:1251-1254`, `:1223`, `:1304` |
| 4 | 요약 생성 로직이 「구성원의 선택 공정 전체를 컴포넌트마다 반복 표시」한다 | **미확인 — 추정** | M1이 코드 미확인으로 명시(`customer-journey.md:248`) |
| 5 | 서명 payload의 `procs` 자체는 정상 → 가격·생산 데이터에 영향 없음 | **미검증** | M1 자체 표기 「~로 보인다(미검증)」(`customer-journey.md:250`) |
| 6 | 실제 셀러어드민 화면에서 이 문자열이 어떻게 잘려/줄바꿈되어 보이는가 | **미확인** | 실주문 0건 + 화면 미접근 |
| 7 | 위젯 배열 `summary`와 `POST /cart/items` 응답 문자열 `summary`가 같은 내용을 담는가 | **미확인** | 가이드는 둘이 **다른 형태**임을 경고할 뿐(배열 vs 문자열, `sdk:1236-1238`), 문자열 생성 규칙은 적지 않았다 |

> **[HARD] 7번이 이 결함의 실제 파급을 가른다.** 배열 `summary`(위젯)와 문자열 `summary`(항목 보관소 응답)는 **서로 다른 값**이고, 셀러어드민에 실리는 것은 **후자**다. 후자가 배열을 그대로 직렬화하는지, 별도 규칙으로 다시 만드는지 확인되지 않았다. 배열만 틀리고 문자열은 정상일 가능성이 열려 있다 — **현 시점에서 「셀러어드민에 「디지털인쇄」 3줄이 보인다」고 단정할 수 없다.** 확정된 것은 「배열이 틀렸다」와 「그 계열의 값이 셀러어드민까지 가는 경로에 있다」 둘이다.

이 카드는 진단이므로 수정 방향은 적지 않는다.

| **1:1문의 유형/담당자 일괄 변경** | 문의유형·담당자 변경 | **답변완료 상태 건은 변경 불가**. 등록된 유형/담당자만 선택 가능 | `management/inquiry/list.mdx` (문의유형/담당자 변경 블록) |

### 4.1 일괄 처리의 공통 제약

- **기간검색 최대 3개월** — 그 이상은 나눠서 조회해야 한다(`order/list.mdx:30`).
- **배송번호 단위 vs 주문번호 단위**가 다르다. 배송번호 기준 목록은 배송번호 단위로, 주문번호 기준 목록은 **상품번호 단위**로 상태가 바뀐다 — 한 주문에 2개 상품이면 상품별 개별 전이가 가능하다(`order/delivery-prepare.mdx:32-38`).
- **거래명세서는 배송번호 기준으로만** 출력된다(`order/list.mdx:97`, `order/list/detail.mdx:77`).

## 5. 권한·계정 — 동선이 갈리는 지점

### 5.1 계정 유형 두 가지

| 유형 | 권한 | 근거 |
|---|---|---|
| **마스터** | 모든 어드민 메뉴에 권한 부여 | `service/admin/list.mdx:45` |
| **일반** | **권한그룹 등록 필수**. 그 권한그룹의 권한만 부여 | `service/admin/list.mdx:46` |

계정 등록은 운영자명 + e-메일 주소로 하고, **해당 운영자가 메일을 받아 직접 아이디/비밀번호를 설정해야 「등록완료」**가 된다. 그 전까지는 「등록대기」다(`service/admin/list.mdx:39-42`, `:51-55`).

부가 설정 둘:
- **외부접속** — 접속 IP 설정에 등록한 사내 IP 밖에서의 접속 허용 여부. 「가능」이면 **SMS 추가 인증** 후 접속(`:57-61`)
- **계정 만료일** — 경과하면 그 계정으로 어드민 접속 불가(`:63-65`)

### 5.2 권한그룹이 동선을 가르는 방식

권한그룹은 「어드민 메뉴를 그룹으로 묶어 권한을 설정」하는 장치다(`service/authoritygroup.mdx:9`). 메뉴 단위 권한이 **3단계**다(`:64-66`):

| 권한 | 뜻 |
|---|---|
| 권한없음 | 조회(읽기)·수정(쓰기) 모두 불가 |
| 조회 | 읽기만 |
| 조회/수정 | 읽기 + 쓰기 |

상위메뉴(상품·주문·클레임·회원·전시·운영·프로모션·파트너·서비스) 일괄 설정 + 하위메뉴 개별 설정이 가능하다(`:59-63`).

**동선을 실제로 가르는 두 스위치**:

1. **개인정보 목록조회** — 해제하면 그 권한그룹 운영자에게 **고객 개인정보(이름·이메일·휴대폰번호 등)가 마스킹**되어 보인다(`:51-53`). 배송·CS 담당자와 통계·기획 담당자를 이 스위치로 가른다.
2. **상품담당자(MD권한)** — 상품등록·관리 담당 지정(`:55-56`).

부수 규칙: 운영자가 등록된 권한그룹은 **삭제 불가**(`:22-24`), 동일 권한그룹명으로 **복사등록 불가**(`:26-28`), 권한보유자 수를 클릭하면 소속 운영자 목록이 보인다(`:40-42`).

### 5.3 CS·업무메시지는 등록된 운영자만

「쇼핑몰에 등록된 운영자만 CS등록과 CS처리를 할 수 있다」(`claim-order/cs.mdx` 검색어 선택 블록, 동일 문구 `claim-order/message.mdx`). 즉 **업무메시지·CS의 「등록자명/처리자명」이 곧 운영자 계정**이고, 이것이 담당자별 처리 현황 집계의 기준이 된다(CS 화면 상단의 「본인이 처리 중인 건수」).

### 5.4 부서/직책

운영자 계정 정보에 쓰이는 부서·직책을 별도 관리한다(`service/admin/department.mdx`). 순서 변경 가능. **후니의 부서/직책 구성은 미확인**.
