# Plan B 시나리오 — 외부가 늦어도 10/6 에 문을 여는 길

> 카드 `L0/CARDS-O.md` §O1 할 일 6 — **각각 P0 급**으로 쓴다.
> 근거: `STRATEGY-D34.md` §4 · `L0/M3/auto-vs-human.md` · `L0/N1/payment-approval-flow.md`
> **범위를 줄이는 결정은 PM(지니)이 한다.** 여기서는 「줄이기로 하면 어떻게 도는가」만 놓는다.

## 0. Plan B 가 필요한 이유 — 세 가지가 우리 손 밖이다

| 늦을 수 있는 것 | 왜 우리 손 밖인가 | Plan B |
|---|---|---|
| 간편결제 심사 | 원천사 심사기간(네이버페이 3~4주 · 카카오 2주 · PAYCO 10~12영업일) | **B-1** 카드·계좌이체·가상계좌만으로 오픈 |
| MES 스펙·품목코드 | 상대 시스템 담당자 회신 · 품목코드 매핑 15/269 | **B-2** 수동 생산지시 |
| 원고 자동검사(PitStop) | 라이선스·도입 결정 | **B-3** 사람 검수 |
| NHN 웹훅 정책 회신 | 문서 공백 12건 | **B-4** 방어형 웹훅 소비자 |
| 위젯 없는 77상품 | 상품 준비 자체 | **B-5** 193종으로 오픈 |

**Plan B 는 「못 하니까 대충」이 아니다.** 다섯 가지 전부 **지금 사람이 하고 있는 방식**이거나 **이미 있는 기능**이다. 새로 만드는 것이 아니라 **자동화를 나중으로 미루는 것**이다.

## B-1. 카드·계좌이체·가상계좌만으로 오픈

**전제**: 이니시스 MID 가 발급돼 있고 카드 결제가 열려 있다. 간편결제(네이버·카카오·PAYCO)는 심사 중.

| 단계 | 조작 | 기대결과 | 확인처 | PG 전 |
|---|---|---|---|---|
| B1-1 | 셀러어드민 결제수단 설정에서 열린 수단만 켠다 | 주문서에 카드·계좌이체·가상계좌 세 가지만 보인다. 간편결제 버튼이 아예 안 보인다 | 셀러어드민 결제수단 설정 · 주문서 화면 | Y |
| B1-2 | 카드로 결제한다 | 결제완료(PAY_DONE)가 된다 | 셀러어드민 전체주문 | N |
| B1-3 | 가상계좌로 주문하고 입금하지 않는다 | 입금대기(DEPOSIT_WAIT)로 남고, 입금기한이 **3~7일**로 설정돼 있다 | 주문 상세 입금기한 | N |
| B1-4 | 입금기한이 원고 보관기간(30일)보다 짧은지 본다 | 입금기한 < 30일. 길면 입금 전에 원고가 사라진다 | 셀러어드민 설정값 | Y |
| B1-5 | 나중에 간편결제가 승인되면 켠다 | **설정만 켜면 붙는다. MID 는 승계되고 주문 구조는 바뀌지 않는다** | 셀러어드민 결제수단 설정 | N |

**이 Plan B 의 값**: 간편결제는 **오픈을 막지 않는다.** 승인되는 대로 스위치를 켜면 된다.
**대가**: 간편결제를 기대한 고객의 이탈. 얼마나 되는지는 우리가 모른다 — 미확인.

## B-2. ★ 수동 생산지시 — 이것이 10/6 의 본선이다

**전제**: MES 자동 접수(WCF)가 미구현이고 품목코드 매핑이 15/269(5.6%)다. **오픈 시점에 자동 접수가 될 가능성은 낮다.**
**중요한 사실**: 지금도 사람이 이 경로로 일하고 있다(`auto-vs-human.md` 17~34번). 새로 만드는 흐름이 아니다.

| 단계 | 조작 | 기대결과 | 확인처 | PG 전 |
|---|---|---|---|---|
| B2-1 | 결제된 주문의 payload 를 의뢰서 양식으로 출력한다 | 종이 한 장에 **자재·공정·작업치수·수량·부수·페이지수·원고 위치**가 다 들어 있다 | 출력된 의뢰서 | Y (기존 주문 payload 로 예행) |
| B2-2 | 셋트 상품 주문으로 같은 것을 한다 | 구성원(표지·내지)마다 자재·공정·치수가 **따로** 찍힌다. 셋트 레벨 공정(제본)도 빠지지 않는다 | 출력된 의뢰서 | Y |
| B2-3 | 작업치수(`work_size`)가 비어 있는 주문으로 한다 | 비면 **완성(재단) 치수로 대체**되고, 대체했다는 표시가 의뢰서에 남는다 | 의뢰서 · payload | Y |
| B2-4 | 원고를 현장이 찾을 수 있는지 본다 | 의뢰서의 원고 위치로 **order 버킷의 실제 파일에 도달한다**(payload 의 key 가 아니라 `t_ord_artworks.ord_key`) | order 버킷 · DB 읽기전용 SELECT | Y |
| B2-5 | 의뢰서를 출력한 뒤 주문상태를 올린다 | 후니 쪽 「제작중」이 되고, 샵바이 쪽도 상품준비중으로 올라간다(사람이 셀러어드민에서 올린다) | 셀러어드민 · 후니 주문 화면 | N |
| B2-6 | 하루치 주문(예: 20건)을 이 방식으로 처리해 본다 | 20건이 **하루 안에 처리된다**. 몇 분 걸리는지 재 둔다 | 실측 시간 | N |

**[HARD] B2-6 이 이 Plan B 의 판정이다.** 종단이 도는지가 아니라 **하루 주문량을 사람 손으로 감당할 수 있는지**가 관건이다. 감당 안 되면 오픈 물량을 줄이거나(상품 축소·주문 상한) MES 자동화를 앞당겨야 한다. **재 보지 않고 「될 것 같다」로 넘어가면 안 된다.**

**대가**: 접수 담당자의 손이 하루 종일 묶인다. 그리고 취소·변경이 오면 **의뢰서가 이미 현장에 가 있는지**를 사람이 기억해야 한다.

## B-3. 사람 검수 (프리플라이트 없이)

**전제**: PitStop Server 미도입 · 바이러스 검사도 미구현.

| 단계 | 조작 | 기대결과 | 확인처 | PG 전 |
|---|---|---|---|---|
| B3-1 | 승격된 원고를 담당자가 연다 | 원고 검수 화면(또는 order 버킷 직접)에서 파일이 열린다 | 검수 화면 | Y |
| B3-2 | 재단선·해상도·색상모드를 눈으로 본다 | 문제 있으면 **재업로드 요청**을 건다 | 담당자 판단 | Y |
| B3-3 | 재업로드 요청을 하면 고객에게 알림이 간다 | 고객이 알림톡을 받고 다시 올린다. 회차가 올라간다 | 알림 수신 · 원고 회차 | N |
| B3-4 | 고객이 다시 올린 원고로 검수를 재개한다 | 새 원고로 검수가 이어진다 | 검수 화면 | N |

**[HARD] B3-3 의 알림(파일 재업로드 요청)은 후니 몫인데 미구현이다.** 알림이 없으면 담당자가 **전화하거나 메일을 보내야 한다.** 그것도 Plan B 이긴 하지만, 하루 몇 건까지 감당되는지 B2-6 처럼 재 봐야 한다.

**대가**: 검수 품질이 담당자에 따라 달라진다. 놓친 결함은 인쇄 사고가 된다.

## B-4. 방어형 웹훅 소비자 (NHN 회신 전)

**전제**: 웹훅 정책 7건이 전부 문서 공백. 특히 `CHANGE_ORDER_STATUS` 의 상태값 목록이 없어 **결제→생산 전환 코드를 정확히 짤 수 없다.**

**설계 원칙**: 「상태값으로 분기」를 **나중으로 미루고**, 지금은 **저장을 먼저** 한다.

| 단계 | 조작 | 기대결과 | 확인처 | PG 전 |
|---|---|---|---|---|
| B4-1 | 어떤 이벤트가 오든 원문을 통째로 저장하고 200 을 준다 | 모르는 이벤트가 와도 **버리지 않는다**. 저장에 실패하면 500 을 줘서 샵바이가 실패로 기록하게 한다 | 수신 로그 · DB 읽기전용 SELECT | Y |
| B4-2 | 같은 이벤트가 두 번 오면 어떻게 되는지 본다 | 중복이 두 번 처리되지 않는다(이벤트 식별자 기준 멱등) | 저장된 행 수 | Y |
| B4-3 | 저장된 원문에서 상태값이 실제로 어떤 문자열로 오는지 센다 | 며칠 쌓이면 **상태값 목록이 관측으로 만들어진다** — 문서가 없어도 우리가 만든 목록으로 분기할 수 있다 | 저장된 원문 집계 | N |
| B4-4 | `GET /webhooks/failed` 를 주기적으로 부른다 | 유실분이 복구된다. **조회 창이 7일이므로 폴링 주기는 7일보다 훨씬 짧아야 한다**(하루 1회 이상 권장) | 폴링 로그 · 복구 건수 | Y |
| B4-5 | 폴링을 며칠 멈춰 본다(스테이징에서) | 7일이 지나면 그 사이 유실분은 **영구히 못 건진다** — 이 위험을 실측으로 확인해 둔다 | 실패 목록 | Y |

**[HARD] 재발송 API 가 없다.** `GET /webhooks/failed` 폴링이 유일한 복구 경로다. B4-4 는 선택이 아니라 필수다.

**대가**: 상태 분기가 늦어진다. 그동안 결제완료→상품준비중 전환은 **사람이 셀러어드민에서** 한다(B2-5 와 같은 손).

## B-5. 193종으로 오픈 (위젯 없는 77종 제외)

**전제**: 판매중 269 · 게시 위젯 193 → 77종은 주문 화면이 없다.

| 단계 | 조작 | 기대결과 | 확인처 | PG 전 |
|---|---|---|---|---|
| B5-1 | 77종을 목록에서 「준비중」으로 표시하거나 감춘다 | 고객이 주문 버튼을 누를 수 있는 상품이 **193종뿐**이고, 77종에서 주문이 시작되는 경로가 0건이다 | 자사몰 상품 목록 · 상세 | Y |
| B5-2 | 77종 각각이 왜 위젯이 없는지 분류한다 | 「위젯만 없다」 / 「가격도 없다」 / 「상품 자체가 미완」 셋으로 나뉜다. 오픈 후 순서가 이 분류로 정해진다 | 라이브 DB 읽기전용 SELECT + 상품마스터 | Y |
| B5-3 | 77종에 대한 문의가 오면 어떻게 하는지 정한다 | 「전화 주문」 또는 「오픈 예정 안내」 중 하나로 정해져 있고, 상담이 그 문구를 갖고 있다 | 운영 안내 문구 | Y |

**대가**: 매출 범위가 준다. 어느 77종인지에 따라 크기가 달라지므로 **B5-2 를 먼저 해야 PM 이 판단할 수 있다.**

## 1. Plan B 다섯 개가 동시에 필요하면 — 오픈이 어떤 모습인가

```
고객: 193종 중 하나를 고른다 → 위젯에서 사양·원고 → 담기 → 카드/계좌이체/가상계좌로 결제
후니: 웹훅 원문 저장 (분기는 사람이) → 담당자가 셀러어드민에서 상품준비중으로 올림
      → 원고 사람 검수 → 의뢰서 출력 → 현장 전달 → 공정 → 포장·송장
      → 담당자가 셀러어드민에 송장 입력
고객: 주문조회에서 배송조회
```

**자동인 곳**: 견적·원고 업로드·결제·주문등록·원고승격·알림(샵바이 몫).
**사람인 곳**: 상태 올리기 · 원고 검수 · 의뢰서 · 송장 입력.

**이 모습으로 오픈할 수 있다.** 다만 **사람 손이 하루 몇 건까지 버티는지**(B2-6)를 재지 않고 문을 열면, 오픈 첫 주에 접수가 밀린다. 그것이 이 Plan B 의 유일한 진짜 위험이다.

## 2. Plan B 를 쓰지 않기로 하면 무엇이 선행조건인가

| Plan B | 안 쓰려면 |
|---|---|
| B-1 | 간편결제 원천사 심사가 오픈 전에 끝나야 한다 (지금 신청 완료·심사 중) |
| B-2 | MES 품목코드 269종 매핑 + WCF 스펙 확정 + 접수 코드 구현 |
| B-3 | PitStop 도입 결정 + 라이선스 + 통합 구현 |
| B-4 | NHN 이 웹훅 정책 7건에 회신 |
| B-5 | 77종의 위젯 제작·게시 |

**이 표가 O2 임계경로의 입력이다.** 각 줄이 「언제까지 되면 Plan B 를 안 써도 되는가」의 역산 기준점이다.
