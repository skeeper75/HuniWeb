## 답 (한 줄)

**`huni_token` 라벨은 등록돼 있지 않다 — 전수 297건 중 0건.** 그리고 이것은 **의도된 상태**다(SDK 가이드: 「토큰 전용 라벨을 **일부러 만들지 않았습니다**」).
**문제는 반대편이다 — 자사몰 코드가 없는 라벨에 값을 싣고, 등록된 `huni_item` 은 안 싣는다.**

## 3. 한 일 (카드 할 일 ①~④)

### ① 읽기 전용 GET 만
`GET /products/search`(6페이지) + `GET /products/{productNo}/options`(297건) = **303 GET**.
스크립트가 `method="GET"` 을 상수로 고정한다(`fetch_labels.py:24`) — 다른 메서드를 낼 경로가 없다.
**쓰기·주문·담기·재견적 호출 0건.**

### ② 표본 대신 전수
카드는 표본 ≥10 을 요구했으나 **297건 전수가 가능했다.** `products/search` 는 `size=100` 에서 400 을 내고 **`size=50` 이 상한**이었다(실측). 페이지 6장으로 전건을 받았다.

### ③ 3분류 + 전수
**판매중 226건의 라벨 조합이 단 하나로 통일돼 있다** — `huni_order|huni_item`. 예외 0건.
판매중지 71건은 텍스트 옵션 0개(관리코드 중복분 껍데기).

### ④ 실패 모드는 코드 근거로만
호출 없이 자사몰 코드만 읽었다. 요지:

| 단계 | 무슨 일이 | 코드 근거 |
|---|---|---|
| 담기 | **화면상 정상으로 보인다** — `huni_order` 는 등록돼 있어 값이 실리고, 금액·요약이 거기서 나온다 | `widget-order.ts:102-111` `parseWidget()` 은 `huni_order` 만 기준으로 판단 |
| 토큰 | **빈 문자열이 되어 조용히 통과** | `widget-order.ts:110-111` `?? ""` |
| 수량 변경 | **아무 메시지 없이 반환** — 오류 문구가 `return` 뒤에 있어 안 뜬다 | `cart-page.tsx:118-119` `if (!token) return;` |
| 결제 직전 재견적 | **통째로 건너뛴다** — 담은 시점의 옛 금액이 결제로 간다 | `cart-page.tsx:171-175` `if (!token \|\| …) continue;` |
| 서버 | 토큰이 오면 **400 으로 시끄럽게 거절**하도록 되어 있다 — 그런데 **여기까지 오지 못한다** | `app/api/printly/requote/route.ts:42-48` |

**서버는 막게 만들어져 있는데 클라이언트가 삼킨다** — 이것이 U-2 가 말한 「조용한 실패」의 정확한 형태다.

### 새로 발견한 잔여 1건

판매중지 71건 중 **`136009417` 프리미엄엽서만 `-DUP-` 접미가 없다**(코드 `PRD_000016` 그대로).
같은 코드를 판매중 `132773412` 가 쓰고 있어 **관리코드 중복이 1건 남아 있다.**
