## 3. 원인 — file:line

### 3-1. 받는 쪽은 완성돼 있다 (인쇄개발 · webadmin)

| 서버키 필수 여부 분기 | `widget_api.py:4210-4223` |

**즉 이것은 「양쪽 다 없다」가 아니라 「받는 쪽만 있고 부르는 쪽이 없다」다.**

### 3-2. 이것이 A-1·A-2 형 오진이 아닌 이유

A-1(원고 업로드 stub)·A-2(에디터 미배선)는 「서버엔 있는데 프론트가 안 부른다」였고, **실제로는 위젯이 부르고 있어서** 철회됐다. I-4 는 다르다.

1. 가이드 §10 담당 경계표가 `order/register`·`cart/*`·결제 직전 갱신을 **명시적으로 「자사몰 몫」** 으로 적었다 — 위젯이 대신 부르는 종류가 아니다
2. 가이드 스스로 「이전 안내로 만드셨다면 이 다섯 가지를 확인해 주세요」 체크리스트를 남겼는데(`:1080-1095`) **자사몰이 그중 토큰·요약·라벨 세 항목에 정확히 걸린다**

**오진이 아니라 2026-08-26 계약 개정에 코드가 아직 안 따라온 상태**다.

## 4. 수정 방향

### 4-1. 언제 부르나 — 「결제 완료를 기다리지 마세요」

**주문이 만들어진 직후**다. 결제 승인을 기다리면 안 된다.

> 입금대기(가상계좌·무통장) 주문도 만들어진 직후 바로 등록해야 원고가 보관 기한(30일)을 넘기지 않습니다. (가이드 `:491-497`)

★ 이번 무통장 선개통에서 **이 문장이 곧바로 걸린다.** 무통장 주문은 「입금대기」로 성립하고 입금확인까지 시간이 뜬다 — 그 사이에 등록이 안 돼 있으면 원고가 위험해진다.

### 4-2. 무엇을 보내나

```
POST /api/w/v1/order/register
X-Huni-Server-Key: <서버키>          // item_id 경로면 필수
{ "site_key": "...", "order_no": "20260827-0001", "line_no": "1",
  "item_id": "2b9aceca-…" }          // 또는 "token": "<서명 토큰>" — 둘 중 하나
```

| 필드 | 규칙 | 근거 |
|---|---|---|
| 사양의 출처 | `token` **또는** `item_id` 중 **하나**. 둘 다 없으면 `400 missing_token` | `widget_api.py:4187-4193` |
| `order_no` | 샵바이 주문번호. 100자 상한 | `widget_api.py:4171-4186` |
| `line_no` | ★ **`orderProductOptionNo` 를 그대로 넣는다.** 상태변경 웹훅도 같은 값을 실어 오므로 그걸로 잇는다. 100자 상한 | 가이드 `:817-834` · `:818` |
| 서버키 | `item_id` 경로 = **무조건 필수**. `token` 경로 = 하위호환 선택(단 헤더를 실었는데 값이 틀리면 `403`) | `widget_api.py:4210-4223` |
| IP 화이트리스트 | **쓰지 않는다** — 자사몰이 Vercel 이라 나가는 IP 가 고정이 아니다 | `widget_api.py:132` |
| Rate limit | 600/분(전용 버킷) | `widget_api.py:437` |

**`line_no` 의 조건은 두 개뿐이다** — ① 한 주문 안에서 항목마다 다를 것 ② **재시도해도 같은 값일 것**.

### 4-3. 재시도를 어떻게 짜야 하나

멱등키는 `(site_cd, shop_ord_no, shop_line_no)` 이고 **DB UNIQUE 인덱스가 유일한 심판**이다.

| 상황 | 서버 응답 | 자사몰이 할 일 |
|---|---|---|
| 정상 | `{ok:true, already:false, qty, total}` | 완료 |
| 같은 자리·같은 사양 재시도 | `{ok:true, already:true, …}` | **성공으로 취급** |
| 같은 자리·**다른 사양** | `409 order_mismatch` | **재시도하지 말 것** — 중간에 재견적이 돌았다는 뜻 |
| UNIQUE 위반인데 행이 없음 | `409 register_failed` | 조사 필요(조용히 성공시키지 않는다) |

★ **`total` 을 문자열로 비교하지 말 것.** 서버가 신규/재시도 모두 `Decimal.quantize(0.01)` 로 정규화하지만, 라이브 실측에서 「같은 주문인데 첫 응답과 재시도 응답의 문자열이 달라 금액이 바뀌었다고 오판」한 사례가 있었다(`widget_api.py:4028-4039`).

★ **재시도는 같은 토큰(또는 같은 사양)으로.** 중간에 재견적이 돌면 `409` 가 나고, 그러면 `_promote_artwork` 가 영영 안 돌아 **원고가 tmp 에서 소멸한다.**

### 4-4. 부분 실패 — 자사몰이 안 해도 되는 것

- 원고 승격 실패는 **등록 응답을 막지 않는다.** 실패해도 `200` 이다. 승격 모듈이 주문을 **보류(HOLD)** 로 세우고 사유를 남긴다 — 「쇼핑몰은 이미 결제된 주문을 되돌릴 수 없고, 파일 문제를 고객에게 알리는 것은 우리 몫」
- 따라서 **자사몰은 승격 결과를 신경 쓰지 않아도 된다.** `200` 이면 끝이다

### 4-5. 선행조건 — 서버키 (★ 함정 주의)

| # | 무엇 | 누가 |
|---|---|---|
| 1 | 서버키(`hsk_` 접두, 50자 내외) 발급 | **후니(인쇄개발)** — 평문 미보관, SHA-256 해시만(`t_wgt_sites.svr_key_hash`) |
| 2 | 자사몰 서버 환경변수에 보관 | 쇼핑개발 |
| 3 | 헤더로 전송 | 쇼핑개발 |

★ **발급 전에 헤더를 미리 실어 보내면 `403 bad_server_key` 로 결제 경로 3개(verify·requote·order/register)가 한꺼번에 막힌다.** 가이드가 가장 강하게 경고하는 함정이다. **발급 → 확인 → 그 다음에 헤더 추가** 순서를 지킬 것.

`item_id` 경로로 갈 것인지 `token` 경로로 갈 것인지가 **서버키 발급의 선행 여부를 가른다.** `DEV-REQUEST-01` 이 `item_id` 채택을 권하므로 **서버키 발급이 사실상 필수 선행**이다.

### ★ 원장 갭 1건 (lead 에게 넘김 — Q1 반영 대상)

**「자사몰이 `order/register` 를 호출한다」에 해당하는 원장 행이 없다.**
전수 확인: `L5/P1/unified-ledger-v2.csv` 504행 중 `order/register`·`S2S` 를 언급한 행은 `STD-MFG-001`(인쇄개발·수신측)·`STD-ORD-029`(재견적) **2건뿐**이고, **호출측(쇼핑개발) 행은 없다.**

즉 원장의 「10/6 실제 걸림 쇼핑개발 174건」에 **이 항목이 안 들어가 있다.** 오픈을 막는 가장 큰 쇼핑개발 항목인데 세어지지 않았다.
→ **신규 행 신설 제안**: 「주문 생성 직후 후니 주문등록 S2S 호출(`order/register`)」 · 담당 쇼핑개발 · 상태 `new` · 오픈차단여부 `작업 항목` · 돈 Y · 주문 Y · 근거 `L0/M2/interface-6.md` I-4 · `ARCHITECTURE-v2.md` A-15.
