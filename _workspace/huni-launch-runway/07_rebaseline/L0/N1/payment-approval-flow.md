# PG 결제승인 흐름 — MID·지불수단이 무엇을 좌우하고, 승인이 무엇을 여는가

> N1 축2 산출물 · 작성 2026-09-02 · 읽기전용 조사
> 카드 [HARD] 전제: `t_ord_orders` 0행 = **미구현이 아니라 미실행**. 이 문서의 모든 관측은 그 구분을 지킨다.

근거 순서는 카드가 정한 대로 ① 매뉴얼(PG PDF 2종) → ② 라이브(개통 도크·스크린샷) → ③ 샵바이 매뉴얼/API 순으로 읽었다.

## 0. 한눈에

돈이 흐르려면 **세 겹의 승인**이 각각 따로 떨어져야 한다. 하나가 열려도 나머지가 닫혀 있으면 결제창은 뜨지 않는다.

| 겹 | 여는 주체 | 여는 대상 | 이 문서에서 |
|---|---|---|---|
| ① 가맹점 계약 | KG이니시스 | 가맹점 자체 | 후니는 **이미 기존 가맹점** — 신규 계약 불필요 |
| ② MID(상점ID) | KG이니시스 | **사이트 1개** | §2 |
| ③ 지불수단 | KG이니시스 + **원천사**(카드사·간편결제사) | **결제수단 1종** | §3 |
| ④ 쇼핑몰 반영 | 샵바이 + 후니 개발팀 | 결제창 노출 | §4 |

핵심 분리: **MID = 「어느 사이트가 결제를 받는가」**, **지불수단 = 「그 사이트가 어떤 수단을 받는가」**.
둘은 같은 메뉴(`변경/추가 → 2. 결제서비스 변경/추가`)의 **다른 항목**이고, 심사 주체도 기간도 다르다.

## 1. PG 심사 파이프라인 — 계약부터 운영까지

### 1-1. 전체 순서

```
[0] 가맹점 계약        ─ 후니는 완료 상태(기존 가맹점)
      ↓
[1] 가맹점관리자 로그인 ─ GID/MID 10자리 + PW, PC 전용, 첫 로그인 시 추가인증 등록 필수
      ↓
[2] 사이트 구축 완료    ─ ★ MID 신청의 선행조건(§1-3). 공사 중 신청 = 반려
      ↓
[3] MID 추가발급 신청   ─ 변경/추가 → 2. 결제서비스 변경/추가 → 상점ID 추가발급
      ↓
[4] 이니시스 사이트 모니터링 심사 ─ 3~5영업일 (카드 재심사 시 +7~10영업일)
      ↓
[5] MID 발급 + 키파일 메일 수신  ─ 신청 팝업에 적은 이메일로 옴
      ↓
[6] 지불수단 추가 신청  ─ 같은 메뉴 → 지불수단 추가 (수단별 별건)
      ↓
[7] 원천사 심사        ─ 수단마다 기간이 다름 (3~5영업일 ~ 3~4주, §5)
      ↓
[8] 승인 SMS + 신청현황 반영 ─ 변경/추가 → 8. 서비스 신청현황
      ↓
[9] 쇼핑몰 연동         ─ ★ 이니시스 승인 ≠ 결제창 노출. 샵바이 설정 + 개발팀 작업
      ↓
[10] 실결제 리허설 → 운영
```

### 1-2. 각 단계가 무엇을 막는가(게이트)

| 단계 | 이것이 없으면 막히는 것 | 근거 |
|---|---|---|
| [1] 로그인 | **모든 신청 화면 자체**. 이니시스는 기존 가맹점의 사업자정보 변경·MID 추가·지불수단 추가/변경·계좌 변경을 전부 가맹점관리자 온라인 신청으로만 받는다(서류 발송 없음) | `docs/huni/shopby-onboarding/src/partpg1.html` (이니시스 안내 인용) |
| [2] 사이트 구축 | **MID 신청 접수 자체**. 「사이트 구축 완료 후 신청 가능」·「사이트 URL 주소 필수 기재(기재한 URL로 모니터링 후 아이디 추가 진행)」 | `docs/huni/PG/MID추가및변경_Manual_251202.pdf` p.2 |
| [3]→[4] 심사 | MID 발급 | 같은 PDF p.3 「신청 후 처리 기간 3-5영업일 소요」 |
| [5] 키파일 | **결제 연동**. 신청 팝업 이메일 칸에 「키파일 수신 이메일 입력」이라 적혀 있고, 이 파일이 쇼핑몰↔이니시스 연결 인증 파일이다. 놓치면 MID를 받고도 붙이지 못한다 | 같은 PDF p.3(팝업 캡처) · `src/partpg2.html` |
| [6]→[7] 원천사 심사 | 해당 수단 1종의 사용 | `docs/huni/PG/지불수단 추가 및 변경 Manual_251202.pdf` 각 탭 「※참고사항」 |
| [9] 쇼핑몰 연동 | 결제창 노출. 「이니시스에서 결제수단이 승인되면 그다음은 쇼핑몰에서 그 수단을 켜는 일이 남습니다 … 개발팀 몫」 | `src/partpg3.html` |

### 1-3. MID 신청 반려 3조건 — 심사의 실체

이니시스는 신청을 받고 **사람이 사이트를 직접 열어본다**. 매뉴얼이 반려 사유를 명시한다.

> 「사이트 내 하단정보 / 판매상품 3개 이상 노출 / 서비스 제공기간 또는 상품 배송기간이 확인되어야 하며,
> 미비한 경우 상점ID 추가 불가로 신청 반려됩니다.」 — `MID추가및변경_Manual_251202.pdf` p.2, `src/partpg2.html` 재인용

추가로 같은 페이지가 명시하는 지연·변동 요인:

- **사업자정보 불일치** — 「사이트 하단 사업자정보와 이니시스에 등록된 사업자정보 불일치 시 아이디 추가 지연 또는 반려될 수 있음」
- **판매상품/상품금액/서비스 제공기간/배송기간에 따라** 보증보험 추가 가입 안내, **월 정산한도 및 정산주기 변경**, **카드 1회 한도 및 일부 지불수단 제한** 가능
- **입점 불가 상품** 포함 시 입점 제한 또는 일부 카드사 차단
- **판매 상품이 입점 당시와 변경된 경우 카드 재심사** — 재심사 시 7~10영업일 추가

인쇄물 중심이면 큰 변수는 낮지만, 굿즈·팬시류가 늘었으면 재심사 사유에 걸릴 수 있다(`src/partpg2.html` 08단계).

### 1-4. 진행 상황을 보는 곳

`변경/추가 → 8. 서비스 신청현황`. 신청일·신청서비스·처리결과(처리상태/처리(반려)사유)가 표로 나온다.
「신청 후 접수 확인 및 처리 진행 사항 확인 가능」·「처리 완료 및 반려의 경우 신청 시 기재된 H/P로 결과 SMS 발송됨」
— `MID추가및변경_Manual_251202.pdf` p.4, `지불수단 추가 및 변경 Manual_251202.pdf` p.14(13. 서비스 신청 현황).
PDF 캡처의 예시 행이 `접수대기` 상태다. 수단별로 여러 건을 신청하면 **건마다 따로 표시**된다(p.14는 신용카드ARS·구에스크로 2행).

## 2. MID(상점ID)가 좌우하는 것

### 2-1. 정의

| 용어 | 이니시스 원문 정의 | 실무 의미 |
|---|---|---|
| **MID** | INIpay서비스 이용시 가맹점에 부여되는 고유의 계정으로 **10자리**로 구성됨(영문 대/소문자 구분함) | **쇼핑몰 한 개에 붙는 결제 계정.** 사이트가 늘면 MID도 늘린다 |
| **GID** | (동일 문구) 10자리 | 여러 MID를 묶어서 보는 상위 계정 |

— `src/partpg1.html` (inicis.com 2026-09-01 직접 확인 인용)

### 2-2. MID가 결정하는 것 (전수)

1. **어느 URL이 결제를 받는가.** 신청서 「URL」 칸은 필수이고, 이니시스가 그 주소를 열어 심사한다(§1-3). MID는 그 사이트에 고정된다.
2. **호스팅 귀속.** 신청서 「1) 요청 내용」 표는 7줄 중 **한 줄만** 체크하는 구조다.

   | 줄 | 대상 | 호스팅정보 칸 |
   |---|---|---|
   | 1. 카페24 ID | 카페24 몰 | 카페24 어드민 / 멀티몰번호 |
   | **2. 고도몰 ID ← 후니** | 고도몰·NHN커머스 계열 | **고도몰 PG ID (GODO~)** |
   | 3. 코드엠 ID | 코드엠샵 | — |
   | 4. 코리아포트원 ID | 포트원 연동 | — |
   | 5. 기타 호스팅 ID | 목록 외 호스팅사 | 호스팅사명 |
   | 6. 독립몰 ID 최초 신청 | 자체 구축 첫 몰 | [연관리비 결제하기] 버튼 |
   | 7. 독립몰 ID 추가 신청 | 자체 구축 추가 | — |

   후니가 「2. 고도몰 ID」인 이유: 이니시스 협약 주체가 고도몰이고 샵바이는 같은 NHN커머스 솔루션이라서다.
   샵바이 규격서 내부도 고도몰 체계를 그대로 쓴다 — 상점번호 필드명이 `godoSno`, 솔루션 구분값이 `SHOPBY`/`GODOMALL` 한 쌍.
   (`src/partpg2.html` 03단계 · `docs/shopby/shopby-api/admin-shop-public.yml`, `workspace-server-public.yml`)
3. **비용 부과 여부.** 호스팅 귀속이 곧 요금 구간이다. 「호스팅에 따라 상점ID 추가 비용이 발생할 수 있으며, 발생 시 별도 연락드릴 예정입니다.」
   「독립몰 ID 최초 신청 시, 연관리비 33만원 결제 후 신청 바랍니다」는 **독립몰(=이니시스 미계약 호스팅) 전용** 문구이고,
   [연관리비 결제하기] 버튼도 6번 줄에만 붙는다. 후니는 제휴 호스팅사(고도몰) 경유라 대상이 아니다.
   공개 요금 범위는 초기등록비 면제~300,000원 / 연관리비 면제~300,000원(VAT 별도). 「납부한 금액은 계약 해지 시에도 환급이 불가」,
   비용 발생 시 「납부 내역이 확인이 되어야 상점 ID 발급이 가능」. (`src/partpg2.html` 「돈이 드나요」 절)
4. **정산주기와 정산계좌.** 신청서 3) 지급 계좌에서 기존 계좌 승계 또는 변경. 「개인사업자는 사업자명/대표자명 계좌 모두 가능하나,
   **법인사업자는 법인명 계좌만** 요청 가능」.
5. **초기 지불수단 세트.** 2) 서비스 선택에서 「기존 상점ID와 동일하게」를 고르면 「선택하신 상점 ID가 사용중인 지불수단이 체크됩니다」.
   에스크로 가맹점은 「추가발급 상점 ID에도 동일하게 에스크로가 적용됩니다」(수수료·종류가 바뀌는 경우 제외).
6. **카드사매입방식.** 자동/수기(직접매입요청)은 **「MID 추가 시에만 신청 가능」** — 즉 MID 발급 이후에는 지불수단 화면에서 바꿀 수 없는 축이다.
   (`지불수단 추가 및 변경 Manual_251202.pdf` p.2 신용카드 탭 ※참고사항)

### 2-3. MID가 결정하지 **않는** 것

- 기존 사이트의 결제. 「기존 MID는 그 자리에 그대로 있고, 옆에 새 MID가 하나 생기는 것뿐」. 옛 사이트 정리는 `중지 및 해지 신청` 메뉴의 별건.
- 결제창에 실제로 뜨는 수단 — 그건 §3 + §4의 몫.

## 3. 지불수단(결제수단) 설정이 좌우하는 것

MID와 **다른 레버**다. 메뉴 위치는 옆이고(`2. 결제서비스 변경/추가 → 지불수단 추가`), 심사 주체·기간·비용 구조가 전부 다르다.

### 3-1. 비용 구조가 MID와 반대다

> 「별도의 지불수단 추가 비용은 부과되지 않으며, **거래 발생 시** 각 지불수단 별 수수료가 적용됩니다.」
> — `지불수단 추가 및 변경 Manual_251202.pdf` p.2 상단 경고문(모든 탭 공통), `src/partpg3.html` 재인용

즉 **여는 것 자체는 무료**이고 거래가 일어날 때만 수수료가 나간다. 쓸지 말지 애매한 수단을 미리 열어두는 것이 손해가 아니다.

### 3-2. 심사 주체가 이니시스가 아니다

> 「각 지불수단은 **원천사 심사 승인 후** 이용 가능합니다.」 (원천사 = 카드사·간편결제사)
> 「지불수단과 부가요청 내용은 **상점ID 구분(업종, 업태, 호스팅 이용 등)에 따라 적용 불가**할 수 있습니다.」
> — 같은 PDF p.2 상단 경고문

두 번째 문장이 §2와의 연결점이다. **MID의 성격이 지불수단의 가부를 제약한다** — 예: 「쇼피파이 호스팅사의 경우 국내 신용카드
지불수단만 사용 가능하여 [계좌이체 / 가상계좌] 신청 불가」(p.3 계좌이체 탭·p.4 가상계좌 탭 ※참고사항).
후니는 쇼피파이가 아니라 고도몰 협약 아래 샵바이라 이 제한에는 걸리지 않는다(`src/partpg3.html`).
간편결제는 업종 제한이 있다 — 「일부 업종(현금, 상품권, 포인트충전)의 경우 간편결제 이용이 불가」(p.6). 인쇄물 판매는 해당 없음.

### 3-3. 어느 MID에 적용되는가 — 가장 많이 빠뜨리는 지점

신청 팝업 하단에 상점ID 목록이 붙고 이렇게 적혀 있다.

> 「귀사의 발급 MID는 아래와 같습니다. **(로그인한 상점 ID제외)** 신청하시는 본 MID 외에 추가로 신청하실 MID를 선택해 주세요.」
> — `지불수단 추가 및 변경 Manual_251202.pdf` p.13 (12. 인증 진행, ④ 신청하기 팝업)

| 대상 | 목록에 | 결과 |
|---|---|---|
| 지금 로그인한 MID | **안 보임** | 자동 적용 (없는 게 정상) |
| 그 외 보유 MID | 보임 | **체크한 것만** 같이 적용 |

따라서 신규 MID 발급 후 기존 MID로 로그인해 지불수단을 신청하면 **새 MID를 목록에서 체크하지 않는 한 새 사이트에는 열리지 않는다.**
반대로 새 MID를 아직 못 받은 상태에서 지금 여는 수단은 기존 MID에만 적용되므로, 발급 후 한 번 더 신청해야 한다.
회피책은 §2-2의 5 — MID 신청 시 「기존 상점ID와 동일하게」. (`src/partpg3.html` 01단계)

### 3-4. 지불수단 설정이 좌우하는 **운영 동작** (수단별 실무 스위치)

### 5-2. 승인이 **즉시**인가 **이연**인가 — 고객 결제 시점 기준

앞의 표는 「가맹점이 수단을 여는 데 걸리는 시간」이고, 아래는 「고객이 결제를 눌렀을 때 승인이 즉시 떨어지는가」다.
**둘은 다른 축이고, 가상계좌에 입금대기 상태가 존재하는 이유가 여기 있다.**

| 결제수단 | 결제 승인 | 왜 | 샵바이 주문 상태 진입점 |
|---|---|---|---|
| 신용카드 | **즉시** | 카드사 실시간 승인 | 결제완료 |
| 실시간계좌이체 | **즉시** | 은행 실시간 출금 승인 | 결제완료 |
| 간편결제(카카오페이·네이버페이·토스·애플페이·삼성페이·PAYCO 등) | **즉시** | 원천사 실시간 승인 | 결제완료 |
| 휴대폰 결제 | **즉시**(승인은 즉시, 대금 회수는 이동통신사 청구) | — | 결제완료 |
| **가상계좌(무통장입금)** | **이연** | 고객에게 계좌만 발급하고, 실제 **입금은 나중에 사람이 한다.** 발급 시점에는 돈이 오지 않았으므로 결제완료가 될 수 없다 → **입금대기** 상태가 존재. PG 시스템이 입금을 확인하면 **자동으로** 입금확인 처리되어 결제완료로 이동하고, 운영자 수동 처리는 **불가** | 입금대기 → (PG 자동) → 결제완료 |
| **무통장입금(계좌이체 아님 · 샵바이 `ACCOUNT`)** | **이연 + 수동** | 계좌만 안내하고 PG를 거치지 않으므로 PG가 입금을 알 방법이 없다 → **운영자가 입금을 확인하고 「입금확인 처리」를 수동으로** 해야 결제완료가 된다 | 입금대기 → (운영자 수동) → 결제완료 |
| 상품권 | 미확인(원천 승인 방식 문서 미기재) | — | 미확인 |
| 에스크로(실시간계좌이체/가상계좌) | 기반 수단을 따름 | 가상계좌-에스크로는 입금대기 경유, PG 자동 확인 | `order/deposit-wait.mdx` ③ |

> 근거: `docs/shopby/shopby_enterprise_docs/order/deposit-wait.mdx`
> — 「주문자가 '무통장입금' 또는 '가상계좌'로 결제수단을 선택하고 … 결제금액을 **입금하기 전 상태인 입금대기 상태**」
> — 「무통장 입금대기 주문 건은 운영자가 결제금액 입금을 확인하고, '입금확인 처리'를 **수동으로** 진행해 결제완료 상태로 변경해야 합니다」
> — 「'가상계좌, 에스크로' 결제수단의 입금대기 주문 건은 **PG 시스템에서 입금이 확인되면 자동으로** 입금확인 처리되어 결제완료 상태로 변경 … 수동으로 '입금확인 처리'가 **불가**」
> — 「**입금대기 상태의 주문 건부터 상품의 재고가 차감**됩니다」

에스크로가 붙으면 결제완료 이후도 제약된다 — 「결제완료 상태의 에스크로 결제 주문 건은 '상품준비중~배송중' 상태로 수동 변경은 가능하고,
**'배송완료'와 '구매확정' 상태로 변경이 불가**」(`order/pay-done.mdx` 상단 Callout).

### 5-3. 샵바이 `payType` enum — 매뉴얼이 부른 수단이 API에 어떻게 실리는가

`docs/shopby/shopby-api/order-shop-public.yml:15252-15300` (`payType`, 결제수단). 이니시스 매뉴얼이 다루는 수단에 해당하는 값만 추린다.

### 6-3. 이 어긋남을 어떻게 읽어야 하나

두 가지 사실이 충돌한다.

1. 원장·게이트 산출물은 「이니시스 **계약 미체결**」이라 적는다.
2. 개통 도크(2026-09-01)는 「후니는 **이미 이니시스 가맹점**입니다. 새로 계약하거나 서류를 부칠 일이 없습니다」라고 적는다
   (`src/partpg1.html`).

두 진술은 **다른 것을 가리키고 있을 가능성이 높다** — (1)은 「샵바이 라이브몰에 붙는 PG(=새 MID) 계약」, (2)는 「법인 단위 가맹점 계약」.
그렇게 읽으면 모순은 아니고, 현재 위치는 **「기존 가맹점 자격은 있으나 신규 사이트용 MID는 아직 신청 전」**이 된다.
다만 이 해석 자체가 추론이므로 **미확인으로 남긴다.**

### 6-5. `t_ord_orders` 0행에 대한 판독

카드 전제대로 **0행은 「미구현」의 증거가 아니다.** 위 §4-2가 보여주듯 결제완료 이후 사슬(웹훅 → `/order/register`)은 계약 문서가 이미 존재하고
SDK 가이드가 라이브에 게시돼 있다(`M2/_evidence/live-verification-20260902.md` L-1). 결제 경로가 열리지 않았으므로 **한 번도 실행되지 않았을 뿐**이다.
다만 이 문서가 확인한 범위에서 **왜 실행되지 않았는가의 정확한 지점(신청 전 / 심사 중 / 승인 후 연동 미완)은 §6-1대로 미확인**이다.
