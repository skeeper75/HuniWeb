RULE-ID: RULE-01
SEVERITY: BLOCKER
겨냥 대상: §4.1 `Intent`, §6 T0/T1 “숫자를 만들지 않는다”
지적: 설계는 LLM Actor가 `qty`와 `budget_krw`를 숫자 값으로 담은 `Intent`를 만들게 한다. `IntentValidator`는 타입·도메인·원문 span 대조만 적고, 숫자 재파싱 권위를 결정론 파서에 둔다는 규정이 없다. 루브릭은 LLM 출력이 수량·코드값을 직접 산출하는 경로를 RULE-01 위반으로 본다.
실패 시나리오: 입력 = “명함 500장, 고급스럽게, 예산 5만원” / 기대 = 결정론 파서가 원문에서 `qty=500`, `budget_krw=50000`을 산출하거나 불일치 시 되묻기 / 실제(예상) = Actor가 `qty=5000` 또는 `budget_krw=500000`을 내면 int 검증을 통과하고 `evaluate_price(..., qty)`가 그 수량으로 가격을 계산한다.
근거: _workspace/huni-worldmodel/04_design/evaluation-rubric.md:57-59, _workspace/huni-worldmodel/04_design/design-FINAL.md:243-256, _workspace/huni-worldmodel/04_design/design-FINAL.md:260-263, _workspace/huni-worldmodel/04_design/design-FINAL.md:469-479, raw/webadmin/webadmin/catalog/pricing.py:428-451

교정안: LLM은 숫자 값이 아니라 span·단위 후보만 내고, `IntentValidator` 또는 별도 `NumericIntentParser`가 수량·예산을 결정론적으로 산출해야 한다. `qty`/`budget_krw`는 재파싱 결과만 심볼릭 계층에 진입시킨다.

RULE-ID: RULE-04
SEVERITY: BLOCKER
겨냥 대상: §4.2 `Outcome.price.amount`, §4.6 `budget_penalty`, §6 T5 예산 문구
지적: 설계의 `price.amount`는 `evaluate_price.final_price`인지, 고객 청구액(VAT 포함)인지 정의하지 않는다. live widget은 `evaluate_price` 결과를 공급가로 보고 VAT 10%를 더해 `payload.total`을 서명한다. 그런데 설계의 Scorer와 PhraseRenderer는 `price.amount`로 “예산 안”을 판단한다. 공급가 기준 예산 통과가 청구액 기준 예산 초과가 되는 돈 오류 경로다.
실패 시나리오: 입력 = 유효 상품/옵션/수량, 발화 “예산 5만원”, 상태 = `evaluate_price.final_price`가 49,000원인 후보 / 기대 = 고객이 실제 낼 53,900원(VAT 포함)을 기준으로 예산 초과 판정 / 실제(예상) = 설계는 49,000원으로 `budget_penalty`와 “예산 안입니다” 문구를 만들고, `/handoff`는 53,900원을 서명한다.
근거: _workspace/huni-worldmodel/04_design/design-FINAL.md:284-286, _workspace/huni-worldmodel/04_design/design-FINAL.md:366-368, _workspace/huni-worldmodel/04_design/design-FINAL.md:508-513, raw/webadmin/webadmin/catalog/widget_api.py:1150-1157, raw/webadmin/webadmin/catalog/widget_api.py:1855-1859, raw/webadmin/webadmin/catalog/widget_api.py:1942-1944
내가 틀렸다면: 설계가 `price.amount`를 VAT 포함 청구액으로 명시하고, `budget_penalty`와 PhraseRenderer가 항상 `payload.total` 동등값을 쓰도록 정의돼 있으면 철회.
교정안: `Outcome.price`를 `supply_amount`, `vat_amount`, `payable_total`로 분리하고, 예산·고객 문구·관측 대조는 `payable_total` 기준으로 고정한다. 공급가를 노출할 때는 “공급가”로 별도 표기한다.

RULE-ID: RULE-13
SEVERITY: MAJOR
겨냥 대상: §6 T-1 `PREMISE_FAIL` 기록, §4.7 `sim_escalation`
지적: 설계는 G0/G0.5/G0.9 전제 감시 실패를 `sim_escalation(esc_kind='PREMISE_FAIL')`로 남긴다고 하지만, `sim_escalation.esc_kind` 허용 집합과 `route_to` 매핑에는 `PREMISE_FAIL`이 없다. 전제 실패 검출은 돈 판정 전 방어선인데, 기록·라우팅 스키마가 자기 주장과 맞지 않는다.
실패 시나리오: 입력 = 임의 견적 시작, 상태 = G0.9 digest 불일치 / 기대 = 루프 중단 + `PREMISE_FAIL` 기록 + 담당 route_to 지정 / 실제(예상) = 문서상 허용 `esc_kind`에 없어서 insert 실패, 미분류 저장, 또는 route 누락 중 하나가 된다.
근거: _workspace/huni-worldmodel/04_design/design-FINAL.md:386-399, _workspace/huni-worldmodel/04_design/design-FINAL.md:467, _workspace/huni-worldmodel/04_design/design-FINAL.md:565-568, _workspace/huni-worldmodel/04_design/design-FINAL.md:613-618
내가 틀렸다면: `esc_kind`가 실제 DDL에서 enum이 아닌 open text이고, `PREMISE_FAIL` route가 별도 절에 정의돼 있으면 철회.
교정안: `PREMISE_FAIL`을 `esc_kind`와 route table에 추가하거나, `BINDING_MISSING`, `DIM_PARITY_FAIL`, `DIGEST_STALE`로 쪼개 명시한다. escalation 기록 실패 자체도 fail-closed 표에 넣어야 한다.
