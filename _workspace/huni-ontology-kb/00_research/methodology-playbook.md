## 0. 한 문장 요약과 용어 안내

**한 문장 요약**: 후니의 지식은 이미 라이브 DB(t_* 34테이블)와 위키·문서에 구조화되어 있으므로, 비싸고 위험한 "AI가 글에서 개념을 발굴하는" 단계는 전부 버리고 — **파일을 정본(正本)으로 삼고, 그래프는 스크립트가 결정론적으로 다시 만들 수 있는 파생 빌드로 두며, 모든 주장에 출처를 강제하고, 검증은 스크립트 대조(결정론 diff)가 판정한다.** 국제 표준(schema.org·CIP4 XJDF 등)에서는 기술 스택이 아니라 **이름표(어휘)만** 빌린다.

| 용어 | 쉬운 설명 |
|---|---|
| 온톨로지(ontology) | 한 분야의 개념(상품·자재·공정…)과 그 관계를 컴퓨터가 이해하게 정리한 "개념 사전 + 관계 지도" |
| 지식그래프(Knowledge Graph, KG) | 개념을 점(노드), 관계를 선(엣지)으로 잇는 지식 저장 방식 |
| 결정론 diff(deterministic diff) | 같은 입력이면 항상 같은 결과가 나오는 스크립트로 두 자료를 비교하는 것 — AI의 "느낌" 판정과 반대 |
| 정본(正本) | 언제나 최종 권위를 갖는 원본. 여기서는 git에 커밋되는 markdown 파일 |
| 파생 빌드(derived build) | 정본에서 스크립트로 만들어내는 산출물. 깨져도 언제든 다시 만들 수 있어 버려도 됨 |
| provenance(출처 추적) | "이 주장이 어디서 왔는가"의 기록. 파일:행 또는 테이블:코드 좌표 |
| frontmatter(프런트매터) | markdown 파일 머리에 두는 구조화 메타데이터(YAML 형식) |

## ① 채택 방법론 총괄 — 7대 설계 원칙 + 상충 판정

5개 렌즈의 채택분은 서로 다른 각도에서 왔지만, 아래 7개 원칙으로 모순 없이 통합된다. 5개 렌즈와 이 레포 26라운드 실전이 **독립적으로 같은 결론에 수렴**한 것이 이 플레이북의 가장 강한 근거다(예: XJDF 2뷰 분리 ↔ 통화 결론 "1옵션≠1공정", 학계 자기교정 한계 ↔ 레포 "생성≠검증").

### 원칙 1 — 파일=정본, 그래프=파생 빌드 (사용자 기확정)

- 정본 = markdown + YAML frontmatter 파일(§9 위키 Karpathy 모델 승계). 그래프·SQLite는 전부 스크립트가 정본에서 다시 만드는 빌드 산출물이며, 언제든 버리고 재빌드할 수 있어야 한다. (렌즈3 A-1·A-3, 렌즈4 R4-12)
- RDF/OWL/트리플스토어/서버형 그래프DB는 전부 기각(④ 참조) — 표준에서는 **개념과 이름만** 빌린다. (렌즈1 A6·A7, 렌즈3 R-3)

### 원칙 2 — 폐쇄 스키마·닫힌 세계: 개체는 발명하지 않는다

- KG의 개체(노드)는 라이브 DB 코드(prd_cd·comp_cd·proc_cd·siz_cd…)와 SOT 분류에서 시작한다. LLM은 문서를 읽고 **기존 개체에 링크만** 할 수 있고, 새 개체 발명(mint)은 금지 — 신규 후보는 격리 큐에 넣고 인간 승인 후에만 등재한다(search-before-mint의 KB 확장). (렌즈2 R1)
- 모든 개체 노드는 실존 앵커(t_* 코드 또는 권위 엑셀 260702 셀 좌표)를 가져야 하며, 앵커 없는 개념은 GAP 노드(공백 선언)로만 존재 가능하다. 283상품·34테이블은 유한 집합이라 "코드 실재 확인"이라는 결정론 검사로 환각 개체를 **완전 차단**할 수 있다 — 외부 연구가 못 누리는 후니의 이점. (렌즈5 R5, 렌즈2 R2)

### 원칙 3 — 그래프 빌드는 결정론 스크립트만, LLM은 집필 층에만

★이번 종합에서 가장 중요한 **상충 판정 C-1**이 여기에 있다(아래 판정 표 참조). 두 층을 분리한다:

- **집필 층(authoring)**: LLM이 문서(통화록·핸드오프·위키)를 읽고, 기존 개체에 대한 링크·설명·결정 이력을 **정본 파일에**(frontmatter·[[교차참조]]·출처 필드) 기록한다. 이때 청크는 markdown 제목 블록 단위(대략 600토큰 이하)로 작게, 누락 의심 시 재추출(gleaning). (렌즈2 R7)
- **빌드 층(build)**: `build_graph.py`(가칭)가 ① 라이브 t_* FK 스냅샷(`_foundation/live-snapshot/` 재사용) ② 정본 파일의 frontmatter+[[교차참조]]를 읽어 **LLM 없이 결정론적으로** 노드/엣지를 생성한다. (렌즈3 A-2)
- 즉 LLM 산출은 반드시 정본 파일을 거치고, 파일에 기록되는 순간 앵커 검사(원칙 2)를 통과해야 한다. LLM이 그래프를 직접 만드는 경로는 존재하지 않는다.

### 원칙 4 — 표준 어휘는 이름표로만: 명명 정렬이 이번 작업의 본질

- 최상위 구조 = 기존 §9 위키 8단 뼈대(정체→차원→BOM→가격사슬→CPQ→위젯→적재→결함) **유지**. XJDF의 "고객 의도(Product Intent) vs 생산 공정(Process)" 2뷰는 새 층이 아니라 옵션↔공정 관계의 **명시 태그**로 반영한다. (렌즈1 결정항목 1 권고안 채택)
- 시드 용어집에 영문 표준 앵커 2컬럼(schema_org_term·xjdf_term)을 추가하고, 표준 매핑 표(렌즈1 ②-5)는 횡단 1페이지 `standards-mapping.md`로 승격한다(상품군 페이지 분산 금지). (렌즈1 A2·A3, 결정항목 2·5)
- EBOM(무엇으로 구성)/MBOM(어떻게 만드나) 명명을 셋트·공정 설명에, Soininen 6개념(component·attribute·resource·port·function·constraint)을 CPQ 문서화 상위 프레임으로 쓴다. (렌즈1 A4·A5)
- **가격의 경계**: 가격 계산 로직은 온톨로지 밖(evaluate_price 단일 권위). 온톨로지는 "이 상품의 가격은 어떤 축으로 달라진다"(use_dims 차원 선언)까지만 기술한다. (렌즈1 결정항목 4)
- 파생 속성(derived attribute — 책등=내지 사양의 함수처럼 다른 요소에서 계산되는 속성)을 관계 타입으로 1급 등재한다. (렌즈1 결정항목 6)

### 원칙 5 — 출처 강제 + 수치는 구조화 필드로만

- 모든 노드/블록에 provenance 정형 필드를 강제한다: `source_file / source_locator(시트·셀 | 테이블·키 | 문서·행) / captured_at(수집일) / badge` + `src_id`(freshness 레지스트리의 원천 ID — 원칙 7의 staleness 전파가 grep으로 되게). 출처 없는 주장 = lint FAIL. (렌즈5 R1, 렌즈4 R4-7 통합)
- 가격·치수·수량 등 **숫자는 산문 문장에 녹이지 않고** 스크립트가 diff할 수 있는 표/필드에만 기록한다(LLM 숫자 전사 금지[HARD]의 KB판). (렌즈5 R2)
- 라이브 오적재 영역은 "라이브 현재값 vs 권위 정답"을 산문이 아닌 **두 필드로 분리**해 양면 표기한다(기계 검사 가능하게). (렌즈5 결정항목 5)

### 원칙 6 — 검증은 결정론 diff가 판정하고, 생성≠검증을 유지한다

- 수치·연결·구조의 판정기는 **결정론 diff 유일**(권위 260702 CSV 캐시 ↔ 노드 수치 오차 0, wiring_scan·grid_diff 계보). LLM 자연어 대조는 판정에 쓰지 않는다. (렌즈5 R3)
- 생성 에이전트와 검증 에이전트 분리 + codex 독립 2차 교차(합의/불일치 분류 후 **불일치만 조사**·무제한 토론 금지) + 표본 역변환 대조(트리플을 문장으로 되돌려 원문 대조)를 게이트로. (렌즈2 R6, 렌즈5 R6)
- 오염 4종(STALE/v03 문서 · 구권위 260610/260527의 260702-diff 셀 · 라이브 오적재 · 환각 개체)을 **기계가 읽는 블록리스트 파일**로 유지하고, 인용 시 lint FAIL. (렌즈5 R4)
- 그래프 구조 lint = "SHACL-lite"(노드 타입·필수 엣지·개수 제약 검사)를 build 스크립트에 내장 + NetworkX(파이썬 그래프 라이브러리 — 저장소가 아니라 빌드 시점 분석 도구)로 고아 노드·끊긴 가격 사슬 검출. (렌즈5 R8 대체안, 렌즈3 A-4)
- 검증 질문 생성에는 CoVe 원리("이 KB가 틀렸다면 어디서?"를 초안과 독립적으로 묻기)를 질의 게이트 시나리오에 차용. (렌즈5 R7)

### 원칙 7 — 자기개선 루프: 외부 측도가 낸 결함 목록만 입력으로 [HARD 승격 권고 2건]

- **[HARD 승격 권고 1]** 보강(수정)은 반드시 결정론 측도(스크립트 diff·DB 실측·골든 재계산)가 낸 **결함 목록만 입력으로** 수행한다. AI의 "다시 읽어보니 이상함" 단독 수정 금지 — 학계(자기교정 역효과 실증)와 레포(생성≠검증)가 3중 수렴한 결론. (렌즈4 R4-1)
- **[HARD 승격 권고 2]** 트리거 5종마다 **숫자 종료척도**를 선언한다(예: 엑셀 델타 반영 누락 0 · STALE 인용 0 · 고아 페이지 0). 종료척도 부재가 이 레포 최대 시행착오("분석 무한 반복")였고, §27 배선 루프의 "결함 0" 수렴 완주가 실증. (렌즈4 R4-3)
- 루프 골격 = 트리거 5종(①권위 엑셀 신버전 셀 diff ②라이브 DB 드리프트 스냅샷 diff ③새 하네스 산출물 Ingest ④질의 실패→미답 CQ 큐 적립 ⑤주기 Lint) → 감지(결정론) → 보강(생성 레인) → 재검증(별도 레인) → 기록(log+레지스트리). 반복 상한 3회, 도달 시 BLOCKED 큐 격리·인간 에스컬레이션. (렌즈4 R4-2·R4-8·R4-13, 결정항목 6)
- freshness(신선도) 관리 = §9 `source-registry.md`(FRESH/PARTIAL-STALE(축)/STALE 3등급)를 **복사가 아닌 단일본 공유**로 승계 + 원천 유형별 **선언형 만료 규칙**(무슨 이벤트가 오면 낡은 것으로 보나 — 시간 경과가 아니라 원천 변경 이벤트 기준) + staleness 전파 스크립트(원천이 STALE로 바뀌면 그 원천을 인용한 블록을 재검토 큐로). (렌즈4 R4-4·R4-5·R4-7)
- 파생 그래프 갱신은 **매번 전면 재빌드**(증분 병합 금지 — 증분 로직 자체가 결함원, §17 "일괄 merge 함정" 실증). (렌즈4 R4-12)

## ② 그래프 저장 형식 — 최종 권고 1개

**권고: "3층 구성 — ⓐ 정본 = markdown+frontmatter 파일(git) → ⓑ 그래프 텍스트 덤프 = `nodes.jsonl` + `edges.jsonl`(git 커밋·정렬 키 직렬화) → ⓒ 질의용 SQLite 단일 .db 파일(gitignore·로컬 재빌드)"** (렌즈3 A-3 채택 + 덤프 포맷 쟁점 해소)

| 층 | 형식 | git | 역할 |
|---|---|---|---|
| ⓐ 정본 | markdown + YAML frontmatter | 커밋 | 사람·LLM이 읽고 쓰는 유일한 권위. 여기만 고치면 됨 |
| ⓑ 덤프 | nodes.jsonl / edges.jsonl (키 정렬·한 줄=한 객체) | 커밋 | 그래프 변화가 diff/PR 리뷰로 보임. 결정론 재빌드 검증(같은 입력→같은 파일)의 대상 |
| ⓒ 질의 | SQLite .db (+ 필요 시 sqlite-vec 확장 여지) | **gitignore** | 재귀 CTE(WITH RECURSIVE — 표 안에서 연결을 따라가는 SQL)로 경로 질의. 언제든 ⓑ에서 재생성 |

- **덤프 포맷은 CSV가 아니라 JSONL로 확정한다**(렌즈3 결정항목 2의 잔여 쟁점을 여기서 판정): 노드 타입마다 속성 구성이 다르고(상품 노드 vs 용어 노드 vs GAP 노드), provenance 4+1필드 같은 중첩 구조가 있어 고정 컬럼 CSV는 빈칸 범벅이 된다. JSONL은 키를 정렬해 직렬화하면 CSV와 동등하게 diff 가능하고, 선택 필드를 자연스럽게 담는다.
- Kuzu(임베디드 그래프DB)는 2025-10 프로젝트 중단(레포 아카이브)으로 후보 탈락, Neo4j 등 서버형은 단일 운영자 규모에 과잉, DuckDB+duckpgq는 성숙도 미달로 보류 — 검토 근거 전부 렌즈3 발견 7.
- 임베딩(sqlite-vec)은 **보류**: 용어집+그래프 탐색을 먼저 돌려보고, 질의 게이트에서 "노드 미발견율"이 실측으로 누적되면 같은 .db 파일에 추가한다(선제 도입은 유지비만 증가). (렌즈3 H-1)

## ⑤ 미해결 질문 — 사용자 확인 필요

설계자 재량(③의 "설계자 구체화"란)이 아니라 **사용자 판단이 필요한** 것만 남겼다.

| # | 질문 | 배경 | 리서처 권고 |
|---|---|---|---|
| Q1 | **용어집·표시중복 산출물의 소유권 통합** — §17(기초데이터 표시중복) 산출물과 시드 용어집을 단일 원천으로 통합하면, 앞으로 표시중복 판정의 정본이 온톨로지 KB 쪽으로 옮겨온다. 이 소유권 이동을 승인하는가? | 이중 관리 금지 원칙(D-10). §17 하네스는 계속 존재하되 용어집을 KB에서 읽게 됨 | 통합 승인 권고(이중 관리 자체가 staleness 원인) |
| Q2 | **1차 문서 코퍼스 범위** — 집필 층이 처음 읽어 들일 문서를 어디까지로 하나: ⓐ docs/kb 6종만 ⓑ ⓐ+각 하네스 HANDOFF/CHANGELOG ⓒ ⓑ+§9 위키 전체 | 범위가 넓을수록 초기 비용·검증량 증가. 파일럿(대표 상품군 1개) 원칙과 연동 | ⓐ로 시작해 파일럿 완주 후 확장 권고 |
| Q3 | **신규 개체 후보 큐의 승인 주체·절차** — LLM이 발견한 새 개념 후보(격리 큐)를 사용자가 직접 건별 승인할지, 게이트 GO에 묶어 일괄 승인할지 | 단일 운영자 환경 — 건별 승인은 정확하지만 부담 | 파일럿 동안은 건별, 이후 게이트 일괄로 전환 권고 |
| Q4 | **KB 범위(scope) 선언** — 자연어 질의가 "범위 밖"이라고 정직하게 거절해야 할 경계를 어디에 긋나(예: 주문·배송·회원 질문은 범위 밖? 경쟁사 가격 비교는?) | 거절형 질의 게이트(렌즈5 결정7)가 성립하려면 범위가 노드로 선언돼야 함 | 1차 범위 = 상품·구성요소·옵션·가격 차원·제약(주문/배송/회원 제외) 권고 |
| Q5 | **루프 실행 방식** — 주기 Lint를 ⓐ 사람이 세션 시작 시 수동 트리거 ⓑ 하네스 재실행 시 Phase 0으로 내장 ⓒ 스케줄 자동화 | ⓒ는 "실 COMMIT 인간 승인" 원칙과 충돌 여지(렌즈4 결정5) | ⓑ 권고(하네스 실행=Lint 선행) |
| Q6 | **국내 인쇄 업계 JDF/XJDF 실사용 여부**(에디쿠스·레드프린팅이 내부적으로 쓰는지) — 실무진(신우진) 확인 요청을 보낼지 | 공개 자료 없음(렌즈1 ④). 쓰고 있다면 표준 앵커(xjdf_term)의 실용 가치가 커짐 | 실무진 질문 큐에 1건 추가 권고(차단 요소 아님 — 답 없이도 D-1~D-22 진행 가능) |
