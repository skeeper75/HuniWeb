# D6 — 상품 구성 바깥의 경계: 에디터·원고·조합템플릿·용지·설정추상화

대상: `raw/webadmin/webadmin/catalog/` 의 `edicus_views.py`(669), `s3_artwork.py`(300), `s3_swatch.py`(196), `paper_views.py`(588), `tmpl_combo.py`(506), `tmpl_combo_views.py`(457), `cfg_utils.py`(441).
읽기 전용 진단이며 대상 파일을 수정하지 않았다.

---

## 요약

이 7개 파일은 "상품 구성(옵션·차원·가격)" 바깥에 있는 **다섯 개의 서로 다른 경계면**이다. 공통 성질은 하나다 — **모두 관리자 화면에서 사람이 표를 채우는 구조이고, 그 표가 자동으로 결과를 예측하거나 역산해 주지는 않는다.**

1. **에디터(Edicus) 연동**은 사실상 **반쪽만 연결돼 있다.** 관리자는 (상품 × 옵션조합) → (PSCode, 템플릿 URI) 를 등록하지만, `TPrdEdicusTemplates` 를 읽는 코드는 이 리포지토리 전체에서 `edicus_views.py` 자기 자신뿐이다(`edicus_views.py:281,307,339,455,585` 외 소비자 0). 반대 방향(에디터가 만든 결과)은 주문 payload 에 `editors:[…]` 로 **불투명하게 그대로 에코**된다(`widget_api.py:1948-1949`).
2. **원고 파일 라이프사이클**은 "임시 버킷 업로드"까지만 구현돼 있고, **결제 후 주문 버킷 승격 워커가 미착수**다(`s3_artwork.py:24-25`, `build_order_key` 호출부 0 — `s3_artwork.py:142`).
3. **조합 템플릿(tmpl_combo)** 은 "옵션 조합 → 실제 투입 자재(BOM)" 매핑이며, 미등록 조합을 주문 시점에 422 로 차단한다(`widget_api.py:1890-1899`). 즉 **사실상 제약규칙 역할을 겸하고 있으나 제약 레이어(`t_prd_product_constraints`)와는 완전히 별개 통로**다.
4. **용지 도메인**은 독립 엔티티가 아니라 **자재 마스터의 유형 필터 뷰**(`paper_views.py:45-48`) + **가격표의 스코프 슬라이스**(`comp_cd='COMP_PAPER'`, `paper_views.py:51`)로 표현된다.
5. **cfg_utils** 는 "제약은 단일 boolean", "삭제는 안전하다"는 **두 개의 큰 거짓 단순화**를 감추고 있다 — 제약 평가는 어떤 규칙이 왜 걸렸는지 돌려주지 않고(`cfg_utils.py:68-79`), 삭제는 트리거·고아·역방향 FK 3중 위험을 헬퍼 뒤로 숨긴다(`cfg_utils.py:158-191, 294-343`).

월드모델 관점 판정: **이 영역은 (2)심볼릭 + (3)지식/온톨로지의 경계에 있고, (4)월드모델(행동→결과 예측)은 전무하다.** 근거는 §월드모델 관점 판정.

## 구조 해설

### (a) 에디터(Edicus) 연동의 계약 — 무엇을 넘기고 무엇을 돌려받는가

**넘기는 것(설계상)**: `(prd_cd, 옵션조합)` → `(ps_cd, tmpl_uri)`.
"옵션조합"의 정의가 이 계약의 전부다. `edicus_views` 는 그것을 **8컬럼 자연키 + 2개 jsonb** 로 표현한다(`edicus_views.py:38-41`, `:573`):

```
자연키 = (siz_cd, plt_siz_cd, print_opt_cd, mat_cd, proc_cd, opt_cd=NULL, coat_side_cnt, bdl_qty)
         + norm_json(opt_sels {옵션그룹코드: 옵션코드})
         + norm_json(proc_dtl {상세키: 값})
```

즉 **차원의 데카르트곱 한 칸 = 템플릿 한 개**다. 화면은 상품에 설정된 값에서 프런트가 데카르트곱을 만들고(`edicus_views.py:7-8`), 관리자가 각 칸에 PSCode/URI 를 채운다. 서버는 이 격자를 full-sync 로 받는다(`:466-474`).

**돌려받는 것(런타임)**: 주문 payload 의 `editors: [{item, mbr, inst, result, …}]`(`widget_api.py:1948-1949`). 검증은 세 가지뿐이다 — 위젯 컴포넌트 소속(`widget_api.py:912-914`), 구성원 좌표 일치(`:915-917`), `result` 비어있지 않음(`:923-925`). **`result` 의 내용·형식·PSCode 대응 여부는 아무도 보지 않는다.**

그리고 결정적 사실(A-13): **양쪽이 서로 연결돼 있지 않다.** 등록된 `ps_cd`/`tmpl_uri` 를 읽는 코드가 이 리포에 없다. 즉 현재 webadmin 관점에서 Edicus 계약은:

- **아웃바운드(어떤 템플릿을 열 것인가)**: 데이터는 있으나 **소비자 미구현** — 위젯/프런트 쪽이나 리포 외부에서 조회한다고 봐야 한다. [추정] 위젯 런타임이 별도 API 로 읽거나, 아직 배선 전이다.
- **인바운드(에디터가 뭘 만들었나)**: **불투명 블롭 통과**. 서명 대상에 포함되어 주문 후 위변조는 막히지만(`widget_api.py:1949`, `_sign`), 그 내용이 주문한 옵션조합과 일치하는지는 서버가 판단하지 않는다.

계약의 성질: **좌표 정합만 보장하고 의미 정합은 보장하지 않는다.**

### (b) 원고 파일 라이프사이클

관측 가능한 단계는 여섯이고, **넷까지만 구현돼 있다**:

```
① presign 발급            widget_api.py:1974-2030 (단일 PUT) / :2065-2135 (멀티파트)
     ↳ 사전검증 _check_files (주문 시점과 같은 한 벌, widget_api.py:2006-2009)
     ↳ 키 생성 s3_artwork.build_key (uploads/YYYY/MM/site/wgt/item/uuid.ext)
     ↳ mbr·inst·item·wgt 를 x-amz-meta-* 로 동봉 (widget_api.py:2014-2020)
② 브라우저 → S3 직접 PUT   서버 미경유, 최대 2GB (s3_artwork.py:3-4)
③ 완료/중단               complete_multipart / abort_multipart (s3_artwork.py:265-290)
④ 주문(handoff) 서명       key 접두 모양 검증만 (widget_api.py:1866-1874) → payload.files 에 에코 서명
─────────── 여기까지 구현 ───────────
⑤ 결제 후 주문 버킷 승격   ★미착수 (s3_artwork.py:24-25, build_order_key 호출부 0 — :142)
⑥ 실측 대조(head_object)  ★미착수 (widget_api.py:896-898)
```

이 라이프사이클이 감추고 있는 **네 개의 신뢰 공백**:

1. **존재 증명 없음** — `key_belongs` 는 접두 문자열 패턴 검사다(`s3_artwork.py:161-175`). "이 서버가 발급했다"도 "오브젝트가 실제로 있다"도 증명하지 않는다. 스스로 문서에 명시한다(`:167-169`).
2. **크기 강제 없음** — presign 서명에는 Content-Type·Key 만 들어가고 크기는 없다. `_check_files` 는 **클라가 보낸 `size` 값**을 본다(`widget_api.py:895-897`).
3. **누수 관측 없음** — 멀티파트 abort 실패는 warning 로그뿐이고, 남은 조각은 목록에 안 보이면서 과금된다(`s3_artwork.py:286-290`, `list_multipart:293-300` 은 운영 점검용 수동 도구).
4. **태그 드리프트가 늦게 드러남** — `PREVIEW_TAGGING = "preview=true"` 가 버킷 수명주기 규칙과 어긋나면 증상이 7일 뒤에, 그것도 "파일이 안 사라지는" 형태로 나온다(`s3_artwork.py:44-48`).

**스와치는 정반대 설계**다(C-1~C-6). 파일이 서버를 통과하므로 매직바이트까지 검증하고(`s3_swatch.py:74-101`), 서빙도 프록시 단일 경로로 잠근다(`:185-196`). 즉 이 코드베이스는 **"검증 가능한 작은 파일"과 "검증 불가능한 큰 파일"에 완전히 다른 신뢰 모델**을 쓴다. 원고가 후자다.

### (c) tmpl_combo 가 표현하는 개념 — 옵션/제약과의 겹침

`tmpl_combo` 가 표현하는 것은 **"고객이 고른 조합 → 실제 투입 자재(BOM)"** 다. 반팔티셔츠에서 "칼라 × 사이즈"마다 blank 자재가 다른 경우가 원형이다(`tmpl_combo.py:3-4`).

**세 레이어와의 겹침 지도**:

| 레이어 | 표현 대상 | 저장 위치 | 겹치는 지점 |
|---|---|---|---|
| 옵션 레이어(CPQ) | 고객이 고를 수 있는 것 | `t_prd_product_option_groups/options/option_items` | 조합 축의 `opt_grp:{G}` 가 **여기서 값을 읽어온다** (`tmpl_combo_views.py:65-69` → `TC.dim_options` → `edicus_views._dim_options`) |
| 제약 레이어 | 고를 수 **없는** 조합 | `t_prd_product_constraints`(JSONLogic) | **연결 없음.** `tmpl_combo` 는 제약을 읽지 않고, 제약도 조합 템플릿을 모른다 |
| 조합 템플릿 | 고른 조합의 **생산 결과** | `t_prd_templates(combo_yn='Y')` + `t_prd_template_selections` | 미등록 조합 = 사실상 "금지된 조합"으로 동작(422) — **제약 레이어의 그림자 역할** |

여기서 가장 중요한 구조적 사실: **D-9(미등록 조합 = 422 fail-closed)** 때문에 조합 템플릿 표는 의도치 않게 **화이트리스트 제약**이 된다. 그런데 이 사실은 제약 레이어(`t_prd_product_constraints`)에 기록되지 않으므로:

- 위젯 프런트의 cascade(즉시 제약 평가)는 이 금지를 **모른다** — `cfg_utils.CLIENT_SUPPORTED_OPS` 로 표현되는 JSONLogic 세계 밖이다.
- 고객은 화면에서 자유롭게 고르다가 **주문 버튼에서만** 막힌다.
- 안내 문구도 별도 코드로 만든다(`tmpl_combo.missing_axis_names:204-216`, `sel_dim_names:219-239`) — 제약 레이어의 `err_msg` 와 무관한 두 번째 오류 메시지 체계다.

또 하나의 겹침: **차원 어휘가 세 벌로 갈려 있다.**

| 소유자 | 상수 | 내용 | 근거 |
|---|---|---|---|
| 가격 | `price_views.DIM_META` | 12종(전체) | `price_views.py:31-44` |
| Edicus | `edicus_views.EDICUS_DIMS` | 6종 + `proc_cd:dtl` + `opt_grp:{G}` | `edicus_views.py:37`, `:212-215` |
| 조합 | `tmpl_combo.COMBO_DIMS` | 5종(`plt_siz_cd`·`proc_cd:dtl` 제외) + `opt_grp:{G}` | `tmpl_combo.py:47-51` |

세 부분집합이 서로 다르고, 각각 제외 사유가 주석으로만 남아 있다(`edicus_views.py:35-36`, `tmpl_combo.py:48-49`, `price_views.py:52-60`). 값 열거는 `edicus_views._dim_options` 하나로 통일돼 있어(`tmpl_combo.py:157`) **열거는 단일 출처, 어휘 선택은 3중 분기**인 상태다.

### (d) paper_views 의 용지 도메인 표현 방식

용지는 **엔티티가 아니라 세 겹의 슬라이스**로 표현된다:

1. **유형 슬라이스** — `mat_typ_cd ∈ PAPER_MAT_TYPES`(`paper_views.py:45-48`). 여기 없는 유형은 이 화면에서 존재하지 않는다. 실제로 260814 에 "출력소재관리 시트의 스티커용지들이 화면에 안 보이던 원인 = 단일 유형 하드코딩"으로 확장됐다(`:41-42`).
2. **계층 슬라이스** — `upr_mat_cd` 자기참조 2단 트리(루트 + 자식 1레벨만 렌더, `_paper_rows:109-119`). 유형을 넘는 부모는 금지(`_valid_upr:387-389`).
3. **가격 슬라이스** — `t_prc_component_prices` 중 `comp_cd='COMP_PAPER' AND mat_cd=이 용지`(`paper_views.py:329`). 다른 구성요소 단가는 **읽기 전용으로 보여주기만** 한다(`:11-13`).

용지의 물성은 자재 마스터 컬럼에 얹혀 있다 — `weight`(평량), `width`/`height`(규격), `depth`(두께 mm), `bdl_qty`(묶음수), `swatch_img_key`/`swatch_color`(견본). 화면은 ㎛ 로 받고 mm 로 저장하는 **단위 변환을 UI 계층에만** 둔다(`paper_views.py:14`). DB 에는 단위 표기가 없다.

즉 이 화면의 본질은 **"용지 담당자가 자재관리 전체를 건드리지 않고 자기 슬라이스만 만지게 하는 격벽"** 이다(`paper_views.py:3-4`). 그리고 그 격벽이 실제로 사고를 막은 기록이 있다 — full-sync 재사용을 거부해 다른 구성요소 92행 삭제를 반복하지 않게 한 결정(E-6, `paper_views.py:249-254`).

### (e) cfg_utils 의 설정 추상화가 감추는 것

`cfg_utils` 는 이름과 달리 "설정"이 아니라 **두 개의 위험 도메인을 함수 뒤로 감추는 파일**이다.

**감추는 것 ①: 제약이 사실은 복잡하다는 사실**

`evaluate_constraints(prd_cd, data) -> bool` 이라는 시그니처는 제약을 단일 술어로 보이게 한다(`cfg_utils.py:68-79`). 실제로 감춰진 것:

- **규칙 신원 상실** — 활성 규칙들을 `{"and":[…]}` 로 병합하는 순간 `rule_cd`·`err_msg`·`disp_seq` 가 사라진다(`:42-60`). False 가 나와도 **어느 규칙이 왜 걸렸는지 이 함수는 말할 수 없다.**
- **엔진 이중화** — 프런트와 백엔드가 서로 다른 구현체 두 벌이고, 수렴은 별도 하네스가 회귀 검증한다(`:85-90`).
- **평가 위치의 비대칭** — 클라 미지원 연산자를 쓴 규칙은 화면 cascade 에서 안 걸리고 서버에서만 걸린다(`:114-121`). 고객 경험이 규칙 내용에 따라 달라진다.

**감추는 것 ②: 삭제가 사실은 위험하다는 사실**

`logical_delete(model, **nat)` 는 한 줄짜리 UPDATE 로 보인다(`cfg_utils.py:137-155`). 그 옆에 있는 것들이 실제 복잡도다:

- 옵션 구성요소는 **트리거 때문에** bulk UPDATE 를 못 쓴다 — 논리삭제 UPDATE 가 폴리모픽 참조 무결성을 재검증하고, 옛 데이터에서 예외를 던져 정상 행까지 롤백시킨다(F-5, `:160-171`).
- 자기참조 마스터는 반대로 bulk 가 안전하다 — 트리거 성격이 다르기 때문(F-6, `:353-357`). **두 정책의 분기 근거가 오직 트리거 정의**다.
- `delete_usage` 는 역방향 FK 를 리플렉션으로 전수 순회하고 **예외를 조용히 `continue`** 한다(`:329-330`). 어떤 관계에서 집계가 실패해도 "사용처 0"으로 보인다.
- 삭제 가능 여부는 3분기 정책(F-10)이고 그 임계값은 `allow_force_leaf` 기본 인자 한 줄로 뒤집힌다(`:364-365`).

즉 `cfg_utils` 의 추상화는 **"단순해 보이는 시그니처 + 도크스트링에만 남은 사고 이력"** 이라는 형태다. 도크스트링에 실사례(매직패브릭 고아, PRD_000068/71 4건, 92행 삭제)가 남아 있는 것은 이 코드베이스의 강점이지만, **기계가 읽을 수 있는 형태가 아니다.**

## 월드모델 관점 판정

이 영역이 (1)뉴로 (2)심볼릭 (3)지식/온톨로지 (4)월드모델(행동→결과 예측) 중 무엇에 해당하는가.

### 판정: **(2)심볼릭이 지배적, (3)지식/온톨로지는 부분적·암묵적, (4)월드모델은 부재, (1)뉴로는 전무.**

#### (1) 뉴로 — **전무 (근거 확실)**

7개 파일 3,157줄 전체에 학습·임베딩·확률·유사도 요소가 없다. 모든 판정이 결정론적 문자열/집합 비교다. 매칭은 `frozenset` 동등성과 문자열 정규화 비교뿐이다(`tmpl_combo.py:299`, `:312`). "비슷한 조합"이라는 개념 자체가 없다.

#### (2) 심볼릭 — **지배적 (근거 확실)**

이 영역의 본질은 **기호 격자와 정확 일치 매칭**이다.

- 자연키 튜플 매칭: `edicus_views.py:573`, `:590-616`
- 화이트리스트 대조(파싱 금지 원칙): `edicus_views.py:141-145`, `:526-531`, `tmpl_combo_views.py:288-290`
- 정규화된 JSON 문자열을 신원 키로: `edicus_views._norm_json:235-237`, `tmpl_combo.norm_dims:141-147` (두 모듈이 같은 규약을 공유)
- 상호배타·허용집합 등 집합 연산으로 표현된 규칙: `edicus_views.py:198-215`, `tmpl_combo_views.py:73-81`
- 제약은 JSONLogic — **명시적 기호 논리**: `cfg_utils.py:42-60`, `:91-98`

fail-closed 가 일관된 원칙으로 관철된다(`tmpl_combo.py:5-6`, `edicus_views.py:160`, `:170-171`, `paper_views.py:554-558`, `s3_swatch.py:124-125`). 이것은 **"모르면 거절"** 이라는 심볼릭 시스템의 정직한 태도다.

#### (3) 지식/온톨로지 — **부분적이고, 결정적으로 코드/주석에 갇혀 있음**

온톨로지의 흔적은 분명히 있다:

- **차원(dimension) 개념 자체**가 도메인 온톨로지다 — `DIM_META` 가 차원 id → (한글명, 타입, 모델, 표시필드) 를 매핑한다(`price_views.py:31-44`).
- **참조차원 코드체계** `OPT_REF_DIM.*` 가 폴리모픽 참조의 타입 태그다(`tmpl_combo.py:41`, `_dim_names:326-332`).
- **상품유형 분류**(완제품/반제품/셋트 구성원)가 `semi_role_cd`·`TPrdProductSets` 로 표현된다(`edicus_views.py:61-71`).
- **자재유형 분류** `MAT_TYPE.*` 가 용지 도메인의 경계를 정의한다(`paper_views.py:45-48`).

그러나 온톨로지로서 **세 가지가 결정적으로 비어 있다**:

1. **관계가 없다.** `MAT_TYPE.01`(디지털인쇄용지)과 `MAT_TYPE.11`(스티커용지)이 왜 같이 묶이고 `MAT_TYPE.13`(합판스티커용지)은 왜 빠지는지 — 그 근거는 **주석 한 줄**이다(`paper_views.py:43` "같은 날 현업 요청으로 제외"). 상하위·유사·배타 같은 관계가 데이터로 없다.
2. **속성의 의미가 없다.** `weight`·`depth` 는 숫자일 뿐 단위조차 DB 에 없다(㎛↔mm 변환이 UI 에만 존재, `paper_views.py:14`). "평량이 높다 = 두껍다 = 고급스럽다" 같은 어떤 추론도 불가능하다.
3. **차원 선택 근거가 기계 판독 불가.** `plt_siz_cd` 가 왜 조합 축에서 빠지는지는 **"고객 선택값이 아니라 서버가 사이즈에서 파생하는 내부 개념"** 이라는 주석에만 있다(`tmpl_combo.py:48`, 같은 취지 `price_views.py:53-54`). 이것은 훌륭한 도메인 지식인데 **코드가 소비할 수 없는 형태**다.

즉 **온톨로지가 도크스트링에 살아 있고 데이터에 없다.** 이 코드베이스에서 가장 값진 자산이 가장 접근 불가능한 형태로 저장돼 있다.

#### (4) 월드모델(행동→결과 예측) — **부재 (근거 확실)**

월드모델의 최소 요건은 "행동 a 를 취하면 상태 s → s' 가 된다"를 **실행 없이** 예측하는 것이다. 이 영역의 모든 함수는 그 반대다.

| 필요한 능력 | 현재 상태 | 근거 |
|---|---|---|
| "이 조합을 고르면 어떤 자재가 투입되는가" | `resolve()` 가 답한다 — **단, 조합이 완전할 때만.** 부분 조합에서는 `matched=None` + 축 이름만 | `tmpl_combo.py:317-320`, `:204-216` |
| "이 조합은 왜 안 되는가" | 답 없음. `evaluate_constraints` 는 bool | `cfg_utils.py:79` |
| "무엇을 바꾸면 되는가" | 답 없음. 어떤 함수도 대안·수정 제안을 반환하지 않음 | 전 파일 |
| "이 주문을 넣으면 성공하는가" | **시도해 봐야 안다.** 검증이 presign / handoff / 조합해석 / 제약평가 4시점에 흩어져 순차 발동 | `widget_api.py:1861`, `:1872`, `:1890`, `_eval_violations` |
| "이 마스터를 지우면 무엇이 깨지는가" | **유일하게 예측을 시도하는 지점** — `delete_usage`(`cfg_utils.py:294-343`)가 역방향 FK 를 리플렉션으로 순회해 영향을 사전 집계한다. 그러나 예외를 조용히 무시하고(`:329-330`) 다단계 파급(자손의 자손의 참조)은 계산하지 않는다 | `cfg_utils.py:294-348` |

**따라서 `cfg_utils.delete_usage` / `logical_delete_cascade` 는 이 영역에서 유일하게 "행동→결과 예측"의 맹아를 가진 코드다.** "삭제하면 이런 것들이 깨진다"를 실행 전에 계산해 사용자에게 보여주고 확인을 받는다(`:391-406`). 이것이 월드모델의 원형이다 — 다만 **삭제 한 가지 행동에 대해서만, 불완전하게** 존재한다.

**핵심 판정**: "의도→주문" 자동화가 요구하는 것은 정확히 (4)다 — "이 의도로 주문하면 성공/실패하고, 실패하면 무엇을 고쳐야 하는가"를 실행 전에 답하는 능력. 현재 시스템은 **(2)로 검증하고 (3)을 주석에 보관하며 (4)는 없다.** 자동화를 얹으려면 최소 두 가지가 필요하다:

- **(3)의 외부화** — 주석 속 도메인 지식(차원 제외 사유, 유형 묶음 근거, 단위, 물성 의미)을 데이터로 승격.
- **(4)의 신설** — 부분 상태를 받아 (가능한 다음 값, 위반 규칙, 필요 원고 수, 미결정 축)을 **한 번에** 돌려주는 예측/설명 엔드포인트. 지금은 그 정보가 `tmpl_combo.resolve`·`cfg_utils.evaluate_constraints`·`widget_api._check_artwork` 세 곳에 흩어져 있고, 각각 서로 다른 시점에 서로 다른 형식으로 실패한다.

[추정] 위 판정 중 "Edicus 템플릿의 실제 소비자가 리포 외부(위젯 런타임/프런트)에 있을 가능성"은 이 리포만으로 확인 불가하다. 그 외 판정은 모두 위 §실측 사실의 파일:라인 근거에 기반한다.

## 미확인

이번 진단에서 **확인하지 못한 것**을 명시한다.

1. **Edicus 측 계약의 반대편** — `ps_cd`(PSCode)와 `tmpl_uri` 를 실제로 소비하는 코드/서비스. 이 리포에는 없다. 위젯 런타임(`raw/widget_monitor` 등)이나 외부 서비스가 읽는지 미확인.
2. **`editors[].result` 의 실제 형식** — 코드가 내용을 보지 않으므로 스키마를 역추론할 근거가 없다. 실제 주문 로그나 Edicus 문서 대조 필요.
3. **버킷 수명주기 규칙의 실제 값** — `PREVIEW_TAGGING="preview=true"`(`s3_artwork.py:48`)와 `abort-incomplete-multipart-7d`(`:229`)가 AWS 콘솔에 실제로 그렇게 설정돼 있는지. 코드는 "이미 걸려 있다"고 주장하지만 검증 불가.
4. **승격 워커의 존재 여부** — `docs/s3-multisite-file-policy.md`·`docs/aws-s3-cors-etag-request.md` 는 읽지 않았다. 별도 리포/배치에 워커가 있을 가능성 미확인.
5. **`tools/cfg_constraints.py`·`tools/constraint_engine_diff.py`** — `cfg_utils` 가 참조하는 CLI 원본과 차등 오라클 하네스를 읽지 않았다. 프런트/백엔드 제약엔진 수렴의 실제 커버리지 미확인.
6. **`sql/` 디렉터리의 DDL·트리거 원문** — 부분 유니크 인덱스(`edicus_views.py:475`), `trg_t_prd_product_option_items_chk_ref`(`cfg_utils.py:162`), `sql/85`·`sql/83`·`sql/76`·`sql/67` 등은 주석 참조만 확인했고 원문 미열람.
7. **`price_views.py` 전문** — `DIM_META`(`:31-44`)·`OPT_GRP_PREFIX`(`:130`)·`WIDGET_EXTRA_DIMS`(`:61`)만 확인. `proc_detail_inputs`·`split_scopes`·`price_grid_save`(용지 화면이 반면교사로 삼는 함수) 미열람.
8. **라이브 DB 실측** — `t_prd_edicus_templates` 실제 행 수, 레거시 `opt_cd` 잔존 67행(`edicus_views.py:15`)의 현재 상태, `combo_yn='Y'` 템플릿 분포 등은 조회하지 않았다(읽기 전용 진단 범위 밖).
9. **프런트 템플릿** — `catalog/templates/catalog/edicus_template_md.html`, `tmpl_combo_md.html`, `paper_management.html` 미열람. 데카르트곱 생성·스마트 병합·값 필터 UI 의 실제 동작 미확인.
10. **테스트 커버리지** — `build_order_key` 의 유일한 소비자라는 테스트(`s3_artwork.py:142`)를 포함해 테스트 파일 전반 미열람.
