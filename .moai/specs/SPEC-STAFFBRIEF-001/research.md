### 1.4 use_dims vs OPT_REF_DIM 검증 (프로젝트 메모리 교정 포함)

- **use_dims = 13키** (`admin.py:185-192` _USE_DIM_CHOICES): siz_cd·plt_siz_cd·print_opt_cd·mat_cd·proc_cd·opt_cd·coat_side_cnt·spot_side_cnt·bdl_qty·page_cnt·siz_width·siz_height·min_qty. min_qty는 "항상 마지막 고정"이라 일반 선택에서 제외(admin.py:193-196) → **선택 가능 12종 + 고정 1종 = 13**. 메모리의 "12종(admin.py:156)"은 비수량 차원 12를 가리키며 라인은 156→185로 드리프트. `price_views.py:38-52` DIM_META와 상호 검증됨(admin.py:184 주석).
- **OPT_REF_DIM = 7종** (`views.py:111-117`): .01 사이즈 / .02 판형 / .03 자재(mat_cd__usage_cd 결합키) / .04 공정 / .05 묶음수(int, "마스터 없는 순수 값 차원") / .06 도수(opt_id) / .07 셋트(sub_prd_cd). 합성 차원(옵션그룹/옵션/추가상품)은 ref_dim_cd 기초코드 아님(views.py:120).
- **의미 구분**: use_dims=가격구성요소 단가표가 어떤 축으로 펼쳐지는가(가격 그리드 열 구성) / OPT_REF_DIM=옵션항목이 어느 마스터 차원을 참조하는가(옵션→차원 배선).

### 2.2 라이브 위젯 아키텍처

- 임베드=스크립트 2줄(`<script src=...widget.js>` + `<huni-widget widget-id site-key>`), 한 페이지 복수 위젯 독립 동작

### 2.3 가격 흐름 — "클라이언트는 표시만, 계산은 항상 서버"

```
고객 브라우저                    후니 서버                파트너(쇼핑몰) 서버
<huni-widget> ─ ① 구성조회 ───▶ /api/w/v1/widgets/{wgt_cd}
  선택 UI      ─ ② 가격(300ms 디바운스) ▶ /price
  가격 표시    ─ ③ 주문(전체 재검증) ──▶ /validate → /handoff ─ 서명 token ─▶ ④ /handoff/verify → 주문 확정
```
- **"위젯 코드를 조작해도 주문 금액은 바뀌지 않습니다"** (widget-sdk-guide.html:480) — 발표용 보안 문구 그대로 사용 가능
- 가격 API = Phase 11 엔진 evaluate_price 재사용, 구성요소별 소계+합계 포함. 셋트=evaluate_set_price
- 디바운스 300ms + 동일 선택 캐시(레드프린팅 검증 패턴 채택)
- 표시 원칙: 가격요약 기본=**합계만**(구성요소별 금액은 원가 노출 우려로 내부·특수 위젯만 선택적 on)
- 핸드오프: /handoff가 가격·제약·원고 전부 재검증 후 HMAC 서명 토큰 발급(유효 3600초, handoff_id=GUID 추적 키). 파트너 서버는 **검증된 payload의 금액으로만** 주문 생성 — 브라우저가 보낸 payload는 참고용

### 2.4 Edicus 라이프사이클 + 원고 업로드

- 조합→템플릿 매핑은 **서버가 결정**(/editor/resolve, 클라이언트 추론 없음), 사용자 토큰도 서버 대리 발급(편집기 비밀키는 서버 밖으로 나가지 않음), 패시브 모드 오버레이, 저장 시 prjid 기록→주문에 자동 실림, 재클릭 시 이어 편집
- **등록 안 된 조합은 편집기가 열리지 않음**(no_editor_mapping) — 잘못된 규격 원고 사고 방지 의도적 안전장치. 편집기 저장을 해야 "원고" 인정
