0. 결론 한 장

쉽게 말하면 — Shopby 에는 "돈을 미리 넣어두는 통장"(예치금)이 없어요. 대신 "적립금"이라는 통장이 있고, 이 통장은 결제할 때 현금처럼 전액 쓸 수 있고 이름도 바꿀 수 있어요. 그래서 적립금 통장에 "프린트머니"라는 이름표를 붙이고, 손님이 돈을 넣는 순간(충전)만 우리가 만들어 주면 됩니다. 나머지(잔액 보기, 결제 때 쓰기, 취소하면 돌려주기, 유효기간)는 Shopby 가 이미 다 해 줍니다.
질문답
Shopby 가 선불 충전을 지원하나아니오. 24개 API 명세·엔터프라이즈 매뉴얼 전체에서 예치금·충전 개념 0건
어떻게 구현하나두 길. A: 적립금을 "프린트머니 원장"으로 재해석 — 후니는 충전 → 적립금 지급 한 구간만 Server API 로. B′: 후니가 충전식 원장을 직접 갖고 Shopby 「외부포인트 연동(방법2)」으로 Shopby 가 결제·취소 때 후니 API 를 호출(§3-B)
후니 원장을 Shopby 가 외부포인트로 인정하나예 — 정식 기능. 단 엔터프라이즈 전용 · NHN 1:1 문의 세팅 · 후니 API 5종 구현 · 결제 경로 가용성 책임이 후니로 이동(§3-B)

3-B. 방안 B′ — 후니 충전식 원장 + Shopby 「외부포인트 연동(방법2)」

쉽게 말하면 — 방안 A 는 "우리가 Shopby 통장에 돈을 넣어 주는" 방식이고, B′ 는 "통장은 후니가 갖고, Shopby 가 결제할 때마다 우리한테 잔액을 물어보고 빼 가는" 방식이에요. Shopby 가 이걸 정식으로 지원합니다 — 단, 엔터프라이즈 플랜 전용이고, 우리 서버가 느리면 손님 결제가 막힙니다.

근거: NHN커머스 워크스페이스 「[엔터프라이즈] 외부 적립금 연동가이드」(원문 md 30KB 확보, 2026-07-01 개정분 포함). Server 명세의 GET /accumulations/externals·EXTERNAL_ACCUMULATION·Shop 이력의 mappingKey(외부포인트 사용 시에만) 가 이 기능의 흔적.

개념

가이드 원문: 「고객사에서 기존에 사용하던 적립금(마일리지)를 전환 절차 없이 그대로 사용할 수 있고, 샵바이에서 고객사의 외부포인트를 연동하는 개념」. 호출 주체가 뒤집힙니다 — A 는 후니가 Shopby 를 부르고, B′ 는 Shopby 가 후니를 부릅니다. 후니 webadmin 이 프린트머니 원장(잔액·트랜잭션)을 갖고, Shopby 는 결제·취소·조회 때마다 후니 API 를 동기 호출해요. Shopby 가 제시하는 두 방식 중 방법1(전환)은 곧 방안 A 의 마이그레이션이고, 방법2(연동)가 B′ 입니다.

충전은 어디서 받나 — B′ 에서도 Shopby 결제를 쓸 수 있어요

  • B′-1 (Shopby 경유): 방안 A 와 같은 충전권 상품 주문 → PAY_DONE 감지 → 이번엔 Shopby 적립금이 아니라 후니 원장에 크레딧. Shopby PG·무통장 흐름을 그대로 쓰고 후니는 결제 모듈이 필요 없음.
  • B′-2 (후니 직접): 후니가 PG 를 직접 계약해 스킨 충전 화면에서 결제 → 원장 크레딧. Shopby 에 충전 주문이 쌓이지 않지만 PG 계약·결제 구현이 후니 몫.

예시로 따라가 보기 (B′)

  1. 회원 A 가 50,000원 충전권을 무통장으로 주문·입금 → webadmin 잡이 PAY_DONE 감지 → 후니 원장 A 잔액 50,000 (Shopby 는 관여 없음)
  2. A 가 명함 주문서를 열면 Shopby 가 GET /accumulations/available-amounts?memberKey=A 를 후니에 호출 → 50,000 응답 → 체크아웃에 "프린트머니 50,000" 표시
  3. 32,000원 사용해 결제 → Shopby 가 POST /accumulations/subtract {32000, mappingKey:주문번호, requestId} 호출 → 후니 원장 18,000, 응답 {no:"TX-123"}
  4. 같은 requestId 로 Shopby 가 재시도해도 후니는 처리 없이 같은 응답을 돌려줘야 함(멱등)
  5. 주문 취소 → Shopby 가 subtract-rollback {no:"TX-123", amount:32000} → 후니 원장 50,000 복원

14-2-3. 재검토 — 입금알림 서비스 대신 토스페이먼츠 가상계좌 API 로 가는 경우 (피드백 2026-09-16)

왜 다시 보나 — 어제 가상계좌를 뺀 이유는 "수수료"였는데, 피드백에 따르면 가입비·연관리비(고정비)는 포트원 추천패키지 등 프로모션으로 면제되는 사례가 많아요. 그러면 남는 비용은 건당 300원뿐이라, "입금자명 매칭"이라는 골칫거리를 아예 없애는 가상계좌를 다시 비교할 가치가 있어요. 최종 확정은 지니 결정 사항(§12 7번).

구조 차이 — 이 안은 "충전권 상품 + Shopby 무통장 주문"을 쓰지 않아요. 후니 스킨 충전 화면 → 후니 서버가 토스 가상계좌를 직접 발급(Shopby 주문 없음) → 고객 입금 → 토스 DEPOSIT_CALLBACK 웹훅 → 후니 원장(B′) 크레딧 또는 Shopby 적립금 지급(A). 즉 §3-B 의 B′-2(후니 직접) 경로이고, 상품 주문 PG(이니시스)와는 계약·정산이 완전히 분리됩니다.

회계 처리 메모

  • 새 시스템 선수금 계정은 기초잔액 = Σ이관액으로 시작하고, 구 장부의 선수금은 같은 금액만큼 이월된다 — 이중 계상 없음.
  • 이관분과 신규분은 잔액은 하나(고객 화면), 원장에서는 source 로 구분 → "이관 잔액이 얼마나 소진됐나"를 언제든 산출.
  • 사용 차감 순서(이관분 먼저 vs 신규분 먼저)는 B′ 면 후니가 정하고, A 면 Shopby 규칙(미확인)에 따름 — 회계상 순서가 필요하면 B′ 가 유리.
  • 음수 잔액(미수금)은 이관 대상이 아니라 별도 채권 관리(260630 MQ-18).

16. 화면 배치와 개발 주체 (피드백 2026-09-16)

피드백: 「프린팅머니·외부포인트 API 5종·증빙 발행·충전운영화면을 지니가 개발하면 webadmin 메뉴, 김동학 대표가 개발하면 별도 화면이 맞다. webadmin 은 상품·위젯 관리 화면 모음인데 쇼핑몰 관리자 기능을 쑤셔 넣는 느낌. 디자인등록 관리는 상품정보의 일부라 webadmin 에 들어가도 된다.」

원칙

  • webadmin = 상품·위젯(카탈로그) 관리 도구. 프린트머니·입금·증빙은 쇼핑몰 운영(주문·결제·정산) 성격이라 결이 다릅니다.
  • 그래도 한 저장소·한 배포가 지금은 가장 쌉니다 — Shopby 클라이언트·웹훅 수신함·장기토큰·프록시가 이미 webadmin 안에 있어서, 별도 서비스로 쪼개면 인증·배포·모니터링을 두 번 만들어요.
  • 절충: Django 앱을 분리(catalog 와 별개의 shopops 앱) + 사이드바 메뉴 그룹 「쇼핑몰 운영」 분리. 코드·메뉴가 따로 있으면 나중에 떼어내기 쉽고, 지금은 "쑤셔 넣은" 느낌 없이 같은 관리자에서 씁니다.
