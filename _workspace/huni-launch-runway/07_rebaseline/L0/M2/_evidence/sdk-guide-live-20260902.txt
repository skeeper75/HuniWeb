⚡퀵스타트 — 5분 안에 위젯 띄우기
발급받은 site_key 와 위젯 코드만 있으면 됩니다. 페이지에 아래 두 줄을 넣으세요.
<!-- ① 위젯 스크립트 (한 번만) -->
<script src="https://huni-admin.printly.co.kr/static/catalog/widget.js"></script>
<!-- ② 위젯을 놓을 자리 -->
<huni-widget widget-id="WGT_000001" site-key="wk_xxxxxxxx"></huni-widget>
이게 전부입니다. 아래처럼 렌더됩니다 — 선택지·가격·검증 전부 위젯이 알아서 처리합니다.
퀵스타트 결과 — 선택을 바꾸면 가격이 자동 재계산됩니다(서버 계산)
💡 위젯은 Web Component(<huni-widget>)라 React·Vue·jQuery·순수 HTML 어디서든 같은 방식으로 동작합니다. 내부는 Shadow DOM(attachShadow)으로 격리돼 페이지 CSS 와 충돌하지 않지만, font-family 처럼 상속되는 CSS 속성은 shadow 경계를 그대로 넘어가므로 폰트는 페이지를 따라갑니다. ⚠ 단, 페이지 어디에도 font-family 를 선언한 곳이 없다면(리셋 안 된 기본 페이지 다수 해당) 상속값은 브라우저 기본 세리프 서체로 귀착합니다 — 페이지에 서체를 선언해 두거나 --hw-font 로 직접 지정하세요(§13 참조).
site_key 와 위젯 코드는 후니 담당자가 전달합니다(§1). 요청하실 때 위젯을 붙일 도메인을 함께 알려 주세요 — 등록된 도메인에서만 동작합니다.
값을 받기 전이라도 라이브 데모에서 실제 동작·이벤트·주문 결과를 먼저 확인할 수 있습니다.

도메인 등록에서 자주 막히는 곳
미리보기(preview) 배포 주소는 별도 등록이 필요합니다. 예를 들어 Vercel 프로덕션 myshop.vercel.app 을 등록해도, 브랜치 미리보기 myshop-git-dev-team.vercel.app 은 다른 호스트라 origin_not_allowed 로 막힙니다. 미리보기에서도 테스트하려면 그 주소를 함께 알려 주세요.
로컬 개발은 localhost · 127.0.0.1 을 등록하면 포트와 무관하게 통과합니다.
등록 도메인의 하위 도메인은 자동 포함됩니다(example.com 등록 → shop.example.com 통과).
브라우저가 아닌 곳에서(서버·curl 등) 호출하면 Origin 이 없어 막힙니다. 다만 주문 토큰 검증(/handoff/verify)은 예외로, 파트너 서버에서 그대로 호출할 수 있습니다(§6).
2동작 구조 — 무엇을 믿어야 하나
고객 브라우저                         후니 서버                    파트너 서버
┌──────────────┐   ① 구성 조회        ┌──────────┐               ┌──────────┐
│ <huni-widget>│ ───────────────────▶ │ /widgets  │               │          │
│  선택 UI      │   ② 가격(300ms 디바운스) /price   │               │          │
│  가격 표시    │ ───────────────────▶ │ /validate │               │          │
│  submit()    │   ③ 주문(전체 재검증) │ /handoff  │──서명 token──▶│ ④ verify │
└──────────────┘                      └──────────┘               │ 주문 확정 │
└──────────┘
가격·검증의 권위는 항상 서버입니다. 브라우저(위젯)는 표시만 합니다 — 위젯 코드를 조작해도 주문 금액은 바뀌지 않습니다.
주문 직전 /handoff 가 가격·제약·원고를 전부 다시 검증하고, 통과해야만 서명 token 을 발급합니다.
파트너 서버는 브라우저가 전달한 token 을 /handoff/verify 로 확인한 뒤 검증된 payload 의 금액으로 주문을 만듭니다.
3임베드 — 선언형과 SDK형
두 방식은 완전히 등가입니다(같은 코드 한 벌). 정적 페이지는 선언형, SPA·동적 마운트는 SDK형이 편합니다.
A. 선언형 (속성)
<huni-widget

4이벤트 레퍼런스
모든 이벤트는 CustomEvent(bubbles + composed)로 <huni-widget> 엘리먼트에서 발화합니다. SDK 는 w.on("ready", …) 처럼 접두사 없이 구독합니다.
이벤트언제detailhuni:ready위젯 로드·첫 렌더 완료{ }huni:change고객이 선택을 바꿈{ selections, qty, … }huni:priced가격 계산 성공{ total, supply, vat, lines }huni:state주문가능 상태 변화 (ready 직후 1회 보장){ canOrder, reasons[], price|null }huni:submit핸드오프 성공{ ok:true, token, payload, handoff_id, summary, expires_in }huni:editor편집기 버튼 클릭 (취소 가능 — §8){ item, mbr, product, widgetId }huni:error가격/검증/핸드오프/편집기 실패{ message, code?, cause? }
발화 순서 계약: huni:ready → huni:state(초기 1회 보장) → 이후 상태가 실제로 바뀔 때만. 같은 상태 연속 발화는 억제됩니다.
5자체 버튼 연동 — hide-submit
위젯 내장 장바구니 버튼 대신 쇼핑몰 자기 디자인의 버튼으로 주문을 걸 수 있습니다.
숨는 것은 버튼 한 줄뿐이고, 미충족 사유 안내는 위젯 안에 남습니다(그것까지 직접 그리려면 hide-reasons 병용).
내장 버튼이 숨고, 쇼핑몰 버튼이 huni:state 로 활성/비활성 동기화되는 모습
<huni-widget id="hw" widget-id="WGT_000001" site-key="wk_…" hide-submit></huni-widget>
<button id="myBtn" disabled>장바구니 담기</button>
<script>
const el = document.getElementById("hw");
// ① 상태 구독 → 버튼 동기화
el.addEventListener("huni:state", (e) => {
myBtn.disabled = !e.detail.canOrder;
myHint.textContent = e.detail.reasons.join(", ");
});
// ② 내 버튼 클릭 → 내장 버튼과 완전히 같은 검증 경로
myBtn.onclick = async () => {
myBtn.disabled = true;              // 중복 제출 방지(호스트 책임 — 아래 주의)
const r = await el.submit();       // 절대 throw 하지 않습니다
if (r.ok) cart.add(r.token, r.payload);
else      showError(r.message, r.reasons || r.violations || r.errors);
myBtn.disabled = !el.canOrder();
};
</script>
주문 조건 미충족은 어떻게 전달되나 — 원고·필수 옵션
고객이 원고를 안 올렸거나 편집기로 디자인을 안 만든 경우, 필수 옵션·수량 규칙을 안 지킨 경우
모두 같은 통로로 전달됩니다 — huni:state 의 canOrder(불리언)와
reasons(사람이 읽는 문구 배열)입니다. 서버에 가기 전에 브라우저에서 판정합니다.
// 선택이 바뀔 때마다 발화 — 버튼 잠금과 안내를 여기서 동기화
el.addEventListener("huni:state", (e) => {
myBtn.disabled  = !e.detail.canOrder;
myHint.textContent = e.detail.reasons.join(", ");
// 예: "원고 업로드 또는 편집기로 만들기", "사이즈 선택", "수량 최소 100"
});
원고 관련 문구는 위젯에 어떤 컴포넌트가 놓였는지에 따라 달라집니다. 파일 업로드와 편집기가
둘 다 있으면 한 벌로 묶여 둘 중 하나만 하면 충족됩니다.
위젯 구성미충족 시 reasons 문구
파일 업로드 + 편집기원고 업로드 또는 편집기로 만들기
파일 업로드만원고 파일 업로드
편집기만편집기로 원고 만들기
업로드 진행 중원고 업로드가 끝나기를 기다리는 중입니다
업로드 실패업로드에 실패한 원고가 있습니다 — 다시 시도해 주세요
셋트 상품(책자 등)은 어느 구성원인지 앞에 붙습니다 — "내지 2 원고 파일 업로드".
편집기는 저장을 해야 충족으로 칩니다(열어보고 닫기만 하면 미충족).
전송이 끝난 파일만 원고로 인정합니다(업로드 중·실패는 미충족).
원고를 나중에 받는 상품이면 후니 담당자가 해당 항목을 선택 항목으로 설정해 이 검사에서 뺄 수 있습니다.
내장 버튼을 숨겨도 안내는 남습니다
hide-submit 이 숨기는 것은 버튼 한 줄뿐입니다. 미충족 사유 안내는 위젯 안에 계속 표시되므로,
호스트가 아무것도 그리지 않아도 고객은 "원고 파일 업로드" 같은 안내를 봅니다.
다만 호스트 버튼은 위젯이 제어하지 못합니다 — 잠그지 않으면 눌리므로 위 예시처럼
huni:state 로 disabled 를 동기화하세요.
사유 UI 까지 직접 디자인하려면 hide-reasons 를 함께 붙입니다. 그러면 위젯은 사유를 그리지 않고,
호스트가 reasons 배열로 전부 그립니다(이 이벤트만으로 충분해 별도 폴링이 필요 없습니다).
<huni-widget … hide-submit hide-reasons></huni-widget>
버튼을 잠그지 않았다면 — submit() 이 즉시 막습니다
미충족 상태에서 submit() 을 불러도 서버로 나가지 않고 곧바로 실패로 돌아옵니다
(huni:error 이벤트도 함께 발화). 네트워크 왕복이 없으니 그대로 사유를 띄우면 됩니다.
{ "ok": false, "code": "incomplete", "message": "주문 조건 미충족",
"reasons": ["원고 업로드 또는 편집기로 만들기"] }
클라이언트 판정을 어떤 식으로든 우회해 주문을 시도하더라도, 서버가 마지막 관문에서
artwork_not_uploaded(422) 로 다시 막습니다 — 원고 없는 주문은 두 겹으로 차단됩니다.
submit() 결과 계약 — 실패도 항상 resolve (reject 없음)
// 성공
{ "ok": true, "token": "…", "payload": {…}, "handoff_id": "550e8400-…", "summary": [...], "expires_in": 3600 }
// 실패
{ "ok": false, "code": "…", "message": "…", "reasons"|"violations"|"errors": [...] }
code언제동반 필드서버 호출not_ready위젯이 아직 로드되지 않음—없음incomplete필수 선택 미완료 (클라이언트 판정)reasons[]없음 — fetch 0회constraint제약 규칙 위반 (validate)violations[]validate 만validate_failedvalidate 네트워크/서버 오류messagevalidate 만handoff_failed핸드오프 거절(422 등)errors[]validate + handoff
알려진 요철 3가지 — 반드시 읽으세요.
① sdk.canOrder() 는 레거시로 사유 배열(string[])을 반환합니다(이름과 다름). 엘리먼트의 el.canOrder() 는 불리언입니다. 새 코드는 getStatus().canOrder 를 쓰세요.
② state.price 는 마지막 서버 응답값입니다 — 선택 변경 후 약 300ms 디바운스 동안은 직전 값이 실립니다.
③ 중복 제출 가드가 위젯에 없습니다. 버튼 연타로 handoff 가 여러 번 서명될 수 있으니 위 예시처럼 호스트가 disabled 로 막아 주세요.
6주문 데이터 수신 — token 검증은 서버에서
submit() 성공 결과의 token 과 payload 를 파트너 서버로 전송합니다(장바구니/주문 API 등 자유).
파트너 서버가 POST https://huni-admin.printly.co.kr/api/w/v1/handoff/verify 에 { site_key, token } 을 보냅니다.
valid:true 면 응답의 payload(검증된 원본) 로 주문을 만듭니다 — 브라우저가 보낸 payload 는 참고용일 뿐, 금액은 반드시 verify 응답 값을 쓰세요.
토큰 유효기간은 3600초입니다. 만료되면 valid:false, reason:"expired" — 고객에게 다시 주문(재서명)을 요청하세요.
handoff_id(GUID)는 submit() 결과에 들어 있습니다 — verify 응답이 아니라 브라우저가 받은 결과에서 꺼내 서버로 함께 넘기세요. 주문 레코드에 저장해 두면 후니 측 로그와 조인되는 추적 키라 문의·장애 조사가 빨라집니다.⚠ handoff_id 는 추적용이지 주문의 신원이 아닙니다 — 재견적(§9)을 부를 때마다 새로 발급되고, 제작 사양 전문은 최초 /handoff 기록에만 남습니다. 주문과 사양을 잇는 것은 토큰이며 그 일을 하는 것이 주문 등록(§10)입니다. 저장하신다면 맨 처음 담을 때의 값을 남겨 두세요.
# 파트너 서버 (예: Node)
const r = await fetch("https://huni-admin.printly.co.kr/api/w/v1/handoff/verify", {
method: "POST", headers: { "Content-Type": "application/json" },
body: JSON.stringify({ site_key: process.env.HUNI_SITE_KEY, token })
}).then(r => r.json());
if (!r.valid) throw new Error("토큰 무효: " + r.reason);
createOrder({ amount: r.payload.total, detail: r.payload });  // 검증된 금액만 사용
7원고 파일 업로드
위젯에 파일 업로드 컴포넌트가 배치돼 있으면 위젯이 전 과정을 자동 처리합니다 — 파트너 코드는 필요 없습니다.
브라우저 → S3 직접 업로드(presigned PUT). 파일이 후니/파트너 서버를 거치지 않습니다.
100MB 초과는 멀티파트로 자동 전환, 파일당 최대 500MB(위젯 설정에 따름).
업로드된 파일 참조는 handoff payload 의 files 에 자동 포함됩니다. 필수 원고가 미업로드면 주문이 artwork_not_uploaded 로 막힙니다.
8편집기(Edicus) 연동 — 고객이 브라우저에서 디자인
원고 파일을 올리는 대신 고객이 웹에서 직접 디자인하게 할 수 있습니다. 위젯에 편집기 버튼(🎨)이 배치돼 있으면
파트너 코드는 0줄입니다 — 버튼을 누르면 위젯이 전체화면 편집기를 띄우고, 저장 결과를 주문 데이터에 실어 줍니다.
동작 흐름 — 무엇이 자동으로 일어나나
고객이 사이즈·옵션을 고르고 편집기 버튼을 누릅니다.
위젯이 서버에 현재 선택 조합을 보내 어떤 편집기 템플릿을 열지 결정받습니다(/editor/resolve).
조합 → 템플릿 매핑은 후니 관리자가 상품별로 등록하며, 클라이언트는 어떤 매핑도 추론하지 않습니다.
위젯이 사용자 토큰을 서버에서 대리 발급받습니다(/editor/token). 편집기 비밀 API 키는 서버 밖으로 나가지 않습니다.
전체화면 오버레이가 열리고 편집기가 패시브 모드로 표시됩니다 — 편집기 내부 툴바 대신 오버레이 상단바(저장 / 저장 후 닫기 / 닫기)가 조작을 담당합니다.
고객이 저장하면 프로젝트 식별자가 위젯에 기록되고, 주문 시 handoff payload 의 editors 에 자동으로 실립니다.
같은 항목을 다시 누르면 이어 편집됩니다(단, 사이에 규격이 바뀌었으면 새 디자인으로 시작).
조건에 따라 열리는 템플릿이 달라집니다
같은 상품이라도 사이즈·옵션 조합마다 규격이 다르므로 서로 다른 편집기 템플릿이 열립니다. 예를 들어 스티커에서
사이즈를 바꾸면 다른 재단 규격의 템플릿이, 커팅 모양을 바꾸면 그에 맞는 템플릿이 열립니다.
등록되지 않은 조합에서는 편집기가 열리지 않습니다(no_editor_mapping).
필수 옵션을 아직 고르지 않은 상태도 마찬가지입니다. 이는 의도된 안전장치입니다 — 조합에 맞지 않는 규격으로
고객이 원고를 만들어 버리는 사고를 막기 위해 느슨하게 근접 매칭하지 않고 차단합니다.
특정 조합에서 계속 막힌다면 후니 담당자에게 해당 조합의 템플릿 등록을 요청하세요.
주문 데이터에 실리는 편집기 결과
주문(handoff) payload 의 editors 배열에 항목별 편집 결과가 담깁니다.
prjid(편집기 프로젝트 식별자)를 주문 레코드에 반드시 저장하세요 — 인쇄용 데이터를 뽑을 때 쓰는 열쇠입니다.
{
"editors": [
{ "item": "WGTI_000123", "mbr": null, "inst": 1,
"result": { "prjid": "-KzvOwkOBG3ym3G9Mp6i", "ps_cd": "124x186@HU_14545",
"saved_at": "2026-08-15T07:21:40.512Z" } }
]
}
편집기 항목이 필수 원고로 설정된 위젯은, 저장 없이 주문하면 artwork_not_uploaded 로 막힙니다.
파일 업로드(§7)와 편집기는 같은 "원고" 경로의 두 방식이며, 한 위젯에 함께 배치할 수도 있습니다.
편집기를 직접 제어하고 싶다면 — huni:editor 가로채기
쇼핑몰이 자체 편집기나 별도 디자인 흐름을 쓰는 경우, huni:editor 이벤트를
preventDefault() 로 취소하면 위젯 기본 오버레이가 뜨지 않습니다. 이때 편집이 끝나면
el.setEditorResult(item, result) 로 결과를 위젯에 알려 줘야 주문에 실립니다.
el.addEventListener("huni:editor", (e) => {
e.preventDefault();                       // 기본 오버레이 취소 — 내가 직접 처리
const { item, mbr, product } = e.detail;
openMyOwnEditor(product).then((r) => {
el.setEditorResult(item, { prjid: r.id });   // 결과를 위젯에 반영(주문에 실림)
});
});
취소하지 않으면(기본) 위젯이 알아서 전부 처리합니다. 이벤트는 알림 용도로도 유용합니다 —
취소하지 않고 로깅·분석에만 쓰면 기본 동작은 그대로 유지됩니다.
오버레이 스타일 조정
오버레이도 CSS 변수로 열려 있습니다(§9 와 동일한 방식).

9장바구니 연동 — 담기부터 결제까지
쇼핑몰은 DB를 만들지 않으셔도 됩니다. 주문 토큰·사양은 저희가 보관하고, 쇼핑몰은 36자짜리
item_id 하나만 샵바이 장바구니 텍스트 옵션에 실으시면 됩니다.
그리고 반드시 필요한 한 단계가 있습니다 — 결제 직전 갱신입니다.
주문 토큰은 유효기간이 1시간이라, 담아 둔 채로 시간이 지나면 그대로는 결제되지 않습니다.

고객 눈에 장바구니는 하나지만, 기록은 두 곳에 남습니다.
이 문서에서 “장바구니”가 나오면 어느 쪽인지 이름을 붙여 적었습니다.

지금은 저희가 대신 보관합니다. 쇼핑몰이 다루실 값은

이미 테이블을 만들어 두셨다면 그대로 두셔도 동작합니다(토큰을 직접
보관하는 기존 방식도 계속 지원합니다). 다만 새로 만드실 필요는 없습니다.
무엇이 어디에 있는지는 이 한 줄로 충분합니다 —
“무엇이 담겼나 · 몇 개인가 · 지웠나”는 샵바이가, “무엇을 어떻게 만드나 ·
얼마인가”는 저희가 갖습니다. 둘을 잇는 것이 item_id 입니다.
수량을 바꾸면 양쪽을 함께 고쳐야 합니다
저희 쪽 PUT /cart/items/{item_id} 로 금액을 다시 받고,
그 금액으로 샵바이 장바구니의 orderCnt(= 금액 ÷ 10)도 고쳐 주세요.
한쪽만 고치면 화면 금액과 결제 금액이 갈립니다.
01먼저 알아야 할 전제 — 토큰 · 서버키
위젯이 주문을 넘길 때 저희가 드리는 token은
저희가 HMAC으로 서명한 주문 사양서입니다.
안에 든 것 — 상품, 선택 사양, 옵션, 후가공, 수량, 원고 파일 키, 그리고 금액
서명이 붙어 있으므로 아무도 내용을 고칠 수 없습니다. 한 글자라도 바꾸면 검증에서 걸립니다
고객이 브라우저에서 금액을 조작해 싸게 주문하는 것을 막는 장치입니다
그리고 이 토큰에는 유효기간 1시간이 있습니다.
여기서 장바구니와 충돌이 생깁니다. 장바구니는 며칠씩 남는 물건인데, 토큰은 1시간짜리
견적서입니다. 담고 1시간이 지나면 그 토큰으로는 결제할 수 없습니다.
왜 유효기간을 늘리지 않나
서명은 위조를 막을 뿐 최신성을 보장하지 못하기 때문입니다.
유효기간을 30일로 늘리면 그동안 이런 것들이 검사 없이 결제로 진입합니다 —
그 사이 개정된 단가, 삭제된 수량 구간, 등록 해제된 자재 조합, 단종된 상품,
수명주기로 이미 지워진 원고 파일.
유효기간은 “이 견적이 아직 유효하다고 저희가 보증하는 시간”이지
“장바구니 보관 기간”이 아닙니다. 늘리면 보증할 수 없는 것을 보증하게 됩니다.
해법은 유효기간을 늘리는 것이 아니라, 결제 직전에 견적을 새로 뽑는 것입니다.
커머스에서 장바구니를 스냅샷으로 두고 결제 직전에 가격·재고를 다시 확인하는 것과 같은
패턴입니다. 저희 경우 “재고” 자리에 단가 등록 여부 · 자재 조합 등록 여부 ·
옵션 제약 규칙이 들어갑니다.
그래서 쇼핑몰은 토큰을 만지지 않으셔도 됩니다
토큰은 다루기 까다로운 값입니다 — 수 KB라 컬럼 길이를 잘못 잡으면 조용히 잘리고,
갱신할 때마다 금액·요약과 한 세트로 바꿔야 합니다. 둘 다
한 번 틀리면 결제가 통째로 막히는 종류입니다.
그래서 저희가 보관합니다. 쇼핑몰은 담을 때 토큰을 저희에게 한 번 넘기고
그 뒤로는 item_id 로만 이야기하시면 됩니다. 갱신도 저희가
한 번에(원자적으로) 처리하므로 “토큰만 갱신하고 금액은 옛것” 같은
어긋남이 생길 자리가 없습니다.
서버키(X-Huni-Server-Key)가 무엇인가 이번에 신설
장바구니 API 와 함께 새로 생긴 사이트별 비밀 열쇠입니다.
저희가 발급해 전달해 드리며, 쇼핑몰 서버가 저희 서버를 부를 때 요청
헤더에 실어 "이 호출은 진짜 자사몰 서버가 보낸 것"임을 증명합니다.
// 형태 — hsk_ 로 시작하는 50자 남짓 문자열 하나. 헤더에 그대로 싣습니다.
X-Huni-Server-Key: hsk_f3K9…
왜 하나 더 생겼나 — 기존 값들이 전부 공개값이기
때문입니다. site_key 는 임베드 태그에 박혀 페이지 소스로 보이고,
item_id 도 샵바이 주문조회 응답으로 고객에게 읽힙니다. 공개값 두 개만으로
사양·금액·원고 파일 키를 내주는 API 를 열 수는 없어서, 서버끼리만 아는
열쇠를 하나 더 만들었습니다.

02전체 흐름
번호는 아래 단계 목록과 같다 — ① 담기(3호출) → ② 장바구니 화면(2호출) → ④ 결제 직전 갱신 → ⑤ 주문 등록. 샵바이는 주문번호만 만들고, 그 번호로 결제 웹훅에서 후니와 다시 만난다.
같은 번호로 아래에서 한 단계씩 설명합니다.
1
담기
위젯 submit() → POST /cart/items → 샵바이 POST /cart
위젯이 준 token 을 저희에게 넘기면 item_id 와
요약 한 줄·금액을 돌려드립니다. 그 item_id 를 샵바이 장바구니
텍스트 옵션(huni_item)에, 요약을 huni_order 에 실으세요.
2
장바구니 화면
샵바이 GET /cart → POST /cart/items/fetch
샵바이 장바구니에서 item_id 들을 모아 한 번에 보내면
줄마다 금액·수량·요약·상태를 돌려드립니다. 왕복 1회로 끝납니다.
3
수량 변경
PUT /cart/items/{item_id} { qty }  ·  샵바이 PUT /cart
저희가 새 금액을 계산해 보관 중인 토큰까지 함께 갱신합니다.
item_id 는 바뀌지 않습니다 — 샵바이에 박아 둔 값을 고칠 필요가 없습니다.
4
결제 직전 갱신 필수
PUT /cart/items/{item_id}  ·  수량 생략
현재 가격으로 다시 계산하고 유효기간이 살아있는 토큰을 새로 발급합니다.
금액이 달라졌으면(price_changed) 고객에게 확인받으세요.
5
결제 → 주문 등록
POST /order/register { order_no, line_no, item_id }
결제가 끝나면 주문번호와 item_id 만 보내 주세요.
토큰은 저희가 꺼내 씁니다.
6
삭제
샵바이 DELETE /cart  ·  DELETE /cart/items/{item_id}
고객이 장바구니에서 빼면 저희 쪽도 지워 주세요. 빠뜨려도 무해합니다 —
30일 뒤 자동 정리됩니다.
핵심
④가 핵심입니다. ③(수량 변경)은 안 만들어도 되지만
④는 없으면 결제 자체가 안 됩니다(토큰 유효기간 1시간).
그리고 ③·④는 같은 API입니다 — 수량을 주면 수량 변경,
안 주면 가격만 다시 계산.
03단계별 구현
공통 — cart/* 는 전부 서버에서만 부릅니다
네 API 모두 요청 헤더에 X-Huni-Server-Key(저희가 발급하는
서버키)가 필수이고, 브라우저에서는 호출할 수 없습니다(CORS 미개방).
왜 site_key 로는 부족한가: item_id 는 샵바이 주문조회 응답으로
그대로 읽히고, site_key 도 임베드 태그에 박히는 공개값입니다.
공개값 두 개만으로 사양·금액·원고 파일 키를 내줄 수는 없습니다.
⚠키를 받기 전에는 헤더를 보내지 마세요. 기존 세 경로
(/handoff/verify · /handoff/requote ·
/order/register)는 아직 서버키가 선택이라
안 보내면 그대로 통과합니다 — 단 /order/register 를
item_id 로 부를 때는 예외 없이 필수입니다(§10). 그런데 발급 전에 값을
실어 보내면 저희 쪽에 대조할 키가 없어 403 bad_server_key
가 되고, 운영 중인 결제 경로 세 개가 한꺼번에 막힙니다.
순서는 ①키 수령 → ②환경변수 저장 → ③헤더 전송 입니다
(cart/* 는 처음부터 필수라 이 순서와 무관합니다).
서버키는 쇼핑몰 서버의 환경변수에만 두세요. 프런트엔드 번들·공개 설정에
절대 넣지 마십시오. 저희도 평문을 보관하지 않습니다 — 발급 순간 한 번만
알려 드리고, 분실하면 재발급뿐입니다(재발급하면 옛 키는 즉시 무효가 되니 교체 시점을
맞춰 주세요).
① 담기 — 토큰을 넘기고 item_id 를 받습니다
위젯 submit() 이 성공하면 그 token 을 쇼핑몰 서버로
보내고, 서버가 저희에게 넘깁니다.
POST /api/w/v1/cart/items
X-Huni-Server-Key: <서버키>
{ "site_key": "...", "token": "<widget.submit() 이 준 토큰>" }
→ { "ok": true, "item_id": "2b9aceca-…", "summary": "디지털 명함 / 스노우250g / 500개",
"total": "41800.00", "qty": 500, "qty_rule": {…}, "expires_at": "2026-09-26T03:31:40" }
이어서 샵바이 장바구니에 담습니다. 넣을 값은 둘뿐입니다.
텍스트 옵션 라벨넣는 값쓰임
huni_item응답의 item_id
기계가 읽는 키 — 장바구니 화면·주문 등록이 이걸로 저희 기록을 찾습니다
huni_order응답의 summary
사람이 읽는 요약 — 셀러어드민 주문 상세에서 담당자가 봅니다
수량(orderCnt)은 금액 ÷ 10 입니다
(판매가 10원 상품 × 수량 방식 — 자세한 것은 §11).
요약(summary)은 저희가 만듭니다
수량·사양이 바뀌면 요약도 함께 바뀌어야 하는데, 브라우저가 만든 문자열을 저장해 두면
그 갱신 통로가 없습니다. 그래서 저희가 만들어 드리고, 갱신 응답에도 새 요약을
함께 실어 드립니다 — 받은 값을 그대로 huni_order 에 넣으시면 됩니다.
요약에는 원고 파일 키·편집기 프로젝트 ID·금액 내역이 들어가지 않습니다.
텍스트 옵션은 주문조회 응답으로 그대로 읽히기 때문입니다.
셋트(책자) 상품도 그대로 담깁니다
중철·무선·PUR·트윈링·하드커버 책자, 엽서북, 스프링노트, 메모패드 —
전부 정상 동작합니다. 셋트는 수량 개념이 부수(copies)라
수량 변경 시 필드 이름만 다릅니다(③ 참고).
② 장바구니 화면 — 한 번에 조회
샵바이 GET /cart 응답의 optionInputs 에서
huni_item 값(= item_id)을 모아 한 번에 보내세요.
POST /api/w/v1/cart/items/fetch
X-Huni-Server-Key: <서버키>
{ "site_key": "...", "item_ids": ["2b9aceca-…", "7f31a0c4-…"] }   // 최대 50건
→ { "ok": true, "items": [
{ "status": "ok", "item_id": "2b9aceca-…", "summary": "…", "total": "41800.00", … },
{ "status": "not_found", "item_id": "7f31a0c4-…" } ] }
응답 순서는 요청 순서 그대로라 샵바이 장바구니 줄과 그대로 짝지으시면 됩니다.
브라우저가 보낸 item_ids 를 그대로 중계하지 마세요 중요
item_id 는 고객이 자기 장바구니에서 볼 수 있는 값입니다
(샵바이 텍스트 옵션에 들어 있습니다). 그리고 저희는 그 항목이 누구 것인지
모릅니다 — 보관소에는 회원 정보가 없고, 저희가 확인하는 것은
“이 사이트의 항목인가”까지입니다.
그래서 쇼핑몰 서버가 클라이언트 요청 본문의 item_ids 를 검사 없이
저희에게 넘기면, 고객 A 가 남의 item_id 를 넣어 다른 고객의
주문 요약과 금액을 읽을 수 있습니다(제작물 제목에 실명이 들어가는 경우가
많습니다).
반드시 이렇게 해 주세요 — item_ids 는
인증된 고객 세션으로 샵바이 GET /cart 를 호출해 받은 결과
에서만 뽑으세요. 클라이언트가 보낸 목록을 그대로 쓰면 안 됩니다.
갱신·삭제도 같은 원칙입니다.
한 줄이 죽어도 나머지 줄은 그리세요
전체를 거절하지 않고 줄마다 status 를 드립니다.
status뜻화면 처리
ok정상그대로 표시 · 주문 가능
expired담은 지 30일 경과“다시 담아 주세요” 표시 · 결제 대상 제외
product_unpublished상품이 판매중지됨“주문 불가” 표시 · 결제 대상 제외
not_found지워졌거나 없는 항목“다시 담아 주세요” 표시
③ 수량 변경 — 저희 쪽과 샵바이를 함께
PUT /api/w/v1/cart/items/2b9aceca-…
X-Huni-Server-Key: <서버키>
{ "site_key": "...", "qty": 1000 }        // 셋트(책자)는 "copies": 20
→ { "ok": true, "item_id": "2b9aceca-…"(그대로), "total": "76000.00", "qty": 1000,
"summary": "디지털 명함 / 스노우250g / 1000개", "price_changed": null, "prev_total": "41800.00" }
응답의 total 로 샵바이 장바구니 수량도 함께 고치고
(orderCnt = total ÷ 10), summary 로
huni_order 텍스트 옵션도 갱신하세요.
토큰 걱정은 안 하셔도 됩니다
예전 방식에서는 “수량만 바꾸고 토큰을 옛것으로 두면 결제 때 수량이 되돌아간다”는
함정이 있었습니다. 이제 토큰 갱신은 저희가 같은 호출 안에서 처리하므로
어긋날 자리가 없습니다.
사양(용지·사이즈·옵션)은 바꿀 수 없습니다 — 바꿀 수 있는 것은 수량(부수)뿐이고,
애초에 보낼 통로가 없습니다. 사양을 바꾸려면 항목을 지우고 상품 페이지에서 다시 담아야
합니다(이유는 06절).
④ 결제 직전 — 갱신 필수
결제 버튼을 누르면 PG 호출 전에 장바구니의 각 항목을 갱신합니다.
수량을 빼고 같은 API를 부르면 됩니다.
PUT /api/w/v1/cart/items/2b9aceca-…
X-Huni-Server-Key: <서버키>
{ "site_key": "..." }        // qty·copies 생략 = 가격만 다시 계산
여기서 세 가지로 갈립니다.
결과쇼핑몰 처리
200 · price_changed: false
그대로 결제 진행
200 · price_changed: true
“장바구니에 담으신 뒤 가격이 변경되었습니다” 안내 후 동의를 받고 진행.
동의 없이 오른 금액으로 결제하면 분쟁이 됩니다
4xx
그 항목은 지금 주문할 수 없는 상태입니다 — 단가 삭제, 자재 조합 등록 해제,
옵션 조합의 현재 규칙 위반, 판매중지, 보관 기간 경과.
해당 항목만 “주문 불가”로 표시하고 결제 대상에서 빼세요.
나머지 항목으로는 결제 가능합니다
error 문구는 고객이 읽을 문장으로 저희가 씁니다 —
그대로 노출해 주시면 됩니다. 단 errors 배열은
담당자용 진단 원문(내부 코드·구성요소명이 섞임)이라 고객 화면에는
가격 계산 실패 응답에 함께 오는 user_errors(고객 문장 배열)를 쓰시고,
errors 는 로그·문의용으로만 남기세요.
⑤ 주문 생성 직후 — 주문 등록
POST /api/w/v1/order/register
X-Huni-Server-Key: <서버키>            // item_id 로 보낼 때 필수
{ "site_key": "...", "order_no": "20260827-0001", "line_no": "1",
"item_id": "2b9aceca-…" }        // 토큰 대신 항목 ID
샵바이 주문조회 응답의 huni_item 값을 그대로 넣으시면 됩니다.
저희가 보관 중인 토큰을 꺼내 씁니다. 자세한 계약(멱등·재시도)은
§10 을 보세요. 결제 완료를 기다리지 마세요 —
입금대기(가상계좌·무통장) 주문도 만들어진 직후 바로 등록해야 원고가
보관 기한(30일)을 넘기지 않습니다(§10).
결제 후에는 만료를 보지 마세요
결제 시점에 금액이 확정됐으므로, 그 이후 단계(주문 생성 · MES 인계 · 원고 이관)에서
만료를 이유로 막으면 결제는 됐는데 주문이 안 들어가는 상황이 됩니다.
저희 쪽 처리도 같은 원칙입니다 — 주문 등록은 재전송해도 안전하고,
등록했다고 항목을 지우지 않습니다.
⑥ 삭제
DELETE /api/w/v1/cart/items/2b9aceca-…
X-Huni-Server-Key: <서버키>
{ "site_key": "..." }        // 없는 항목이어도 204 — 재시도 안전
// 본문을 못 싣는 클라이언트(axios.delete 등)는 …?site_key=... 쿼리로 보내도 됩니다
고객이 장바구니에서 뺐을 때 저희 쪽도 정리해 주시면 좋지만, 빠뜨려도 무해합니다 —
30일이 지나면 저희가 자동으로 지웁니다.
04API 명세 — /api/w/v1/cart/*
메서드 · 경로용도요청 본문
POST /cart/items담기
{ site_key, token, shop_cart_no? }
POST /cart/items/fetch일괄 조회(≤50)
{ site_key, item_ids: [ … ] }
PUT /cart/items/{item_id}수량 변경 · 결제 직전 갱신
{ site_key, qty? | copies? }
DELETE /cart/items/{item_id}정리
{ site_key } → 204
공통 헤더 X-Huni-Server-Key 필수.
shop_cart_no 는 선택입니다 — 샵바이 장바구니 번호를 알려 주시면 문의 조사 때
저희가 빨리 찾습니다(동작에는 영향 없음).
담기 · 갱신 응답
{
"ok": true,
"item_id":    "2b9aceca-edf5-4b8c-a682-0dec3f96af51",  // ★불변
"summary":    "디지털 명함 / 스노우250g / 500개",       // huni_order 에 그대로
"total":      "41800.00",   // 청구액(부가세 포함) — orderCnt = total ÷ 10
"qty":        500,          // 셋트는 0 — 대신 copies 가 옵니다
"qty_rule":   { "min": 100, "max": 5000, "incr": 100, "dflt": 500 },  // 수량 스테퍼 재료(dflt=초기값)
"expires_at": "2026-09-26T03:31:40",               // 보관 만료(담은 날 + 30일) — 한국시간, 오프셋 없음
// 갱신(PUT)에만 — prev_total 은 담기에도 옵니다(재견적 아니면 null)
"price_changed": false,        // 수량을 안 바꾼 호출에서만 판정
"prev_total":    "41800.00",
// 담기(POST)에만
"repriced": false,             // 정상 경로에선 언제나 false
// (repriced 가 true 면 prev_total 에 고객이 본 옛 금액이 함께 옵니다)
// 셋트(책자)일 때만
"is_set": true, "copies": 20
}
price_changed · prev_total은
수량(부수)을 바꾸지 않은 호출에서만 의미가 있습니다
(같은 조건으로 다시 계산한 결과라 직접 비교가 성립합니다).
수량을 바꾼 호출에서는 비교 조건이 다르므로 price_changed는
null로 내려갑니다.
총액은 수량에 비례하지 않습니다
인쇄는 수량 구간별 단가가 적용되어 1000개가 500개의 정확히 2배가 아닙니다
(보통 개당 단가가 내려갑니다). 이걸 오류로 처리하지 마세요.
담기 응답에 repriced 가 true 로 오면 — 금액을 확인하세요
담기 호출에 넘긴 토큰이 유효기간(1시간)을 넘긴 상태였다는 뜻입니다. 그때는 옛 금액을
그대로 굳히지 않고 저장 전에 다시 계산합니다. 위젯 담기 직후에 부르는
정상 경로에서는 언제나 false 이고, 고객이 화면에서 본 금액이 그대로
저장됩니다.
⚠true 일 때는 고객이 화면에서 본 금액과 장바구니에 담긴 금액이
다를 수 있습니다(고객이 위젯을 열어 둔 채 한 시간 넘게 자리를 비운 사이 단가가
바뀐 경우). 그래서 prev_total 에 고객이 보고 있던 옛 금액을

일괄 갱신

다른 점은 필드 이름 하나뿐입니다 — 단일 상품은 qty,
셋트는 copies. 셋트에 qty 를 보내면

호출 상한 — 장바구니는 전용 몫을 씁니다 (사이트당 분당 600회)

① 샵바이 장바구니 보존 기간이 며칠인가요?
저희 항목 보관 기간(expired)을 그 값에 맞추겠습니다.
현재는 30일로 잡아 두었습니다 — 아래 ②의 원고 보관 기간에 맞춘 값입니다.
장바구니 보존 기간이 30일보다 짧으면 알려 주세요. 그쪽에 맞춰 더 줄이겠습니다.
기간은 “처음 담은 시각”부터 셉니다
갱신을 부르면 토큰은 새로 나오지만, 만료 계산의 기준점은 최초로 담은 시각
그대로입니다. 즉 결제 직전 갱신을 아무리 자주 불러도 30일이
연장되지 않습니다. 원고·편집기 프로젝트가 실제로 삭제되는 시점은
갱신 횟수와 무관하니, 상한도 그래야 맞습니다.
② 원고 파일은 30일 뒤 삭제됩니다 — 이보다 오래 담아두면 주문이 성립하지 않습니다
결제 전 원고는 임시 저장소에 있고 30일 수명주기가 걸려 있습니다
(이 규칙의 목적 자체가 “장바구니만 담고 안 산 원고 정리”입니다).
그래서 항목 보관 기간도 30일로 맞췄습니다.
갱신은 원고 존재를 확인하지 않습니다
30일 이내라면 갱신은 통과하지만, 그 사이 원고가 삭제되었다면 주문은 뒤 단계에서
실패합니다. 현재로서는 장바구니 보존 기간을 30일 이하로 두는 것이
가장 확실한 방어입니다. 원고 존재 여부를 갱신 단계에서 확인하는 것은 저희 쪽
후속 작업으로 검토 중입니다.
③ 편집기(Edicus)로 만든 원고의 보존 기간은? (저희가 확인 중)
편집기로 제작한 디자인은 파일이 아니라 Edicus 쪽 프로젝트로 보관되고,
주문에는 그 프로젝트 ID만 실립니다. 편집만 하고 결제하지 않은 프로젝트를 Edicus가
일정 기간 뒤 자동 삭제한다면 그 기간이 곧 샵바이 장바구니 보존 기간의 상한이
됩니다 — ②의 원고 파일과 완전히 같은 구조의 문제입니다.
저희가 Edicus 담당자에게 확인하고 있습니다.

왜 이렇게 나누나
원고 파일과 제작 사양의 원장은 저희에게 있고, 생산 현황은 생산 시스템에 있습니다.
쇼핑몰이 그 둘을 중계하려면 양쪽 사정을 다 알아야 합니다 —
그래서 중계는 저희가 맡고, 쇼핑몰은 주문까지만 책임집니다.
주문 등록 필수 신설
주문을 만든 직후, 주문번호와 item_id 를 저희에게 보내 주세요
(토큰을 직접 보관하는 기존 방식이라면 토큰을 — 그 경우 이미 하고 계신
handoff/verify 호출 바로 옆자리입니다).
1
결제 직전 재견적으로 최종 토큰 확보 지금 동작 중
PUT /api/w/v1/cart/items/{item_id}  (토큰 직접 보관 시 POST /handoff/requote)
앞 장(§9)의 결제 직전 갱신
(PUT /cart/items/{item_id})이 이 자리입니다. 거기서 확정된 금액이
실제로 청구되는 금액이고, 그 사양이 저희 쪽에 서명된 채로 보관됩니다.
토큰을 직접 보관하시는 기존 방식이라면 POST /handoff/requote 가 같은 자리입니다.
2
쇼핑몰에서 주문 생성
금액은 ①의 재견적 결과를 씁니다. 여기서 쇼핑몰 주문번호가 만들어집니다.
3
주문 등록 호출 필수
POST /api/w/v1/order/register
주문번호와 토큰을 한 번 보내 주시면, 저희가 토큰을 검증해
사양과 원고 파일을 그 주문번호에 묶어 보관합니다.
이 순간부터는 주문번호만으로 모든 것이 이어집니다.
// 쇼핑몰 주문 생성 직후
await fetch("https://huni-admin.printly.co.kr/api/w/v1/order/register", {
method: "POST",
headers: { "Content-Type": "application/json",
"X-Huni-Server-Key": process.env.HUNI_SERVER_KEY },  // item_id 로 보낼 때 필수
body: JSON.stringify({
site_key:  process.env.HUNI_SITE_KEY,
order_no:  orderNo,        // 쇼핑몰 주문번호
line_no:   lineNo,         // 주문 항목(옵션) 식별자 — 한 주문에 여러 건일 때
item_id:   itemId          // 샵바이 huni_item 텍스트 옵션의 값 (권장)
// token: token          // 토큰을 직접 보관하신다면 이쪽 — 둘 중 하나만
})
});
item_id 로 보내면 토큰을 만질 일이 없습니다 달라진 점
토큰 대신 장바구니 항목 보관소(§9)의 item_id 를 보내시면,
저희가 보관 중인 토큰을 꺼내 씁니다. 그 값은 샵바이 주문조회 응답의
huni_item 텍스트 옵션에 그대로 들어 있으니 따로 저장하실 필요가 없습니다.
기존 token 방식도 그대로 지원합니다 — 둘 중 하나만 보내시면 됩니다.
둘 다 없으면 missing_token 으로 거절합니다.
item_id 로 보내실 때는 헤더 X-Huni-Server-Key 가
필수입니다(token 으로 보내실 때는 아직 선택 — 단 헤더를
실었는데 값이 틀리면 그 호출도 403 입니다).
item_id 와 site_key 는 둘 다 고객이 볼 수 있는 값이라,
그 둘만으로 주문이 등록되게 둘 수는 없기 때문입니다.
등록이 끝나도 항목을 지우지 않습니다 — 이 API 는 재전송이 정상 경로라
(아래 already 참고) 지우면 재시도가 실패하기 때문입니다.
line_no 가 무엇인가
주문번호는 한 건에 하나지만 만들 물건은 여럿일 수 있습니다.
예를 들어 한 주문에 명함 200장과 스티커 500장이 담기면 사양도 원고도 생산도 따로입니다 —
주문번호만으로는 둘을 구분할 수 없어서 주문번호 + 항목번호로 보관합니다.
값 자체는 무엇이든 됩니다. 조건은 두 가지뿐입니다 —
① 한 주문 안에서 항목마다 다를 것
② 재시도해도 같은 값일 것(그래야 같은 항목이 두 번 등록되지 않습니다).
샵바이라면 orderProductOptionNo(주문상품옵션번호)를 그대로 넣으시면 됩니다.
상태변경 웹훅도 이 값을 실어 보내므로 저희 쪽에서 그대로 이어집니다.
숫자 타입이지만 문자열로 보내셔도 무방합니다.
쇼핑몰이 주문을 만들 때 이미 갖고 있는 식별자를 쓰는 것이 가장 안전합니다 —
저희가 "1, 2, 3 으로 매기세요"라고 하면 재시도 때 같은 번호라는 보장이 없습니다.

저희는 사양대로 만듭니다. 할인은 쇼핑몰의 판매 정책이지 생산 조건이 아닙니다.
저희가 금액을 보는 것은 사고 감지용입니다(예: 개발 실수로 금액이 빠진 채

중간에 재견적을 한 번 더 불러 토큰이 새로 발급됐더라도, 내용이 같으면 같은 주문으로 봅니다.
보내는 시점
주문이 만들어진 직후 — 결제 완료를 기다리지 마세요.
입금대기(가상계좌·무통장) 상태여도 보내 주세요.
저희가 그 시점에 원고 파일을 안전한 곳으로 옮겨 둡니다.
보내지 않으면 입금이 늦어질 때 원고가 보관 기한(30일)을 넘겨 사라질 수 있습니다.
결제 완료 자체는 저희가 쇼핑몰 웹훅으로 따로 받습니다 — 알려주지 않으셔도 됩니다.
빠뜨리면 어떻게 되나
결제는 됐는데 무엇을 만들어야 하는지 모르는 주문이 됩니다.
저희 쪽에서 생산 접수를 진행하지 않고 담당자에게 알립니다(조용히 넘어가지 않습니다).
그래도 사람 손이 한 번 들어가야 하므로, 이 호출은 실패 시 재시도해 주세요.
왜 토큰인가 — 추적용 아이디가 아니라
제작 사양 전문은 서명된 토큰 안에 들어 있습니다. 저희는 토큰만 있으면 언제든 원본을 꺼낼 수 있습니다.
handoff_id 는 추적·디버깅용 조인 키라서 이 용도에는 맞지 않습니다
(재견적할 때마다 새로 발급되고, 사양 전문을 담고 있지도 않습니다).
쇼핑몰 주문 데이터에 handoff_id 를 함께 저장해 두시면 문의·장애 조사 때 유용합니다 —
필수는 아닙니다.
하지 않으셔도 되는 것
아래는 전부 저희가 처리합니다. 개발하지 마세요.
✕원고 파일 저장·이동·보관
위젯이 저장소로 직접 올리고, 주문 이후 이동도 저희가 합니다. 쇼핑몰 서버를 파일이 지나가지 않습니다.
✕파일 오류 검사와 고객 재업로드 안내
인쇄 적합성 검사, 재업로드 요청 알림, 재업로드 화면 전부 저희 몫입니다.
✕생산 시스템 연동
쇼핑몰이 생산 쪽과 직접 주고받을 일은 없습니다.
✕주문상태를 '상품준비중'·'배송준비중'으로 올리는 처리
생산 진행에 맞춰 저희가 올립니다.
✕송장번호 등록
출고 시 저희가 등록합니다. 고객 배송조회는 그때 자동으로 열립니다.
제작 사양에 자동으로 실리는 값 — payload.work_size
완성(재단) 사이즈는 고객이 고른 그대로지만, 후가공 때문에 종이를 더 크게 써야
하는 경우가 있습니다(예: 말아박기는 사방으로 여유가 필요합니다). 이럴 때 저희
서버가 등록 시점에 실제 작업 크기(작업사이즈)를 다시 계산해 보관 사양의
work_size 에 담습니다 — 원고 검수·생산(MES) 이 기대하는 치수는
완성사이즈가 아니라 이 값입니다.
언제 실리나 — 여유가 설정된 후가공을 고른 항목에만. 해당이 없거나
계산이 실패하면 null입니다.
값의 형태 — { w, h }(mm) · m(상·하·좌·우 여유) ·
procs(여유를 만든 공정 코드). 셋트 상품은 members 로
구성원마다 독립 계산됩니다(표지 후가공이 내지 치수를 키우지
않습니다).
여러 후가공을 함께 고르면 방향별 최대값 한 번만
적용됩니다(더하지 않습니다) — 20mm 여유와 10mm 여유를 같이 고르면 20mm 만
커집니다.
재전송해도 안전합니다 — work_size 는 멱등 비교에서
제외되므로, 이 기능이 배포되기 전에 이미 등록된 주문을 다시 보내도
order_mismatch 로 막히지 않습니다.
응답에는 나오지 않습니다
work_size 는 order/register 응답에 실리지 않습니다 —
저희 내부 제작 데이터입니다. 파싱할 필드로 기다리지 마세요.
고객 화면에도 같은 값이 보입니다
위젯도 같은 규칙으로 계산합니다. 후가공 때문에 작업 사이즈가 커지면 고객 화면에서도
'작업 사이즈' 행이 강조되고 "○○ 선택 시 사방 N mm 크게 작업합니다" 같은 사유 문구가
붙습니다 — 쇼핑몰이 따로 안내 문구를 만들지 않아도 됩니다.
주의할 것 세 가지
1 · 쇼핑몰 관리자에서 주문 상태를 손으로 바꾸지 마세요
저희가 생산 진행에 맞춰 상태를 올립니다. 사람이 먼저 바꾸면

그 자리는 짧은 item_id(huni_item)가 대신합니다.

16위젯 없이 API 직접 쓰기 (고급)
자체 UI 를 완전히 직접 그리는 극단 시나리오입니다. 위젯이 해 주던 것(선택지 렌더·제약 연동·업로드·검증 호출 순서)을 전부 직접 구현해야 하므로 권장하지 않습니다 — 그래도 필요하면 호출 순서는 이렇습니다.
(선택) GET /catalog 로 임베드 가능한 위젯·상품·카테고리 목록을 받아 상품 페이지를 구성합니다.
GET /widgets/{wgt_cd} — meta.prod_dims·opt_groups 로 선택 UI 를 그립니다. cfg.items 가 화면 구성(순서·숨김·기본값)입니다.
선택이 바뀔 때마다 POST /price — 응답 total 을 표시합니다. ok:false 면 그 조합은 판매 불가로 처리하세요.
(원고가 있으면) POST /upload/presign → 응답 url 로 S3 에 PUT → 반환 key 보관.
POST /handoff — 최종 선택값 전체 + files(3의 key). 성공 시 token/payload.
파트너 서버에서 POST /handoff/verify 후 주문 확정(§6과 동일).
직접 호출 시에도 검증 규칙은 동일하게 적용됩니다 — 위젯을 우회한다고 통과 기준이 느슨해지지 않습니다(fail-closed). 화면에서 허용한 조합이 handoff 에서 422 로 거절되면, 화면 로직이 서버 규칙과 어긋난 것입니다.

18FAQ
Q. site_key 가 HTML 에 노출돼도 되나요?네. 공개키입니다. 도메인 제한(origin_not_allowed)과 서버 재검증(handoff)이 보안을 담당하고, 금액·재고에 영향을 줄 수 있는 값은 전부 서버가 다시 계산합니다.
Q. 위젯이 "주문 불가" 라는데 이유를 어디서 보나요?위젯 하단 사유 박스, 또는 huni:state 의 reasons 배열. hide-reasons 를 켰다면 reasons 를 직접 그려 주세요.
Q. 여러 위젯을 한 페이지에 놓아도 되나요?됩니다. <huni-widget> 을 여러 개 두면 각각 독립 동작합니다(이벤트는 각 엘리먼트에서 발화).
Q. 테스트는 어디서 하나요?라이브 데모 페이지에서 임베드 동작·이벤트·submit 결과를 코드 없이 확인할 수 있습니다. 별도 테스트 환경 site_key 가 필요하면 후니 담당자에게 요청하세요.
