# 무통장 실주문 1건 관통 — 실행 절차서 (실무진용)

> 작성일 **2026-09-02** · 카드 `L0/CARDS-Q.md` §Q2 할 일 1 · lane `plan-huniweb`
> **이 문서는 절차서다. 이 레인은 주문을 넣지 않았다.** 실행은 지니·실무진이 직접 한다.
> 입금확인은 **실무진이 자기 셀러어드민 계정으로** 누른다(지니 확인 2026-09-02 16:5x).

## 0. 이 절차가 왜 지금 생겼나

샵바이가 PG 승인 전에 **무통장입금**을 먼저 열어 주기로 했다. 무통장 주문은
「입금대기」로 성립하고, 운영자가 **[입금확인 처리]** 를 손으로 누르면 「결제완료」가 된다
(`L0/N1/shopby-order-state-machine.md` T2·T4·B2).

그래서 **PG 승인을 기다리지 않고도 주문 1건이 13단계를 끝까지 지나가는지** 볼 수 있다.
지금까지 「승인 후에만 확인 가능」으로 미뤄 뒀던 것들이 여기서 닫힌다.

바뀌지 않는 것도 적어 둔다. **카드·계좌이체 같은 PG 수단의 승인은 여전히 별개**이고,
무통장은 「먼저 돌려볼 길」이지 오픈 결제수단의 대체가 아니다.

## 1. 시작하기 전에 — 준비물과 금지사항

### 준비물

| 무엇 | 왜 | 누가 |
|---|---|---|
| 자사몰 **비회원(게스트) 브라우저 창** — 시크릿 모드 권장 | E-5·E-6(비회원 경로)을 같이 닫는다. 상품 297건 전건이 **비회원 구매 가능**임을 실측했다(`api-check-a13-a5.md`) | 실행자 |
| **셋트(제본) 상품 1종** — 예: 무선책자·하드커버링책자·엽서북 | 셋트여야 `summary` 라벨 붕괴(E-4)가 같은 주문에서 같이 관측된다 | 실행자 |
| 작은 원고 파일 1개(PDF 등) | 원고 승격(t_ord_artworks)을 보려면 실제 파일이 있어야 한다 | 실행자 |
| 셀러어드민 계정 | 입금확인 처리는 셀러어드민에서만 된다(B2) | **실무진 본인 계정** |
| 라이브 DB 읽기 접속 | 후니 수신 확인은 SELECT 로만 한다 | 개발/지니 |
| 입금할 실제 금액 | 무통장은 **진짜 입금이 있어야** 결제완료로 넘길 명분이 선다. 소액 상품을 고르는 편이 낫다 | 실행자 |

### 금지사항

```
① 셀러어드민에서 주문상태를 손으로 올리지 않는다 — 입금확인 처리 1회만 예외.
   상태는 후니 서버가 올리는 것이 계약이다(sdk-guide :924-928).
② 라이브 DB 는 SELECT 만. INSERT·UPDATE·DELETE 0건.
③ 설정 변경 0건. 화면은 보기만 한다.
④ 계정 값(주소·아이디·비밀번호)은 어떤 파일에도, 캡처 이미지 안에도 남기지 않는다.
⑤ 「기대값과 다르다」를 실패로 적지 말 것 — 그대로 적는다. 이 절차의 목적은
   통과가 아니라 관측이다. 특히 단계 8·9 는 지금 코드 상태로는 안 되는 것이 정상이다(§3).
```

### [HARD] 미리 알고 들어가야 할 것 — 단계 8·9 는 지금 막혀 있다

저장소 전수 grep 결과, 자사몰이 후니에 주문을 알리는
**`POST /api/w/v1/order/register` 호출이 코드에 없다**(`L0/M2/contract-c2-shopby.md` F-1 · `:396`).
웹훅 수신함(`t_ord_webhooks`)은 받아서 쌓기만 하고 **소비자가 0개**다
(`L0/N1/webhook-catalog.md` :235·:239).

그래서 이 관통은 **단계 7까지는 지나가고, 단계 8에서 멈출 가능성이 매우 높다.**
그것을 확인하는 것이 이 절차의 절반이다 — 「안 해봐서 모르는 것」을 「해봤더니 여기서 끊긴다」로 바꾼다.
멈추면 §4 「끊긴 지점부터의 우회」로 간다.

## 2. 13단계 절차

각 단계는 네 칸이다 — **보는 곳 · 기대값 · 캡처할 것 · 안 되면 어디를 보나**.

### 단계 1 — 상품 보기

| 칸 | 내용 |
|---|---|
| **하는 일** | 시크릿 창에서 자사몰 상품 목록 → 셋트 상품(예: 무선책자) 상세로 들어간다 |
| **보는 곳** | 브라우저 화면 · 개발자도구 콘솔 |
| **기대값** | 목록에 시작가가 보이고, 상세에서 위젯이 그려지며 콘솔에 `huni:state` 이벤트가 1회 이상 찍힌다 |
| **캡처할 것** | ① 상품 상세 화면 전체 1장 ② 콘솔의 `huni:state` 첫 출력 1장 |
| **안 되면** | 위젯이 안 그려지면 그 상품에 위젯이 게시되지 않은 것이다(판매중 269 중 게시 193 — 77종은 위젯 없음, `L0/M1/customer-journey.md`). 다른 셋트 상품으로 바꾼다 |

### 단계 2 — 옵션 고르기(위젯)

| 칸 | 내용 |
|---|---|
| **하는 일** | 사이즈·내지종이 등 필수 항목을 고른다. 아무것도 고르지 않은 초기 상태의 콘솔도 한 번 본다 |
| **보는 곳** | 위젯 화면 · 콘솔 `huni:state.reasons` · 담기 버튼 |
| **기대값** | 초기에는 `reasons` 에 「사이즈 선택」 「내지종이 선택」 「제작물 제목 입력」 「원고 파일 업로드」 등이 들어 있고 `canOrder=false` 이며 담기 버튼이 눌리지 않는다. 다 고르면 `reasons` 가 비고 버튼이 열린다 |
| **캡처할 것** | ① 초기 `reasons` 배열 ② 전부 고른 뒤의 `huni:state` |
| **안 되면** | 다 골랐는데 버튼이 안 열리면 `reasons` 에 남은 항목을 그대로 적는다. 제약 규칙(`POST /validate`) 이 막고 있을 수 있다 |

### 단계 3 — 실시간 견적

| 칸 | 내용 |
|---|---|
| **하는 일** | 수량을 바꿔 가며 가격이 다시 계산되는지 본다 |
| **보는 곳** | 위젯 가격 표시 · 네트워크 탭 `POST /price` |
| **기대값** | 옵션·수량을 바꿀 때마다 `POST /price` 가 한 번씩(디바운스 300ms) 나가고 총액이 갱신된다. 화면 총액과 응답 총액이 같다 |
| **캡처할 것** | ① 최종 총액이 보이는 위젯 화면 ② `POST /price` 응답 본문 1건 |
| **안 되면** | 가격이 0 이거나 안 나오면 그 상품의 가격 구성요소가 라이브에 덜 적재된 것이다. 상품을 바꾸고 상품코드를 적어 둔다 |

### 단계 4 — 원고 올리기/편집

| 칸 | 내용 |
|---|---|
| **하는 일** | 준비한 파일을 올린다(편집기 상품이면 편집기로 들어가 저장한다) |
| **보는 곳** | 업로드 진행 표시 · 네트워크 탭 `POST /upload/presign` → S3 PUT |
| **기대값** | presign 응답이 오고 S3 PUT 이 200/204 로 끝난다. 위젯이 파일명을 보여 준다 |
| **캡처할 것** | ① 업로드 완료된 위젯 화면 ② presign 응답의 **키 경로**(파일명 부분만 — 서명 값은 가린다) |
| **안 되면** | PUT 이 403 이면 presign 만료·버킷 정책 문제다. 시각을 적어 두고 개발에 넘긴다 |

### 단계 5 — 장바구니 담기 ★E-4 관측 지점

| 칸 | 내용 |
|---|---|
| **하는 일** | 「장바구니 담기」를 누르고, 장바구니 화면을 연다 |
| **보는 곳** | 네트워크 탭 `POST /handoff` → 자사몰 서버 → 샵바이 장바구니 · 장바구니 화면 |
| **기대값** | 담기가 성공하고 장바구니에 1줄이 생긴다. **위젯 총액이 그대로 보인다.** 샵바이 수량 칸(`orderCnt`)은 총액÷10 이다 |
| **★ 같이 볼 것 (E-4)** | 담기 응답의 `summary` 배열에서 **표지코팅·박가공·형압 세 라벨의 값**을 본다. 셋 다 「디지털인쇄」로 나오면 라벨 붕괴가 재현된 것이다(`customer-journey.md` §6.1) |
| **캡처할 것** | ① 장바구니 화면 1장 ② 담기 응답의 `summary` 배열 전문 ③ 샵바이 장바구니의 수량 표시 |
| **안 되면** | 장바구니에 **「10원 × N개」만 뜨고 위젯 총액·요약이 사라졌다면** `huni_order` JSON 파싱이 실패한 것이다(`contract-c2-shopby.md` :378). 화면 그대로 캡처 — 이건 결함 증거다 |

### 단계 6 — 무통장으로 주문한다 ★DEPOSIT_WAIT 만들기

| 칸 | 내용 |
|---|---|
| **하는 일** | 주문서로 넘어가 **비회원(게스트)** 로 주문자 정보를 넣고, 결제수단에서 **무통장입금**을 고른 뒤 주문을 완료한다. **아직 입금하지 않는다** |
| **보는 곳** | 주문완료 화면 · 발급된 주문번호 · 안내된 입금계좌와 **입금기한** |
| **기대값** | 주문번호가 발급되고 주문상태가 **`DEPOSIT_WAIT`(입금대기)** 로 잡힌다. 입금 전인데도 **재고가 이미 차감**된다(`state-machine` §4-2). 이 시점에도 즉시 취소가 가능하다 |
| **★ 같이 볼 것 (E-3)** | 주문 직전과 직후의 **상품 재고 수치**를 둘 다 적는다. 후니는 금액을 수량으로 넣으므로 재고가 `총액÷10` 만큼 한 번에 빠진다. 실제로 얼마가 빠졌는지가 E-3 이다 |
| **★ 같이 볼 것 (E-5)** | 비회원인데 **주문완료 문자/메일이 오는가**. 오면 문구에 「1,316」 같은 금액÷10 숫자가 수량처럼 노출되는지 본다 |
| **캡처할 것** | ① 주문완료 화면(주문번호 보이게) ② 입금기한 안내 ③ 주문 전·후 재고 수치 2장 ④ 받은 알림 원문 |
| **안 되면** | 결제수단에 무통장이 없으면 샵바이 개방이 아직 안 된 것이다 — 진행을 멈추고 지니에게 알린다. 비회원 주문이 막히면 상품 설정 문제인데, 실측상 297건 전건 비회원 구매 가능이므로(§`api-check-a13-a5.md`) 몰 단위 설정을 본다 |

> **입금기한 주의**: 원고 파일 임시 보관이 30일이다. 입금기한이 그보다 길면 입금 전에 원고가 사라진다.
> 가이드 권장은 **3~7일**(sdk-guide :937-940). 안내된 기한이 그보다 길면 그대로 적어 둔다.

### 단계 7 — 주문 성립 확인(셀러어드민) ★A-1 관측 지점

| 칸 | 내용 |
|---|---|
| **하는 일** | 실무진이 셀러어드민 → 주문관리 → **입금대기 주문리스트**를 열고, 그 주문의 상세로 들어간다. **아직 입금확인을 누르지 않는다** |
| **보는 곳** | 주문관리 > 입금대기 주문 > 주문번호 클릭 |
| **기대값** | 그 주문 1건이 목록에 있고, 주문 상세의 옵션 칸에 **`huni_order` 와 `huni_item` 두 값이 잘리지 않고** 보인다 |
| **★ 같이 볼 것 (A-1)** | `huni_order` 가 **줄바꿈되는가 · 뒤가 잘리는가**. 그리고 단계 5에서 본 `summary` 라벨 붕괴가 **이 화면까지 전파됐는가** — 「표지코팅: 디지털인쇄」가 여기 그대로 보이면 담당자가 읽는 문장이 틀린 것이다 |
| **캡처할 것** | ① 입금대기 목록에서 그 주문 행 ② 주문 상세 전체 ③ 옵션 칸 확대 1장 |
| **안 되면** | 옵션 칸이 비었거나 값이 잘렸으면 **길이 상한에 걸린 것**이다. 잘린 위치를 캡처한다 — 이것이 계약이 `huni_token` 을 금지한 이유의 실물 증거다(`contract-c2-shopby.md` F-2) |

### 단계 8 — 입금 → [입금확인 처리] → 후니 수신 확인 ★핵심 관문

| 칸 | 내용 |
|---|---|
| **하는 일** | ⓐ 안내된 계좌로 실제 입금한다 → ⓑ **실무진이 자기 계정으로** 입금대기 주문리스트에서 **[입금확인 처리]** 를 누른다 → ⓒ 5분 뒤 후니 DB 를 읽는다 |
| **보는 곳** | ⓐⓑ 셀러어드민 입금대기 목록 · ⓒ 라이브 DB(읽기전용 SELECT) |
| **기대값 (플랫폼 쪽)** | 주문상태가 **`DEPOSIT_WAIT` → `PAY_DONE`(결제완료)** 으로 바뀐다. 이 전이는 **입금대기 목록에서만** 가능하고 결제완료로만 바뀐다(B2) |
| **기대값 (후니 쪽)** | 아래 SELECT 3건. **현재 코드 상태에서는 ②③이 0행일 가능성이 매우 높다**(§1 [HARD]) |
| **캡처할 것** | ① 입금확인 처리 직전 목록 ② 처리 직후 주문상태가 결제완료로 바뀐 화면 ③ SELECT 3건의 출력 그대로 ④ 처리 시각 |
| **안 되면** | §4 「끊긴 지점부터의 우회」로 간다. **여기서 멈추는 것 자체가 관측 결과다** |

읽을 SQL 3건 (SELECT 만, `<주문번호>` 는 단계 6에서 받은 값):

```sql
-- ① 웹훅이 후니에 도착했는가 (샵바이가 웹훅 URL 을 알고 있어야 행이 생긴다)
SELECT hook_id, evt_typ, shop_ord_no, shop_ord_sts, hook_sts, reg_dt
  FROM t_ord_webhooks
 WHERE shop_ord_no = '<주문번호>'
 ORDER BY reg_dt;

-- ② 주문 등록이 들어왔는가 (자사몰이 order/register 를 불러야 행이 생긴다)
SELECT ord_id, shop_ord_no, shop_line_no, prd_cd, qty, tot_amt, ord_sts, reg_dt
  FROM t_ord_orders
 WHERE shop_ord_no = '<주문번호>';

-- ③ 항목 보관소에 담긴 이력이 있는가 (단계 5 의 흔적)
SELECT item_id, prd_cd, summ_txt, tot_amt, qty, shop_cart_no, orig_dt, exp_dt
  FROM t_wgt_cart_items
 ORDER BY orig_dt DESC
 LIMIT 10;
```

| 결과 | 읽는 법 |
|---|---|
| ① 0행 | 샵바이에 **웹훅 URL 이 등록되지 않았다**(A-3 미확인). 등록 화면을 찾는 것이 먼저다 |
| ① ≥1행 · `hook_sts=RECEIVED` 로만 남음 | 정상이다. 수신함은 받아서 쌓기만 하고 **소비자가 없다**(`webhook-catalog.md` :235) |
| ② 0행 | **예상된 결과.** `order/register` 호출이 코드에 없다(F-1). 결제는 됐는데 무엇을 만들지 후니가 모르는 상태 |
| ③ 0행 | 자사몰이 후니 항목 보관소를 쓰지 않고 있다는 뜻이다. 단계 5의 `huni_item` 값과 대조한다 |

### 단계 9 — 원고 승격

| 칸 | 내용 |
|---|---|
| **하는 일** | 단계 8 ② 가 1행 이상일 때만 의미가 있다. 원고가 임시 버킷에서 주문 버킷으로 옮겨졌는지 읽는다 |
| **보는 곳** | 라이브 DB |
| **기대값** | `t_ord_artworks` 에 파일 수만큼 행이 생기고 `art_sts='PROMOTED'` · `ord_key` 가 채워진다. `decl_size`(신고값)와 `file_size`(실측값)가 같다 |
| **캡처할 것** | SELECT 출력 그대로 |
| **안 되면** | 단계 8 ②가 0행이면 여기도 당연히 0행이다 — **이건 미구현이 아니라 앞이 안 왔기 때문**이다. 둘을 섞어 적지 않는다. `art_sts='FAILED'` 면 `fail_rsn` 을 그대로 옮겨 적는다 |

```sql
SELECT a.art_id, a.item_cd, a.orig_file_nm, a.decl_size, a.file_size,
       a.art_sts, a.fail_rsn, a.promo_dt
  FROM t_ord_artworks a
  JOIN t_ord_orders o ON o.ord_id = a.ord_id
 WHERE o.shop_ord_no = '<주문번호>';
```

### 단계 10 — 생산지시 (수동)

| 칸 | 내용 |
|---|---|
| **하는 일** | 담당자가 원고를 확인하고 조판한 뒤 작업의뢰서를 출력해 현장에 넘긴다. **MES 연동은 미구현이므로 전부 손으로 한다**(`L0/M3/mes-handoff.md` §0) |
| **보는 곳** | webadmin 주문 화면 · 출력된 의뢰서 종이 |
| **기대값** | 의뢰서가 출력되고, 현장이 그 종이만 보고 작업을 시작할 수 있다(자재·공정·작업치수가 다 적혀 있다) |
| **캡처할 것** | ① 출력된 의뢰서 1장(사진 가능) ② 의뢰서에서 **빠져 있어 손으로 채운 항목** 목록 |
| **안 되면** | 의뢰서에 없는 정보를 담당자가 따로 물어봐야 했다면 그 항목을 그대로 적는다 — 그게 MES 인계 명세의 입력이 된다 |

### 단계 12 — 포장·출고

| 칸 | 내용 |
|---|---|
| **하는 일** | 1차포장 후 제작번호 바코드를 찍고, 박스포장 후 송장을 출력하고 주문번호 바코드를 찍는다 |

| **기대값** | 제작번호 바코드로 포장완료가 되고, 그 주문의 모든 상품이 포장완료면 자동으로 제작완료가 된다. 주문번호 바코드로 출고완료가 된다 |
| **캡처할 것** | ① 포장완료 화면 ② 출고완료 화면 ③ 출력된 송장 1장(주소는 가린다) |
| **안 되면** | 바코드가 안 읽히면 셋트 상품의 제작번호 채번 문제일 수 있다. 읽히지 않은 값을 적는다 |

### 단계 13 — 배송·주문조회 ★A-4·A-6 관측 지점

| 칸 | 내용 |
|---|---|
| **하는 일** | 후니가 샵바이에 상태와 송장번호를 올린다 → 고객(시크릿 창) 주문조회를 연다 → 셀러어드민에서 거래명세서와 통계를 본다 |
| **보는 곳** | 셀러어드민 주문 상세 · 고객 주문조회 화면 · 거래명세서 출력 창 · 통계 > 매출/상품별 |
| **기대값** | 샵바이 주문상태가 배송중으로 바뀌고 송장번호가 붙는다. 고객 주문조회에서 배송조회가 열린다 |
| **★ 같이 볼 것 (A-4)** | 거래명세서 출력 창에 **수량이 어떻게 찍히는가**. 「10원 × 1,500개」로 나오면 그대로 캡처한다. **단, 실측상 `viewShopSpecification=false` 라 고객에게는 노출되지 않는다**(`api-check-a13-a5.md`) — 운영자 화면에서만 확인된다 |
| **★ 같이 볼 것 (A-6)** | 통계 > 매출·상품별에서 그 주문이 **몇 개 팔린 것으로 집계되는가**. 1건이 1,500개로 잡히면 그 화면을 캡처한다 |
| **캡처할 것** | ① 송장 붙은 주문 상세 ② 고객 주문조회 화면 ③ 거래명세서 출력 창 ④ 통계 화면 2장(매출·상품별) |
| **안 되면** | 후니가 상태를 못 올리면 그건 단계 8 ②가 0행이기 때문이다 — 이 경우 **실무진이 셀러어드민에서 손으로 배송중까지 올려** 단계 13의 나머지(거래명세서·통계·주문조회)를 관측한다. 손으로 올렸다는 사실을 반드시 기록에 남긴다 |

## 3. 이 관통이 닫는 미확인 — 어느 단계에서 닫히는가

| 미확인 | 내용 | 닫히는 단계 | 판정 |
|---|---|---|---|
| **E-1** | 현금영수증·세금계산서의 실제 수량 표기 형식 | 단계 8 이후 발행 시도 | **부분 — 현 설정으로는 못 닫는다.** 실측 `cashReceipt=false` · `usePaymentReceipt=false`(`api-check-a13-a5.md`) → 발행 기능이 꺼져 있다. 설정을 켜는 것은 별도 승인 사안 |
| **E-2** | 결제승인 후 거동 전반(`PAY_DONE` 이후 상태·`nextActions`·클레임 플래그) | 단계 8 ⓑ ~ 단계 13 | **닫힌다** — 무통장 입금확인이 곧 `PAY_DONE` 이다 |
| **E-3** | 「입금대기부터 재고 차감」의 실제 소모량 | **단계 6** (주문 전·후 재고 2회 측정) | **닫힌다** — 입금 없이도 관측된다 |
| **E-4** | `POST /cart/items` 응답 `summary` 생성 규칙 · 라벨 붕괴 전파 | **단계 5**(응답) + **단계 7**(셀러어드민 전파) | **닫힌다** — 셋트 상품을 골랐을 때만 |
| **E-5** | 비회원 주문에도 shopby 자동 알림이 나가는가 | **단계 6** | **닫힌다** — 비회원 구매 가능 전건 실측 확인됨 |
| **E-6** | 게스트 경로 전체의 라이브 검증 | 단계 1~6 전체를 시크릿 창으로 | **부분** — NCPPay 게스트 **결제**는 PG 수단이라 무통장으로 대체되지 않는다 |
| **A-1** | 주문 상세에서 `huni_order` 텍스트 옵션의 렌더 형태 | **단계 7** | **닫힌다** |
| **A-4** | 거래명세서 출력 화면의 수량 표기 | **단계 13** | **닫힌다**(운영자 화면 한정 — 고객 노출은 꺼져 있음) |
| **A-6** | 판매 통계의 수량 기준 지표 | **단계 13** | **닫힌다** |

> **덤으로 닫히는 것**: A-3(웹훅 URL 등록 실재)은 단계 8 ①의 0행/≥1행으로 **간접 판정**된다.
> 행이 생기면 등록돼 있다는 뜻이다. 0행이면 등록 여부는 여전히 미확인이다(등록됐는데 못 온 경우와 구분 불가).

## 4. 끊긴 지점부터의 우회 — 어디서 멈춰도 나머지를 건진다

관통이 통째로 실패하는 것을 막기 위해, **끊긴 지점마다 뒤를 이어 보는 법**을 미리 정해 둔다.

| 어디서 멈췄나 | 그래도 건질 것 | 어떻게 |
|---|---|---|
| 단계 6 — 무통장 수단이 안 보임 | 없음 | 즉시 중단·지니 보고. 샵바이 개방이 선행 조건이다 |
| 단계 8 ① — 웹훅 0행 | 단계 8 ⓑ 까지의 상태 전이(E-2 절반) | 셀러어드민 화면만으로 상태·`nextActions` 를 관측하고, 웹훅 등록 화면 탐색을 A-3 로 넘긴다 |
| 단계 8 ② — 주문등록 0행 (**가장 유력**) | 단계 10~13 전부 | 생산은 **손으로** 접수한다. 셀러어드민에서 실무진이 상태를 배송중까지 올려 단계 13의 A-4·A-6·주문조회를 관측한다. **손으로 올린 사실을 기록에 남긴다** |
| 단계 9 — 승격 0행/FAILED | 단계 10~13 | 원고 파일을 임시 버킷 키로 직접 내려받아 현장에 넘긴다(임시 30일 이내) |
| 단계 10 — 의뢰서에 정보 부족 | 단계 11~13 | 빠진 항목을 손으로 채우고, 그 목록을 그대로 남긴다 |

> **원칙**: 손으로 우회한 단계는 「통과」가 아니라 **「우회」** 로 적는다.
> 우회한 단계는 여전히 **㉡ 우리가 아직 안 만든 것**으로 남는다.

## 6. 이 문서가 하지 않은 것 [HARD 기록]

- **주문 0건 · 입금확인 0건 · 설정 변경 0건 · 폼 제출 0건.** 이 레인은 절차만 썼다.
- **셀러어드민 접속 0회.** 화면 이름·경로는 매뉴얼 근거(`selleradmin-ops.md`·`order/*.mdx`)에서 왔다.
- 단계 8 ②가 0행일 것이라는 예상은 **코드 grep 근거**(F-1)이지 관측이 아니다. 실행이 이를 뒤집으면 그쪽이 맞다.
