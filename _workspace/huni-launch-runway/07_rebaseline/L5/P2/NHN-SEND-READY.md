## [답변 1] 저희 「견적엔진」이 무엇인가

**한 줄로 말씀드리면 — 사내 인쇄 가격표를 데이터베이스에 담아 두고, 고객이 고른 옵션 조합에 해당하는 금액을 찾아 계산해 주는 저희 자체 서버 프로그램입니다.**

### 무엇을 받고 무엇을 내보내나

| 구분 | 내용 |
|---|---|
| 받는 것(입력) | 상품 1종 + 옵션 조합 — **사이즈/판형 · 용지(자재) · 인쇄 도수 · 후가공 · 페이지/묶음수 · 수량** |
| 내보내는 것(출력) | **총 청구액 1개(원)** |
| 계산 방식 | 규칙 기반 계산. **같은 입력 → 항상 같은 출력**(무작위·시세·시간 요소 없음) |
| 값의 출처 | 후니 사내 **권위 가격표(엑셀 2종: 상품마스터 · 인쇄상품 가격표)** 를 그대로 데이터베이스에 적재한 값 |

### 왜 이런 것이 필요한가 — 인쇄물의 특성

인쇄 주문제작은 **똑같은 「명함」이라도 용지·도수·후가공·수량 조합에 따라 원가가 전혀 다릅니다.**
그래서 인쇄업계는 상품마다 하나의 판매가를 붙이지 않고, **조합별 단가표**를 씁니다. 저희 견적엔진은 그 단가표를 프로그램으로 옮긴 것입니다.

### 값이 바뀌는 때는 언제인가

**사내 가격표를 개정할 때뿐입니다.** 개정은 저희가 사람 손으로 하고, 개정 전후로 같은 조합의 값이 달라집니다.
**고객의 구매 행위 자체는 값을 바꾸지 않습니다.**

## [답변 2] 「구매 시점 가격 변동」의 기준과 실제 조합 수치

### 기준 — 시점 기준의 변동은 없습니다

| 질문 | 후니 답 |
|---|---|
| 시간에 따라 변하나요 | **아니오.** 시간·재고·시세에 연동되는 요소가 없습니다 |
| 고객마다 다르나요 | **아니오.** 회원 등급별 차등가는 쓰지 않습니다 |
| 그럼 무엇이 금액을 바꾸나요 | **고객이 고른 옵션 조합과 수량, 그 둘뿐입니다** |
| 수량은 어떻게 반영되나요 | 수량 구간별 할인율이 가격표에 이미 적혀 있고, 그 표대로 적용합니다 |

### 실제 조합 수치 — 저희 상품 하나를 예로 듭니다

**상품: 아크릴키링 · 기본 사이즈 · 수량 1,000개**

| 항목 | 값 |
|---|---|
| 최종 청구액 | **2,550,000원** |
| 계산식 | (인쇄·가공비 × 수량구간 할인율) + 후가공비 |
| 값의 근거 | 후니 권위 가격표 「계산공식집초안」 |
| 재현성 | 같은 조합을 몇 번 계산해도 **2,550,000원** |

같은 방식으로 상품·옵션·수량 조합마다 값이 가격표에 정해져 있으며, 요청하시면 다른 조합의 예시도 드리겠습니다.

보시는 대로 **조합마다 값이 미리 정해져 있습니다.** 구매 시점에 저희가 값을 지어내는 것이 아닙니다.

### 그렇다면 왜 「옵션 사전 전수등록」이 어려운가

이 부분이 저희가 가장 도움을 구하고 싶은 지점입니다.

**수량이 연속된 값이기 때문입니다.** 고객은 1개부터 수만 개까지 아무 수량이나 넣을 수 있고, 수량마다 금액이 다릅니다.
사이즈·용지·도수·후가공까지 곱하면 **한 상품의 조합 수가 실용적으로 열거 불가능한 규모**가 됩니다.

  <sub>왜 묻는가 — 취소·교환·반품·환불 네 개 매뉴얼이 모두 상세한 내용을 이 문서로 넘기는데, 저희에게는 그 문서가 없습니다.</sub>

## 4부. API 규격서 표기 확인 (1건 · 세부 5가지) ★v2 신설

**13. 저희가 규격서를 읽으며 발견한 아래 5가지가 표기 오류인지, 아니면 저희가 잘못 읽은 것인지 확인 부탁드립니다.**

저희는 아래를 **저희 쪽 판단대로 고쳐서** 개발을 진행하고 있습니다. 저희 판단이 틀렸다면 알려 주세요.

| # | 어디 | 저희가 본 것 | 저희가 맞다고 판단한 것 | 그렇게 판단한 근거 |
|---|---|---|---|---|
| 13-1 | 상품 옵션 수정 | 경로에 상품번호가 붙는 형태(`/products/{productNo}/options`)로 적힌 자료가 있습니다. 그리고 요청 항목에 `saleType`, 필수 `optionNo` 가 적혀 있습니다 | 경로는 **`PUT /products/options`**(상품번호 없음). 요청 항목에 `saleType` 과 필수 `optionNo` 는 **없습니다** | 상품 서버 규격서의 `products-options-915318368` 스키마에 그 두 항목이 아예 없습니다 |
| 13-2 | 장바구니 응답의 `groupId` | 숫자(number)로 적힌 곳이 있습니다 | **문자열(string) · 값이 없을 수 있음(nullable)** | 주문 서버 규격서 `cart-1115878954` 스키마 |
| 13-3 | 장바구니 응답의 `optionInputs` | `inputLabel`·`inputValue` 가 **필수**로 적힌 곳이 있습니다 | **필수가 아님 · 값이 없을 수 있음**. `inputNo` 도 값이 없을 수 있음 | 같은 스키마 |
| 13-4 | 교환 신청 API 의 식별자(operationId) | 취소·반품과 같은 형태로 적힌 곳이 있습니다 | 교환만 **`post-profile-order-options-no-claims-exchange`** (취소·반품은 `...-claims-cancel` / `...-claims-return`) | 클레임 규격서 실제 경로 |
| 13-5 | 카테고리 조회 API 의 식별자 | `get-categories` | **`get-categories-by-keyword`** | 전시 규격서 |

  <sub>왜 묻는가 — 저희 개발 문서를 규격서에 맞춰 고쳐 둔 상태입니다. 규격서 쪽이 맞다면 저희 구현을 되돌려야 하므로, 어느 쪽이 정본인지 확인이 필요합니다. **급하지는 않습니다.**</sub>

  <sub>참고로 하나 더 — 토큰 갱신(`PUT /oauth2` refresh)은 규격서(yml)에서 찾지 못했고 개발 가이드 문서에만 있었습니다. 규격서에 없는 것이 맞나요?</sub>

## 5부. 주문서 요청 규격의 실제 계약 (1건) ★v2 신설

**14. 주문서 생성(`POST /order-sheets`) 요청 규격에 대해 세 가지 확인 부탁드립니다.**

**14-1.** 규격서에는 `products` 항목이 **필수(required)** 로 적혀 있습니다. 그런데 저희가 **장바구니 번호(cartNos)만** 넣어 호출했더니 **정상(200)으로 응답**했습니다.
→ **어느 쪽이 실제 계약인가요?** `products` 없이 `cartNos` 만으로 호출하는 것이 정식으로 지원되는 방식인가요, 아니면 지금은 통하지만 나중에 막힐 수 있는 방식인가요?

**14-2.** `products` 와 `cartNos` 를 **둘 다** 넣으면 어느 쪽이 우선하나요? 합쳐지나요, 한쪽이 무시되나요, 오류인가요?

**14-3.** `recurringPaymentDelivery`(정기결제 배송) 항목의 **구조와 각 값의 의미**를 알려 주세요. 규격서 설명만으로는 어떤 형태로 넣어야 하는지 판단하지 못했습니다. 저희는 현재 정기결제를 쓰지 않지만, 필수 항목인지 여부는 알아야 합니다.

  <sub>왜 묻는가 — 저희 주문 생성 경로 전체가 이 API 하나를 지납니다. 지금 통하는 방식이 「정식 지원」인지 「우연히 통하는 것」인지 모른 채로 오픈하면, 어느 날 조용히 주문이 안 되는 상태가 될 수 있습니다.</sub>

### (부수) 정산 안내 문서의 계산식 표기 하나 확인 부탁드립니다

**정산 안내 문서 두 곳의 계산식 표기가 서로 다릅니다.**

- 매출 내역 조회 문서 ⑨번 항목: `(F = A = B + C − D − E)`
- 정산 현황 조회 문서 ⑩번 항목: `F = A − B + C − D − E`

바로 아래 붙은 설명 글(「판매액 빼기 판매수수료 더하기 배송비 …」)과 맞는 것은 **뒤쪽**입니다. 저희는 뒤쪽을 정본으로 보고 진행하고 있는데, 맞는지 확인해 주시고 문서를 고쳐 주시면 감사하겠습니다.
<sub>이 항목은 급하지 않습니다. 위 14건에 대한 답을 우선 부탁드립니다.</sub>
