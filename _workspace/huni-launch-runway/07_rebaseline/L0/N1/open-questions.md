# N1 미확인 통합 — shopby 플랫폼 전체 플로우

> 6개 산출물의 미확인을 **「무엇을 하면 닫히는가」** 로 다시 묶었다.
> 원본 항목번호(U-n)는 각 산출물 안에 그대로 있고, 여기서는 실행 단위로 다시 센다.
> 작성 2026-09-02 · 카드 `CARDS-N.md` §N1

## 왜 이렇게 묶었나

산출물별로 나열하면 「셀러어드민을 봐야 닫히는 것」이 6개 문서에 흩어진다.
한 번 접속해서 한 번에 볼 수 있는 것을 여섯 번 나눠 보게 만드는 정리는 실행이 안 된다.
그래서 **닫는 수단** 기준으로 묶었다. 묶음 하나가 곧 한 번의 작업이다.

## 우선순위 요약

| 묶음 | 닫는 수단 | 건수 | 이게 안 닫히면 |
|---|---|---|---|

| **B** | 샵바이(NHN커머스) 문의 | 12 | 웹훅 사슬·정산 정책이 통째로 공백 |

## A. 셀러어드민 실화면 1회 접속으로 닫히는 것 (14건)

**★ 선행 차단**: 셀러어드민 **접속 주소·자격증명이 이 저장소에 없다.**
`docs/huni/shopby-onboarding/` 전수 확인 결과 PG 설정 캡처만 있고 셀러어드민 URL·계정은 0건이다.
카드의 「라이브 읽기전용」 지시에 따라 로그인을 시도하지 않았다. **자격증명 확보가 A 전체의 선행조건이다.**

접속이 되면 아래를 **한 번에** 확인한다(순서대로 보면 화면 이동이 최소가 된다).

| # | 무엇을 볼 것인가 | 어느 화면 | 출처 |
|---|---|---|---|
| A-1 ★ | **주문 상세 1건** — 후니 주문이 실제로 어떻게 보이는가. `huni_order` 텍스트 옵션의 렌더 형태(줄바꿈·잘림) | 주문관리 > 전체주문 조회 > 상세 | selleradmin U-1·U-3 |
| A-2 ★ | **부분취소 창을 열어서**(실행하지 않음) 단위가 수량인가 항목 전량인가 | 주문 상세 > 부분취소 | selleradmin U-6 · state 7번 |
| A-3 ★ | **웹훅 URL 등록 화면의 실재와 위치** — 앱(App) 등록 수정페이지로 추정, 문서 근거 0 | 미상(앱 관리 추정) | webhook 1·2 |
| A-4 | **거래명세서 출력 화면**에 수량이 어떻게 찍히는가 | 주문관리 > 거래명세서 | headless U-4 |
| A-5 | **`viewShopSpecification` 현재 설정값** — 켜져 있으면 거래명세서가 고객에게 도달 | 몰 설정 | headless U-5 |
| A-6 | **판매 통계**가 수량 기준 지표를 어떻게 보여주는가 | 통계 > 매출/상품별 | headless U-6 · selleradmin U-7 |
| A-7 | **자동 알림 세부 트리거 전수** — 매뉴얼은 카테고리까지만 열거 | 자동 SMS·자동 메일·알림톡 템플릿 설정 | headless U-7 |
| A-8 | **알림톡·SMS 이중 발송 항목** — 둘 다 켜면 템플릿이 두 벌 | 위와 동일 | headless U-8 |
| A-9 | **주문처리기간 설정값** — 자동배송완료·자동구매확정(1~30영업일). 후니는 서버가 상태를 올리므로 자동 전이와 충돌 여부 문제 | 서비스관리 > 쇼핑몰 관리 | selleradmin U-4 |
| A-10 | **운영자 계정·권한그룹 구성** — 개인정보 목록조회를 누가 갖는가 | 서비스관리 > 운영자 관리 | selleradmin U-9 |
| A-11 | **옵션 스캐닝 출고 사용 가능 여부** — 후니 상품은 옵션관리코드가 비어 옵션바코드가 없다 | 배송준비중 > 스캐닝 | selleradmin U-8 |
| A-12 | **샵바이 결제수단 설정 실화면** — 이니시스 지불수단과의 교집합 | 결제수단 설정 | payment U-8 |
| A-13 | **상품 226개의 「비회원 구매 불가」 설정값** | 상품 목록 또는 조회 API | headless U-12 |
| A-14 | **금지 설정 4종이 실제로 꺼져 있는가** — 수량비례/중량 배송비·최대구매수량·즉시할인. 가이드의 주장이지 관측이 아니다 | 배송/상품 설정 | headless C-3 |

> 실주문이 없어도 **수기주문 1건이면 화면 구조는 확인된다.** 다만 주문 생성은 이 카드의 범위 밖이고, 읽기전용 지시에도 걸린다 — 별도 승인 사안이다.

## B. 샵바이(NHN커머스) 문의로만 닫히는 것 (12건)

문서·스펙·매뉴얼 어디에도 없어서 **읽어서는 닫히지 않는다.** 사람에게 물어야 한다.

### B-1. 웹훅 — 통째로 공백 (7건)

★ 이 묶음이 가장 크고, 가장 위험하다. 웹훅은 결제승인 이후 사슬의 유일한 신호원인데 **정책이 하나도 문서화돼 있지 않다.**

| # | 미확인 |
|---|---|
| B-1a | **재시도 횟수·백오프·타임아웃** — 서술 0건 |
| B-1b | **성공 판정 기준** — HTTP 2xx인가, 본문 형식을 보는가 |
| B-1c | **데드레터 이후 동작** — 재발송 트리거가 있는가 (**재발송 API 는 없다**) |
| B-1d | **서명·검증 수단** — 헤더 이름·알고리즘·시크릿 전부 미정의 |
| B-1e | **인바운드 URL 제약** — HTTPS 강제? 샵바이 발신 IP 고정? 포트 제약? |
| B-1f | **순서 보장 / 중복 발송** — at-least-once인가, 순서가 보장되는가 |
| B-1g | **payload 스키마 33종 전부** — 스펙이 본문을 `data: string` 으로만 정의. 특히 `CHANGE_ORDER_STATUS` 의 상태값 목록 |

**부수 위험**: 조회는 7일 이내 기간만 가능하고 재발송 API 가 없다.
→ 유실 복구는 `GET /webhooks/failed` 폴링뿐이고, **폴링 주기가 7일을 넘으면 그 사이 유실분은 영구히 못 건진다.**

**카탈로그 구멍**: 33종에 **결제완료 전용 이벤트도, 취소·반품 전용 이벤트도 없다.**
`CHANGE_ORDER_STATUS` 의 상태값으로 판별해야 하는데 그 상태값 목록이 B-1g로 미확인이다 — **잠재 블로커**.

### B-2. 정산 (4건)

| # | 미확인 |
|---|---|
| B-2a ★ | **쇼핑몰 정산데이터(후니 자신의 정산)의 주기·항목·수식** — 저장소에서 확인된 정산 문서는 **전부 파트너사 정산**이다. 우리 정산 문서가 없다 |
| B-2b | **정산 집계 이후 발생한 반품·환불이 어느 달에 어떤 부호로 반영되는가** — 두 정산 문서 어디에도 서술 없음 |
| B-2c | **PG 수수료의 위치** — 정산 수식 `F = A−B+C−D−E` 어디에도 PG 수수료 항이 없다 |
| B-2d | **shopby 플랫폼 수수료** — NHN커머스가 쇼핑몰에서 받는 몫을 다루는 문서 없음 |

### B-3. 기타 (1건)

| # | 미확인 |
|---|---|
| B-3a | **외부 「클레임/정산 정책」 문서 전체** — `shopby-help.nhn-commerce.com/support/order/claim/claim-policy`. 네 클레임 문서가 모두 여기로 상세를 넘기는데 저장소에 없다 |

## C. PG 실계정 캡처 1장으로 닫히는 것 (3건) ★런칭 일정 전체

| # | 미확인 | 닫는 방법 |
|---|---|---|
| **C-1** ★★ | **후니가 PG 파이프라인 어느 단계에 있는가** (신청 전 / 심사 중 / 승인 후 연동 미완) | 이니시스 가맹점관리자 `변경/추가 → 8. 서비스 신청현황` **실계정 캡처 1장**. 행 없음=신청 전 / 접수·처리대기=심사 중 / 처리완료=승인 |
| C-2 | 이니시스 「네이버페이」가 샵바이 **주문형/결제형** 중 무엇을 여는가 | 이니시스 상담 또는 샵바이 네이버페이 연동 문서 |
| C-3 | 후니에게 상점ID 추가 **비용이 붙는지** | 이니시스 사후 통보 대기 (납부 확인돼야 발급) |

### ⚠️ C-1 에 대한 정직한 기록

카드는 「PG 결제승인 심사 중」을 전제로 준다. **그 전제를 저장소 증거로 뒷받침하지 못했다.**

- 보유 스크린샷 9장이 **전부 매뉴얼·공개 화면**이고 후니 실계정 화면이 0장이다.
- 개통 도크(2026-09-01)는 「계정 확보 — 누가 로그인 정보를 갖고 있나」 단계이고 **「고도몰 PG ID 미확정」** 이라 신청서 작성조차 불가로 읽힌다.
- 원장 `X-PG-CONTRACT-01` 은 「계약 미체결·미착수·라이브몰 결제수단 ACCOUNT/NONE만」.

**이 어긋남의 해석은 추론이므로 미확인으로 남긴다** — 원장의 「계약 미체결」은 신규 사이트용 PG 계약, 도크의 「이미 기존 가맹점」은 법인 단위 계약을 가리키는 것으로 보이나 확증이 없다.

**단, 지니의 「현재 결제승인을 받고 있다」는 진술은 문서에 없는 1차 지식일 수 있다.**
문서가 그것을 부정하는 것이 아니라, **문서만으로는 확인되지 않는다**는 것이 이 항목의 내용이다.

## D. PM 결정 대기 (5건)

읽어서도, 물어서도 닫히지 않는다. **결정해야 닫힌다.**

| # | 결정할 것 | 늦으면 |
|---|---|---|
| **D-1** ★ | **어떤 결제수단을 열 것인가** — 결정 기록 자체가 없다 | 원천사 심사가 **네이버페이 3~4주 · 카카오페이 최초 2주 · PAYCO·L.pay 10~12영업일**. 10/6 역산이면 여기가 먼저 걸린다 |
| **D-2** ★ | **현금영수증·세금계산서 수량 표기 대응책** | **대응책 자체가 존재하지 않는다.** 계약에서 해법이 진술된 적 없는 유일한 항목 |
| D-3 | **알림 템플릿 수량 치환 제거 여부·시점** | 가이드 스스로 ★미확정으로 남김. PM ↔ NHN |
| D-4 | **배송비 정책** — 운영정책 260827 의 수량 기반 배송비를 어떻게 할 것인가 | 수량이 금액이므로 수량 기반 배송비는 성립하지 않는다 |
| D-5 | **에스크로를 쓸 것인가** | 쓰면 MID 추가 시 자동 승계되고, **배송중 진입 시 모든 상태 수동변경이 전면 봉인**된다 — 상태 머신에 직접 영향 |
| D-6 | **게스트에 `item_id` 방식을 도입할 때의 소유권 검증 설계** | 설계 미정. 게스트는 서버 장바구니가 없어 **검증원 자체가 없다** |

## E. 실주문 1건으로만 닫히는 것 (6건) — PG 승인 이후에만 가능

**승인 전에는 원천적으로 못 닫는다.** 실물이 아직 존재하지 않기 때문이다.

| # | 미확인 |
|---|---|
| E-1 | **현금영수증·세금계산서의 실제 수량 표기 형식** — 가이드는 "품목·수량 표기"라는 사실만 적고 형식을 적지 않음 |
| E-2 | **결제승인 후 거동 전반** — `PAY_DONE` 이후 상태·`nextActions`·클레임 플래그의 실제 값 전부 미관측 |
| E-3 | **「입금대기부터 재고 차감」의 실제 소모량** — 후니 금액-수량 방식과 결합했을 때 |
| E-4 | **`POST /cart/items` 응답 문자열 `summary` 생성 규칙** — 라벨 붕괴가 셀러어드민까지 전파되는지를 가르는 **유일한 관문**. (서버키가 있으면 승인 전에도 1회 호출로 닫힌다) |
| E-5 | **비회원 주문에도 shopby 자동 알림이 나가는가** |
| E-6 | **게스트 경로 전체의 라이브 검증** — NCPPay 게스트 결제·로컬 장바구니. 커밋 작성자 본인이 미검증 명시 |

> E-4 는 엄밀히는 실주문이 필요 없다 — 셋트 상품 토큰으로 `POST /api/w/v1/cart/items` 를 **1회 호출**하면 닫힌다(서버키 필요). **승인 전에 닫을 수 있는 유일한 E 항목**이므로 우선순위가 높다.

## G. 문서 간 충돌 — 해석 확정이 필요한 것 (4건)

추가 조사가 아니라 **어느 쪽을 따를지 정하는** 문제다. 정하지 않으면 시나리오 기대값이 둘로 갈린다.

| # | 충돌 | 갈리는 지점 |
|---|---|---|
| **G-1** ★ | **교환 신청 가능 상태** — `claim-order/exchange/condition.mdx` 1행은 "결제 완료 이후 **모든** 상태", `order/buy-confirm.mdx` ③은 구매확정에서 "주문자가 **직접 교환·반품 신청 불가**" | 구매확정에서 (ㄱ)완전 불가 (ㄴ)운영자 대행만 가능 |
| **G-2** ★ | **부분취소(옵션 단위)의 허용 상태 범위** — API 는 단일/복수 옵션취소를 제공하나 어느 `orderStatusType` 에서 되는지 스펙·매뉴얼 어디에도 없다 | 매트릭스는 주문취소와 같은 경계로 **가정**했고 미검증. **수량이 곧 금액이라 환불액에 직결** |
| G-3 | **배송보류의 API 표현** — 어드민 라벨 `상품준비중_배송보류` 와 API `holdDelivery`(bool) 의 정확한 대응, 배송보류 중 `orderStatusType` 이 원래 값을 유지하는지 | 스키마에서 추론한 구조이며 라이브 확인 전 |
| G-4 | **정산 수식 표기** — `settlement.mdx §⑨` 의 `(F=A=B+C-D-E)` 는 표기 오류. `settlement-list.mdx §⑩` 의 `F = A−B+C−D−E` 가 정본 | 이미 정본을 채택했으나, 샵바이 문서 자체의 오류이므로 문의 시 함께 확인 |

### G-5 (충돌은 아니나 같은 성격) — 스펙에만 있고 설명이 없는 상태 4건

`EXCHANGE_WAIT`(교환대기) · `REFUND_DONE`(주문상태 축) · `PAY_WAIT`(결제대기) 의 수명·전이 조건 · `EXCHANGE_PROC_WAITING_PAY`/`EXCHANGE_PROC_WAITING_REFUND` 의 발생 조건. 전부 enum 에만 존재하고 매뉴얼에 설명이 없다.

## 부록 · 이 카드가 관측하지 않은 것 [HARD 기록]

- **라이브 브라우저·셀러어드민 접근 0회.** 자격증명이 없어 로그인을 시도하지 않았다.
- **주문·결제·클레임·알림 발송·폼 제출 0건.**
- 6개 산출물 전체가 **문서·스펙·기존 산출물 대조**이며, 라이브 실화면 근거는 M1 이 남긴 위젯 캡처 1장뿐이다.
- **PG 결제승인이 도달한 실주문이 없다** → 승인 이후 거동은 전부 **㉢ 미관측**이다.
  이는 **미실행이지 미구현이 아니다.** 6개 문서 어디에서도 「0행/미관측」을 「미구현」으로 읽지 않았다.
