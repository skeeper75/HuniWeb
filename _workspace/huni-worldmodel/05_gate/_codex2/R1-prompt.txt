## 과제

아래 두 규칙 **각각에 대해**, 루브릭이 그 규칙에 대해 적힌 `violation_test` 를 **문언 그대로** 적용해 위반/비위반을 판정하라.

- RULE-02 (뉴로→심볼릭 인터페이스의 타입화)
- RULE-12 (단일 정의·단일 편집표면)

[HARD] 규칙 매핑 규율: 어떤 규칙의 위반을 주장하려면 **그 규칙의 violation_test 에 적힌 항(①②③ / (a)(b)(c) 등)을 정확히 지목**하고 그 항의 문언 기준으로만 판정하라. 다른 기준(일반적 소프트웨어 공학 상식, 다른 규칙의 기준, "부족해 보인다"는 인상)으로 판정하는 것은 무효다. violation_test 가 묻지 않는 것을 재면 그것은 오판이다.

### 조사할 구체 지점 (판정을 위한 안내이지, 결함이 있다는 전제가 아니다)

1. 설계 문서가 뉴로 계층에서 심볼릭 계층으로 넘기는 산출물(의도 객체 또는 동등물)의 **필드 스키마**를 선언하는가. 선언한다면 그 선언이 RULE-02 violation_test 가 요구하는 3항(① 필드 목록 + 각 필드의 도메인 출처가 어느 `t_*` 축인가, ② 미확정(unknown) 표현 방법, ③ 이 스키마를 검증하는 지점의 위치)을 각각 어디에서 충족/미충족하는가. 특히 ①의 "각 필드의 도메인 출처"가 **모든 필드에 대해** 닫히는지, 아니면 일부 필드가 출처 미선언으로 남는지를 필드 단위로 확인하라.
2. 설계가 값 도메인 출처로 지목한 것들이 **실제 조회 가능한 권위**인지. 예컨대 어떤 축의 값 도메인을 특정 테이블/컬럼의 조회로 지정했다면, 그 조회 대상이 설계 문서 안에서 식별 가능하게 특정되어 있는가, 아니면 이름만 언급되고 어느 그릇에서 어떻게 얻는지가 비어 있는가.
3. 설계가 도입하는 각 개념(차원·규칙·효과·상태 등)에 대해 "정의가 사는 곳"이 **정확히 하나** 지정되어 있는가(RULE-12 violation_test ①). 두 곳 이상에 병렬 존재하거나 "코드와 DB 양쪽에 둔다"에 해당하는 것이 있는가. 특히 설계가 값 도메인·축 정의를 새로 기술하는 대목이 있다면, 그것이 **기존 권위를 참조·재배선**하는 것인지 아니면 **기존 정의와 병렬인 새 정의를 신설**하는 것인지 문언 근거로 판별하라. 후자면 RULE-12 ① 위반 방향이고, 나아가 기존 5벌 병렬을 6벌로 늘리는지도 확인하라.
4. 설계가 새 규칙 표현을 도입한다면 그 표현이 webadmin 폼빌더에서 역파싱 가능한지에 대한 판정이 문서에 있는가(RULE-12 violation_test ②).
5. 게이트/검사 절차의 분모(무엇을 몇 개 중 몇 개로 세는가)가 여러 곳에 선언될 때, 그 분모 정의가 서로 다른 곳에 병렬로 존재하는지, 아니면 하나의 정의와 그로부터의 사상(projection)으로 정리되어 있는지 확인하라 — RULE-12 ① 관점.

## 입증책임 규약 [HARD]

- **근거가 불충분할 때의 기본값은 '위반 성립'이 아니라 '각하'다.** 불확실을 결함으로 환산하지 마라. "~할 수도 있다", "~가 우려된다", "~는 검증되지 않았을 수 있다"는 판정 근거가 아니다.
- 위반을 주장하려면 다음 5요건을 **전부** 갖춰라. 하나라도 못 갖추면 그 지적을 제기하지 마라.
  (a) 위반 RULE-ID + **그 규칙 violation_test 의 정확한 항**을 지목
  (b) 재현 가능한 실패 시나리오 — 입력(상품·옵션·수량 등 구체값) / 기대 결과 / 실제(예상) 결과 3항
  (c) 근거 — `파일경로:라인`. 너의 일반 지식·경험은 근거가 아니다. 근거를 못 찾으면 `not found` 라고 명시하고 지적을 취하하라
  (d) 자기 반증조건 — "설계 문서 ○○에 △△가 명시되어 있다면 이 지적은 철회된다"
  (e) 교정 방향(MAJOR 이상 주장 시 필수) — 어느 규칙을 어떻게 만족시킬 것인가
- 자동 각하: 루브릭 §2.3 J-1~J-5 에 해당하는 지적은 제기하지 마라(이미 기각된 접근의 재제안 / 이미 잘 되고 있는 것을 결함으로 제기 / 다른 트랙 소유 작업의 미수행 지적 / `[추정]`·미확인 표기 사항을 확정 결함으로 제기 / 도메인 도구 없이 텍스트 패턴만으로 확정한 결함 주장).
- **위반이 없으면 없다고 답하는 것이 정상 결과다.** 억지로 찾지 마라. 규칙마다 반드시 결함이 하나씩 나와야 하는 것이 아니다.
- 위 두 규칙 밖의 규칙(RULE-01, RULE-03 등)은 이번 심사 범위가 아니다. 범위 밖 사항을 발견하면 별도 절에 "범위 밖 관찰"로만 적고 판정하지 마라.

## 출처 강제 [HARD]

모든 사실 주장에 `파일경로:라인` 을 달아라. 인용한 라인 번호는 네가 실제로 읽은 현재 판본의 좌표여야 한다. 좌표를 확인하지 못한 주장은 `not found` 로 표기하고 사실로 올리지 마라. 문서에서 근거를 찾을 수 없으면 "해당 기술이 문서에 없음(검색 방법: <어떤 문자열을 어느 파일에서 찾았는가>)" 형태로 적어라.

## 출력 형식 (이 형식을 정확히 따라라)

각 규칙에 대해 다음 블록을 하나씩 낸다.

```
[RULE-02]
판정: CLOSED  또는  STILL_OPEN
   (CLOSED = violation_test 를 적용했고 위반이 나오지 않았다)
   (STILL_OPEN = violation_test 의 특정 항을 위반한다)
적용한 violation_test 항: <①/②/③ 등 그대로 인용>
판정 근거:
   - <파일경로:라인> — <그 라인이 무엇을 말하는가>
   - <파일경로:라인> — ...
항별 충족표:
   ① ... : 충족 / 미충족  근거 <파일경로:라인 또는 not found>
   ② ... : 충족 / 미충족  근거 <...>
   ③ ... : 충족 / 미충족  근거 <...>
```

판정이 STILL_OPEN 이면 그 블록 바로 뒤에 5요건 블록을 붙인다.

```
[STILL_OPEN 5요건 — RULE-02]
(a) 위반 RULE-ID + violation_test 항: ...
    주장 등급: BLOCKER / MAJOR / MINOR
(b) 실패 시나리오:
    입력 = ...
    기대 = ...
    실제(예상) = ...
(c) 근거: <파일경로:라인> (복수 가능)
(d) 자기 반증조건: ...
(e) 교정 방향: ...
```

마지막에 다음 절을 둔다.

```
[범위 밖 관찰]
- (있으면) ... — 판정하지 않음
- 없으면 "없음"

[근거를 확인하지 못한 항목]
- (있으면) 무엇을 찾으려 했고 어디서 못 찾았는가
- 없으면 "없음"
```
