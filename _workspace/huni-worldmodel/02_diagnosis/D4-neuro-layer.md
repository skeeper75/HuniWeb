# D4 — 뉴로 계층 정밀 진단: webadmin 관리자 비서 에이전트

대상: `raw/webadmin/webadmin/catalog/` 의 `assistant.py`(827줄) · `assistant_tools.py`(1,116줄) · `assistant_manual.py`(279줄) · `assistant_issue.py`(362줄) — 전량 정독.
[HARD] raw/webadmin 은 읽기 전용으로만 취급했다. 어떤 파일도 수정하지 않았다.

---

## 요약

이 계층은 **"LLM + 화이트리스트 도구 + 주입된 지식 + 사후 텍스트 검수"** 로 구성된 **읽기 전용 Q&A 에이전트**다. 구조적으로 잘 만들어졌다 — 시스템 프롬프트는 손글 규칙(_ROLE_TEXT) + 도메인 가이드 + DB 스키마 자동 다이제스트 + 메뉴얼 원고 4블록으로 조립되고, 도구는 10종이 화이트리스트 디스패처를 통해서만 실행되며, `run_sql` 은 정규식 게이트 + 읽기전용 트랜잭션 + 무조건 롤백의 3중 방어를 갖는다. 유일한 쓰기 경로(`draft_issue`)는 초안 행 생성까지만 하고 실제 GitHub 등록은 담당자 클릭 뒤 별도 뷰에서만 일어난다(fail-closed 2단 분리).

그러나 **월드모델은 존재하지 않는다**. 행동의 결과를 미리 예측하는 장치, 여러 안을 내부에서 굴려보는 장치, 선택 이력을 누적해 계획을 세우는 장치가 **코드에 하나도 없다**. `_verify_*` 3종은 "행동 검증"이 아니라 **완성된 답변 텍스트 1회 사후 검수**이며, 실패해도 초안을 그대로 내보내는 fail-open이다. 대화 로그(`TAstChatLogs`)는 write-only — 어디에서도 다시 읽지 않는다. 이 계층은 **뉴로(추론) + 심볼릭 가드(정규식·화이트리스트) + 지식 주입** 3영역만 채워져 있고, 4번째 영역(월드모델)은 빈칸이다. 다만 `simulate_price`가 감싸는 `pricing.evaluate_price` 는 결정론적 forward 모델이므로 — 에이전트 내부가 아니라 **외부 도구로서** — 월드모델의 씨앗은 이미 코드베이스에 있다.

## 실측 사실

### (a) 시스템 프롬프트가 실제로 주입하는 것

시스템 프롬프트는 **모듈 로드 시 1회** 조립되어 전역 상수 `SYSTEM_BLOCKS` 에 고정된다(`assistant.py:226`). 런타임 인터폴레이션이 금지된다(파일 헤더 `assistant.py:19-21`).

#### `_build_system_blocks(guide)` — `assistant.py:207-223`

블록 조립 순서와 조건이 실측된다:

| 순서 | 블록 | 조건 | 근거 |
|---|---|---|---|
| 1 | `_ROLE_TEXT`(역할·쉬운말·조회·대상고정·코드확인·답변원칙·이슈보고 규칙) | 무조건 | `assistant.py:210` |
| 2 | DB 스키마 다이제스트 | `digest` 가 truthy일 때만 | `assistant.py:211-213` |
| 3 | 메뉴얼 원고 | `manual` 이 truthy일 때만 | `assistant.py:214-216` |
| 4 | 도메인 가이드(또는 폴백 지침) + `cache_control` | 무조건 (마지막) | `assistant.py:221-222` |

- 마지막 블록에만 `cache_control={"type":"ephemeral","ttl":"1h"}` 을 건다(`assistant.py:222`). 주석에 사유가 실측 수치로 기록돼 있다 — "33.5K 시스템 프롬프트가 5분 TTL 이라 5분~1시간 간격 턴(실측 19건)마다 콜드 재기록됐다. 1h 쓰기는 2배 단가지만 콜드 횟수 27→8 로 줄어 순절감"(`assistant.py:217-218`).
- 빈 text 블록은 Messages API 400이므로, 빈 값이면 블록 자체를 **생략**하는 방어가 세 군데 모두 걸려 있다(`assistant.py:141-147`, `163-191`, `194-204`).

#### `simulate_price` 가드 정밀 (`assistant_tools.py:264-300`)

1. 코드 100자 절단·공백 제거(`:266`), 빈 값이면 error(`:267-268`).
2. 상품 실재 확인 — `TPrdProducts.objects.filter(pk=prd_cd).exists()`(`:273-274`). **`del_yn` 조건이 없다.**
3. 셋트 상품이면 계산하지 않고 "가격 시뮬레이터 화면에서 확인하세요" note 반환(`:275-277`). 셋트 구성원 분해가 1차 범위 밖.
4. `selections` 는 dict 가 아니면 `{}` 로 강등(`:279`), `qty` 는 최소 1(`:280`).
5. `evaluate_price(..., mode="lenient")` 고정 호출(`:281-282`). `evaluate_price` 의 시그니처는 `(target, selections, qty, grade_cd=None, mode="lenient", as_of=None, only_comps=None, proc_sels=None, skip_plate=False)`(`pricing.py:428-429`) — 도구는 앞 4개만 노출하고 `as_of`(기준일)·`only_comps`(what-if 부분집합)·`proc_sels`·`skip_plate` 를 **전혀 노출하지 않는다**.
6. 구성요소는 상위 20개만 잘라 반환(`:284-288`).
7. 어떤 예외도 `{"error": ...}` 로 감싼다(`:298-300`) — SSE 뷰가 5xx로 죽지 않게.

#### `run_sql` 가드 정밀 (`assistant_tools.py:547-732`)

방어선이 파일 주석에 5항으로 명시돼 있고(`:530-538`), 코드에서 전부 확인된다.

**정적 게이트 `_sql_guard`(`:619-656`)**
- 빈 값 거부(`:623-624`), **4,000자 초과 거부**(`:625-626`).
- **주석(`--`, `/*`) 포함 시 거부**(`:627-628`) — 주석을 통한 가드 우회 차단.
- 끝의 세미콜론 1개만 제거하고, **본문에 `;` 가 남아 있으면 거부**(`:629-633`) — 다중문 스택 차단.
- 선두 6자가 `select` 또는 `with` 여야 함(`:634-636`).
- 금지어 정규식(워드 경계): `insert update delete drop alter create truncate grant revoke copy vacuum call do merge into set lock refresh nextval setval`(`:557-561`). `into` 는 `SELECT … INTO` 가 테이블을 만들기 때문, `set` 은 세션 설정 변경 때문이라고 주석에 명시(`:555-556`).
- 금지 함수: `pg_read_file pg_read_binary_file pg_ls_dir pg_stat_file pg_sleep pg_terminate_backend pg_cancel_backend lo_import lo_export dblink`(`:562-566`).
- **차단 테이블 전역 스캔**: `t_cus_*`(고객 개인정보) · `t_ast_*`(비서 자체 로그·이슈 초안) · `django_*` · `auth_*` · `pg_*` · `information_schema`(`:579-580`, `:641-642`).
- **테이블 화이트리스트**: `FROM/JOIN` 뒤 식별자를 추출(`:582-586`, `_sql_tables` `:602-616`)해 CTE 이름은 통과시키고(`:588-589`, `:647-648`), 스키마는 `public` 만(`:650-651`), **베이스 이름이 `t_` 로 시작하지 않으면 거부**(`:653-654`). `EXTRACT(YEAR FROM col)` 류 오탐은 검사 사본에서 제거(`:591`, `:605`).

**실행 게이트 `run_sql`(`:670-732`)**
- `LIMIT` 이 없으면 `SELECT * FROM (q) _q LIMIT n+1` 로 감싼다(`:682`) — n+1 로 뽑아 초과 여부 판정(`:696-698`).
- `transaction.atomic()` 안에서 **`SET TRANSACTION READ ONLY`** 실행(`:690`) — "서버측 최종 방어선 — 정규식을 뚫는 표현이 있어도 쓰기는 DB 가 거부한다"(`:689`).
- **`SET LOCAL statement_timeout = '10s'`**(`:691`, `_SQL_TIMEOUT` `:550`).
- 조회 후 **무조건 `_SqlRollback` 예외를 던져 롤백**(`:699-701`). `_SqlRollback` 은 "커밋 경로 없음"을 위한 내부 신호 클래스(`:598-599`).
- 행수 상한 100 기본 / 200 최대(`:547-548`, `:679`), **결과 총 문자수 20,000 캡** — 초과하면 뒤에서부터 행을 버린다(`:549`, `:711-714`).
- `_to_jsonable`(`:59-81`)로 Decimal→float, 날짜→ISO, UUID→str, **바이너리는 `<이진자료 N바이트>` 로 치환**(이미지 바이트가 답변에 실리지 않게, `:79-80`).
- **D-06 경고 note**: 참조 테이블 중 `del_yn` 컬럼 보유 테이블이 있는데 쿼리에 `del_yn` 문자열이 없으면 "삭제된 행이 포함될 수 있습니다" 경고를 붙인다(`:719-727`). **거부하지 않는 이유가 명시** — 감사·이력 조회처럼 삭제행을 봐야 하는 정당한 경우가 있어서(`:722-723`).
- 파일 헤더에 D-06 한계가 자백돼 있다: "`tools/audit_del_yn.py` 는 정적 감사기라 **여기서 실행되는 동적 SQL 은 원리적으로 못 잡는다**. 이 도구의 D-06 방어선은 ①결과 note 경고 ②도구 설명 ③`_ROLE_TEXT` 규칙 셋뿐"(`assistant_tools.py:6-8`, `:540-544`).

#### 쓰기 경계의 정적 고정

`raw/webadmin/tests/test_assistant.py:258-313` 의 AST 검사가 경계를 코드로 못박는다 — `assistant_tools.py` 전체를 `ast.parse` 해 `save/create/update/delete/bulk_create/bulk_update/raw/execute/executemany/cursor` 호출을 스캔하고(`:275`), **`connection.cursor`/`cur.execute` 는 `run_sql` 함수 span 안에서만 허용**한다(`:282`, `:302`, `:313`). 심어놓은 위반을 검사기가 실제로 잡는지 검증하는 메타 테스트도 있다(`:328-341`).

#### 디스패처

`run_tool`(`assistant_tools.py:1100-1116`) — `_DISPATCH` 에 없는 이름은 **실행하지 않고** `{"error": "알 수 없는 도구입니다"}`(`:1106-1108`). 모든 예외를 error dict 로 흡수(`:1109-1113`), dict 이 아닌 반환도 error 로 강등(`:1114-1115`), 최종 `_to_jsonable` 통과(`:1116`).

#### 진행 표시 힌트의 정보 누출 방지

`tool_hint`(`:1061-1077`) — 코드 도구는 검색 정규식·경로를 절대 노출하지 않고 고정 문자열 `"화면 동작"` 만 반환(`:980`, `:1069-1070`). `_hint_cut`(`:983-992`)은 `/`·`\` 포함 또는 소스 확장자로 끝나면 **힌트를 폐기**한다. `_prd_name` 은 `del_yn="N"` 필터를 걸어 삭제 상품이면 빈 힌트가 된다(`:1004-1005`).

### (c) `_verify_prompt` / `_verify_call` / `_verify_verdict` — 자기검증 장치의 실제 검사 내용

이 3함수는 **완성된 답변 초안 텍스트를 1회 사후 검수**하는 장치다. 도구 호출 자체나 행동 결과를 검증하지 않는다.

**동작 구조** (`assistant.py:776-806`)
- 모델의 text delta 를 **실시간 중계하지 않고** `draft_parts` 버퍼에 모은다(`:682-684`). 담당자에게는 `status` 이벤트만 나간다.
- 루프 종료 후 초안이 비어있지 않으면 남은 예산을 계산하고, **15초 미만이면 검증을 건너뛴다**(`_VERIFY_MIN_SEC`, `:458`, `:783-784`).
- 검증 호출 성공 시 판정에 따라 초안 또는 수정본을 `_delta_chunks`(60자 단위, `:462`, `:536-538`)로 쪼개 `delta` 이벤트 송출(`:815-817`).

**`_verify_prompt(question, draft, tool_summaries)`** — `assistant.py:487-500`
조립하는 입력:
1. `[담당자 질문]` — 원문 4,000자 절단(`:488`)
2. `[이번 턴에 호출한 도구와 결과]` — 각 도구의 `name` / `args` / `result` 를 **각각 2,000자 절단**(`_VERIFY_TOOL_CUT`, `:457`, `:493-495`). 수집 시점에도 자르지만 여기서 한 번 더 자른다(`:491-492`).
3. 도구 호출이 하나도 없으면 **"도구 조회 없이 쓴 초안이니 근거 부족을 특히 주의해서 보라"** 는 문구를 대신 넣는다(`:496-498`)
4. `[초안]` 전문
5. `_VERIFY_INSTRUCTION`(`:464-484`)

**`_VERIFY_INSTRUCTION` 이 검사시키는 7항** (`assistant.py:467-480`)
1. 초안의 각 주장에 도구 조회/코드 확인 근거가 있는가
2. 화면 경로·메뉴 이름·필드명이 **시스템 프롬프트의 지식 문서(도메인 가이드·메뉴얼 원고)와 일치**하는가 / 없는 화면·필드를 지어내지 않았는가
3. 근거 없는 단정 — 특히 **"없습니다·안 됩니다·지원하지 않습니다" 부정 단정을 "조회 결과에 안 보인다"는 이유만으로** 하지 않았는가
4. 화면 동작·정렬·표시 규칙 주장인데 코드 확인 근거가 없으면 문제 — **"~로 보입니다"로 넘긴 것도 같은 문제로 본다**
5. 화면 컨텍스트의 대상과 다른 상품·위젯을 기준으로 답하고 있지 않은가
6. 답 첫 줄에 기준 대상을 밝혔는가
7. 담당자 이해 가능성 — 코드값·화면 주소·내부 사정(도구·표·컬럼·SQL·조회 한계) 노출, 설명 없는 전문 용어

출력 계약: 문제 없으면 **정확히 `OK` 한 단어**, 문제 있으면 **수정된 최종 답변 전문**(초안 말투 유지, 마크다운 금지, 검사 과정·수정 이유 쓰지 말 것)(`:482-484`).

**`_verify_call(client, question, draft, tool_summaries, timeout_sec)`** — `assistant.py:503-523`

**`_verify_verdict(txt)`** — `assistant.py:526-533`

- `" .\"'\`"` 를 벗기고 대문자화해 `"OK"` 와 정확히 일치 → `(False, None)`(`:531-532`).

**fail-open 성격** — 검증 호출이 예외를 내면 초안을 그대로 송출하고 로그만 남긴다(`:800-802`). 파일 헤더에 정책으로 못박혀 있다: "정확도 장치가 가용성을 깨서는 안 된다"(`:438-439`). 검증 실행 여부는 `tool_calls` 에 `{"name":"_verify","verified":…,"revised":…}` 로 기록된다(`:804-806`).

### (e) [핵심] 이 에이전트에게 "세계 모델"이 있는가

**없다. 단정한다.** 세 가지 하위 질문 각각에 대해 코드 증거로 판정한다.

#### e-1. 행동의 결과를 미리 예측하는가 — **없음**

- 유일한 행동 실행 지점은 `AT.run_tool(name, tool_input, ctx)`(`assistant.py:744`). 그 앞뒤 어디에도 "이 도구를 부르면 무엇이 나올지 추정한다", "예측과 실제를 비교한다"는 코드가 없다. 앞에는 `tool` start 이벤트 송출(`:741-742`), 뒤에는 소요시간 측정과 `done` 이벤트(`:745-748`)뿐이다.
- `ok = not (isinstance(result, dict) and "error" in result)`(`:746`)로 성공/실패 플래그를 만들지만, 이 값은 **SSE 이벤트와 로그로만 흘러가고** 다음 결정에 되먹임되지 않는다. `tool_calls` 에 적재되어(`:749`) 최종적으로 `_log_chat`(`:826`)에 저장될 뿐이다.
- 도구 실패 시 재시도·대체도구 선택·백오프 로직이 **코드에 없다**. 실패한 결과 JSON이 그대로 모델에게 되돌아간다(`:765-768`) — 즉 복구는 전적으로 모델의 다음 토큰 생성에 위임된다.

#### e-2. 여러 안을 내부에서 굴려보는가 — **없음**

- 메인 루프(`assistant.py:624-774`)는 **단일 선형 while**이다. 분기는 세 가지뿐: 예산 초과 break(`:625-633`), 루프 상한 도달 시 `force_final`(`:635-640`), `stop_reason == "tool_use"` 면 도구 실행 후 `continue`(`:723-772`). 후보 생성·비교·선택·되감기(rollback) 코드가 없다.
- 모델 호출은 매 반복 **1건**이다(`client.beta.messages.stream(**stream_kwargs)`, `:668`). n-best 샘플링·self-consistency·다중 후보 비교가 없다. `temperature`/`top_p`/`top_k` 는 계약상 금지(`assistant.py:5-6`)라 샘플 다양화 수단 자체가 봉인돼 있다.
- `_verify_call`(`:503-523`)이 유일한 2번째 모델 호출이지만 이는 **후보 비교가 아니라 완성 텍스트 1회 검수**다. 그리고 **재검증 루프가 없다** — 수정본을 받으면 그대로 송출한다(`:797-799`). 수정본이 또 틀렸는지 다시 검사하지 않는다.
- `simulate_price` 는 결정론적 forward 모델(`pricing.evaluate_price`)을 감싸므로 "행동 전 결과 계산"의 성질을 가지지만, **에이전트 내부의 심의 장치가 아니라 모델이 명시적으로 호출해야 하는 외부 도구**이며, `only_comps`(what-if 부분집합)조차 노출되지 않아(`assistant_tools.py:281-282`) 대안 비교 용도로는 쓸 수 없다.

#### e-3. 선택의 이력을 누적해 계획을 세우는가 — **없음**

- **서버는 대화 상태를 보관하지 않는다.** 매 요청마다 클라이언트가 `messages` 전체를 보내고(`assistant.py:575`, `:581`), 서버는 그것을 검증·절삭만 한다(`_clean_messages` `:284-313`). 최근 20개 / 총 60,000자 상한이 걸려 있고(`:48-49`), 초과분은 **앞에서부터 버린다**(`:301-310`) — 오래된 계획 맥락은 구조적으로 소실된다.
- `TAstChatLogs` 는 **write-only** 다. `_log_chat`(`:545-560`)이 `objects.create` 로 쓰기만 하고, 이 코드베이스의 비서 경로 어디에서도 다시 읽어 프롬프트에 넣지 않는다. 즉 **세션 간 학습·기억이 0**이다.
- `api_msgs` 는 요청 처리 시간 동안만 존재하는 지역 리스트(`:610`)이며 함수 종료와 함께 사라진다.
- 계획 표현체(plan/goal/subtask/상태기계) 자료구조가 **어느 파일에도 없다**. `force_final` 이라는 bool 하나(`:623`)가 전부다.
- 이슈 초안의 상태기계(`DRAFT → SUBMITTING → SUBMITTED / VERIFY / CANCELED`, `assistant_issue.py:276-277`)는 존재하지만 이는 **인간 승인 워크플로의 상태**이지 에이전트의 계획 상태가 아니다. 에이전트는 `DRAFT` 를 만든 뒤 그 행을 다시 읽지도, 결과를 확인하지도 않는다.
- 축적되는 유일한 것은 `usage` 토큰 카운터(`:606`, `:710-715`, `:792-796`)뿐 — 비용 집계용이다.

**결론**: 이 에이전트는 **한 턴 안에서만 사는 반응형(reactive) 도구 사용자**다. 관찰→행동→관찰의 루프는 있으나, 그 루프 어디에도 (i) 결과 예측 (ii) 대안 시뮬레이션 (iii) 이력 누적 계획이 없다.

### (f) 이 계층을 확장할 때 가장 먼저 막히는 지점

우선순위 순 (모두 코드 근거 있음):

1. **`SYSTEM_BLOCKS` 가 모듈 로드 시 1회 고정된 전역 상수** — `assistant.py:226`. 도메인 가이드·메뉴얼·스키마를 바꾸면 **프로세스 재시작 전까지 반영되지 않는다**. 그리고 "런타임 인터폴레이션 절대 금지"(`:54`)가 계약이라, 사용자별·상품별·세션별 동적 지식 주입을 하려면 캐시 설계 전체(1h TTL 브레이크포인트 + TTL 순서 규칙, `:217-222`)를 다시 짜야 한다. **여기가 첫 번째 벽이다.**

2. **프롬프트 예산 포화** — 주석에 실측 33.5K 토큰(`assistant.py:20`). 여기에 스키마 다이제스트와 메뉴얼 원고가 이미 무제한으로 들어가 있고(`_build_schema_digest` 는 전 모델 순회 `:174`, 메뉴얼은 상한 없이 이어붙임 `assistant_manual.py:270`), 상한 검사는 "500자 미만이면 생략"이라는 **하한 검사뿐**(`assistant_manual.py:273`)이다. 지식을 더 넣으면 캐시 쓰기 단가와 콜드 재기록 비용이 즉시 튄다.

3. **`TOOL_SPECS` 순서가 동결됨** — `assistant_tools.py:872-874`("위 6개 순서·내용은 이후에도 절대 바꾸지 않는다… 새 도구는 **뒤에만** 붙인다"), 테스트로도 고정(`tests/test_assistant.py:134`). 도구를 논리적으로 재편성하거나 계층화(도구 그룹·라우팅)하는 리팩터가 캐시 계약과 정면 충돌한다.

4. **루프 상한 8 + wall-clock 240초** — `config/settings.py:355`, `:363`. 다단계 계획(조사→가설→검증→재조사)은 8루프 안에 들어가지 않는다. 상한 도달 시 `force_final` 로 도구를 잠그고(`tool_choice: none`) 답을 강제하는 경로(`assistant.py:635-640`, `:664-666`)가 이미 "조사 미완료"를 상시 흡수하고 있다 — 즉 **깊은 추론은 구조적으로 잘려 있다**.

5. **쓰기 경계가 AST 테스트로 못박혀 있음** — `tests/test_assistant.py:258-313`. 에이전트에게 어떤 쓰기 능력(예: 설정 변경 제안 적용, 초안 저장)을 주려면 이 화이트리스트를 손대야 하고, 그 순간 "업무 데이터 읽기 전용"이라는 전체 안전 논증(`assistant_tools.py:10-15`, `assistant_issue.py:4-8`)이 무너진다. **가장 되돌리기 어려운 지점.**

6. **서버 무상태** — 세션 저장소가 없다(`assistant.py:575`, `:581`). 계획·목표·중간 산출물을 다음 턴으로 넘기려면 새 저장 계층과 그것을 프롬프트로 되먹이는 경로를 둘 다 신설해야 하는데, 후자가 다시 (1)의 벽에 부딪힌다.

7. **동시성 2 슬롯 × LocMem** — `assistant.py:390-419`, `config/settings.py:367`. `REDIS_URL` 미설정이라 세마포어가 워커당으로 동작한다는 사실이 주석에 자백돼 있다(`assistant.py:394-396`). 병렬 서브에이전트·팬아웃형 확장은 gunicorn sync 워커 3개를 즉시 고갈시킨다.

## 구조 해설

전체 흐름을 코드 순서대로 재구성하면:

```
POST /api/assistant/  (assistant.py:568)
  ├ 키 미설정 → SSE error 프레임 (HTTP 는 항상 200, :570-572)
  ├ _clean_messages 검증 (:581)  ← 20개/60K자/user 시작·끝 강제
  ├ _acquire_stream_slot 세마포어 (:586)
  └ _chat_generator (:597)
       api_msgs[-1] += _screen_context_text(screen)   (:611-612)
       while True:                                     (:624)
         예산 체크 → 초과 시 초안 강등 또는 error       (:625-633)
         루프상한 → force_final + _FORCE_FINAL_NOTE     (:635-640)
         status "자료를 조회하는 중…"                    (:645-646)
         stream(model, SYSTEM_BLOCKS, TOOL_SPECS, ...)  (:654-668)
           text_delta → draft_parts 에 축적(중계 안 함)  (:682-684)
         usage 누적 (:710-715) / refusal 처리 (:717-721)
         stop == tool_use ?
           ├ yes: final.content 통째로 append (:729)
           │      각 tool_use 블록마다 run_tool (:744)
           │      tool_result 를 user 메시지로 append (:769)
           │      continue
           └ no : break
       ── 검증 패스 ──
       draft 비었나? / 남은 예산 < 15s?  → 스킵         (:781-784)
       _verify_call → _verify_verdict                   (:788-799)
       실패 시 fail-open (초안 송출)                     (:800-802)
       final_txt 를 60자 청크로 delta 송출               (:815-817)
       done(usage)                                       (:819-823)
  finally: 슬롯 해제 + _log_chat                         (:824-827)
```

**설계상 두드러진 판단 3가지**

1. **"실시간 타이핑" 을 포기하고 정확도를 샀다.** text delta 를 중계하지 않고 버퍼링 후 검수하는 구조(`assistant.py:12-15`, `:682-684`)는 UX 손해를 status 이벤트로 메꾼다. 사유가 코드에 기록돼 있다 — "담당자 1명이 드물게 묻는 사용 맥락이라 속도·비용보다 단일 답변의 정확도가 절대 우선(사용자 확정 2026-08-07)"(`:435-436`).

2. **실사용 오답이 곧바로 프롬프트 규칙 + 검증 항목으로 승격된다.** 대상 혼동 오답(`:94-102`)과 정렬 추정 오답(`:104-113`)이 `_ROLE_TEXT` 규칙이 되고, 동시에 `_VERIFY_INSTRUCTION` 의 검사 항목(`:474-477`)으로 이중화됐다. 사이즈별 수량 규칙 누락 오답은 도구 반환 필드 추가(`assistant_tools.py:202-205`)와 스키마 다이제스트 도입(`assistant.py:166-167`)으로 이어졌다. **개선 루프는 있으나 그것은 코드 밖(사람)에서 돈다.**

3. **모든 실패가 fail-open 또는 정중한 강등으로 끝난다.** 가이드 로드 실패→폴백 지침, 다이제스트/메뉴얼 실패→블록 생략, 검증 실패→초안 송출, 예산 소진→부분 초안 송출, 루프 상한→도구 잠그고 마지막 1회. 예외는 이슈 등록 경로 하나 — 거기만 fail-closed 다(`assistant_issue.py:4-8`, 중복 확인 조회 실패 시 `"unknown"` 반환 `:214-216`).

## 결함·공백

**F1. `simulate_price` / `get_widget_config` 의 D-06 비대칭 (확인된 사실)**
`get_product_config` 는 삭제 상품을 명시적으로 선차단하고 사유까지 주석에 남겼다(`assistant_tools.py:142-152`). 그러나 `get_widget_config`(`:231`)과 `simulate_price`(`:273-274`)의 상품 실재 검사는 `filter(pk=prd_cd).exists()` 로 **`del_yn` 조건이 없다**. 삭제된 상품의 위젯 목록과 가격이 계산되어 담당자에게 노출될 수 있다. `get_product_config` 주석이 지적한 바로 그 유출 경로("코드를 직접 말하거나 다른 도구 결과에서 얻은 코드로")가 두 도구에는 막혀 있지 않다.
※ 다만 `get_widget_config` 는 위젯 자체에 `exclude(del_yn="Y")` 가 있어(`:234`) 삭제 위젯은 걸러진다 — 노출되는 것은 "삭제 상품에 붙은 살아있는 위젯"이다.

**F2. `_verify_verdict` 의 판정이 이진이고 되먹임이 없다 (확인된 사실)**
`OK` 가 아니면 무엇이든 수정본으로 간주한다(`assistant.py:531-533`). 검수 모델이 지시를 어기고 "문제 없어 보입니다. 다만…" 같은 설명문을 내면 그 설명문이 그대로 담당자에게 최종 답변으로 송출된다. 수정본에 대한 재검증도, 형식 검사(마크다운 미포함 여부 등)도 없다.

**F3. 검증 effort 가 본 답변보다 낮다 (확인된 사실)**
본 답변 `high`(`config/settings.py:358`), 검증 `medium`(`:360`). 더 약한 추론이 더 강한 추론의 산출물을 심판한다. 비용상 합리적 선택이지만, 검수자가 놓친 오류는 구조적으로 통과한다.

**F4. `run_sql` 의 `current_setting` 계열 미차단 [추정]**
금지 함수 목록(`assistant_tools.py:562-566`)에 파일 읽기·sleep·dblink 는 있으나 `current_setting()` / `pg_settings` 뷰 경유 조회는 없다. 다만 `pg_*` 식별자는 `blocked` 정규식으로 차단되므로(`:579-580`) `pg_settings` 는 막힌다. `current_setting('...')` 은 워드 경계 금지어에도, 블록 정규식에도 걸리지 않는다. **실제로 어떤 값이 새는지는 라이브에서 검증하지 않았으므로 [추정]이다.**

**F5. `--` 전면 거부의 부작용 [추정]**
`assistant_tools.py:627-628` 은 SQL 문자열 안에 `--` 가 있기만 해도 거부한다. 상품명·코드에 하이픈 두 개가 들어간 리터럴 비교(`where prd_nm like '%A--B%'`)는 정당해도 실행되지 않는다. 실사용 빈도는 확인하지 않았다.

**F6. 스키마 다이제스트가 컬럼 코멘트 유무에 전적으로 의존 (확인된 사실)**
`assistant.py:177-180` — `db_comment` 가 빈 컬럼은 다이제스트에서 통째로 빠지고, 코멘트가 하나도 없는 모델은 아예 목록에 없다(`:181-182`). 즉 **"봇이 존재를 아는 정보"의 범위가 DDL 코멘트 작성 커버리지에 직결**된다. 코멘트 누락 = 봇의 인식 공백이며, 이 공백은 로그에도 남지 않는다.

**F7. 메뉴얼 원고 블록에 상한이 없다 (확인된 사실)**
`assistant_manual.py:263-276` — 하한(500자) 검사만 있고 상한이 없다. 메뉴얼 원고가 커지면 시스템 프롬프트가 무제한 팽창하며, 그 비용은 1h TTL 캐시 쓰기 단가로 즉시 반영된다.

**F8. 대화 로그가 소비되지 않는다 (확인된 사실)**
`TAstChatLogs` 는 `_log_chat`(`assistant.py:545-560`)에서 쓰기만 된다. 오답 사건이 실제로 프롬프트 개선으로 이어진 흔적이 코드 주석에 여럿 있으나(`:94`, `:104`, `:166`), 그 경로는 **사람이 로그를 읽고 코드를 고치는 수동 루프**다. 자동 회귀 검출·프롬프트 튜닝 피드백이 없다.

**F9. 슬롯 세마포어가 전역이 아니다 (확인된 사실, 자백됨)**
`assistant.py:394-396` — LocMem 캐시라 워커당 카운트. 실질 상한 = `ASSISTANT_MAX_CONCURRENT × 워커수`. 코드가 스스로 이 한계를 주석으로 밝히고 Redis 도입 시 자동 격상됨을 명시한다.

## 월드모델 관점 판정

4영역 중 이 계층이 실제로 채우는 것을 증거로 판정한다.

### (1) 뉴로 — **강하게 존재**

- Anthropic Messages API 스트리밍 호출이 추론의 유일한 엔진이다(`assistant.py:654-668`). thinking 블록이 기본 on 이며 파라미터로 끄지 않는다(`:5-6`), effort `high`(`config/settings.py:358`).
- 도구를 언제·어떤 인자로 부를지, 결과를 어떻게 해석할지, 어떤 문장으로 답할지가 **전부 모델 토큰 생성에 위임**돼 있다. 서버 측에는 도구 선택 로직이 없다 — `run_tool` 은 모델이 지목한 이름을 디스패치만 한다(`assistant_tools.py:1100-1116`).
- 2차 뉴로 계층: 같은 모델의 검수 호출(`assistant.py:503-523`). LLM-as-judge 패턴이다.
- **판정: 이 영역이 이 계층의 본체다.**

### (2) 심볼릭 — **존재하나 전부 "가드" 역할, "추론"은 아님**

증거로 확인되는 심볼릭 장치:
- SQL 정적 게이트 — 정규식 6종(`assistant_tools.py:569-595`), 금지어/금지함수 리스트(`:557-566`), 테이블 화이트리스트 판정(`:644-656`), CTE 이름 해소(`:606`), 함수 내부 `from` 오탐 제거(`:591`, `:605`).
- 도구 화이트리스트 디스패처(`:1080-1097`).
- 경로 정규화·확장자 화이트리스트(`:381-411`).
- 메시지 역할 시퀀스 복구 알고리즘(`assistant.py:272-313`) — Messages API 의 "user 로 시작·역할 교대" 제약을 절삭 후 복구하는 규칙 기반 로직.
- HTML→텍스트 정규식 파이프라인(`assistant_manual.py:37-55`).
- 이슈 등록 상태기계 + 원자 claim(`assistant_issue.py:294-310`) + 숨은 마커 기반 중복 확인(`:199-223`).
- AST 기반 쓰기 경계 검증(`tests/test_assistant.py:258-313`).

**중요한 구분**: 이 심볼릭 장치들은 전부 **입출력을 검사·차단·정규화**한다. 도메인에 대한 **연역·추론**(제약 전파, 규칙 기반 결론 도출, 일관성 검사)을 수행하는 심볼릭 엔진은 이 4파일에 없다. 유일하게 도메인 연역에 가까운 것은 `pricing.evaluate_price`(외부 모듈)이며, 이 계층은 그것을 도구로 **호출만** 한다.

**판정: 안전 게이트로서의 심볼릭은 충실. 추론 엔진으로서의 심볼릭은 없음.**

### (3) 지식/온톨로지 — **존재하나 "프롬프트 텍스트"로만 존재**

- 4개 지식원이 시스템 프롬프트에 텍스트로 주입된다: 손글 규칙(`_ROLE_TEXT`) / 도메인 가이드 214줄 16.6KB / DB 스키마 다이제스트(모델 메타 자동 생성) / 메뉴얼 원고 2종.
- 다이제스트는 **코드 배포마다 자동으로 최신 스키마를 따라간다**(`assistant.py:167-168`) — 이 점에서 손글 문서보다 온톨로지에 가깝다. 그러나 **구조가 없다**: `"테이블설명: 컬럼코멘트, 컬럼코멘트, …"` 평문 나열이며(`:183`) FK 관계·타입·카디널리티·제약이 담기지 않는다.
- 질의 가능한 지식 표현체(그래프·트리플·규칙 베이스)가 **없다**. 지식은 오직 "모델 컨텍스트 안의 문자열"로만 존재하며, 프로그램이 그것을 조회·추론·검증할 수 없다.
- 검증 항목 2번(`assistant.py:469-470`)이 "지식 문서와 일치하는가"를 검사하지만, 이 검사조차 **또 다른 LLM 호출**이다 — 기계적 조회가 아니다.

**판정: 지식은 풍부하되 온톨로지가 아니라 "긴 텍스트"다. 프로그램적으로 질의·추론 불가.**

### (4) 월드모델 (행동→결과 예측) — **없다. 비어 있다.**

(e)절의 세 증거를 판정으로 옮기면:

| 월드모델의 구성요소 | 코드에 있는가 | 증거 |
|---|---|---|
| 행동 → 결과 예측 함수 | **없음** | `run_tool` 호출(`assistant.py:744`) 앞뒤에 예측·비교 코드 부재 |
| 예측 오차 신호 / 되먹임 | **없음** | `ok` 플래그(`:746`)는 SSE·로그로만 흐르고 결정에 미반영 |
| 다중 후보 생성·비교 | **없음** | 반복당 모델 호출 1건(`:668`), temperature 계열 봉인(`:5-6`), n-best·self-consistency 부재 |
| 되감기(rollback)/재시도 | **없음** | 도구 실패 시 재시도·대체 로직 부재. 실패 JSON 을 모델에 되돌릴 뿐(`:765-768`) |
| 계획 표현체(plan/goal/subtask) | **없음** | 자료구조 부재. `force_final` bool 하나(`:623`)가 전부 |
| 상태 지속(턴 간 / 세션 간) | **없음** | 서버 무상태(`:575`, `:581`), 20개/60K자 절삭(`:48-49`, `:301-310`), `TAstChatLogs` write-only(`:545-560`) |
| 결과 관찰 후 학습 | **없음** | 로그를 다시 읽는 코드가 이 계층 어디에도 없음 |

**단정한다: 이 에이전트에 월드모델은 없다.** 관찰→행동→관찰의 반응 루프만 있고, 그 루프는 매 요청마다 처음부터 다시 시작한다.

**다만 두 개의 씨앗은 이미 있다 — 이것이 이 진단의 실질적 발견이다:**

1. **`pricing.evaluate_price` 는 완성된 결정론적 forward 모델이다.** 시그니처가 `(target, selections, qty, grade_cd, mode, as_of, only_comps, proc_sels, skip_plate)`(`pricing.py:428-429`)로, `only_comps`(구성요소 부분집합 what-if)와 `as_of`(시점)를 이미 지원한다 — 즉 **"이 선택을 하면 가격이 얼마가 되는가"를 반사실적으로 굴려볼 수 있는 시뮬레이터**가 코드베이스에 존재한다. 그런데 비서 도구는 그 중 4개 인자만 노출한다(`assistant_tools.py:281-282`). **월드모델의 실행기는 있는데 에이전트에게 연결되어 있지 않다.**

2. **`_verify_*` 는 "결과 판정기"의 골격이다.** 현재는 텍스트 검수용이지만, 입력을 `(question, draft, tool_summaries)`(`assistant.py:487`)로 받는 구조는 그대로 `(목표, 계획, 실행결과)` 판정기로 재해석 가능하다. 다만 현재는 **1회·fail-open·되먹임 없음**(`:781-802`)이라 판정 결과가 다음 행동을 바꾸지 못한다.

**최종 판정**: 이 영역은 **(1) 뉴로 + (2) 심볼릭 가드 + (3) 텍스트 지식** 의 3축으로 구성되어 있고, **(4) 월드모델은 빈칸**이다. 확장의 최소 경로는 새 아키텍처를 짓는 것이 아니라 — 이미 있는 `evaluate_price` 의 반사실 인자를 도구로 열고, `_verify_*` 의 판정 결과를 루프로 되먹이는 것이다. 단, 그 두 변경 모두 (f)의 1번 벽(`SYSTEM_BLOCKS` 고정)과 4번 벽(루프 8회 / 240초)에 즉시 부딪힌다.

## 미확인

- **`docs/assistant-domain-guide.md` 214줄의 내용**은 읽지 않았다(파일 실재·크기만 실측). 그 안에 온톨로지에 준하는 구조가 있는지는 판정하지 않았다 — (3)의 판정은 "이 4파일이 그것을 텍스트로 통째 주입한다"는 사실에 근거하며, 가이드 내부 구조와는 독립이다.
- **`tools/manual_content.py` / `tools/widget_manual_content.py` 원고 실물**은 읽지 않았다. `assistant_manual.py` 가 어떤 키를 뽑는지는 코드로 확정했으나, 실제 원고 분량·최종 블록의 토큰 크기는 미측정이다.
- **`SYSTEM_BLOCKS` 의 실제 토큰 수**는 측정하지 않았다. 33.5K 라는 수치는 `assistant.py:20`, `:217` 의 주석 기록을 인용한 것으로, 이 진단에서 재측정하지 않았다.
- **프런트엔드 채팅 패널**(SSE 이벤트 소비자, `draft` 프레임 처리, 캡쳐 업로드)은 이번 진단 범위 밖이다. `assistant.py:751-758` 이 보내는 `draft` 프레임을 패널이 어떻게 렌더하는지 미확인.
- **F4(`current_setting` 미차단)**는 정적 코드 판독에 근거한 [추정]이다. 라이브 DB에 대해 실행 검증하지 않았다(라이브는 읽기 전용 원칙이며, 가드 우회 시도 자체를 수행하지 않았다).
- **F1(삭제 상품 가격/위젯 노출)의 실제 재현 여부**는 확인하지 않았다. 코드상 `del_yn` 필터 부재는 확정 사실이나, 실사용에서 삭제 상품 코드가 모델에 도달하는 경로의 빈도는 미측정이다.
- **`ASSISTANT_MODEL` 기본값 `claude-opus-5`**(`config/settings.py:353`)에 대해 `_fallback_kwargs`(`assistant.py:243-254`)가 `claude-opus` 접두사로 폴백을 부착한다는 것은 코드로 확인했으나, 라이브 환경변수 실제 값은 확인하지 않았다.
- 웹 검색을 사용하지 않았으므로 Sources 절은 없다.
