## 2. 위젯이 생산으로 넘기는 것 — payload 전수

`widget_api.py` `api_handoff` 가 HMAC 서명하는 payload 의 **전 키**(`:3388-3455`). 서명 안쪽이라 **주문 후 위변조 불가**다.

### 2.1 식별·버전

| 키 | 뜻 |
|---|---|
| `v` | payload 버전(1) |
| `site_cd` · `wgt_cd` · `ver_no` | 사이트 · 위젯 · 위젯버전 |
| `prd_cd` | 상품코드 |
| `ts` | 발급 시각 (재견적 나이 상한의 기준점) |

### 2.2 ★ 생산 정보 (MES 가 실제로 필요로 하는 부분)

| 키 | 내용 | MES 관점 |
|---|---|---|
| `selections` | 고객이 고른 차원 값(사이즈·자재·도수·인쇄옵션 등) | **무엇을 만드나** |
| `sel_opts` | 브라우저가 보낸 **원본 옵션코드 배열** (제약 평가 계약) | 원본 보존 |
| `sel_opt_grps` | 선택된 옵션 **그룹** 코드 (재견적 재현용) | — |
| **`options`** | **서버가 전개한 주문·MES 전달용 상세** — 그룹/옵션 이름 + **내부 구성요소**(`ref_dim` · `ref_dim_nm` · `cd` · `cd2`) | ★ **고객 언어 → 생산 언어 번역 결과** |
| **`combo`** | 조합 템플릿 전개(옵션 조합 → **자재**). 없으면 `null`(키는 항상 존재) | ★ **어떤 자재로 만드나** |
| `set` | 셋트 상품이면 서버가 정제한 셋트 본문 | 셋트 분해 입력 |
| `addons` | 선택 추가상품 내역(name/qty/amount) + `components`(자재·공정 전개) | ★ **추가상품의 자재까지 MES 로 넘긴다**(D-04) |
| **`proc_sels`** | **공정 선택 + 공정 상세옵션(dtl_opt)** + `side`/`side_nm`(적용면: 공통/앞면/뒷면) | ★ **어떤 공정을 타나** |
| `spine` · `spine_color` | 책등 계산 파생값(서버 재계산이 권위) | 제본 사양 |
| `pages` | 페이지수 — 인쇄용지 장수 산출 입력 | 용지 소요량 |
| `case_cnt` | 건수(같은 사양 반복) | ★ **MES 작업 분해 단위** (규칙 미정 — U-8) |
| `order_title` | 제작물 제목 (**MES 필드 nvarchar(100)**) | 작업의뢰서 제목 |

### 2.3 원고

| 키 | 내용 |
|---|---|
| `files` | 업로드 원고. `key` 는 **임시(tmp) 버킷 S3 키** — MES 는 이 키로 못 가져간다 |
| `editors` | 편집기(Edicus) 산출물. 파일과 같은 좌표계(`item`·`mbr`·`inst`) |
| `edicus_uid` | 편집기 원고의 주인 — 결제 후 Edicus 주문 API **필수 헤더** |
| `dsn_cd` | 디자인 코드 (사후 식별) |

### 2.4 금액

`supply`(공급가) · `vat`(부가세 10%) · `total`(청구액) · `grade_cd`(고객등급) · `**qty_info`(수량 규칙).

### 2.5 [HARD] MES 가 가져갈 파일 목록의 출처는 payload 가 **아니다**

> 「**MES 에 넘길 키 목록의 출처가 이 표다** — payload 의 키로는 MES 가 가져갈 수 없다.」
> — `catalog/models.py:1086` (`TOrdArtworks` docstring)

payload 의 `files[].key` 는 **tmp 버킷 키**다. MES 는 **order 버킷**에서 가져간다. 그 사이를 잇는 것이 승격이고, 승격 결과가 `t_ord_artworks` 다. **MES 인계 payload 를 만들 때 파일 목록은 `t_ord_artworks` 의 최신 회차에서 뽑는다**(`artwork_promote.py:296` `latest_artworks`).

### 2.6 MES 대사(對査) 보호 규칙 — 이름을 바꾸면 안 된다

| 규칙 | 근거 |
|---|---|
| 주문 전송 payload 는 **원래명을 유지**하고 표시명은 **별도 키로 동봉** | `price_views.py:121` |
| `opt_nm` / `opt_grp_nm` 을 바꾸면 안 된다 — **MES 대사는 내부명·코드 기준** | `widget_api.py:1929` |
| `MES_ITEM_CD` 는 **한글화·약어화 금지, 대문자 원형 그대로** | `manual_content.py:620` · `raw/webadmin/CLAUDE.md` D-05 |
| `order_title` 은 **UTF-16 길이**로 세야 한다 — MES 는 SQL Server `nvarchar(100)` 이고 `nvarchar(n)` 은 '문자 n 개'가 아니다 | `widget_api.py:1351-1353` |
| 「면별선택여부=Y」 공정은 **적용위치가 주문 데이터에 실려 MES 로 간다** | `manual_content.py:628` · `models.py:600` |
| 「작업여백」이 있으면 **작업사이즈가 실려 생산(MES)·원고 검수 기준이 된다** | `manual_content.py:688` · `work_margin.py:102` |

## 3. 인계 방식 — 설계 확정안 (코드 없음)

### 3.1 왜 SQS 로 느슨하게 잇는가

```
Shopby → API Gateway → SQS(주문 큐) → 인터페이스 워커 → 관리서버(인쇄정보 조회) → MES WCF → MES SQL Server
                                                    실패 시 재시도 → DLQ(유실 방지)
```

- MES(Windows/WCF) ↔ 신규(Linux/Django)를 큐로 느슨히 결합 → **MES 점검·다운에도 주문 접수 지속**, 쌓였다 재처리(DLQ).
- 워커 → MES WCF 는 **VPC/보안그룹 제한 사설 경로**. 인터넷에 열지 않는다. **MES SQL Server 직접 접근 금지**(WCF 경유).
- 출처: `aws-architecture-huni.pdf` p.7 §3.2 · p.11 §6.

> **[미확인 · U-2]** 1차는 API Gateway+SQS 대신 **관리서버 직접 수신 + DB 큐**로도 충분하다는 판단이 설계문서 §12-12 에 남아 있다. **둘 중 무엇으로 갈지 미결.**

### 3.2 왜 MES 가 Shopby 웹훅을 직접 받으면 안 되나 (결론 확정)

1. **웹훅에 파일 키가 실려 있지 않다**(보안 원칙: 웹훅은 키를 나르지 않음). 파일 키는 우리 DB 에서만 해석된다.
2. Shopby 웹훅은 **실패해도 재전송되지 않아** 보정 폴링이 반드시 필요한데, 그 로직을 SQL Server/WinForms 에 얹는 것은 무겁다.

⇒ **웹훅 수신 주체는 우리**로 확정. MES 는 우리에게서 **정리된 주문 한 건**을 받는다.

### 3.3 인터페이스 5방향 · 24건

#### 우리 → MES (WCF) — 5건, **전부 미구현**

| # | 인터페이스 | 언제 | 주요 내용 |
|---|---|---|---|
| MES-1 | **주문 접수(신규 등록)** | 결제완료 + 검사 통과 후 | 주문헤더(주문번호·주문일시·고객·배송지·결제수단) + 품목별 **제작사양 전문**(상품·옵션·자재·공정·수량·건수·규격) + **원고 파일 목록**(order 버킷 키·회차·해시) + `handoff_id` |
| MES-2 | 주문 취소 통보 | 고객 취소 / 미입금 만료 | 접수 후면 "생산중지 요청" 의미 |
| MES-3 | **원고 교체 통보** | 재업로드 회차 증가 시 | 새 회차 키 전달 → MES 가 다시 복사 |
| MES-4 | 배송지·수령자 변경 통보 | `UPDATE_RECEIVER` 수신 시 | 출고 전에만 유효 |
| MES-5 | 주문 조회(재동기화) | 담당자 요청 / 정합성 점검 | 선택 |

#### MES → 우리 (우리가 제공하는 API) — 7건, **전부 미구현**

**MES 는 Shopby 를 직접 호출하지 않는다** — 항상 우리를 거친다(인증·재시도·상태 일관성을 한 곳에서).

| # | 인터페이스 | MES 쪽 행동 | 우리가 이어서 하는 일 |
|---|---|---|---|
| FR-1 | **주문 상태 변경 통보** | 접수완료/생산대기/생산중/생산완료 | **접수완료 → 잠금(CAS) + Shopby 상품준비중(TO-2)** |
| FR-2 | **송장번호 등록** | 출고 처리 | Shopby 배송처리(TO-3) → 고객 배송조회 열림 |
| FR-3 | **주문 취소 요청** | 담당자가 고객 통화 후 취소 | Shopby 취소(TO-4) → 환불 |
| FR-4 | **원고 재업로드 요청** | 담당자 판단 | 재업로드 링크 발급 + **알림톡** + `FILE_HOLD` |
| FR-5 | 취소요청 승인/거부 | 클레임 판단 | Shopby 클레임 승인/거부(TO-5) |
| FR-6 | 프리플라이트 재실행 요청 | 재검사 원할 때 | 검사 큐 재투입(선택) |
| FR-7 | 주문 메모 기록 | 담당자 메모 | Shopby 주문 메모 동기화(선택) |

**인증·경로**: MES(EC2 Windows) → 우리 서버는 **VPC 사설 경로 + API 키**. 인터넷 미개방.

**★ MES 쪽 신규 화면 작업**: FR-3(취소 버튼) · FR-4(재업로드 요청 버튼) · FR-5(취소요청 승인/거부) 는 **MES WinForms 에 버튼과 사유 입력이 새로 생겨야 한다.** 이건 MES 담당 개발자의 작업 범위다.

## 4. 상태값 왕복 — 「상태값들을 서로 주고받으면서 처리」의 실체

지니가 준 구조 사실 7번의 「상태값 왕복」은 **두 개의 서로 다른 왕복**이다. 섞지 말 것.

### 왕복 A — MES ↔ 우리 ↔ Shopby (주문 상태)

```
MES 접수완료 ──FR-1──▶ 우리(cancelable=false 잠금) ──TO-2──▶ Shopby 상품준비중 ──▶ 고객 화면
MES 출고     ──FR-2──▶ 우리                        ──TO-3──▶ Shopby 배송준비중 + 송장 ──▶ 고객 배송조회
고객 취소    ──웹훅──▶ 우리(cancelable 확인)        ──MES-2──▶ MES 생산중지 요청
```

**함정 — 메아리 무한루프**: 우리가 Shopby 상태를 바꾸면 그 변경이 다시 웹훅으로 돌아온다. `PRODUCT_PREPARE`/`DELIVERY_*` 웹훅은 **우리가 올린 것의 메아리**이므로 **우리가 만든 변경인지 표시해 두고 걸러내야** 한다(`order-to-mes-process.md` §8.1).

### 왕복 B — MES 내부 공정 상태 (현장)

공정관리 PDF Summary 의 「To Do List」가 이 축이다.

```
공정명: 출력완료 / 커팅완료 / 봉제미싱입고 / 아크릴가공입고 / 제본입고 / 박작업입고
       ↑ 앞공정은 안찍으면 다음공정 못찍히게 (선후관계 강제)
```

**이건 MES 안에서만 도는 상태이고 고객 화면에 나오지 않는다.** 고객에게는 `제작중` 한 칸이다.

**[미확인]** 왕복 B 의 상태가 왕복 A 의 `IN_PRODUCTION` 안에서 어떻게 접히는지 — FR-1 이 「생산대기/생산중/생산완료」만 통보하는 설계이므로 세부 공정 상태는 안 넘어온다. 대시보드가 필요하면 별도 인터페이스가 필요하다.

## 5. MES 발 산출 데이터 (공정관리 PDF Summary)

MES 가 이미 뽑을 수 있다고 선언한 것 — **신규 시스템이 다시 만들 필요가 없는 것들**이다.

**1차 데이터**: 디지털인쇄 일별 출력량 · 스티커 일별 출고건(량)/미출고건(량) · 봉제미싱 입고건(량)/미출고건(량) · 아크릴가공 입고건(량)/미출고건(량) · 제본 입고건(량)/미출고건(량)
**2차 데이터**: 각 팀별 입고예정 건(량) · 공정별 평균리드타임 · 공정별 평균 제작기간

> 「**공정라우트 설정 후** 디테일한 데이터 추출가능」 — 즉 위 2차 데이터는 **공정라우트가 데이터로 설정된 뒤**에나 나온다. 현재는 미설정(`process-route.md` §4).

|---|---|---|---|
| **B-1** | **상품 ↔ MES 품목코드 매핑** | **15 / 269 (5.6%)** | 매핑이 없으면 MES-1 payload 를 만들 수 없다. 원천 엑셀에서 재추출 → 중복 7건 판정 → 일괄 적재가 필요. 입력·중복검증 UI 는 이미 상품 편집 화면에 있으나 **목록에 빠져 있어 현황 파악이 어렵다** |
| **B-2** | **MES 실제 상태 코드·WCF 스펙** | 미확인(설계는 추정) | 이것부터 맞춰야 §7 매핑표가 고정된다. **상대가 있어 협의 리드타임이 길다 → 가장 먼저 착수** |
| **B-3** | **우리가 제공할 API 4종 정의서** | 미작성 | FR-1~4 스펙 협의의 출발점 |
| **B-4** | 주문 상태머신 + **취소 경합 잠금(CAS)** | 미구현 | 환불했는데 생산되는 사고를 막는 유일한 장치 |
| B-5 | 원고 승격 실전 검증 | 코드 있음 · 실행 0건 | MES 는 order 버킷에서 가져가므로 승격이 접수의 **전제** |

**착수 순서(2026-08-18 사용자 결정)**: ① 원고 승격 → ② MES 인터페이스 → **나중**: 파일 검사(PitStop·n8n 선행 필요).
그 이유: MES 는 order 버킷에서 가져가므로 승격이 접수의 전제이고 · 승격은 S3 복사·태깅이라 지금 만들 수 있으며 · **검사 없이 접수하는 것은 지금 운영 방식과 같아서**(사람이 눈으로 확인) 중간 단계로 성립한다.
