§2 고객이 보는 것, 위젯

위젯이 무엇인가

위젯은 고객이 상품을 주문할 때 보는 주문서 화면 전체입니다(위젯 매뉴얼 §1). 상품 페이지에 붙는 작은 보조 창이 아니라, 옵션 선택 · 가격 표시 · 원고 업로드 · 장바구니 담기까지를 한 번에 처리하는 화면 그 자체입니다.

관리자가 위젯빌더에서 양식을 조립해 게시하면 고객 화면에 반영됩니다. 위젯빌더는 저장 버튼 없이 0.6초마다 자동저장되는데, 이는 작성 중인 초안일 뿐입니다. [게시]를 누른 순간 그 시점의 구성이 통째로 버전 스냅샷(그대로 굳어진 사본)으로 저장되고 고객에게 보입니다. 잘못 게시했으면 이전 버전으로 되돌릴 수 있습니다.

고객의 주문 여정 5단계

  • 1. 상품 페이지에서 주문 양식을 만난다. 상품마다 관리자가 조립해 게시한 양식이 붙어, 그 상품에 맞는 선택지만 보입니다.
  • 2. 옵션을 고른다. 안 되는 조합은 고르는 순간 회색으로 비활성화되고 취소선과 이유가 표시됩니다. 순서를 바꿔 골라도 결과가 같습니다.
  • 3. 가격이 즉시 바뀐다. 선택할 때마다 약 0.3초 안에 서버가 계산한 가격으로 갱신됩니다(합계+부가세).
  • 4. 원고를 준비한다. 완성 파일 업로드(클라우드 직접 업로드, 파일당 최대 500MB) 또는 브라우저에서 바로 디자인(Edicus 편집기 — 아래 설명).
  • 5. 장바구니에 담고 주문한다. 서버가 가격 · 제약 · 원고를 전부 재검증한 뒤 위변조 방지 서명 토큰을 발급합니다(유효 1시간). 쇼핑몰 장바구니에는 식별자만 넘어가고 결제 직전에 견적이 다시 갱신됩니다. 원고 파일은 30일간 보존되며 그보다 오래되면 주문이 성립되지 않습니다.

WORKED EXAMPLE — 옵션 하나를 골렀을 때 벌어지는 일

모양엽서 위젯에서 고객이 용지 그룹에서 "스노우지"를 고르고 항목 "150g"을 선택합니다. 화면은 0.3초 안에 후니 서버에 가격을 물어보고, 서버가 계산한 합계+부가세로 표시를 바꿉니다. 이때 스노우지 150g과 함께 쓸 수 없는 후가공이 있다면 그 후가공 항목은 회색으로 잠기고 이유가 붙습니다. 고객이 브라우저의 개발자 도구로 금액 표시를 바꿔도 주문 시점에 서버가 전부 재검증하므로 실제 주문 금액은 바뀌지 않습니다.

가격은 어떻게 계산되나

클라이언트는 표시만 하고 계산은 항상 서버가 합니다. 고객 브라우저는 가격을 보여 주기만 하고 계산은 전부 후니 서버의 가격 엔진이 맡습니다. 주문 시점에는 가격 · 제약 · 원고를 전부 재검증합니다. 위젯 SDK 가이드의 문구를 그대로 옮기면 "위젯 코드를 조작해도 주문 금액은 바뀌지 않습니다". 부가 방어로 사이트당 분당 240회, 서버 간 통신은 분당 600회의 요청 한도가 있습니다.

게시되어 있다고 전부 살 수 있는 건 아닙니다

이 브리핑에서 가장 중요한 주의사항입니다. 게시됨 ≠ 주문 가능.
  • 2026-08-22 전수 감사에서 게시 위젯 194개 중 98개의 상품 가격계산이 막혀 있었습니다(정상 통과 88개). 내역은 처음부터 가격이 안 나오는 94 · 일부 값만 문제인 4 · 시작 기본값 미선택 8입니다.
  • 원인 유형(2026-08-22 감사): 매칭 단가 없음 54 · 단가 미등록 47 · 셋트 계산 실패 16 · 공식/단가 미구성 15 · 계산 실패 7.
  • 2026-08-27 재진단(SPEC-WIDGET-WIRING-001)에서는 같은 게시 위젯 194개를 다른 기준으로 나눠 BROKEN 66 · WARN 2 · OK 119 · NE 6 · INFRA_FAIL 1로 판정했습니다.
  • 다만 이 감사 수치의 재현율은 65%(2026-08-27 재진단에서 확인)입니다. "98개"는 불변하는 값이 아니라 그날의 진단이며, 조치가 진행된 뒤에는 다시 점검해야 실제 상태를 말할 수 있습니다.

한마디로 정리하면 위젯 화면 자체는 정상적으로 돌아가지만 그 안에 채워야 할 상품 데이터가 아직 전부 채워지지는 않았습니다. 그 갭은 매일 메워지는 중입니다(아래 데이터 품질 섹션 참조).

라이브 위젯의 기술 정체

오늘 고객이 만나는 위젯은 웹 표준 기술(Web Component + Shadow DOM)로 만들어진 바닐라 자바스크립트입니다. 어떤 프레임워크로 만든 쇼핑몰에 붙여도 동작하고, 위젯이 페이지의 다른 요소와 스타일을 서로 침범하지 않도록 격리됩니다. 임베드는 스크립트 두 줄이면 충분하고 한 페이지에 여러 위젯을 독립적으로 띄울 수 있으며, 겉모양은 --hw-* CSS 변수로 쇼핑몰 쪽에서 색을 바꿀 수 있습니다.

참고로 위젯을 요즘 방식으로 다시 만드는 React 재구현 트랙이 별도로 진행 중입니다(사내 작업 산출물). 라이브 위젯과 구분되는 별개 트랙이며 라이브 전환 여부는 아직 확인되지 않았습니다. 오늘의 라이브 위젯은 위에서 말한 웹 표준 구현입니다.

Edicus 원고 편집기 — 실제로 동작합니다

4단계의 브라우저 디자인은 Edicus 편집기가 맡습니다. 옵션 조합에 맞는 규격 템플릿이 자동으로 열리는데, 어떤 템플릿을 열지는 서버가 결정하고(/editor/resolve), 편집기 로그인 토큰도 서버가 대신 발급해 줍니다(편집기 비밀키는 서버 밖으로 나가지 않습니다). 편집 결과를 저장하면 프로젝트 번호(prjid)가 주문에 자동으로 실리고, 나중에 다시 클릭하면 이어서 편집할 수 있습니다. 등록되지 않은 조합은 편집기가 열리지 않도록 설계된 안전장치입니다(잘못된 규격의 원고 사고 방지). 완성 파일 업로드 길은 클라우드 직접 업로드로 앱서버를 거치지 않으며 파일당 최대 500MB(100MB 초과 시 자동 분할 전송), 미업로드 시 주문이 차단됩니다.

제약규칙 폼빌더도 눈에 둘 만합니다. 금지 조합 · 필수 동반 · 호환 여부를 양식으로 작성하면 즉시 검증이 돌아갑니다. §2의 "고르는 순간 잠기는" 동작이 이 규칙들입니다(2026-09-07 기준 103건 등록).

자주 묻는 증상 5가지와 점검법

  • 가격이 0원으로 나와요 → 대부분 단가표에 해당 행이 없거나 적용일자가 미래입니다.
  • 고객 화면이 안 바뀌어요 → 게시를 안 했을 가능성이 가장 큽니다. 저장만으로는 고객에게 반영되지 않습니다.
  • 지웠는데 다시 살아나요 → 논리삭제라서, 같은 코드로 다시 등록하면 부활한 것처럼 보입니다.
  • 단가표에서 필터 건 채로 저장했더니 행이 줄었어요 → 필터가 눈에 안 보이는 행을 숨긴 상태로 저장된 것입니다. 행 유실 위험이 있으니 주의하세요.
  • 자사몰에 가격이 안 떠요 → 시작가 미계산이 가장 흔한 원인이고, 그중에서도 '사이즈 기본값 미지정'이 최빈 원인입니다.

§5 직접 확인해 볼 것

  • 가격 시뮬레이터 /admin/price-simulator/ — 공식이 연결된 상품을 골라 옵션을 바꿔 가보면 가격이 어떻게 굴러가는지 체감할 수 있습니다.
  • 퀵스타트 문서 — 모양엽서를 예시로 상품 등록부터 시작가 계산까지 한 바퀴 돌리는 입문 문서입니다(2026-09-06 재생성본).
