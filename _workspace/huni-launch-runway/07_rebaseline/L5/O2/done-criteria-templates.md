# `done_criteria` 문장 템플릿 — O3 가 원장 전건에 채울 때 쓴다

> 목적: 원장 501+ 행의 「무엇이 되면 이 항목이 끝난 것인가」를 **한 사람이 읽고 같은 판정을 내리는 문장**으로 통일한다.
> 원칙 하나만 기억하면 된다 — **눈으로 보거나 셀 수 없으면 완료조건이 아니다.**

---

## 0. 쓰는 법 (3단계)

1. 그 행의 **상태**(`done`/`partial`/`todo`/`new`)를 본다 → §1 에서 상태별 뼈대를 고른다.
2. 그 행의 **대분류**를 본다 → §2 에서 대분류별 확인처를 끼운다.
3. `<...>` 를 그 행의 실제 값으로 바꾼다. 바꿀 값이 없으면 **그 행은 완료조건을 못 쓴다는 뜻**이므로 §4 로 간다.

---

## 1. 상태별 뼈대

### `done` — 이미 된 것
```
<파일:줄> 에 구현이 있고, <확인처> 에서 <관측 문장> 이 1회 확인된다.
```
- **`done` 은 근거에 `file:line` 이 반드시 있어야 한다**(lead 결정 · `LEAD-VERDICT-N.md` §2-1).
- 「라이브에 있다」와 「한 번이라도 돌았다」는 다르다. `A-11` 이 그 예다(코드는 라이브인데 `t_ord_orders` 0행). 안 돌았으면 `done` 이 아니라 **미실행**으로 적는다.

예)
`huni-skin-shopby/src/app/api/auth/signup/route.ts:8-33 에 구현이 있고, 라이브 회원가입 화면에서 신규 계정 1건이 생성되는 것이 1회 확인된다.`

---

### `partial` — 일부만 된 것
```
<이미 되는 부분> 은 <확인처> 에서 확인되고, <아직 안 되는 부분> 이 <확인처> 에서 <관측 문장> 으로 바뀐다.
```
- **안 되는 부분을 반드시 명시한다.** 「보완한다」는 완료조건이 아니다.

예)
`파일 업로드는 위젯 드롭존에서 되고, 업로드된 원고가 주문에 연결되는 것이 t_ord_artworks 행 1건으로 확인된다.`

---

### `todo` — 아직 안 한 것 (그릇은 있음)
```
<확인처> 에서 <관측 문장> 이 확인된다.
```
- 가장 짧은 형태. **확인처와 관측 문장 둘 다 있어야 한다.**

예)
`셀러어드민 배송비 설정 화면에서 「수량 기준 배송비」가 꺼져 있는 캡처가 1장 있다.`

---

### `new` — 그릇부터 만들어야 하는 것
```
<만들 것> 이 <어디> 에 생기고, <확인처> 에서 <관측 문장> 이 확인된다.
```
- `new` 는 **「무엇을 새로 만드는가」를 먼저 쓴다.** 안 그러면 다음 사람이 범위를 못 잡는다.

예)
`공정 라우트 테이블이 라이브 DB 에 생기고, 상품 1건에 대해 라우트 행이 1건 이상 조회된다.`

---

### 「미실행」 — 코드는 있는데 한 번도 안 돌린 것
```
<코드 위치> 는 라이브다. <확인처> 에서 <관측 문장> 이 1회 관측되면 닫힌다. 지금은 0 건이다.
```
- `N3 §0.2` 3분류(미구현·미실행·미확인)를 그대로 쓴다. **0행 = 미실행이지 미구현이 아니다.**

## 2. 대분류별 확인처 — 「어디를 보면 판정되나」

| 대분류 | 기본 확인처 | 관측 문장 예 |
|---|---|---|
| 상품·카탈로그 | 라이브 스토어프론트 화면 | 「카테고리 <이름> 을 눌렀을 때 상품이 N개 이상 뜬다」 |
| 옵션·견적 | 위젯 실화면 + 가격 시뮬레이터 | 「<옵션> 을 바꾸면 표시 금액이 <권위값> 으로 바뀐다」 |
| 원고·파일 | 위젯 드롭존 + `t_ord_artworks` | 「파일 1건 업로드 후 `t_ord_artworks` 에 행 1건이 생긴다」 |
| 장바구니·주문 | 라이브 장바구니 화면 + 샵바이 주문 API 응답 | 「장바구니에 담긴 금액이 위젯 표시 금액과 원 단위까지 같다」 |
| 결제 | 결제 화면 + 이니시스 가맹점관리자 | 「결제수단 목록에 <수단> 이 보인다」 |
| 배송 | 셀러어드민 배송 설정 화면 | 「<설정> 이 꺼져 있는 캡처가 1장 있다」 |
| 회원·인증 / 마이페이지 | 라이브 화면 (테스트 계정) | 「<동선> 을 1회 완주한 캡처가 있다」 |
| 클레임·CS | 샵바이 응답의 `nextActions`·`cancelable`/`exchangeable`/`returnable` | 「<상태> 에서 `cancelable` 이 <값> 으로 내려온다」 |
| 프로모션 / B2B / 정산·통계 | 셀러어드민 해당 화면 | 「<화면> 에 <항목> 이 노출된다」 |
| 정보·콘텐츠 | 라이브 페이지 URL | 「<URL> 에 접속하면 <문구> 가 보인다」 |
| 운영자·상품가격 | webadmin 화면 + 라이브 DB 읽기 | 「<화면> 에서 <값> 을 저장하면 <테이블> 에 행이 생긴다」 |
| 운영자·주문운영 | 셀러어드민 주문 화면 / webadmin | 「주문 1건이 <상태> 로 보인다」 |
| 운영자·회원CS | 셀러어드민 회원·게시판 화면 | 같은 형태 |
| 시스템·플랫폼 | 코드 + 로그 + 응답 | 「<엔드포인트> 호출 로그가 1건 이상 있다」 |
| 생산·공정 | webadmin 화면 + 라이브 DB + 출력물 | 「주문 1건의 의뢰서가 출력물로 1장 있다」 |

## 3. 돈·주문 항목은 한 단계 더

원장에 `돈여부=True` 또는 `주문여부=True` 인 행은 **관측 문장에 숫자를 넣는다.**

```
<확인처> 에서 <조건> 일 때 금액이 <권위값 숫자> 로 표시된다.
```

예)
`가격 시뮬레이터에서 무선책자 A5·기본조합일 때 금액이 13,160원으로 표시된다.` (현행 5,964원)

**「정상 동작한다」·「가격이 맞다」는 돈 항목의 완료조건이 될 수 없다.** 권위값 숫자가 없으면 §4 로 간다.

---

## 4. 완료조건을 못 쓰는 행 — 그대로 두지 말 것

아래 중 하나면 `done_criteria` 칸에 **완료조건 대신 그 사유를 적는다.**

| 사유 | 칸에 적을 문장 |
|---|---|
| 외부 계약이 선행 | `차단 — <외부 주체> 회신/승인 전에는 완료조건을 쓸 수 없다. 선행 노드 <노드ID>` |
| PM 결정이 선행 | `결정 대기 — <결정 항목>. 정해지면 완료조건이 갈린다` |
| 문서 간 충돌 | `분기 — (ㄱ) <조건A> / (ㄴ) <조건B>. 어느 쪽인지 미확인 (<출처>)` |
| 권위값이 없다 | `권위값 미확보 — <어디> 에서 정답 숫자를 먼저 받아야 한다` |
| 범위 미결 | `범위 미결 — 10/6 안인지 밖인지 PM 미결정 (<출처>)` |

**빈칸으로 두지 않는다.** 빈칸은 「없다」가 아니라 「아직 안 봤다」로 읽히고, 그러면 G1 이탈 조건 3(빈칸 0)이 거짓으로 통과한다.

---

## 5. 자기 점검 5줄 (원장 한 행을 쓰고 나서)

- [ ] **확인처**가 있는가 — 「어디를 보면」이 문장 안에 있는가
- [ ] **관측 문장**이 있는가 — 보거나 셀 수 있는가
- [ ] 「검토한다 / 정리한다 / 준비한다 / 보완한다 / 정상 동작한다」를 쓰지 않았는가
- [ ] `done` 이면 `file:line` 이 있는가
- [ ] 돈·주문 항목이면 **숫자**가 있는가
