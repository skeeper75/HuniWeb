# CPQ 자동견적 설계 자료 — 통화 종합 + 위젯 테스트 결과

> 출처: 260702 통화 P7(1:31–1:50) 실무 결정·라이브 테스트 + P4 교육 내용 종합. 01~03 문서를 입력으로 하는 최상위 설계 문서.

## 1. 이번 통화에서 합의된 시스템 구성 (1:40:43)

김동학이 화이트보드 정리하듯 확인하고 신우진이 승인한 3+1 구성:

| # | 구성 | 역할 | 참조 모델 |
|---|------|------|----------|
| 1 | **상품(상세)페이지 빌더** | 쇼핑몰 상품 페이지 제작·등록 | 기존 바이상상 200개 상품(엘리멘터 등록에 2개월 소요) 대체 |
| 2 | **에디터** (캔버스형) | 고객 디자인 편집 — 인쇄 특화 옵션 내장 | "미리캔버스 + 에디쿠스" 결합: 에디터 기능은 오픈 디자인 수준이면 충분, **에디쿠스에서 흡수할 것은 인쇄 필수 옵션들**(칼선, 화이트 레이어, 코롯토 프리뷰 등) |
| 3 | **위젯 빌더 (CPQ)** | 옵션 선택 → 제약 발동 → 자동견적 | 이번 테스트 대상 |
| +α | **어드민(소재관리 등)** | Shopby에 없는 인쇄 특화 관리 화면 | 출력소재관리 페이지 별도 개발, Shopby 어드민과 병행 |

에디터의 오브젝트 단위 결정: "블록 단위가 아니라 객체(오브젝트) 단위로 만들어야 할 것 같다"(김동학) + 스냅 기능 필수(신우진). 문서 기반(노션류)이 아니라 디자인 기반이므로 **에셋 체계가 선행** — Adobe DAM(Experience Manager) 분석 과제 부여.

## 2. 위젯 라이브 테스트 기록 (1:43–1:50)

### 2.1 테스트 환경

- 김동학이 기존 데이터를 DB로 크롤·적재("다 긁어왔다"), Railway 호스팅, 위젯이 DB 연동 상태로 동작. Vercel에 올렸던 이전 버전은 DB 미연동으로 최신 아님 — **소스 전달 완료, 테스트 기준은 Railway 버전**.
- 성능 이슈 관찰: "우와 진짜 느리다" — 원인 미상, 서 대표(호스팅/인프라 관련) 문의 예정.

### 2.2 테스트 시나리오: 프리미엄 엽서

옵션 그룹 로딩 확인: 인쇄, 종이, 모서리, 오시, 미싱, 가변텍스트/이미지 등.

**발견된 데이터 정합 문제와 결정:**

| 이슈 | 관찰 | 결정 |
|------|------|------|
| 1:1 옵션의 노이즈 | 사이즈 73×98 선택 시 오시 등이 조건 없이 노출 | 사이즈와 1:1로 결정되는 옵션(단일값)은 위젯 선택지에서 **삭제** — 김동학이 현장에서 다수 옵션 그룹 삭제("이거 다 필요 없는 거네") |
| 사이즈별 3개 변형 | "사이즈마다 3개씩" 존재하는 항목 확인 | 옵션-사이즈 매핑 규칙(302건 분류)을 위젯 데이터에 반영 필요 |
| 수량 증분 누락 | 수량 그룹에 min/max/step 데이터 없음 | 현장에서 직접 입력해 검증 |

**첫 제약조건 발동 테스트 (성공):**

```
규칙: 사이즈 73×98 클릭 시
  → 수량: min=15, step=15, max=1000  (예시 1)
  → 수량: min=12, step=12, max=1200  (예시 2)
저장 → 위젯 반영 확인 ("네 됐어요")
```

→ 검증된 사실: **수량은 단순 정수가 아니라 (min, max, step) 3요소 구조**이며, 이는 판걸이수와 연동된 도메인 규칙(15장 = 판당 UP수 배수 단위 판매)이다. 발동조건(제약) 엔진이 옵션값 → 타 그룹 파라미터 변경을 지원함을 실물로 확인.

### 2.3 테스트에서 도출된 위젯 요구사항

1. `option_value → {min, max, step}` 파라미터 주입 (수량뿐 아니라 범용화 여지).
2. 1:1 결정 옵션의 자동 숨김(내부 확정값 처리) — internal 승격 규칙.
3. 발동조건 편집 UI: "규칙 하나만 얘기해 → 즉시 입력·저장·확인" 루프가 작동함. 이 루프가 제약 57건 이관 작업의 표준 절차가 됨.
4. 옵션 그룹 노출 순서 = 엑셀 순서(02 문서 §3.3), 위젯 빌더에서 재배열 가능.
5. 성능: DB 조회 지연 프로파일링 필요 (Railway 구간인지 쿼리인지 미확인).

## 3. 마이그레이션 전략 (김동학 제안, 1:32:06 — 합의)

2단계 접근:

1. **1단계 (즉시)**: 기존 바이상상 상품페이지 HTML을 그대로 긁어와 신규 쇼핑몰 DB에 등록 → 쇼핑몰에 상품이 "일단 나오도록". 운영 데이터 무손실 포팅 우선.
2. **2단계 (병행)**: 포팅된 HTML을 템플릿으로 분석해 **빌더를 역으로 재구성** — 신규 상품부터 빌더로 등록, 기존 상품은 점진 전환.

근거: 환OO(담당자)이 200개 상품을 일일이 재등록하는 데 또 2개월을 쓸 수 없음. "덜어내기" 원칙과 일치 — 완벽한 빌더 이관보다 동작하는 쇼핑몰 먼저.

## 4. 주문 플로우 설계 (에디쿠스 링크 매니저 벤치마크, 1:19–1:23)

에디쿠스 링크 매니저에서 확인한 검증된 UX 패턴:

```
스마트스토어(외부 채널)에서 사이즈·기본옵션만 선택 → 구매
  → 편집 링크가 고객에게 자동 발송
  → 고객이 링크 클릭 → 에디터 오픈 (가이드 이미지 표시 가능)
  → 편집 완료 버튼 → API 경유 견적 확정 → 인쇄소 직송
```

핵심: **파일 업로드가 불가능한 외부 채널(스마트스토어 등)에서도 주문을 받는 구조.** 후니 CPQ 위젯도 동일 패턴 — "위젯 하나만 잘 만들면 카페24, 텐바이텐, 갓피플, Shopify(Printful 모델) 어디든 붙인다"(P6). 위젯은 자사몰 전용 컴포넌트가 아니라 **채널 범용 임베드 자산**으로 설계한다.

## 5. 통합 설계 원칙 (01~03 문서 종합)

1. **2계층 분리**: 옵션 레이어(고객) ↔ 공정 레이어(생산/원가). 옵션→공정 매핑 테이블이 MES 연동의 전제.
2. **아키타입별 가격 엔진 3종** + `price_origin`(계산/협의) 메타. 고정가형은 재계산 불가 자산으로 관리.
3. **온톨로지 선행**: 룰 합의 → 경쟁사 코퍼스 정렬 → 스키마 귀속 (03 문서 파이프라인).
4. **제약은 JSONLogic 단일 표현**: 위젯 발동조건·엑셀 ★마커·RP 제약 패턴 모두 동일 문법으로 수렴.
5. **암묵지 목록 관리**(02 문서 §6): 롤 계산, 책등 공식, 계산식 셀 등 엑셀 밖 로직 7건을 백로그로 명시 추적.
6. **덜어내기**: 마이그레이션 2단계 전략, 1:1 옵션 삭제 결정 모두 "지금 필요 없는 것 제외" 원칙의 적용.
