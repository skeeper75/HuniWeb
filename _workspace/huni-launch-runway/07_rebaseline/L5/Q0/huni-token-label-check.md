## 0. 답 — 한 줄

**`huni_token` 라벨은 샵바이 상품에 등록돼 있지 않다. 297개 전수 중 0건이다.**

그리고 **이것은 결함이 아니라 의도된 상태다** — SDK 가이드가 「토큰 전용 라벨을 **일부러 만들지 않았습니다**」라고 명시한다.
**진짜 문제는 반대편에 있다: 자사몰 코드가 그 없는 라벨에 값을 싣고 있다.**

## 2. 3분류 결과 (빈칸 0)

| 분류 | 건수 | 어떤 상품인가 |
|---|---:|---|
| **`huni_token` 있음** | **0** | 없다 |
| **`huni_item` 있음** | **226** | **판매중 전건.** 라벨 조합이 `huni_order` + `huni_item` **하나로 완전히 통일**돼 있다 |
| **둘 다 없음** | **71** | 전부 **판매중지(STOP)** 상태. 텍스트 옵션이 0개다 |
| **합** | **297** | 분류 빈칸 **0** |

### 판매중 226건의 라벨 조합은 단 한 가지다

```
huni_order | huni_item        ← 226건 전부. 예외 0건.
```

**흔들림이 없다.** 226개 상품 전부가 정확히 같은 두 라벨을 갖고 있다.
`inputMatchingType` 은 둘 다 `PRODUCT`, `required` 는 둘 다 `false` 다(표본 확인 `132773412`).

### 판매중지 71건은 텍스트 옵션이 0개다

이 71건은 관리코드 중복분이다(§5). 판매를 멈춘 껍데기라 라벨이 붙어 있지 않다 — **정상이다.**

## 3. 이것이 왜 정상인가 — 가이드가 그렇게 정했다

`raw/webadmin/docs/widget-sdk-guide.html:1912-1922` (후니가 쇼핑몰팀에 준 SDK 가이드) 원문:

| 항목 | 이전 안내 | 지금 | 왜 바뀌었나 |
|---|---|---|---|
| **텍스트 옵션** | 등록된 것이 **0개**였습니다 — 값을 실을 자리가 없어 **담기 자체가 동작할 수 없었습니다** | **`huni_order` · `huni_item` 2개 등록 완료** | 「라벨이 상품에 등록돼 있어야 `optionInputs` 로 값을 실을 수 있습니다. 저희 쪽 선행 작업이었고 끝냈습니다」 |
| **토큰 위치** | 정해진 자리가 없었습니다 | **샵바이에는 넣지 않습니다. 토큰 전용 라벨을 일부러 만들지 않았습니다** | 「텍스트 옵션은 **주문조회 응답으로 그대로 읽힙니다.** 토큰은 금액·사양의 권위라 노출되면 안 되고, 값 길이 상한이 확인되지 않아 **조용히 잘리면 서명 검증이 전부 실패**합니다」 |

**⇒ API 실측 결과가 가이드와 정확히 일치한다.** 등록: `huni_order`·`huni_item` 2개. 미등록: `huni_token`. 의도대로다.

이로써 A 팩 U-2 칸의 「문서끼리 어긋난다」는 **해소됐다** — 문서(계약서·가이드)와 라이브(API 실측)는 **일치한다.**
**어긋나는 것은 자사몰 코드 한쪽뿐이다.**

## 4. 그래서 무엇이 깨지나 — 코드 근거만 (호출 0)

[HARD] 이 절은 **코드를 읽어서만** 썼다. 담기·주문·재견적을 **한 번도 호출하지 않았다**.

### 4.1 자사몰이 실제로 싣는 것

`huni-skin-shopby/src/components/product/huni-widget.tsx:69-77`
```ts
const inputs: OptionInput[] = [
  { inputLabel: "huni_token", inputValue: r.token },      // ← 라벨 미등록
];
inputs.push({ inputLabel: "huni_order", inputValue: JSON.stringify(order) });
```
같은 패턴이 `src/lib/api/requote.ts:72-75` 에도 있다.

**그리고 `huni_item` 은 어디에서도 안 싣는다** — `grep -rn "huni_item" src` → **주석 0건, 코드 0건**.

| 라벨 | 샵바이 등록 | 자사몰이 싣나 | 결과 |
|---|---|---|---|
| `huni_order` | **O** (226 전건) | **O** | 정상 — 값이 실린다 |
| `huni_item` | **O** (226 전건) | **✕ 안 실음** | **등록된 자리가 비어 있다** |
| `huni_token` | **✕ 미등록** | **O 실음** | **실을 자리가 없다** |

**두 방향으로 동시에 어긋나 있다.** 등록된 칸은 비우고, 없는 칸에 넣는다.

### 4.2 담기 자체는 실패하지 않는다 (화면상)

`huni_order` 는 등록돼 있으므로 값이 실린다. 그 값 하나로 장바구니 표시가 성립한다 —
`src/lib/api/widget-order.ts:102-129` `parseWidget()` 은 **`huni_order` 만 있으면 파싱에 성공**한다.

```ts
const raw = optionInputs?.find((i) => i.inputLabel === "huni_order")?.inputValue;
if (!raw) return undefined;                                    // ← huni_order 가 기준
const token =
  optionInputs?.find((i) => i.inputLabel === "huni_token")?.inputValue ?? "";   // ← 없으면 빈 문자열
```

**토큰이 없어도 `undefined` 를 반환하지 않는다.** `?? ""` 로 **빈 문자열이 되어 조용히 통과**한다.
금액·수량·요약은 `huni_order` 에서 나오므로 **장바구니 화면은 정상으로 보인다.**

### 4.3 실패는 「토큰이 필요한 순간」에 난다 — 그리고 아무 메시지가 없다

빈 토큰은 자바스크립트에서 거짓값(falsy)이다. 그래서 아래 두 자리에서 **경고 없이 건너뛰어진다.**

| 자리 | 코드 | 무슨 일이 일어나나 |
|---|---|---|
| **장바구니 수량 변경** | `src/components/cart/cart-page.tsx:118-119`<br>`const token = l.widget?.token;`<br>`if (!token) return;` | 고객이 수량을 바꿔도 **아무 일도 안 일어난다.** 오류 문구(`toast.error`)는 이 `return` **뒤**에 있어서 뜨지 않는다 |
| **결제 직전 정규화 재견적** | `src/components/cart/cart-page.tsx:171-175`<br>`if (!token \|\| l.widget?.qtyRule \|\| …) continue;` | 재견적을 **통째로 건너뛴다.** 장바구니에 담은 시점의 옛 금액이 그대로 결제로 간다 |

그 아래 서버 경로는 토큰이 오면 정상적으로 막는다 — `src/app/api/printly/requote/route.ts:42-48`
```ts
const token = body?.token?.trim();
if (!token) return NextResponse.json({ ok: false, error: "token 이 필요합니다." }, { status: 400 });
```
**그런데 여기까지 오지 못한다.** 앞의 두 가드가 호출 자체를 막기 때문이다.
**서버는 시끄럽게 거절하도록 만들어져 있는데, 클라이언트가 조용히 삼킨다.** 이것이 U-2 가 말한 「조용한 실패」의 정확한 형태다.

### 4.4 아직 확인하지 못한 것 (호출 금지라 못 봤다)

| 무엇 | 왜 미확인 |
|---|---|
| 미등록 라벨을 담기 API 에 보내면 **오류인가 무시인가** | 담기 호출 금지. 가이드는 「값을 실을 수 있다/없다」까지만 말하고 **거절 여부는 안 적혀 있다** |
| 거절이면 담기가 **400 으로 실패**한다 — §4.2 의 「화면상 정상」이 뒤집힌다 | 위와 같음 |
| 텍스트 옵션 값의 **길이 상한** | 스펙에 `maxLength` 0건(`remediation-spec.md` A-BIND-1) |

**⇒ §4.2~4.3 은 「무시된다」쪽 가지다.** 「거절된다」쪽이면 증상이 더 크고(담기 자체 실패) **더 빨리 드러난다.**
어느 쪽이든 **고쳐야 할 코드는 같다**(§6).

## 7. 무엇을 고쳐야 하나 (제안 · 실행은 쇼핑개발)

**두 갈래가 있고, 가이드는 앞쪽을 정본으로 정해 뒀다.**

| 갈래 | 무엇을 하나 | 가이드 입장 |
|---|---|---|
| **(가) 코드를 계약에 맞춘다** ★ | `huni_token` 을 **빼고**, `huni_item`(36자 항목 키)을 **싣는다**. 토큰은 후니 항목 보관소(`t_wgt_cart_items`)에서 항목 키로 찾아 쓴다 | **정본.** 「토큰 전용 라벨을 일부러 만들지 않았습니다」 |
| (나) 샵바이에 `huni_token` 라벨을 만든다 | 226개 상품에 라벨 추가 | **가이드가 명시적으로 반대한다** — 토큰이 주문조회 응답으로 노출되고, 길이 상한 미확인이라 조용히 잘릴 수 있다 |

**(나)는 권고하지 않는다.** 지금 상태(라벨 없음)가 오히려 **보안상 옳은 상태**다 —
토큰이 실리지 않아서 §4.4 의 노출 위험(서명 토큰·S3 원고 키·Edicus `prjid`)이 **현재는 실현되지 않고 있다.**

> 이 관점에서 보면 **라벨 미등록이 사고를 막아 준 셈**이다. 라벨을 만들면 조용한 실패는 없어지지만 **노출이 시작된다.**
