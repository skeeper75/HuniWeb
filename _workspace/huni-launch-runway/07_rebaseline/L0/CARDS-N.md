**0행 = 미구현의 증거가 아니라 미실행의 결과**다(PG 결제승인 심사 중). 두 판정은 다르다. 이후 모든 「0행」 관측에 이 구분을 적용하라.

## N1 — shopby 플랫폼 전체 플로우 (`plan-huniweb`)

**질문**: shopby(NHN 헤드리스 커머스) 플랫폼 **자체**가 어떻게 도는가. 어느 상태에서 무엇이 가능하고 무엇이 막히는가.
M2 는 「우리가 어떤 API 를 부르는가」를 했다. 이 카드는 **「플랫폼이 어떻게 동작하는가」**다 — 다른 질문이다.

**재료**
- `huni-skin-shopby/docs/api/` — frontend/backend 문서 28건(order·cart·member·coupon·product·review·board·auth·category·common)
- `docs/huni/shopby-onboarding/` — 개통 도크(`후니-외부서비스-개통-도크.html`) + PG 설정 화면 캡처 다수(`img/pgMid*`·`pgPay*`·`pgHosting` 등)
- `docs/huni/PG/지불수단 추가 및 변경 Manual_251202.pdf` · `MID추가및변경_Manual_251202.pdf`
- `docs/huni/후니프린팅_1차런칭_개발범위_Shopby갭_개발방안_260630.xlsx`
- SDK 가이드 §11(샵바이 연동규칙) — 이미 답이 있는 부분은 재조사하지 말고 인용하라
- 셀러어드민 라이브 실화면(읽기전용)

**조사 축**
1. **주문 상태 머신** — 주문이 가질 수 있는 상태 전수, 전이 조건, 각 상태에서 가능/불가능한 조작. 특히 **결제승인 전/후 경계**(지니가 지목한 지점)
2. **결제승인 흐름** — PG 심사·MID·지불수단 설정이 무엇을 좌우하는가. 승인 나면 무엇이 열리는가. 현재 어느 단계인가(미확인이면 미확인)
3. **주문 → 클레임** — 취소·교환·반품의 상태별 가능 여부. SDK 가이드가 언급한 「상품준비중부터 즉시취소 불가」 경계 확인
4. **정산** — 정산 주기·권위·수수료. 후니가 갖는 것과 shopby 가 갖는 것
5. **셀러어드민 운영 동선** — 실무진이 매일 무엇을 보고 무엇을 누르는가. 후니 주문이 셀러어드민에 어떻게 보이는가(M1: 셋트 위젯 라벨 3개가 「디지털인쇄」로 보이는 문제)
6. **웹훅** — shopby 가 내보내는 이벤트 전수, 등록 방법, 재시도 정책. M2: 수신함은 있고 소비자 0건
7. **회원·비회원** — 게스트 주문이 shopby 에서 어떻게 취급되는가. M2: 부분 성립(재견적·주문등록 미성립)
8. **헤드리스 경계** — shopby 가 직접 고객에게 내보내는 것(알림톡·문자·현금영수증·세금계산서). M2 (b) 가 지목한 수량 노출 문제의 전모

**산출** `L0/N1/`: `shopby-order-state-machine.md`(★상태 전이표) · `payment-approval-flow.md` · `claim-settlement.md` · `selleradmin-ops.md` · `webhook-catalog.md` · `headless-boundary.md` · `open-questions.md` · `progress.md`

**완료조건** ① 주문 상태 전이표가 「어느 상태에서 무엇이 가능/불가」를 덮음 ② 결제승인 전/후 경계 명시(현재 단계는 미확인이면 미확인) ③ webhook 이벤트 전수 + 등록 방법 ④ 셀러어드민에서 후니 주문이 어떻게 보이는지 실화면 근거 ⑤ 근거는 문서·실화면 우선, 코드는 보조
