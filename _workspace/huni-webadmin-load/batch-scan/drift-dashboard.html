§36 Huni-Webadmin-Load · 가격 커버리지 감사

드리프트 전수 스캐너 — 진단과 교정

「상품 등록 base코드 ≠ 가격 적재 base코드」 드리프트를 전 상품에서 잡아내고, 권위(상품마스터·가격표) 대조로 원인을 규명해 webadmin UI로만 교정한 기록.

Taxonomy

드리프트 4유형 + 오탐

v4 배치 스캐너는 「기본조합 1개가 가격 나오면 정상」이라 일부 값만 미적재인 부분 드리프트를 놓쳤다. 전수 스캐너는 상품이 등록한 모든 차원 값을 스윕해 가격 그리드에 매칭 행이 없는 셀을 찾는다.

Remediation

상품별 진단·교정

칩으로 필터. 카드를 눌러 before → after·교정 방식·권위 검증을 펼친다.

Engine limit

제약엔진 한계 — 지니 질문 답

화이트인쇄명함의 잔여 오탐(클리어양면)과 「단면만」 처리 방식을 결정한 근거.

시뮬레이터 제약규칙은 「프런트 cascade(비활성화)」용이지 가격 차단이 아니다

_sim_constraints_meta()가 활성 제약을 읽어 지금 선택으론 불가능한 값을 계산해 위젯에 넘겨 grey-out 시킬 뿐, 가격계산은 그리드 매칭만 한다(불가조합 = 매칭행 없어 0원).

Architecture

raw/webadmin/tools의 verifier들과 대비한 결론.

새 하네스는 불필요 — 진단은 tools/ verifier로, 교정은 기존 §36 harness로 분리

tools/ 성격
verify_load.py·verify_optcode_integrity.py = 결정론 · 읽기전용 DB SELECT · exit 0/1 리포트. 교정은 안 함(수동 webadmin 또는 _apply_*.py).
진단
신설·검증됨tools/verify_price_coverage.py 작성 완료. 「값별 any-row-exists」 결정론 검사라 상관차원 오탐 0(폼·포맥스 CLEAN 판정). 게다가 브라우저 스캐너가 add-on final>0에 가려 놓친 base 갭 3건(아크릴 자석·집게·헤어끈)을 신규 검출 → 교정 후 전수 DRIFT 0. 브라우저 스캐너는 런타임 교차검증용으로 유지.
교정
기존 활용재키·미적재·과등록·구조복원 각각 권위 대조 + 도메인 판단 + 서로 다른 webadmin 메커니즘이 필요 → 이미 §36 huni-webadmin-load의 목적·에이전트(hwl-preflight·mapping-auditor·ui-loader·sim-verifier)가 담당. method-skill(드리프트 4유형 교정 루프)만 추가하면 형식화 완성.
