## 핵심 요지 (3줄)

1. **문서 A = RED의 "주문→자동생산→배송" 16단계 무인 파이프라인의 설계 전모**다. 핵심은 고객이
   PDF에 **레이어(후가공)+별색만 지정**하면 시스템이 전처리(Preprocess)에서 CMYK/후가공/별색을
   자동 분리하고, 그 분리 결과(벡터라인 길이·복잡도)로 **실시간 자동견적**을 내며, 자동조판·파일변환·
   JDF까지 만들어 각 장비로 무송(無送)한다.
2. **결정론 엔진의 심장 = 전처리(레이어 분리) + 견적(가장자리 길이 측정) + 조판(Nesting/Object Locator).**
   사람 개입은 오류 승인·미해결 예외에만. "전문 디자이너 없이 파일처리 자동화"가 명시 목표(A p2).
3. **문서 B = 그 자동화를 떠받치는 회사·장비·데이터 역량**(400여 장비·14만 회원·250여 사이트·
   PDF 단일 진입 → 모든 장비로 toss). "RED DATA ANALYSIS CENTER"가 PDF를 .DXF/.JDF/.CUT/.HPGL 등으로 분배.

## ★고객 배송 전 여정 (문서 A 16단계 — 근거 A p3~5)

RED 자동화 시스템의 공식 단계표. **파랑=주문접수 / 하늘=자동검사·견적 / 초록=고객검수·승인 / 빨강=생산·배송.**

| 단계 | 이름 | 무엇을 하나 | 주체 | 근거 |
|---|---|---|---|---|
| 1 | 고객에게 템플릿 제공 | 공정 최적화 템플릿+제작가이드 배포(사이즈별 .ai, 후가공 레이어 구조) | 시스템 | A p3,4,9 |
| 2 | 템플릿 활용 파일제작 | 고객이 왜곡 없이 파일 제작(후가공=레이어명으로 지정) | 고객 | A p4 |
| 3 | 주문 접수 | 인쇄옵션·후가공 주문접수, **주문내용=XML로 DB 저장** | 고객/시스템 | A p4 |
| 4 | 파일 업로드 | 작업파일 PDF 임시폴더 저장(`yyyyMMdd_주문번호_상세번호.pdf`) | 고객 | A p4,10 |
| 5 | **유효성검사 Preflight** | CMYK모드·여백·재단사이즈·앞뒷면배열·후가공레이어 갯수·폰트크기 검사, 예측가능 오류는 자동수정 | 시스템 | A p4,11,14,15 |
| 6 | **전처리 Preprocess** | 레이어 유무 판정→면을 선으로/중복선 제거/레이어 단일화/후가공·별색 분리→후가공별 PDF+미리보기 생성 | 시스템 | A p4,16,17 |
| 7 | **자동 견적** | 후가공 데이터(벡터라인 길이·복잡도)+인쇄단가로 후가공별 정밀견적 자동산출, 기본인쇄비와 합산 | 시스템 | A p4,35,36 |
| 8 | 썸네일+최종견적 제공 | 인쇄/후가공 미리보기+최종견적 실시간 표시 | 시스템 | A p4,13 |
| 9 | 고객 검수확인 | 고객이 파일 정확성 확인, 문제시 재업로드/수정 | 고객 | A p4,5 |
| 10 | 입금확인(결제) | 견적 확인 후 결제→자동 인쇄 진행 | 고객 | A p4 |
| 11 | **데이터 검증** | 원본PDF vs Preflight 미리보기를 **이미지 매칭 알고리즘**으로 재대조 | 시스템 | A p5,38,39 |
| 12 | 주문 승인 | 검증 통과시 최종 주문 승인 | 시스템 | A p5 |
| 13 | **자동 조판** | 같은 후가공끼리 파일 분류, 유휴/가능장비 정보 제공, 조판 PDF 생성 | 시스템 | A p5,40~46 |
| 14 | 인쇄물 생산 | 추천 장비에 인쇄/후가공 진행 | 장비 | A p5 |
| 15 | **이미지매칭 물류관리** | 완성물 스캔→DB 썸네일과 매칭→회원·주문·배송정보 확인 | 시스템 | A p5,47~49 |
| 16 | 배송 | 배송 진행 → 고객 수령 | 물류 | A p5 |

**여정 요약(한 문장)**: 템플릿 다운(1) → 파일제작(2) → 주문·업로드(3~4) → **자동 프리플라이트/전처리/견적**(5~8)
→ 고객검수·결제(9~10) → **데이터 재검증·승인**(11~12) → **자동조판·생산**(13~14) → **스캔 이미지매칭 물류**(15) → 배송(16).

### WebToProduct 20단계와 대조 (근거: `../webtoproduct-analysis.md` §4)

| 축 | WebToProduct 20단계(덱) | 문서 A 16단계 | 판정 |
|---|---|---|---|
| 골격 | 주문→견적→매칭→파일변환→생산→배송 | 동일 골격 | **거의 일치** |
| 프리플라이트 | 축으로 언급 | **1개 시스템으로 상세 플로우차트화**(p14~15) | ★A가 구체화 |
| 후가공 분리 | "후가공별 파일분리" 1스텝 | **14개 레이어 처리 프로세스 각각 플로우차트**(p16~34) | ★A가 크게 구체화 |
| 견적=인쇄+후가공 | evaluate_price 점검대상 | **후가공견적=벡터라인 길이·복잡도(스코딕스=점 분포도)로 산출** 공식 명시(p7,35,36) | ★A가 근거 제공 |
| 조판/임포지션 | "임포지션" | **Nesting/Object Locator+PDF Generator+File Converter+JDF** 4서브시스템(p40~46) | ★A가 아키텍처 제공 |
| 물류/배송 | 배송 스텝 | **이미지매칭(SURF) 물류관리 시스템**으로 구체화(p47~49) | ★A가 신규 상세 |
| 데이터검증 | (덱에 약함) | **원본PDF↔미리보기 이미지매칭 재검증 단계 별도**(p11,38) | ★A 신규 |

→ **문서 A는 20단계 덱의 "후반부(생산·배송)"와 "견적 엔진"을 실제 서브시스템 플로우차트로 해부한 판**이다.
프린틀리에 없던 **후가공 14종 처리 세부·견적 산식·조판/파일변환 장비배선·물류 이미지매칭**이 새로 확보됨.

## 자동화 아키텍처 (모듈·데이터 흐름)

### 데이터 계약
- **주문내용 = XML로 DB 저장**(A p4). 작업파일 = PDF, 파일명 규칙 `yyyyMMdd_주문번호_상세번호.pdf`(A p4,10).
- 각 처리단계가 결과파일·상태정보를 **폴더 분기 + DB Update**로 남김(원본백업/리포트/성공/실패 폴더, A p14).
- 문서 B: **PDF 단일 진입점** → "RED DATA ANALYSIS CENTER" → `.DXF/.JDF/.CUT/.ZCC/.HPGL/.PDF/.TIFF`로 분배
  → 모든 장비로 toss("WE CAN TOSS PDF TO ANY OF OUR MACHINES", B p9).

### 6대 서브시스템 (A)
1. **Preflight(유효성검사, p14~15)**: PDF 이동→임시폴더 복사→검사·수정→[원본백업/리포트/성공/실패]폴더 분기
   →XML Deserialize→성공여부 판정→Status/오류 DB Update. 검사항목 7종(CMYK·여백·재단·앞뒷면·후가공레이어수·폰트크기·기타).
2. **Preprocess(전처리, p16~34)**: 레이어 有→CMYK/후가공 레이어 분리, 레이어 無(Raster)→CMYK영역+Spot Color 분리.
   - 공통 스텝: 레이어존재확인→타 레이어삭제→**면을 선으로**→**중복선 제거**(실패=에러폴더)→견적용 데이터분석→레이어 단일화→Spot Color명 영문변환→썸네일.
   - **14개 후가공 레이어 처리(각 플로우차트)**: CMYK / Cut(커팅) / Crease(오시) / DashRule(미싱) / KissCut(반칼) /
     Marking(마킹) / Fold(접지) / GoldFoil(금박) / SilverFoil(은박) / Brail(점자) / Punch(타공) / Emboss(형압) /
     White(흰색별색) / Scodix(스코딕스). (근거 p19~34)
   - 특이 처리: 금박/은박/화이트/형압 = **CMYK 100%**로 단일화. 점자(Brail) = 모든 오브젝트 **1.5mm Bleed**+Clear PDF 분리.
     스코딕스 = Vector→Grayscale→단일채널→**Dithering**(점 분포)→임시파일 정리(p34).
3. **자동 견적(p35~37)**: 주문정보 로드→기본인쇄비 계산→후가공견적 데이터 로드→총액 계산→DB.
4. **데이터 검증(p38~39)**: 원본PDF를 이미지화→Preflight 썸네일과 **이미지매칭 비교**→일치=승인, 불일치=원인분석
   (내부오류=수정 후 재처리 / 고객오류=재업로드 요청).
5. **자동 조판(p40~46)**: 정형(사각형)=Object Locator / 비정형(원형·캐릭터)=Nesting Locator →
   PDF Generator(돔보·바코드·재단선·ColorBar·생산공정정보 생성, 다중후가공 병합·Flatten) →
   File Converter(포맷변환) → **생산공정 수립+JDF 생성**(장비별 소요시간 예측·최적 장비플로우 추천).
6. **이미지매칭 물류관리(p47~49)**: 완성물 스캔→DB 썸네일 매칭→회원·주문·배송정보 확인→배송.

### 조판 장비 배선 (A p43,45)
- **Object Locator 산하**: AeroCut / Zund / DaeHo / SmartStacker / RD / Etc Locator.
- **File Converter 매핑**: PDF2TIFF→Scodix, PDF2DXF→Hicon, PDF2SCRIPT→Kongbug, PDF2INI→AeroCut,
  PDF2ZCC/PDF2CUT→Zund·SmartStacker, PDF2JDF→대호, PDF2GPGL→Graphtec.

## 결정론 엔진 / 방법 (사람 개입 최소화 지점)

- **자동견적 산식(★핵심, A p7,35,36)**:
  - 기본 인쇄비 = f(용지 종류, 종이 두께 g수, 인쇄도수, 재단사이즈, 수량, 건수) — 미리 DB에 단가 저장.
  - 후가공비 = 전처리에서 **면을 선으로 변환→중복선 제거→생성된 벡터라인의 길이+복잡도** 계산 × 후가공 단가.
  - **스코딕스만 예외** = 벡터 길이가 아니라 **점(dot)의 분포도**로 산출.
  - 총액 = 기본인쇄비 + 후가공비 (합산 후 DB 저장). → 후가공을 크기가 아닌 **실제 가공선 길이**로 과금 = 중복과금 제거(A p6 "기존 견적은 전체크기로 과금해 불필요비용 청구").
- **레이어 자동분리**: 고객은 레이어+Spot Color만 지정, 나머지 자동(A p18 "고객은 단순히 레이어와 Spot color만 지정").
- **자동수정**: RGB→CMYK, 0.5pt 미만 선, 재단사이즈 불일치 크롭 등 예측가능 오류를 프로그램이 자동 제안·수정(A p12).
- **이미지매칭(2회)**: ① 데이터검증(원본↔미리보기) ② 물류(스캔↔썸네일). **SURF(Speeded Up Robust Features)**
  알고리즘 사용 — 현장 조명·회전에 강함(A p49). → 잡티켓/작업지시서 없이 실물만 스캔해 주문·회원·배송 정보 복원.
- **JDF 생성 + 장비 소요시간 예측**: 공정별 장비 소요시간을 예측해 유휴·중복처리 가능 장비 추천(A p37,43,46).
  머신러닝 학습 배치정보 기반 최적배치는 "추후"(A p43 — 미구현 계획).
- **사람 개입 잔존 지점**: 오류 승인(고객, p12), 결제(p10), 고객오류 재업로드(p39), 물류 내부오류 재작업/수동검색(p47).

## ★프린틀리 시사 (온톨로지·북극성 관점)

1. **후가공 공정 축이 뼈대다.** 견적·프리플라이트·조판·파일변환·물류가 모두 **14종 후가공 레이어**를 축으로
   자동화된다. 프린틀리 온톨로지의 사양·장비·파일포맷 노드는 **후가공 공정(Cut/Crease/Fold/Foil/Emboss/
   Scodix/White/Brail/Punch/KissCut/DashRule/Marking + CMYK)**을 1급 개념으로 모델링해야 "고객이 원하는
   인쇄물"을 값 생성 없이 조립할 수 있다.
2. **견적은 "실제 가공선 길이"로 결정된다** = 온톨로지에 후가공별 **과금 단위(벡터라인 길이 / 스코딕스=점 분포)**를
   속성으로 담아야 벤더 엔진 라우팅 시 견적 근거가 선다. 고정가/면적가 모델만으로는 RED식 후가공 견적을 흡수 못함.
3. **PDF+XML 데이터 계약이 파이프라인을 잇는다.** 주문=XML, 파일=PDF(레이어=후가공 시맨틱). 프린틀리가
   벤더 엔진을 브로커링하려면 이 **레이어명↔후가공 시맨틱 매핑**(한글 레이어명→영문 후가공 코드)을 온톨로지가 표준화해야 한다.
4. **파일포맷=논리/가상 2층 모델의 실증.** File Converter(PDF→TIFF/DXF/CUT/ZCC/JDF/HPGL/GPGL)+장비배선이
   프린틀리 특허 "장비 가상화(C3)"·"파일포맷 논리/가상 2층"의 실물 근거. 온톨로지가 **(후가공→포맷→장비)** 삼각 매핑을
   담으면 다중벤더 라우팅의 결정론 근거가 된다.
5. **이미지매칭(SURF)이 "데이터 없는 완성물"을 주문에 되잇는다** = 물류·재주문 온톨로지 노드(완성물↔주문↔회원)의
   연결키가 이미지라는 점. 프린틀리 AI 에이전트의 "재주문/추적" 시나리오에 흡수 후보.
6. **회사 DNA = 의도 경청** → 프린틀리 대화형 에이전트의 "말하지 않은 것까지 파악"이 RED 철학과 정렬(마케팅 근거로도 활용 가능).

## GAP (불확실·문서 미기재)

- **G1**: (주)천혜명 ↔ RED(레드프린팅/베러웨이) 관계 불명. 천혜명=자동화 특허 개발사로 추정되나 문서 A만으로 단정 불가.
- **G2**: 문서 A는 2015년 **기획서**(설계 의도). 실제 라이브 구현 정도·현행 여부는 이 문서로 확인 불가(라이브 역공학=§11 rpmeta 별도).
- **G3**: 견적 단가 테이블(용지·후가공 실단가)은 문서에 없음 — "미리 DB에 저장"만 언급. 구체 숫자 GAP.
- **G4**: 머신러닝 기반 최적배치·소요시간 예측은 "추후/학습된 배치정보 기반"으로 표기 = 문서 A 시점 미구현 계획일 가능성(A p43).
- **G5**: 16단계에 "포장" 단계 명시 없음(배송으로 직결). WebToProduct 20단계의 포장·검수 세분과 대조 필요.
- **G6**: XML 스키마·JDF 상세 필드·이미지매칭 임계값 등 구현 파라미터는 다이어그램 수준, 정밀 스펙 아님.
