# 후니 제약(Constraint) 레이어 — 개발자 전달안 (초안)

> Huni-Constraint-Rules 하네스(§31) Phase 1 산출.
> 목적: 비판이 아니라 "개발자가 바로 착수할 수 있는, 우선순위 있는 개선 목록".
> 근거: 내부 실측(파일:라인) + 외부 CPQ 베스트프랙티스(→ `cpq-best-practices.md`).
> 시간 추정 없음 — 우선순위 라벨(High/Med/Low)만. 쉬운 한국어로 씀(실무진도 읽는 문서).
> 상태: **초안** — hcr-gate-validator(CR7) 근거 실재 검증 통과 후 확정본으로 승격.

## 0. 현재 제약 레이어가 어떻게 돌아가는가 (한눈에)

한 문장 요약: **관리자가 폼빌더로 규칙을 만들면 JSONLogic으로 저장되고, 그 규칙은 "미리보기 버튼"과 "SKU 저장 시 경고"에서만 평가된다. 정작 가격계산·주문에는 규칙이 전혀 반영되지 않는다.**

- **저장 위치** — `t_prd_product_constraints` (복합PK `prd_cd`+`rule_cd`, 컬럼 `rule_typ_cd`·`logic`(JSONB)·`err_msg`·`disp_seq`·`use_yn`·`del_yn`). 저장 로직 = `views.py:2525-2538`.
- **규칙 유형 3종** — `.01` 호환 / `.02` 금지 / `.03` 필수동반. JSONLogic 템플릿 = `views.py:120-130`(.01/.03 = or-implication, .02 = not-and).
- **평가(병합)** — 활성 규칙(`use_yn='Y'` `del_yn='N'`)을 `{"and":[...]}`로 즉석 병합(`cfg_utils.py:23-53`) 후 panzi-json-logic으로 평가(`cfg_utils.py:61-72`).
- **손님 선택 → 데이터 계약(var 키)** — `VAR_KEY_MAP`(`views.py:52-60`): `siz_cd`·`plt_siz_cd`·`mat_cd__usage_cd`(자재 결합키)·`proc_cd`·`bdl_qty`·`opt_id`·`sub_prd_cd`, 옵션은 `sel_opt_grps`/`sel_opts` 배열(`views.py:67-70`).
- **폼빌더 3경로** — ① 복수조건 빌더(`conditions_json`, `views.py:2465-2473`) ② 고급 직접 JSONLogic 입력(`raw_logic`, `views.py:2454-2464`) ③ 하위호환 단일조건(`views.py:2474-2493`).
- **강제(적용) 지점 2곳뿐** — ⓐ SKU 템플릿 저장 콜백(`views.py:3058-3080`, 경고만·차단 안 함) ⓑ 검증 미리보기 Ajax(`views.py:2798-2846`, 관리자가 버튼 눌러야 함).

## 1. 잘된 점 (유지·계승할 것)

- **JSONLogic 표준 채택** — 규칙을 자체 DSL이 아니라 널리 쓰이는 JSONLogic로 저장(`views.py:120-130`, `cfg_utils.py:67`). 클라이언트/서버 양쪽에서 같은 규칙을 평가할 수 있는 기반. 폼빌더 JS에도 동일한 `VAR_KEY_MAP`·절 생성 로직이 미러링됨(`constraint_builder.html:597-668`) → 서버/클라 정합.
- **폼빌더 3경로 설계** — 비전문가용 드롭다운 빌더 + 개발자용 고급 직접입력의 2층 구조는 업계 베스트프랙티스(no-code 빌더 + 코드 열람/미세조정)와 정합(`cpq-best-practices.md §3-A`).
- **복수조건 빌더(AND/OR 그룹)** — 그룹·AND/OR 배지로 다중 조건을 시각적으로 조립(`constraint_builder.html:461-559`, `views.py:133-193`). 업계의 "조건 가지(branch)" 패턴과 정합(§3-B).
- **검증 미리보기(/validate/ Ajax)** — 저장 없이 샘플 조합을 즉석 테스트, 막힌 규칙명까지 반환(`views.py:2798-2846`, `blocked_rule` 포함). "영향 미리보기"의 씨앗이 이미 있음(§5-B).
- **복합PK + 논리삭제** — `prd_cd`+`rule_cd` 자연키, `del_yn='Y'` 논리삭제(`cfg_utils.py:80-98`, `views.py:2410-2416`). 물리 삭제 안 함 → 이력 보존에 유리.
- **자동 채번** — `rule_cd`(RULE_NNN)·`disp_seq` max+1 자동채번(`views.py:2496-2523`)으로 관리자 입력 부담 감소.
- **역파싱 시도 + 정직한 폴백** — 저장된 JSONLogic을 빌더로 되돌리려 시도하고(`views.py:200+`), 실패하면 "빌더로 역변환 불가 → 고급 JSON 창에서 수정하세요"라고 정직하게 안내(`constraint_builder.html:265-269`). 못하는 걸 숨기지 않음.

## 2. 개선 · 보완 · 강화 · 수정 (항목별: 현상 → 근거 → 제안 → 우선순위)

### C-1. 가격계산·시뮬레이터가 제약을 전혀 안 본다
- **현상** — 손님이 "금지된 조합"을 골라도 가격이 그대로(0원도 아님) 계산되어, 규칙이 있으나 마나.
- **근거** — `pricing.py`·`price_views.py` 전체에 constraint 참조 0건(grep 결과 매칭 없음). `evaluate_price`/`simulate` 어디서도 `evaluate_constraints`를 호출하지 않음.
- **제안** — 가격계산의 진입점(또는 시뮬레이터 응답)에서 `evaluate_constraints(prd_cd, data)`를 호출해, 위반 조합이면 가격과 함께 "이 조합은 제약 위반" 플래그(+`blocked_rule`)를 돌려주도록 계약 확장. 단, 강제(차단)의 최종 권위는 주문 단계(§4)에 두고, 여기서는 신호만.
- **우선순위** — **High**

### C-2. 진짜 강제 지점이 없다 (경고뿐)
- **현상** — 규칙을 어겨도 저장·진행이 막히지 않는다. SKU 저장 콜백은 위반 시 `warn=1`과 세션 메시지만 남기고 저장은 그대로 통과("저장 결과 불변").
- **근거** — `views.py:3058-3062` 주석 "위반 시 warn=1 추가 + 세션에 경고 메시지 저장 ... 저장 결과 불변". 위젯/카트/주문 경로에는 validate 호출 자체가 없음.
- **제안** — §6(위젯)·§24(Shopby 주문)에 validate 강제 지점을 배치(아래 4부 로드맵). 관리자 SKU 저장은 "경고" 유지가 맞지만(운영 편의), 손님 주문 경로는 "차단"이어야 함.
- **우선순위** — **High**

### C-3. 깨진 규칙 처리가 두 경로에서 서로 다르다 (하나는 500, 하나는 조용히 통과)
- **현상** — logic이 잘못됐거나 데이터 키가 안 맞아 평가가 예외를 던질 때, 경로마다 결과가 다르다.
- **근거** — `cfg_utils.py:61-72` `evaluate_constraints`는 `jsonLogic(...)`을 try 없이 호출 → 예외 시 **500**. 반면 `validate_preview`는 `except Exception: result = True`(`views.py:2836-2837`) → 깨진 규칙을 **조용히 통과**시킴. 특히 "금지" 규칙이 깨지면 막아야 할 조합이 허용됨(위험).
- **제안** — 깨진 규칙 처리 정책을 하나로 통일. 권고: 예외를 삼키지 말고 (a) 로그 + 관리자 알림, (b) 안전 기본값은 규칙 유형에 따라 결정("금지"가 평가 불능이면 통과가 아니라 보류/차단이 안전). `evaluate_constraints`에도 방어 로직 추가하되, 예외를 은폐하지 말고 구조화된 결과로 반환.
- **우선순위** — **High**

### C-4. logic 안의 코드가 실재하는지 검증하지 않는다 (규칙 부패)
- **현상** — 규칙 저장 시 logic에 들어간 `siz_cd`·`mat_cd__usage_cd` 등의 값이 그 상품에 실제로 등록된 차원행인지 확인하지 않는다. 나중에 자재가 은퇴하면 규칙은 존재하지 않는 코드를 가리키며 "부패"한다.
- **근거** — 저장 경로(`views.py:2495-2538`)는 logic을 JSONB로 그대로 저장. FK/실재성 검증 없음. `dim_choices`(`views.py:2307-2378`)는 후보를 주지만, 고급 직접입력(`raw_logic`)은 아무 값이나 통과.
- **제안** — 저장 시 logic을 순회해 var 키·값이 현재 상품의 차원행(또는 옵션)에 실재하는지 검사, 없으면 경고(하드 차단은 선택). 별도로 "부패 규칙 스캐너" 배치(전 상품 규칙의 코드 실재성 점검)를 두면 자재 은퇴 시 조용한 부패를 잡는다.
- **우선순위** — **Med**

### C-5. 수동 규칙 드리프트 — 신규 자재/사이즈 추가 시 규칙이 안 따라온다
- **현상** — 규칙을 사람이 하나씩 손으로 쓰므로, 새 자재·사이즈가 들어오면 관련 호환/금지 규칙을 사람이 다시 챙겨야 한다.
- **근거** — 규칙은 전부 수동 입력(폼빌더 3경로 모두 관리자 입력). 데이터에서 유도되는 경로 없음.
- **제안** — 단가행(component_prices)·차원행이 곧 "실재 조합"의 원천이므로(`cpq-best-practices.md §7`), 단가행 격자에서 호환 규칙을 자동 유도(또는 관리자에게 "이 조합은 단가행이 없는데 규칙도 없음" 제안)하는 보조 도구. 장기적으로 규칙기반 → 데이터기반 전환의 발판.
- **우선순위** — **Med**

### C-6. 규칙 충돌·중복·죽은 규칙을 감지하지 않는다
- **현상** — 서로 모순되는 규칙, 완전히 겹치는 중복, 어떤 조합으로도 발동 안 되는 죽은 규칙이 쌓여도 알 수 없다.
- **근거** — 저장 경로에 규칙 간 관계 분석 없음(`views.py:2495-2538`은 단일 규칙만 처리). 목록 화면(`constraint_builder.html:183-256`)도 나열만.
- **제안** — 저장/조회 시 배치로 ① 모순(같은 조합을 하나는 금지·하나는 필수) ② 중복(동일 logic) ③ 죽은 규칙(실재 차원행 조합으로 절대 발동 안 됨)을 스캔해 관리자에게 배지로 경고(`cpq-best-practices.md §4-B`).
- **우선순위** — **Med**

### C-7. 감사추적·규칙 소유권 없음
- **현상** — 누가·언제·왜 규칙을 바꿨는지 남지 않는다. `use_yn` 토글·삭제·수정에 이력이 없다.
- **근거** — `t_prd_product_constraints`에 변경자·변경사유·이전값 컬럼 없음. 저장은 `update_or_create`로 덮어씀(`views.py:2526`).
- **제안** — 규칙 변경 이력 테이블(또는 감사 컬럼: `upd_by`·`chg_rsn`·이전 logic 스냅샷). 업계 원리상 감사추적은 문제 조사 시간을 크게 줄인다(`cpq-best-practices.md §1-B`).
- **우선순위** — **Low**

### C-8. impact(사용처) 뷰가 제약 규칙을 차원행 단위로 못 본다
- **현상** — "이 자재를 지우면 어떤 규칙이 깨지나?"를 차원행 단위로 볼 수 없다.
- **근거** — `v_cfg_ref_impact`의 CONSTRAINT 레그는 `ref_dim_cd=NULL`이라 차원행 단위 매칭 불가(`views.py:2683`, `views.py:2758` 주석 §4-B 한계). 상품 단위 총계만 안내(`views.py:2768-2776`).
- **제안** — 규칙 logic을 파싱해 참조하는 차원행을 추출·인덱싱(뷰 또는 보조 테이블)하면, 차원행 삭제 경고에 "이 값을 쓰는 규칙 N건"을 표시할 수 있다. C-4(실재성 검증)와 같은 파싱 인프라를 공유.
- **우선순위** — **Low**

## 3. 시각화 보완 · 강화

### V-1. 호환성 매트릭스 히트맵 — **High**
- 상품별 "자재 × 사이즈"(또는 임의 두 차원) 격자를 초록(허용)/빨강(금지)/회색(규칙 없음)으로 렌더링. 관리자가 규칙 커버리지의 구멍을 한눈에 본다.
- 근거: 업계는 다차원 관계를 매트릭스로 보여주는 것이 표준(`cpq-best-practices.md §5-A`). 데이터 원천 = 규칙 logic + 차원행(§29 대시보드가 이미 읽는 라이브 스냅샷 재사용).

### V-2. 자연어 규칙 요약 렌더 — **Med**
- JSONLogic을 사람이 읽는 문장으로 되돌려 목록에 표시("A4 + 50매는 함께 선택 불가"). 현재 목록은 규칙명 + JSON 원문만(`constraint_builder.html:209-211`).
- 근거: 자연어 요약은 비전문가가 규칙을 훑을 때 실수를 잡음(`cpq-best-practices.md §3-C`). RULE_TYPE_TEMPLATES(`views.py:120-130`)가 정형이므로 역방향 문장 생성이 어렵지 않음(비정형 raw_logic만 예외 처리).

### V-3. 영향 미리보기 ("이 규칙이 막는 조합 N개") — **Med**
- 규칙 저장 전에 "현재 등록된 조합 중 M개가 막힘/요구됨"을 계산해 보여줌. 현재는 샘플 1건 수동 테스트만(`views.py:2798-2846`).
- 근거: 과잉·과소 제약을 저장 전에 잡는 업계 패턴(`cpq-best-practices.md §5-B`). 이미 있는 validate 로직을 차원행 전조합에 배치로 돌리면 됨.

### V-4. §29 대시보드 Cytoscape 연계 — **Med**
- §29 상품 준비도 대시보드(webadmin product_viewer + Cytoscape 그래프)에 "제약 규칙" 레이어를 얹어, 상품 노드에 규칙 배지·충돌 경고를 표시. 규칙이 참조하는 차원행을 간선으로 연결하면 부패(끊긴 간선)가 시각적으로 드러남.
- 근거: 대시보드가 이미 라이브 스냅샷·실항목 노드를 그림(§29 메모리). 제약 레이어는 그 위 오버레이로 붙일 수 있음. C-4/C-8의 파싱 인프라를 공유.

## 4. 강제(validate) 지점 로드맵

**원칙** — 클라이언트(위젯)는 UX용 즉시 피드백, **서버가 최종 권위**. 주문 확정 직전 서버가 반드시 재검증(`cpq-best-practices.md §6-B`). 표준 흐름 = 담기 → 구성 → 가격 → 검증 → 결제(§6-A).

### R-1. 위젯 실시간 필터링/경고 (§6 하네스) — **High**
- 손님이 옵션을 고를 때 위젯이 유효하지 않은 조합을 즉시 걸러 안내. 위젯은 서버/클라 공용 JSONLogic(`VAR_KEY_MAP` 이미 미러링됨, `constraint_builder.html:597-668`)을 그대로 쓸 수 있음.
- 데이터 계약: 손님 선택을 `siz_cd`·`mat_cd__usage_cd`·`sel_opts` 등 var 키로 실어야 규칙이 평가됨(`views.py:66` 계약). 위젯 어댑터가 이 shape로 변환해야 함.
- 성격: UX 유도(강제 아님).

### R-2. 카트 담기 시 서버 검증 (§24 Shopby) — **High**
- 카트에 담는 순간 서버가 `evaluate_constraints`(또는 validate 엔드포인트)를 호출해 위반 조합을 차단/경고. 위젯을 우회한 조합도 여기서 걸림.
- 근거: 업계 표준 add → configure → **validate** → checkout(`cpq-best-practices.md §6-C`).

### R-3. 주문 확정 직전 최종 재검증 (§24 Shopby) — **High**
- 결제/주문 확정 직전 서버가 필수 검증을 다시 수행(Checkout API 패턴, `cpq-best-practices.md §6-A`). 여기서 위반이면 하드 차단. 이 지점이 "진짜 강제"의 최종 게이트.

### R-4. 가격계산 응답에 제약 신호 동반 (C-1 연계) — **Med**
- 견적/시뮬레이터 응답에 "이 조합 제약 위반 + blocked_rule"을 함께 실어, UI가 가격과 함께 경고를 표시. 강제는 아니고 신호(강제는 R-2/R-3).

### R-5. 관리자 SKU 저장 경고 유지 — **Low (현행 유지)**
- 현재 SKU 저장 콜백의 "경고만·차단 안 함"(`views.py:3058-3080`)은 운영 편의상 유지가 맞음. 단 C-3(깨진 규칙 처리 통일) 적용 대상.
