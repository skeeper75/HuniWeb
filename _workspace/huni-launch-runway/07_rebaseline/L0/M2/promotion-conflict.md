## 0. 전제 — 무엇이 확정되어 있는가

샵바이는 외부에서 계산한 금액을 주문에 실을 수 없다. 그래서 **판매가 10원짜리 상품을 「총액 ÷ 10」 개수만큼 주문**해 결제액을 표현한다. 코드 원문:

```ts
// src/lib/api/widget-order.ts:20-34 (verbatim)
/**
 * shopby 금액 적재 단위(원). shopby 는 외부 금액 지정을 받지 못하므로
 * "판매가 10원 상품 × 수량(=금액÷10)" 으로 결제 금액을 표현한다(후니 §11 확정).
 * 후니 가격엔진이 청구액 1원 단위를 절삭 → 항상 10원 배수라 정확히 표현된다.
 * @see https://huni-admin.printly.co.kr/sdk/guide/#sbi
 */
export const SHOPBY_AMOUNT_UNIT = 10;

/**
 * 위젯 총액(원) → shopby 주문 수량(orderCnt). 결제액 = 단가(10원) × orderCnt = 총액.
 * 총액은 10원 배수라 반올림은 정확. 최소 1(0원 주문 방지).
 */
export function amountToOrderCnt(total: number): number {
  const t = Number(total) || 0;
  return Math.max(1, Math.round(t / SHOPBY_AMOUNT_UNIT));
}
```

실제 호출부: `src/components/product/huni-widget.tsx:265` (`orderCnt: amountToOrderCnt(total)`), 재견적 경로는 `src/lib/api/requote.ts:84`.

| Q4 | **1회 최대구매수량 제한** | **충돌** | 그 값이 곧 **결제 금액 상한**이 된다 | 100으로 두면 1,000원 초과 주문이 전부 막힘 | **주문 실패** | A `sale-info.mdx` 「⑭ 최대구매수량 … 회원 아이디 1인 / 1회 / 기간제한」 · B `:1103-1104` |
| Q5 | **재고 수량 = 결제 한도** | **충돌(현재 값 기준으로 실재하는 상한)** | 「샵바이는 주문이 등록되는 시점에 주문 수량만큼 재고를 차감합니다. 수량이 곧 금액이므로, **재고 × 10원이 그 상품으로 받을 수 있는 누적 결제금액의 한도**가 됩니다」. 재고 관리를 끄는 설정은 샵바이에 존재하지 않는다 | 현재 라이브 재고 9,999(C등급 주장) → **상품당 누적 99,990원**. 85,000원 주문 1건이면 남은 여유가 14,990원 | **주문 실패(품절)** | B `sdk-guide-live-20260902.txt:1070-1085` |
| Q6 | **단건 주문 상한** | **미확인 — 다만 정황이 매우 강함** | 재고 9,999 < 필요 수량 19,800 인 주문(= 198,000원, **가이드 자신의 예시**)이 통과할 수 있는지가 문서에 없다. 「재고가 1개 이상이면 정상」이라는 문장은 상품 판매 가능 여부를 말하는 것이고, `orderCnt > 재고` 요청의 거절 여부는 별개 | 성립한다면 **단건 상한 = 재고 × 10원 = 99,990원**. 운영정책의 「10만원 이상 무료배송」 기준선이 **현재 재고로는 도달 불가능**해진다 | **주문 실패** | B `:1045-1046`(198,000원 → 수량 19,800 예시) vs B `:1085`(현재 재고 9,999) — 두 값의 충돌. §5-④ 라이브 확인 필요 |
| Q7 | **사은품 지급조건** | **무해** | 지급조건이 금액조건뿐. 「금액기준 : 판매가 − 즉시할인금액 ± 옵션가 − 추가할인금액 − 상품쿠폰 할인금액」 | — | — | A `promotion/free-gift/condition/add.mdx` 「③ 금액조건」 |

## 2. 워크드 예시 — 총액 85,000원 (= 판매가 10원 × orderCnt 8,500)

`amountToOrderCnt(85000) = max(1, round(85000/10)) = 8500` (`widget-order.ts:32-34`).
가이드 자체 예시와 같은 형태다: 15,000원 → 수량 1,500 / 198,000원 → 수량 19,800 (`sdk-guide-live-20260902.txt:1045-1046`).

| 시나리오 | 샵바이 계산 | 고객이 실제로 내는 돈 | 내야 하는 돈 | 차이 |
|---|---|---|---|---|
| 기본(프로모션 없음, 배송비 FREE) | 10 × 8,500 | **85,000** | 85,000 | 0 |
| **정액 3,000원 상품쿠폰** | (10 × 8,500) − 3,000 | **82,000** | 82,000 | **0 (정상)** |
| ↑ 만약 개당 차감이었다면 | (10 − 3,000) × 8,500 | 음수 → 0 또는 오류 | 82,000 | **−82,000 / 주문 실패** ← 샵바이 문서가 명시적으로 부정한 경로 |
| ↑ 만약 할인액이 수량배였다면 | 3,000 × 8,500 = 25,500,000 할인 | 0 | 82,000 | **−82,000** ← 동일하게 부정됨 |
| 정률 10% 상품쿠폰 | 85,000 × 0.9 | **76,500** | 76,500 | 0 |
| 주문쿠폰 정액 5,000원 | 85,000 − 5,000 | **80,000** | 80,000 | 0 |
| 적립금 10,000원 사용 | 85,000 − 10,000 | **75,000** | 75,000 | 0 |
| 적립금 적립 1% | 적립 850원 | — | 850원 | 0 |
| 배송비 `CONDITIONAL` 10만원 미만 3,000원 | 85,000 + 3,000 | **88,000** | 88,000 | 0 |
| **배송비 `QUANTITY_PROPOSITIONAL_FEE` 2개당 3,000원** | 85,000 + `ceil(8500/2)`×3,000 | **12,835,000** | 88,000 | **+12,747,000 (과청구)** |
| **즉시할인 정액 5원** | (10 − 5) × 8,500 | **42,500** | 85,000 | **−42,500 (과소청구)** |
| **추가할인 「500개 이상 500원」, 개당 적용 가정** | (10 − 500) × 8,500 | 음수 → 0/오류 | 85,000 | **−85,000 또는 주문 실패** (배분 미확인 = Q3) |
| **1회 최대구매수량 100** | 8,500 > 100 | **주문 거절** | 85,000 | 매출 0 |
| **재고 9,999 상태에서 198,000원 주문** | 필요 수량 19,800 > 재고 9,999 | **주문 거절(추정 — Q6 미확인)** | 198,000 | 매출 0 |

### 2.1 표시와 결제가 조용히 어긋나는 경로 (검출 난도 최상)

몰 화면의 라인 금액은 **위젯이 계산한 총액**을 권위로 그린다:

```ts
// src/lib/api/widget-order.ts:132-144 (widgetPricing)
// 위젯이 있으면 위젯 총액을 권위로, 없으면 shopby 계산가를 그대로 쓴다.
```

반면 실제 결제액은 샵바이가 `판매가 × orderCnt` 로 계산한다. **즉시할인(Q1)·추가할인(Q2)이 켜지면 화면은 85,000원인데 결제는 42,500원**이 되고, 화면만 봐서는 절대 알 수 없다. 유일한 교차 검증 지점은 주문서 `POST /order-sheets/{no}/calculate` 의 `paymentInfo.paymentAmt` 이며, 몰은 이 값을 받아 표시용으로만 쓴다(`use-order-sheet.ts:246-252`). **위젯 총액 ≠ `paymentAmt` 인 경우를 막는 가드는 현재 코드에 없다.**

## 5. 최종 판정

### 판정: **조건부 충돌**

「10원 상품 × N개」 구조는 **쿠폰·적립금과는 충돌하지 않는다**(문서로 확정). **배송비와는 유형에 따라 충돌하며, 충돌하는 유형은 금액이 수천 배 단위로 틀어진다.** 그리고 **배송비 밖에도 수량 기반 장치가 넷 더 있다**(즉시할인 · 구매수량별 추가할인 · 1회 최대구매수량 · 재고).

축별 결론:

| 축 | 판정 | 근거 등급 |
|---|---|---|
| **쿠폰** | **충돌하지 않는다** — 정액·정률·상품·주문·최소기준금액 전부 금액 기준 | 핵심 문장은 **B등급**(SDK 가이드가 인용한 샵바이 원문). 로컬 `docs/shopby/` 에서 그 원문 페이지를 찾지 못했으므로 **A등급 직접 확인이 남아 있다** |
| **적립금** | **충돌하지 않는다** — 적립률(%)·사용액(원) 모두 금액 기준 | 적립률 %는 **A등급**(`sale-info.mdx` ⑧). 적립 상한/최소 사용단위/최대 사용비율은 **미확인**(M5). 현재 미사용이라는 것은 **C등급 주장**(M6) |
| **배송비** | **조건부 충돌** — `FREE`/`CONDITIONAL`/`FIXED_FEE`/`PRICE_FEE` 안전, `QUANTITY_PROPOSITIONAL_FEE`/`QUANTITY_FEE`/`WEIGHT_FEE` 치명 | 유형별 동작은 **A등급**(매뉴얼 + OpenAPI enum). 「현재 FREE 이고 금지 유형은 전부 꺼져 있다」는 **C등급 주장** |
| **배송비 이외 수량 장치** | **충돌** — Q1·Q2·Q4·Q5 | Q1·Q2·Q4는 **A등급**. Q2는 SDK 가이드 §11 금지 목록에 **없는 항목**으로, 이 조사의 신규 발견 |
| **후니 가격엔진 이중청구** | **없다** | **실측**(catalog 앱 배송비 식별자 0건) |

### 5.1 라이브에서 확인해야 하는 것 (여기서는 수행하지 않음)

「켤 수 있고 켜면 터진다」와 「지금 켜져 있다」는 다른 명제다. 아래는 전부 후자 — **후니팀의 주장을 재확인하는 절차**다.

① **샵바이 쿠폰 정액 할인 배분 규칙의 A등급 원문**
   - 어디: 샵바이 도움말(NHN Commerce GitBook) 「할인쿠폰 관리 > 쿠폰등록 > 금액설정」 또는 샵바이 FAQ 중 정액 쿠폰 배분을 설명한 페이지
   - 무엇: 「상품별 총 상품금액을 기준으로 … 수량별로 할인되지 않음」 문장의 원 위치
   - 왜: 현재 이 문장은 SDK 가이드가 인용한 형태로만 존재한다(로컬 `docs/shopby/` 전수 grep에서 미발견)
   - 대안 검증: 테스트몰에서 판매가 10원 상품 × 100개 주문서에 정액 3,000원 상품쿠폰을 적용해 `POST /order-sheets/{no}/coupons/calculate` 응답의 `productCouponDiscountAmt` 가 3,000 인지 확인

② **배송비 템플릿 유형 전수**
   - 화면: 상품관리 > **배송비 관리 > 배송비 템플릿관리**
   - 확인: 등록된 **모든** 템플릿의 「배송비유형」이 `무료 / 조건부 무료 / 유료(고정) / 금액별 차등` 넷 안에 있는지. 하나라도 `수량비례`·`수량별 차등`·`중량별 차등`이면 즉시 중단
   - 병행: 각 상품의 **배송정보 > 배송 템플릿** 이 그 안전 템플릿을 쓰는지(226개 전수)

③ **상품 중량 입력값**
   - 화면: 상품관리 > 상품 조회 > (상품) > 배송정보
   - 확인: 중량 필드가 **비어 있는지**. 지금 중량 배송비를 안 쓰더라도 값이 들어 있으면 나중에 켜는 순간 D3가 터진다

④ **재고와 단건 주문 상한** ★ 가장 시급
   - 화면: 상품관리 > 상품 조회 > 재고
   - 확인 1: 현재 재고가 정말 9,999 인지(= 상품당 99,990원)
   - 확인 2: **재고보다 큰 수량의 주문이 거절되는지** — 테스트 상품(판매중지 후 원복)으로 `orderCnt > 재고` 주문서 생성을 시도해 응답 확인. 이것이 Q6의 유일한 결론 방법
   - 확인 3: 후니 서버의 재고 자동 보충 주기와 기준값. 「10만원 이상 무료배송」 정책을 쓰려면 재고가 최소 수만 단위여야 한다

⑤ **즉시할인 / 추가할인 프로모션**
   - 화면 A: 상품관리 > 상품 조회 > (상품) > 판매정보 > **즉시할인** — 226개 전부 미설정인지
   - 화면 B: 프로모션 > **추가할인 관리** — 등록된 추가할인이 0건인지. 특히 「구매 수량별」 설정이 있는지(Q2)
   - 화면 C: 상품 판매정보 > **⑩ 프로모션** 항목을 「불가능」으로 두면 상품쿠폰·추가할인·사은품이 통째로 막힌다. 현재 어떤 값인지

⑥ **1회 최대구매수량**
   - 화면: 상품 판매정보 > **⑭ 최대구매수량**
   - 확인: 「제한 없음」인지. 값이 있으면 그 값 × 10원이 결제 상한

⑦ **적립금 설정**
   - 화면: 운영관리 > **적립금 설정 관리 > 적립금 지급 설정 / 사용 설정**
   - 확인: 기본 적립률이 %인지(정액 지급 항목이 있는지), 적립 상한·최소 사용단위·최대 사용비율(M5)
   - 병행: 「쿠폰 사용 시 적립금 적립 제한」 설정 여부 — 켜져 있으면 쿠폰 사용 주문에 적립이 0이 된다(A `addform.mdx` 상품적용 쿠폰 ⑤ 혜택제한 Callout)

| **M2** | **주기 감사 스크립트** — 배송비 템플릿 유형 / 상품 중량 / 즉시할인 / 추가할인 / 최대구매수량 / 재고를 Admin API로 매일 조회해 금지값이 나오면 알림 | D1~D3, Q1·Q2·Q4·Q5 | 개발 소(Admin API 조회 + 알림). **M1의 규율 의존을 기계로 바꾸는 유일한 수단.** 강력 권고 |
| **M3** | **결제 직전 금액 정합 가드** — `POST /order-sheets/{no}/calculate` 의 `paymentInfo.paymentAmt` 와 위젯 총액(± 배송비 ∓ 쿠폰/적립금)을 대조해 불일치면 결제 차단 | Q1·Q2와 「표시≠결제」(§2.1) 전부. **원인을 몰라도 사고를 막는 마지막 방어선** | 개발 소~중(`use-order-sheet.ts` 계산부 + 체크아웃 게이트). 오탐 시 결제 차단이라 허용 오차 설계 필요. **가장 비용 대비 효과가 큼** |
| **M4** | **수량 기반 배송비를 「배송비 상품」으로 별도 상품화** — 배송비도 10원 상품으로 만들어 위젯이 수량을 계산해 장바구니에 함께 담음 | 운영정책의 「실외용배너거치대 수량 1개당 배송비 / 봉투 1000장 단위」 요구를 샵바이 기능 없이 충족 | 개발 중. 주문쿠폰의 「동일 배송비 템플릿」 제약(C7)과 상호작용 확인 필요. 세금계산서·환불 단위가 상품으로 잡히는 회계 영향 검토 필요 |
| **M5** | **수량 기반 배송비를 후니 가격엔진 총액에 흡수** — 위젯이 배송비까지 계산해 총액에 포함, 샵바이 배송비는 전 상품 `FREE` 고정 | 동일 요구. D1~D3를 아예 사용하지 않게 됨 | 개발 중~대. **현재 가격엔진에 배송비 개념이 0건**(D11)이므로 신규 도메인 추가. 주소(제주·도서산간)를 위젯이 알 수 없어 지역 추가배송비는 여전히 샵바이 몫 — 두 곳에 배송비가 생겨 이중청구 위험이 새로 생긴다. **M4보다 위험** |
| **M6** | **상품쿠폰을 계속 봉인** — `productCoupons: []` 하드코딩 유지 | (없음 — 상품쿠폰 자체는 안전) | 비용 0이지만 **정책이 원하는 「한 상품 당 하나의 쿠폰」·「상품쿠폰」을 포기**한다. C1/C2가 안전하다고 확정되면 봉인을 풀 근거가 있다. 봉인 유지는 방어가 아니라 기능 미구현으로 읽어야 함 |
| **M7** | **재고를 상한값 근처로 채우고 자동 보충 임계를 매출 규모에 맞게 상향** | Q5·Q6 | 운영 부담 소. 최대 2,147,483,647(≈214억원). 후니 서버가 이미 자동 보충 중이라는 주장(B `:1088-1091`) — **임계값과 주기를 §5-④에서 확인한 뒤 조정** |
| **M8** | **1회 최대구매수량을 「제한 없음」으로 고정하고 감사 대상에 포함** | Q4 | 비용 0. M2에 포함시키면 됨. 부작용: 어뷰징 대량 주문을 수량으로 막을 수단이 사라진다 → **금액 기준 한도로 대체해야 하며 샵바이에 그 기능이 있는지 미확인** |

### 권고 순서
**M3(금액 정합 가드) → M2(주기 감사) → M1(운영 규율 문서화) → §5 라이브 재확인 → M4 또는 M7.**
M3와 M2는 「무엇이 켜졌는지 모르는 상태」에서도 사고를 막는다. 나머지는 원인을 알아야 동작한다.

## 7. 미확인 목록 (닫지 못한 것)

1. **샵바이 정액 쿠폰 배분 규칙의 A등급 원문** — 로컬 `docs/shopby/` 전수 grep에서 「수량별로 할인되지 않음」 미발견. 현재 B등급 인용에만 의존
