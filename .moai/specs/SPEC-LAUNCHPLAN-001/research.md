## 3. 문서 형태의 근거 — S0 §6 을 왜 뼈대로 쓰는가 (이탈 3건 선언)

반려 사유(「무슨 문서인지 모르겠다」)에 대응하는 요소가 §6 골격에 1:1로 있다:

| 반려가 가리킨 결핍 | 골격의 대응 |
|---|---|
| 전체 그림이 없다 | §1 1쪽 요약 · §5 시스템 배치도 |
| 프로세스가 없다 | §4 주문 스윔레인(레인 3~7) |
| 내 할 일을 체크할 자리가 없다 | §6 트랙별 체크리스트(담당·완료 증거·체크 방법·선행·상태) |
| 무엇이 오픈에 필요한지 모른다 | §2 범위 In/Out 두 표 분리 + 동결 규칙 |
| 언제 되는지 모른다 | §3 마일스톤 · §7 임계경로 → 도출 오픈일 |
| 누가 결정하나 | §8 Go/No-Go(결정권자 1인) · §11 RACI(항목당 A 1명) |

「최상위 트랙 5~7 · 각 3~5 항목」은 1쪽 보고서 관행(리스크 3~5)과 스윔레인 레인 3~7 의
교집합에서 나온 안전선이다. 현재 트랙은 **7개**로 상한에 있다 — 여덟 번째 트랙을 만들지 않는다.
**「각 3~5 항목」도 계약이다**(REQ-LP-009 · AC-LP-007(a)). 상한이 없으면 트랙 제목을 씌운
300행 표가 모든 기계 검사를 통과하고, 그것은 9/16 에 반려된 물건과 구조적으로 같다.

### 3-1. 행 계약의 원문은 「마감」을 포함한다

S0 §6-5 의 행 계약은 **「담당 · 완료 증거 · 마감 · 상태 · 블로커」**다. 초판은 마감을
체크 방법으로, 블로커를 선행으로 바꿔치기하고 그 사실을 적지 않았다 — 결과적으로 아티팩트
5종에 「마감」이 0건이었다. 성공 정의가 「자기 일을 체크하고 **일정을 잡는다**」인데 날짜 칸이
없었던 것이다. 목표일을 여섯 번째 칸으로 복원했다(REQ-LP-009). P-1 과 충돌하지 않는다 —
P-1 이 금지한 것은 **오픈일 판정**이지 작업 항목 목표일이 아니다.

### 3-2. 척추가 CTO 의 10구간보다 2.8배 잘다

재작성의 근거는 「CTO 가 구간으로 사고한다」인데 척추는 28구간이다. 그 사실이 기록되지
않으면 읽는 사람의 언어가 사라진다. 그래서 상위 = CTO 10구간, 하위 = 28구간으로 접는
매핑을 요구사항화했다(REQ-LP-007). CTO 문서가 5분 안에 읽히는 이유는 구간마다 붙은
**영향 한 문장**(「결제는 됐는데 무엇을 만들지 모르는 주문이 됩니다」)이므로 그 칸도 계약이다.

실무진의 일상 질문은 「옵션을 바꾸면 어디서 가격이 정해지고 어느 화면에서 고치나」이고,
트랙 체크리스트는 그 답을 주지 못한다. 세 블록으로 답한다(셋째는 §3-3-1) — 메뉴 지도(**37행**,
webadmin 매뉴얼 2종 기준)와 옵션↔가격 도식(구성요소 → 가격공식·가격구성요소·단가표
`use_dims` 12축 → 위젯 cfg·기본값 → 고객 화면 → `/api/w/v1/price`). **각 단계는 고치는
화면 이름을 반드시 단다** — 없으면 그림이 아니라 개념도다.

**[HARD] 갭 개수는 상수가 아니다.** 초판은 「갭 6」을 네 문서에 박았는데, **어느 원천
판독으로도 6 이 나오지 않는다** — 원장 CSV 갭 열은 13(실질 텍스트) / 11(비결함 2건 제외) /
5(★ 표기)로 갈리고, 오늘자 실측은 매뉴얼 갭 **3건**이다. 상수를 기계 검사에 박으면 정직한
문서가 FAIL 하고, 통과하는 유일한 길이 「갭 표기를 그 수에 맞춰 조정하는 것」이 된다 —
기계 검사가 문서 왜곡을 보상하는 형태이고, 이 절의 존재 이유(실무진이 화면을 찾게 하는 것)가
먼저 깨진다. 그래서 수를 검사하지 않고 **「수 + 판정 기준 + 원천」이 함께 선언됐는지**를
검사한다(AC-LP-014(c)). 「37」도 원천이 사이드바 33 + 비사이드바 4 로 나누므로 전수라 부를 때
내역 한 줄을 단다.

도메인 정본이 못 박은 두 문장을 도식에 그대로 싣는다: 「위젯의 선택지는 전부 상품 설정에서
온다」 · 「**위젯은 가격을 정하지 않는다** — 금액은 가격공식·단가표·할인테이블이 정하고
위젯은 결과를 보여 줄 뿐이다」. 실무진이 노출 단계에서 이상한 값을 보면 **가격 단계를**
고쳐야 한다는 것이 이 절의 실용적 목적이다.

### 3-3-1. 실측의 깊이 — 왜 (c) 1:1 대조인가 (지니 결정 260917)

지니가 「§G 판매 준비 프로세스·§H 상태 판정 규율이 전제한 webadmin 실측의 **깊이**가 무엇인가」를
물었다. 당시 AC 를 그대로 읽으면 답은 이랬다:

| 층 | 현행 AC 가 실제로 요구한 깊이 |
|---|---|
| §G (`AC-LP-014`) | **실측 요건 0** — 메뉴 37개 나열 · 갭 열 보유 · 갭 수 + 기준 + 원천 선언 · 도식 5단계 화면 라벨. 전부 **문서 내부의 명시 검사**이고 화면을 본 흔적을 요구하지 않는다 |
| §H (`AC-LP-007(d)`) | **(a) URL 렌더 + 시각만** — 상태가 `작동` 인 행이 `URL@일시`(≥ 2026-09-16)를 갖는지. 그 URL 에서 **무엇을 확인했는지**는 검사하지 않는다 |

즉 매뉴얼 SCREENS 원고와의 1:1 대조는 **어느 AC 도 요구하지 않았다**.

깊이의 선택지는 셋이었다 — **(a)** URL 렌더 + 시각(현행) · **(b)** 화면별 핵심 요소 표본 확인 ·
**(c)** 매뉴얼 원고 요소와의 1:1 전건 대조. **지니 결정 = (c)**. 현행 AC 가 그것을 강제하지
않으므로 SPEC 을 확장했다(REQ-LP-017 확장 · AC-LP-014(e) 추가 — **REQ 18 · AC 16 수는 불변**).

**분모의 원천은 매뉴얼 원고 두 파일이다** — 실측(2026-09-17):

```
wc -l raw/webadmin/tools/manual_content.py         → 1468
wc -l raw/webadmin/tools/widget_manual_content.py  → 1117
                                                     합 2585
```

두 파일 모두 최상위에 `SCREENS` 리스트를 갖고, `manual_content.py` 는 `MODEL_ADMIN_SCREENS` 를
추가로 갖는다(`grep -n "^SCREENS\|^MODEL_ADMIN_SCREENS"` 로 확인). 여기서 나오는 **화면별
요소·버튼·패널 전건**이 매트릭스의 행이다.

**[HARD] 그 전건 수를 어디에도 상수로 적지 않는다.** 이 SPEC 은 같은 실패형으로 이미 두 번
감사에 잡혔다 — 「외부 의존 딱 2건」(review-1 C-2) · 「갭 6」(review-2 N-1). 상수를 박으면
정직한 문서가 FAIL 하고, 통과하는 유일한 길이 「행 수를 상수에 맞춰 조정하는 것」이 된다.
그래서 검사는 **3항 사슬 관계**다:

```
원고 grep 분모  ==  부록/CSV 행 수  ==  본문 요약 층 집계 수
      (산출 규칙과 재현 명령을 문서가 선언)
```

**층 분리의 이유와 그 대가**: 2,585행 원고에서 나오는 요소 전건은 수백 행 규모일 수 있고,
그것을 §6 본문에 그대로 실으면 §6 이 **행 목록**이 되어 9/16 반려 원인이 §7 에서 §6 으로
이사한다 — `AC-LP-016(e)` 사람 판정(「옵션을 바꾸면 어느 화면에서 고치나」)이 정확히 그 실패를
잡는 자리다. 그래서 **본문 = 요약 층**(집계 · 결과 4종 분포 · **불일치 목록** ·
**`쓰기경로-dev환경필요` 목록**) / **부록 = `<details>` 전건 층 + CSV 경로**로 나눈다.
매트릭스는 전건 그대로 만들고 문서에도 실린다 — **어디에 싣는가**만 정한 것이다.
층을 나눈 대가(요약과 전건이 어긋날 위험)는 위 3항 사슬이 함께 메운다.

**쓰기 경로는 판정하지 않는다**: 등록·수정·삭제·게시·저장은 P-9(쓰기 0)에 걸리므로 라이브에서
누르지 않고 `쓰기경로-dev환경필요` 로 둔다. 이 집합은 곧 **dev 환경이 서기 전에는 판정 불가한
경로**이므로 T1 오픈 테스트 진입 조건과 연결되며, 그 연결을 문서가 한 줄로 명시한다.

### 3-3-2. 소유 라벨 — 범위 판정 장치 (지니 정정 260917)

배치도의 **모든 노드**와 스윔레인의 **모든 레인명**이 소유 라벨을 동반하고, 값은 **정확히 두
개**다 — **`NHN 제공`**(Shopby SaaS: 셀러어드민 · 주문/결제/회원 원장 · Shop/Server API ·
NCPPay) · **`후니 개발`**(자사몰 스킨 `shopby.huniprinting.co.kr` — 김동학 · webadmin · 위젯 ·
가격엔진 · DB — 서희항). 체크리스트 행은 같은 구분을 **속성**으로 싣는다(`data-owner` ·
`data-work`) — 여섯 칸 계약을 깨지 않기 위해서다.

**이건 표기 문제가 아니라 범위 판정 장치다.** 소유 라벨이 없으면 NHN 이 제공하는 기능이
「우리가 개발할 것」으로 계획서에 섞여 들어가고, 그러면 임계경로가 **실제보다 길게** 나온다 —
이번 사이클 내내 막아 온 것(토스 계약이 외부 의존에서 지워져 임계경로가 **짧게** 나오는 것,
review-1 C-2)의 정확한 **거울상**이다. 한쪽은 할 일을 빠뜨려 짧아지고, 다른 쪽은 하지 않을 일을
집어넣어 길어진다. 둘 다 일정이 거짓이 되는 경로다.

그래서 **분류 제약**을 건다 — 셀러어드민(NHN 제공)에서 관측한 항목의 분류는 **「설정/확인」만**
허용하고 **「개발/수정」을 금지**한다. NHN 서비스는 우리가 고칠 수 있는 대상이 아니므로
「개발/수정」으로 적히는 순간 그 자체가 오분류이고, `AC-LP-006(e)③`(`data-owner="nhn"` ×
`data-work="dev"` 0건)이 그것을 기계로 잡는다. 값 집합을 열거형으로 고정하고 그 밖의 값 0건을
검사하는 방식은 실측 결과 4종(§3-3-1)과 같은 관용이다.

**세 번째 값 `ext` 가 필요한 이유**(리드 검산 260917): 담당 칸은 처음부터 `외부(<대상>)` 형식을
인정했는데(확정 전제 P-8 의 역할 5종 중 「외부」) 소유 라벨을 두 값으로 닫으면 이니시스 PG ·
토스페이먼츠 · MES 벤더 · 구 사이트 운영사 · 인프라팀 행이 **들어갈 값이 없어** `AC-LP-006(c)`
를 통과하고 `(e)①` 에서 전량 FAIL 한다 — 두 검사가 동시 만족 불가인 형태(review-1 C-1 과 같은
계열)라 `ext` 를 추가했다. 함께 `data-work` 에 `wait`(회신·계약·심사 대기)를 두고 **`ext`
전용**으로 묶었다. `nhn` 과 `ext` 는 「우리가 고칠 수 없다」는 점에서 같아 둘 다 `dev` 를
금지하지만 성격이 다르다 — `nhn` 은 **이미 제공되는 것**(설정만 하면 된다), `ext` 는 **아직
오지 않은 것**(기다려야 한다). 그 차이를 표시하지 않으면 외부 대기가 「설정」으로 뭉개져
일정에서 사라지고, 그것이 곧 토스 계약이 지워지던 실패다. `ext` × `wait` 집합은
`AC-LP-012(b)` 의 §8 선행/외부 대기 항목과 **같은 집합**이다.

실무진 관점에서도 답이 달라진다. `AC-LP-016(e)` 는 「옵션을 바꾸면 **어느 화면에서 고치나**」를
묻는데, 셀러어드민이면 답은 「NHN 설정에서 확인」이지 「개발 요청」이 아니다 — 소유 라벨이
화면마다 붙어 있어야 그 한 문장이 나온다.

### 3-4. 상태 판정의 근거 — 화면 없이 `작동` 은 없다 (지니 확정 260917)

라이브 판정은 ego-browser 로만 한다(space 20 재사용 · p1 신규몰 · p2 webadmin ·
p3 셀러어드민 · p4 구 사이트 · 읽기 전용). **「전건 재실측」의 뜻은 「28구간을 모두 한 번씩
본다」가 아니라 「`작동` 으로 적을 행은 전부 화면 근거를 갖는다」로 한정한다** — AC-LP-007(d)가
검사하는 것도 그것뿐이고, 요소 수준의 1:1 대조는 §3-3-1 의 매뉴얼 요소 대조가 맡는다.
run 단계 M0 에서 그 근거를 모으며, **체크 방법 문장이 곧 재실측 절차**다 — 따라갈 수 없는
문장은 그 자체가 결함이다.

**승계의 한계**: 오늘 입력 조사(S1~S4)는 코드·문서만 본 것이다. 따라서 `작동` 표기는
9/16 라이브 실측 승계분에 한정되며, 입력 카드가 `구현-미검증` 으로 적은 행을 화면 확인
없이 승격시킬 수 없다. **미관측은 부재의 증거가 아니지만 작동의 증거도 아니다.**

## 5. 이 SPEC 이 조사하지 않는 것

- 654행 원장의 재실측·재분류 — 재사용만 한다.
- 스킨·webadmin 코드의 신규 역공학 — 기존 조사 산출물과 증거를 그대로 인용한다.

**예외(조사하는 것 1건)**: 라이브 **화면 관측**은 REQ-LP-018 이 의무화한다. M0 의
ego-browser 재실측은 새 역공학이 아니라 **상태 판정의 필수 근거**이며, 읽기 전용 탐색만
한다(저장·주문·결제·삭제·발송 버튼 0). 초판의 「이 SPEC 은 브라우저를 쓰지 않는다」는
철회한다.
