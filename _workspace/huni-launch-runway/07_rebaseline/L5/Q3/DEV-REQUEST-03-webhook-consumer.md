## 1. 증상

**수신함은 있는데 그것을 읽는 쪽이 없다.**

`t_ord_webhooks` 에 행만 쌓이고 아무 일도 일어나지 않는다. 결제가 완료돼도 원고 승격·검수·생산 접수·송장 중 **어느 것도 시작되지 않는다.**

`I-4`(`order/register`)를 붙여도 이게 없으면 파이프라인은 **끊긴 채**다. 두 개가 다 있어야 결제 → 생산이 이어진다.

## 2. 재현

```bash
cd /Users/innojini/Dev/HuniWeb
grep -rn "TOrdWebhooks" raw/webadmin/webadmin/
# → 2건뿐
#   models.py:1123        (모델 정의)
#   shopby_hook.py:124    (create — 저장)
# 읽는 코드가 0건이다.
```

라이브: `t_ord_webhooks` 적재 건수 확인 필요. **0건이면 「아직 실행 안 됨」이지 「구현 안 됨」이 아니다** — PG 승인 심사 중이라 결제가 한 건도 안 일어났기 때문이다. 반면 **소비자 0 은 코드 관측에서 나온 구현 부재**다. 이 둘을 섞지 말 것.

## 3. 원인 — file:line

### 3-1. 수신부는 잘 만들어져 있다 (건드리지 말 것)

`raw/webadmin/webadmin/catalog/shopby_hook.py` — 133줄 전체가 **수신·저장 전용**이다.

| 하는 일 | file:line |
|---|---|
| 메서드 `POST`/`PUT` 아니면 `405` | `shopby_hook.py:92-93` |
| 비밀 경로 `hmac.compare_digest` 대조 → 불일치면 **404**(403 아님) · 시크릿 미설정이면 무조건 실패 | `:73-78`, `:94-95` |
| 256KB 상한 절단(`_truncated: True` 기록) · 파싱 실패해도 `{"_unparsed": raw}` 로 통째 저장 | `:108`, `:110` |
| `eventType`·`orderNo`·`orderProductOptionNo`·`orderStatusType`·`claimStatusType` 추출 | `:50`, `:59`, `:112-121` |
| `t_ord_webhooks` 에 `hook_sts="RECEIVED"` INSERT → 200 | `:120`, `:124`, `:133` |
| INSERT 실패 → 원문 로그 + **500** | `:125-129` |

파일 docstring 이 설계 의도를 못 박아 뒀다 — 「**이 파일이 하는 일은 하나다: 잃어버리지 않는 것.**」 / 「샵바이는 **실패한 웹훅을 다시 보내지 않습니다**」 / 「**웹훅 본문은 판단 근거가 아니라 신호입니다.**」

**일부러 하지 않는 것 3가지**(docstring 명시) — 이 결정을 뒤집지 말 것:
1. **중복 제거 안 함** — 페이로드에 이벤트 고유번호가 없어 재전송인지 진짜 두 번인지 구분 불가. 「임의의 키로 접으면 진짜 사건을 잃습니다」
2. **rate limit 안 검** — 「재전송이 없으므로 우리가 한 건이라도 거절하면 그 주문은 사라집니다」
3. **처리 안 함** — 「무거운 일을 요청 안에서 하면 타임아웃 = 유실입니다」

### 3-2. 없는 것 — 소비자

- `eventType` 분기 **0건**. 무엇이 오든 동일하게 저장만 한다. `_UNKNOWN` 도 저장한다
- 상태값 4종(`RECEIVED`·`DONE`·`FAILED`·`IGNORED`)이 **정의만 되어 있다**(`shopby_hook.py:43-46`). `RECEIVED` 외에는 **코드 어디서도 세팅되지 않는다**
- `GET /webhooks/failed` 를 부르는 코드 **0건**

## 4. 수정 방향

### 4-0. [HARD] 설계 원칙 — 「전건 저장 → 상태값 분기는 나중」

**지금 분기를 짜지 말 것.** 이유가 문서로 확정돼 있다.

| 왜 | 근거 |
|---|---|
| 결제완료 **전용 이벤트가 33종에 없다.** 결제 완료는 `CHANGE_ORDER_STATUS` 의 **상태값**으로 판별해야 하는데, **그 상태값 목록이 미확인**이다 | `webhook-catalog.md` §6.4 |
| payload 스키마가 **33종 전부 미확인** — 스펙이 `data: string` 으로만 정의한다 | `webhook-catalog.md` §2 |
| 가이드가 「`orderProductOptionNo` 가 웹훅에 실려 온다」고 하지만 **그건 후니 가이드의 서술이지 샵바이 스펙의 문언이 아니다** | `webhook-catalog.md` §6.3 ⚠ |

**즉 지금 분기를 짜면 추측으로 짜게 된다.** 순서는 이렇다.

```
① 전건 저장 (이미 됨)                     ← 건드리지 않는다
② 소비 루프: 저장된 행을 읽어 「주문 조회 API 로 다시 읽어」 판단   ← 이번 개발
③ 실측으로 상태값 목록이 확정된 뒤 분기를 붙인다  ← 나중
```

### 4-1. [HARD] 판단은 payload 가 아니라 조회 재확인으로 (fail-closed)

**웹훅 본문을 믿고 상태를 바꾸지 말 것.** 이유:
- 서명·인증 헤더가 **없다**(`webhook-catalog.md` §5 — 스펙 전체에 서명 수단 서술 0건)
- 따라서 **비밀 경로가 유출되면 누구나 가짜 주문 이벤트를 쏠 수 있다**

방어는 하나뿐이다 — **웹훅은 「무언가 일어났다」는 신호로만 쓰고, 실제 상태는 샵바이 주문 조회 API 로 다시 읽어서 판단한다.** 조회가 실패하면 **진행하지 않는다**(fail-closed). 이것이 설계상 이미 정해진 방침이며(`interface-6.md` I-5 §양쪽 담당) 아직 미구현인 부분이다.

### 4-2. 소비 루프 — 최소 형태

| 단계 | 하는 일 |
|---|---|
| 1 | `t_ord_webhooks WHERE hook_sts='RECEIVED'` 를 오래된 순으로 읽는다 |
| 2 | `shop_ord_no`(+ `shop_line_no`)로 **샵바이 주문 조회 API 를 호출**해 현재 상태를 읽는다 |
| 3 | 조회 결과의 상태로 후니 주문(`t_ord_orders`)을 진행시킨다 |
| 4 | 성공 → `hook_sts='DONE'` · 처리 불필요(범위 밖 이벤트·우리가 만든 메아리) → `'IGNORED'` · 실패 → `'FAILED'`(사람이 봐야 한다) |

**멱등은 처리 단계의 책임**이다(수신부가 중복 제거를 안 하기로 했으므로). 같은 주문·같은 상태가 두 번 와도 결과가 같아야 한다 — 「이미 그 상태면 아무 일도 안 한다」로 짠다.

**메아리 필터**: 후니가 샵바이에 올린 상태변경이 웹훅으로 되돌아온다. 무한루프를 막아야 한다 → 원장 `STD-MFG-030`.

### 4-3. 유실 구제 — `GET /webhooks/failed` 폴링 (★ 7일 창)

**샵바이는 실패한 웹훅을 다시 보내지 않는다.** 재발송 API 도 없다. 구제 경로는 조회 하나뿐이다.

| 성질 | 값 | 근거 |
|---|---|---|
| 한 번의 질의 **검색 창** | **7일 이내** | `workspace-server-public.yml:581` |
| 실패 레코드 **보관** | 6개월 | `:583` |
| 필수 파라미터 | `startDateTime` · `endDateTime`(둘 다 required) | `:598-609` |
| 페이징 | `page`(기본 1) · `pageSize`(기본 10) | `:586-597` |
| 정렬 | `direction` 기본 `DESC` | `:641-646` |
| 몰 필터 | `mallNos` | `:610-621` |

★ **폴링 주기가 7일을 넘으면 구멍이 난다.** 검색 창이 7일이기 때문이다. **하루 1회 이상**을 권한다(보관은 6개월이므로 놓친 구간을 나중에 되짚을 수는 있으나, 한 번의 질의로는 7일까지만 볼 수 있다).

폴링이 찾아낸 실패분은 **수신함에 넣고 소비 루프를 태운다**(별도 처리 경로를 만들지 말 것 — 경로가 둘이면 멱등이 깨진다).

### 4-4. 어느 이벤트부터 붙이나

| 우선 | eventType | 왜 |
|---|---|---|
| **1 (필수)** | `CHANGE_ORDER_STATUS` | 결제완료 → 원고 승격 → 검수 → 생산 접수 → 송장. 그 흐름의 유일한 트리거. **결제완료 전용 이벤트가 없으므로 상태값으로 판별** |
| **2 (필수)** | `CREATE_ORDER` | 주문 생성 포착. `order/register`(→ `DEV-REQUEST-02`)가 붙기 전까지 **그 공백의 대체 경로가 될 수 있는지 판단 필요** |
| **3 (사실상 필수)** | `UPDATE_RECEIVER` | 수령자 변경이 생산·송장 이후면 배송 사고. 후니가 송장 등록 주체 |
| 4 (운영) | `ADD/UPDATE_TASK_MESSAGE` | CS 연동. 런칭 필수 아님 |
| 5 (범위 밖) | `MEMBER_*`·`ACCUMULATION_*`·`PRODUCT_*`·`INQUIRY_*` | 원장 소유가 샵바이/후니로 갈려 있어 런칭 흐름에 개입 안 함 → `IGNORED` |
| 해당 없음 | `GD_*` 9종 | 고도몰 전용 |

★ **취소·반품 전용 이벤트가 카탈로그에 없다.** 취소 가능 경계(입금대기·결제완료 = 즉시 취소 / 상품준비중·배송준비중 = 취소요청 후 승인 / 배송중부터는 반품)를 웹훅으로 알 수단이 `CHANGE_ORDER_STATUS` 뿐이라면 **상태값 매핑이 런칭 블로커가 된다.** 무통장 관통 1건에서 실측으로 상태값을 확보하는 것이 가장 빠른 길이다.

## 5. 확인 방법

| # | 무엇을 | 어떻게 | 기대값 |
|---|---|---|---|
| 1 | 소비자가 생겼나 | `grep -rn "TOrdWebhooks" raw/webadmin/webadmin/` | **3건 이상**(정의·생성 + **읽는 곳**) |
| 2 | 수신되나 | 무통장 주문 1건 후<br>`SELECT hook_id, evt_typ, shop_ord_no, hook_sts FROM t_ord_webhooks ORDER BY reg_dt DESC LIMIT 10;` | **행 생성** · `evt_typ` 에 실제 이벤트명 |

| 4 | 소비되나 | 같은 SELECT 를 소비 루프 후 | `hook_sts` 가 `RECEIVED` → **`DONE`/`IGNORED`** 로 바뀐다 |
| 5 | 조회 재확인을 하나 | 소비 루프 로그 | **샵바이 주문 조회 호출이 찍힌다**(payload 만 보고 처리하면 안 됨) |
| 6 | 멱등한가 | 같은 웹훅을 두 번 넣는다 | 결과 동일 · 후니 주문이 두 번 진행되지 않는다 |
| 7 | 유실 구제 | `GET /webhooks/failed` 를 7일 창으로 호출 | 응답 200 · 실패분 0건이면 유실 없음 |
| 8 | 메아리를 거르나 | 후니가 샵바이에 상태변경을 올린 뒤 | 되돌아온 웹훅이 `IGNORED` |

**3번이 이번 무통장 관통의 최대 수확**이다. `CHANGE_ORDER_STATUS` 의 상태값 목록은 **문서로는 닫히지 않고 실측으로만 닫힌다.**
