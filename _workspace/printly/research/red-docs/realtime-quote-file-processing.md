## 2. 핵심 요지 (한 문단)

이 시스템은 고객이 웹에서 **주문 접수 → PDF 파일 업로드**를 하면, 서버가 그 파일을 (a) **유효성검사(Preflight)** 하고 (b) **인쇄 레이어 + 각 후가공 레이어로 자동 분리·저장**한 뒤, 이 분리된 레이어를 재료로 **세 갈래를 병렬 실행**한다 — ①**자동 견적**(레이어에서 커팅 길이·면적·가변 개수를 실측해 후가공비 산출 + 인쇄비 합산), ②**미리보기 이미지 생성**(고객 검수용), ③**파일 처리(Preprocess)**(생산 장비가 먹을 수 있게 레이어별 최적화). 산출된 견적은 웹 화면에 실시간 표시되어 고객 1차 검수(주문/금액 확인)를 거치고, 파일 오류는 수정·미리보기로 보여 고객 2차 검수를 받은 뒤, 결제(PG 연계)→**조판 프로세스**로 넘어간다. 핵심 발명 포인트는 **후가공 견적을 사람 견적 없이 파일 레이어의 기하(길이/면적/개수)에서 결정론적으로 산출**한다는 것과, **원본 PDF vs Preflight 미리보기를 이미지 매칭으로 자동 대조해 데이터 무결성을 검증**한다는 것.

## 3. ★자동 견적 메커니즘 (p4, p2)

### 3.1 입력 (사양 축)
- **주문 제품 사양** = 인쇄물 종류/규격(가격테이블 조회 키). 문서에 개별 축 명세는 없으나 "인쇄용 가격 테이블"·"일반 후가공 가격 테이블" 조회로 처리(p4).
- **업로드 PDF의 레이어 구조** = 후가공 견적의 실입력. 어떤 후가공 레이어(Cut/Crease/Punch…)가 파일에 존재하는지, 그 레이어의 기하가 견적 변수(길이/면적/개수)를 결정.

### 3.2 계산 흐름 (p4 「실시간 자동 견적 시스템 개요」 플로우)
시작 → **두 트랙 병렬**:

**(A) 기본 인쇄견적** — "자재비 + 인쇄비 등"
1. 인쇄용 가격 테이블 불러오기
2. 기본 견적 계산
3. 견적 합산 → DB 업데이트

**(B) 후가공 견적** — 분기점 = "주문 제품 및 후가공에 필요한 **Layer 존재 여부 체크**"
- **N (해당 후가공 레이어 없음)** → "일반 후가공 가격 테이블 불러오기" → 일반 후가공 계산 → 합산 → DB 업데이트  
  = 파일 기하에 안 걸리는 후가공은 **가격테이블 룩업**(고정 단가)으로 처리.
- **Y (레이어 존재)** → "견적에 필요한 요소 체크" → 아래 3가지 **기하 계산기** 중 해당 항목 실행:

  | 계산기 | 세부 단계 (p4) | 용도 |
  |---|---|---|
  | **길이 계산** | 면을 선으로 변환 → 중복선 제거 → 패스 정렬 → **커팅길이 계산** → 복잡도 계산 | Cut/KissCut/Crease/DashRule 등 **선 기반 후가공** 비용(칼선 총길이·형태 복잡도) |
  | **면적 계산** | 벡터→Grayscale → 이미지→Grayscale → 픽셀을 0과 1로 분리 → 오브젝트 면적 계산 | Foil/White/Emboss/Scodix/Marking 등 **면적 기반 후가공** 비용(도포/박 면적) |
  | **가변오브젝트 계산** | 가변영역 확인 → 가변갯수 계산 | Punch(타공 개수) 등 **개수 기반 후가공** 비용 |

  → 후가공 견적 합산 → DB 업데이트

**최종**: (A)+(B) → **최종 견적 계산 및 DB 업데이트** → 종료

### 3.3 가격 결정 요소 (요약)
- 인쇄비/자재비 = 제품 규격 기반 **가격테이블 룩업**(결정론적, 이 문서엔 값 없음).
- 후가공비 = **파일 레이어 기하에서 실측한 변수**(커팅 길이, 후가공 면적, 가변 개수) × 단가. 이게 발명의 핵심 — 후가공 견적을 **작업자 수기 견적 없이 파일에서 자동 산출**.
- 파일에 후가공 레이어가 없으면 **일반 후가공 가격테이블(고정 단가)** 폴백.

## 4. ★파일 처리 파이프라인 (p3, p6~p20)

파일 처리는 **두 단계**로 나뉜다: (Ⅰ) 견적/미리보기 직전의 **레이어 분리 저장**(p3), (Ⅱ) 생산용 **레이어별 Preprocess 최적화**(p6~20).

### 4.1 Preflight 유효성검사 (p2 3단계)
- 업로드 파일 → "유효성검사(Preflight)" 통과 후 Preflight 폴더에 안착. (개별 검사 규칙은 이 문서에 없음 = GAP)

### 4.2 레이어 분리 후 저장 (p3 「Layer 분리 후 저장」)
- Preflight 폴더에서 파일 불러오기 → **Layer 존재 여부 체크(Y/N)**:
  - **Y (레이어 이미 있음)**: Layer 폴더로 복사 → **인쇄 안 되는 Layer 제거** → **Layer명 영문 변환** → **레이어 단일화** → 종료.
  - **N (레이어 없음)**: Spot Color 폴더로 복사 → **파일 내에 인쇄 및 후가공 레이어 생성**.
- **레이어 명명 규약(별색 = Spot Color 2)** (p3 노란 박스):
  - 인쇄용 레이어: `SpotColor 2 CMYK`
  - 후가공 레이어: `SpotColor 2 {Cut, Crease, Brail, Fold, KissCut, Dash Rule, Punch, Emboss, White, Marking}`
  - → **후가공 종류가 곧 하나의 별색 레이어**로 표현됨(생산 장비/RIP가 별색으로 인식).

### 4.3 파일 처리(Preprocess) 프로세스 (p6)
- **① CMYK Layer 분리 처리 → ② 후가공 Layer 분리 처리 → 각 결과 파일 저장 + 파일경로정보 DB서버로 전송.**
- 즉 "고객 업로드 파일을 **인쇄 및 후가공에 편리하도록 최적화**하는 작업"(p6 정의).

### 4.4 레이어별 전처리 상세 (p7~p20) — 각 후가공 = 독립 처리 루틴
| # | 레이어 (가공) | 처리 단계 (p) | 정의(문서 인용) |
|---|---|---|---|
| 1 | **CMYK** (인쇄) p7 | White Spot Color명 변경 → Object Flatten → 최적화·정리 → **Font Outline** | 잉크별 레이어 분리, 인쇄 시 4색 합쳐 색 표현 |
| 2 | **Cut** (컷팅) p8 | Cut Layer 처리(단일 스텁) | 일반 칼로 못 자르는 캐릭터 모양 등을 칼 제작해 자름 |
| 3 | **Crease** (오시) p9 | 스텁 | 접을 수 있는 선을 눌러 누름선 생성 |
| 4 | **DashRule** (미싱) p10 | 스텁 | 뜯어지게 하는 점선(구멍 뚫린 선) |
| 5 | **KissCut** (반칼) p11 | 스텁 | 스티커 칼집만 내고 이형지는 안 잘림 |
| 6 | **Marking** (마킹) p12 | 스텁 | 판촉물 표면에 로고/정보 표시 |
| 7 | **Fold** (접지) p13 | 스텁 | 오시 가공 후 자동으로 접는 것 |
| 8 | **GoldFoil** (금박) p14 | **CMYK 100%** 변환 | 금색 판박 느낌으로 종이에 찍음(잉크 아님) |
| 9 | **SilverFoil** (은박) p15 | **CMYK 100%** | 은색 판박 |
| 10 | **Brail** (점자) p16 | Clear PDF용 복사 → Layer명 Clear 변경 → **모든 오브젝트 1.5mm Bleed** → 최종 폴더 복사 | 시각장애인용 부호글자 처리 |
| 11 | **Punch** (타공) p17 | 스텁 | 구멍 뚫기 |
| 12 | **Emboss** (형압) p18 | **CMYK 100%** | 종이 위로 볼록하게 올라오게 |
| 13 | **White** (흰색 별색) p19 | **CMYK 100%** | 흰색은 투명 인식→인쇄 안 됨. CMYK 4색으로 흰색 못 만들어 별색 처리 |
| 14 | **Scodix** (스코딕스) p20 | Object Flatten → Vector→Grayscale(실패 시 **에러 폴더 이동**) → Raster→Grayscale → 단일채널 변경 → **Dithering** → (성공 시 임시파일 정리, 실패 시 에러 폴더) | 디지털 엠보싱 인쇄기로 투명잉크 부분 엠보싱/메탈릭/펄 구현 |

> 주: Scodix(p20)만 **에러 처리 분기**가 명시됨(Vector→Grayscale 실패, Dithering 후 실패 시 에러 폴더로 파일 이동). 나머지 대부분은 단일 스텁으로 상세 미기재 = GAP.

### 4.5 미리보기 이미지 생성 프로세스 (p5)
- 각 인쇄/후가공 레이어 파일 불러오기 → **이미지 파일로 변환** → 이미지 사이즈 설정 → 미리보기 이미지 파일 저장 → **DB에 이미지 경로 저장**.
- 목적(p5): 인쇄 레이어와 미리보기 이미지를 생성해 **고객에게 제공하고 고객 검수를 받음**.

### 4.6 데이터 검증 시스템 (p21~22) — 파일처리 무결성 게이트
- **이미지 매칭 알고리즘** 사용. 순서(p22):
  1. 고객 원본 PDF를 이미지 파일로 변환·저장
  2. Preflight로 생성된 미리보기 이미지를 작업폴더에서 불러옴
  3. **원본 PDF 이미지 ↔ Preflight 미리보기 이미지 비교**(후가공 레이어별 썸네일 비교판단)
  4. **일치** → 주문 승인 데이터 DB 저장
  5. **불일치** → PDF 분석·원인 파악 → **내부오류면(Y)** 파일 수정 후 PDF 재처리 / **내부오류 아니면(N=고객 주문오류)** 고객에게 **파일 재업로드 요청**
- = 파일 분리/변환 과정에서 원본이 훼손·오해석되지 않았는지 자동 검증하는 **결정론적 게이트 + 사람/고객 개입 폴백**.

## 5. 고객 배송 여정 내 위치 (p2 전체 개요 플로우)

13단계 마스터 플로우 (p2, 번호는 문서의 원 번호):
```
1 주문 접수
2 파일 업로드
3 유효성검사(Preflight)
4 인쇄 및 각 후가공 레이어 분리 후 저장   ← 여기서 3갈래 병렬 분기
   ├─ 5  자동 견적 프로세스  → 7 웹 화면에 최종 견적 제공
   ├─ 6  미리보기 이미지 생성 프로세스
   └─ 12 파일 처리 프로세스
8 고객 주문 내용과 금액 확인   ⇢ [고객 1차 검수]
9 파일 오류 수정 및 미리보기 제공
10 고객 검수 확인             ⇢ [고객 2차 검수]
11 결제 화면, PG 프로세스 연계
13 조판 프로세스   ← 12(파일처리) 결과가 여기로도 합류
```
- **위치**: 「자동 견적 + 파일 처리」는 **주문 접수 직후 ~ 결제 이전**의 프론트엔드 구간. 생산(조판·인쇄·후가공·배송)의 **앞단 관문**.
- **앞 연결**: 주문 접수 → 파일 업로드 → Preflight → 레이어 분리(모든 후속의 공통 재료).
- **뒤 연결**: 견적/미리보기가 **고객 2회 검수**(1차 금액·주문, 2차 파일 수정본)를 통과 → 결제 → **조판 프로세스**(별도 특허 문서). 파일처리(12) 산출물은 검수와 무관하게 조판(13)으로도 직접 흘러감.
- 배송 자체는 이 문서 범위 밖(조판 이후 생산·물류) = 이 문서는 "**받는 여정의 시작 관문(견적 확정 + 인쇄가능 파일 확보)**"까지만 다룸.

## 6. 결정론 vs 판단 경계

| 자동(결정론) | 사람/고객/외부 결정 |
|---|---|
| Preflight 유효성검사 (p2) | **고객 1차 검수** = 주문 내용·금액 확인(p2 #8) |
| 레이어 존재 판정·분리·명명·단일화 (p3) | **고객 2차 검수** = 파일 수정본 확인(p2 #10) |
| 인쇄비 = 가격테이블 룩업 (p4) | **결제**(PG, 고객 행위) (p2 #11) |
| 후가공비 = 길이/면적/개수 기하 실측×단가 (p4) | 데이터 검증 불일치 시 **"내부오류" 판정**(p21 — 사람/규칙?, 문서상 자동/수동 불명 = GAP) |
| 미리보기 이미지 생성·경로 DB 저장 (p5) | 내부오류 아닐 때 **고객에 재업로드 요청**(p21 #6) |
| 레이어별 Preprocess 변환(CMYK 100%, Grayscale, Dithering, Bleed 등) (p7~20) | |
| 원본PDF↔미리보기 **이미지 매칭 대조**(p21) | |
| Scodix 에러 폴더 자동 라우팅 (p20) | |

- **핵심 경계**: **가격 값(단가·가격테이블)은 이 문서에 없음** — 시스템은 "가격테이블을 불러온다"까지만 정의하고 **테이블 값은 외부 권위(별도 가격 마스터)**. → 프린틀리의 "값=엔진, 온톨로지=축까지" 경계와 정확히 일치.
- 자동 산출되는 것 = **견적 변수(기하)**와 **파일 형상 변환**. 사람이 결정 = **검수 승인/결제/오류 귀책 판정**.

## 7. 데이터 모델 후보 (온톨로지 모델링 대상)

문서에서 추출되는 데이터 항목 (프린틀리 온톨로지 노드/축 후보):

**A. 제품/주문 사양 축**
- 주문(제품 종류·규격) → 가격테이블 조회 키 (p4)
- 인쇄 사양: CMYK 4색, 별색(Spot Color) (p3, p7)

**B. 후가공(post-process) 타입 온톨로지** — p3 명명규약 + p7~20 = **14종 후가공 별색 레이어**
- 선 기반: Cut, KissCut(반칼), Crease(오시), DashRule(미싱), Fold(접지)
- 면적 기반: GoldFoil(금박), SilverFoil(은박), Emboss(형압), White(흰색별색), Marking(마킹), Scodix(스코딕스)
- 개수 기반: Punch(타공)
- 특수: Brail(점자, 1.5mm Bleed)
- → 각 후가공에 **{레이어명, 처리 루틴, 견적 계산 클래스(길이/면적/개수), 정의}** 속성. 프린틀리 "후가공 축" 자산과 직접 대응.

**C. 견적 계산 클래스 (계산 방식 축)**
- 길이 계산(커팅길이·복잡도) / 면적 계산(도포·박 면적) / 가변오브젝트 계산(개수) / 가격테이블 룩업(일반 후가공·인쇄비) (p4)

**D. 파일 속성/처리 상태 축**
- 파일 폴더 상태: Upload / Preflight / Layer / Spot Color / Clear PDF / 에러 폴더 / 최종 폴더 (p3, p16, p20, p21)
- 레이어 존재 여부, 레이어명(영문), 별색 채널, Grayscale 단일채널, Dithering, Bleed(1.5mm), Font Outline, Object Flatten (p3, p7, p16, p20)
- 미리보기 이미지(경로 DB 저장), 썸네일 (p5, p21)

**E. 검수/승인 상태**
- 고객 1차 검수, 2차 검수, 주문 승인 데이터, 불일치 원인(내부오류/고객오류) (p2, p21)

## 8. 프린틀리 시사

1. **북극성 정합**: 이 문서는 "고객이 원하는 인쇄물을 받는 여정"의 **견적 확정 + 인쇄가능 파일 확보** 관문을 벤더(RED)가 어떻게 자동화했는지 보여주는 **레퍼런스 구현**. 프린틀리 AI 에이전트가 고객을 이 관문까지 안내하는 것이 목표와 일치.
2. **값=엔진 경계 재확인**: RED도 "가격테이블을 불러온다"까지만 프로세스로 정의하고 **가격 값은 테이블(외부 권위)**에 위임 → 프린틀리의 "견적=벤더별 엔진, 온톨로지는 축까지"와 동형. **후가공 견적은 파일 기하에서 나오므로 온톨로지가 아니라 파일처리 엔진의 산물** — 온톨로지는 "이 후가공은 길이/면적/개수 어느 계산 클래스인가"라는 **축·분류**만 담당.
3. **후가공 축의 표준 어휘**: 14종 후가공 별색 레이어명(Cut/Crease/KissCut/…/Scodix)은 **CIP4/XJDF의 후가공 Intent(§35 다중브랜드 온톨로지)와 매핑할 벤더 실어휘**. RED의 SpotColor 명명규약 = 프린틀리 후가공 온톨로지의 브랜드 앵커 후보.
4. **파일처리 = 잡티켓의 물리적 담체 근거**: 레이어 분리·명명·경로 DB 저장(p3,p5,p6)은 주문이 "잡티켓"으로 생산에 전달되는 물리 메커니즘. 프린틀리 잡티켓 모델이 담아야 할 **파일 아티팩트/폴더 상태 필드**의 실사례.
5. **검수 게이트 = AI 자동화 한계선**: 고객 2회 검수 + 오류 귀책 판정(p2,p21)은 **사람 판단이 반드시 개입하는 지점**. 프린틀리 AI 에이전트도 이 경계에서 "값 생성/승인 금지, 확인 요청" 원칙(D-18) 적용 대상.
6. **데이터 검증(이미지 매칭)**: 원본↔미리보기 자동 대조(p21)는 파일처리 무결성을 보장하는 결정론 게이트. 프린틀리가 다중벤더 파일처리를 중개할 때 "벤더 처리 결과가 고객 원본과 동등한가" 검증 패턴으로 재사용 가능.

## 9. GAP (불확실·문서 미기재)

- **가격 값/단가/가격테이블 스키마 전무** — 이 문서는 프로세스만, 실제 단가·구간은 별도 가격 마스터(문서 밖).
- **Preflight 유효성검사 세부 규칙 미기재**(p2 3단계) — 무엇을 검사하는지 없음.
- **각 후가공 계산 클래스 매핑이 명시적이지 않음** — 어느 후가공이 길이/면적/개수 중 무엇으로 계산되는지는 문서에서 **추론**(p4 계산기 세부단계 + 후가공 물리 특성 기반). 문서에 표로 명시된 것은 아님.
- **레이어 전처리 대부분이 단일 스텁**(Cut/Crease/DashRule/KissCut/Marking/Fold/Punch p8~13,17) — 내부 알고리즘 없음. Scodix(p20)·Brail(p16)·CMYK(p7)만 다단계 상세.
- **"내부오류" 판정 주체 불명**(p21) — 자동 규칙인지 작업자인지 미기재.
- **DB 스키마·테이블명 없음** — "DB 업데이트/DB에 경로 저장"만 서술.
- **조판 프로세스(#13)·배송은 범위 밖** — 별도 특허 문서(자동조판시스템 V1~4.0).
- **문서 연대 2015** — 현 레드프린팅 라이브와 차이 가능(V8.0이나 스텁 다수). 라이브 실화면 대조 미수행(지니 확정 대기).
