# D5 — 운영자 암묵지가 갇힌 곳 (webadmin admin.py / views.py 전수 진단)

- 대상: `raw/webadmin/webadmin/catalog/admin.py` (2,029줄), `raw/webadmin/webadmin/catalog/views.py` (4,273줄)
- 보조 근거: `catalog/basecodes.py` (32줄), `catalog/cfg_utils.py` (441줄, 함수 목록만)
- 읽기 전용. 이 진단 과정에서 raw/webadmin 및 라이브 DB는 단 한 줄도 변경하지 않았다.
- 중복 회피: `_workspace/huni-admin-manual/` 의 화면 맵(01)·값 도메인(02)·화면 인덱스(03)는 "화면이 무엇인가"를 다룬다. 이 문서는 그 화면들이 **전제하는 순서와 규칙**, 즉 문서화되지 않은 채 코드에 굳어 있는 지식을 다룬다.

## 요약

후니 webadmin은 Django admin의 제너릭 자동 등록 위에 얹힌 **규칙 엔진**이다. `_make_admin()`이 34개 t_* 테이블을 기계적으로 화면화하고(`admin.py:1149-1218`, `admin.py:1759-1924`), 그 위에 상품 도메인 특유의 예외가 조건 분기로 덧대어져 있다. 결과적으로 **"무엇을 먼저 등록해야 무엇이 가능한가"라는 운영 절차 지식이 화면 어디에도 표시되지 않고, 폼 필드가 비어 보이거나 드롭다운이 빈 목록으로 나오는 방식으로만 간접 전달된다.**

핵심 결함 세 가지:

1. **참조차원(ref_dim) 정의가 코드 4곳 + DB 트리거 1곳, 총 5벌로 병렬 존재한다** — `VAR_KEY_MAP`(views.py:61-69), `DIM_REF_MODELS`(views.py:1882-1890), `_DIM_LABEL_FIELDS`(views.py:1893-1901), `_IMPACT_SECTIONS`(views.py:3670-3678), 그리고 주석이 "동일하게 유지"하라고 지시하는 DB 함수 `fn_chk_opt_item_ref`(views.py:1881). 차원 하나를 늘리려면 사람이 5곳을 손으로 맞춰야 한다.
2. **기초코드의 "의미"가 코드 리터럴에만 있다** — `SEMI_ROLE.02`=표지(admin.py:1508), `PRD_TYPE.02`=반제품(admin.py:1603), `MAT_TYPE.01`=종이(admin.py:1942), `SEL_TYPE.02`=다중선택(views.py:2001). 기초코드 테이블은 코드·이름을 담지만 **역할(semantic role) 컬럼이 없어**, 이름이 바뀌면 코드 분기가 조용히 어긋난다.
3. **제약 규칙 평가가 fail-open이다** — JSONLogic 평가 예외는 "통과"로 처리된다(views.py:3836-3839, views.py:4101-4104). 잘못 저장된 규칙은 오류 없이 **무력화**되며 아무도 모른다.

이 영역은 **심볼릭 계층은 두껍고, 지식/온톨로지 계층은 거의 비어 있으며, 월드모델(행동→결과 예측)은 세 개의 미완성 싹**(옵션 미리보기·검증 미리보기·사용처 배지)만 존재한다.

## 구조 해설

### 3층 구조

```
[1층] 제너릭 자동 등록      _make_admin() / _apply_readability()
      34개 t_* 테이블 → ModelAdmin 자동 생성          admin.py:1149-1218, 1038-1075
                ↓ 예외 덧대기 (if _model is M.X)      admin.py:1775-1920
[2층] 상품 뷰어 (커스텀)    SECTIONS 8종 read-only 표 + 섹션별 편집 팝업
                                                       views.py:718-754, 1123-1331
[3층] 드릴다운 (3계층)      옵션그룹 → 옵션 → 구성요소 / SKU → 선택값
                                                       views.py:2738-3005
```

1층은 **DB 스키마가 곧 화면**이다. `db_comment`가 폼 라벨이 되고(`admin.py:1057-1061`), 첫 `_nm` 필드가 `__str__`이 된다(`admin.py:1041-1054`). 즉 **DB 주석이 UI 문구의 단일 원천**이라는, 문서화되지 않은 강력한 계약이 존재한다.

2·3층은 1층으로 표현 불가능한 것들의 도피처다. 복합PK 모델은 Django 5.2 admin이 단독 등록을 못 해(`admin.py:1770-1772`) 전부 인라인 또는 커스텀 뷰로 밀려났고, `CompositePKInlineFormSet`(`admin.py:1258-1357`)이 3중 버그를 손으로 우회한다.

### 저장 경로의 이중성

같은 상품 하위 데이터를 **두 경로**가 저장한다.

- `section_edit()` (views.py:1373-1873) — 상품뷰어 섹션 팝업. full-sync 방식(손대지 않은 행도 매번 재기록).
- `_save_drilldown_row()` (views.py:2526-2735) — 옵션/SKU 드릴다운. 행 단위.

두 경로가 **자연키 재채번·키변경 revive·유니크 충돌 선검사**를 각각 구현한다(views.py:1751-1807 vs views.py:2700-2735). 규칙은 유사하나 코드는 별개다.

### 논리삭제 정책의 3중 경로

`cfg_utils.logical_delete_cascade`가 단일 정책 출처로 지정되어 있고(`views.py:1058-1074`), admin 액션(`admin.py:750-784`), 삭제 확인 화면(`admin.py:786-842`), 마스터-디테일 화면(`views.py:1058-1074`) 세 경로가 이를 호출한다. admin.py:754-757의 주석이 명시: "액션 경로처럼 확인 화면을 우회하는 경로 방어를 위해 여기서도 fail-closed 를 재확인한다(마지막 관문)".

## 월드모델 관점 판정

### (1) 뉴로 — **부재**

`admin.py`/`views.py` 전체에 모델 추론·임베딩·확률적 판단이 없다. 전부 결정론적 분기와 DB 조회다.

- [추정] 같은 패키지에 `assistant.py`(827줄)·`assistant_tools.py`(1,116줄)가 존재하나 이번 진단 범위 밖이다. 이름으로 보아 LLM 계층일 가능성이 있으나 **읽지 않았으므로 판정하지 않는다**.

### (2) 심볼릭 — **강함, 그러나 산재**

명시적 규칙 체계가 두껍게 구현되어 있다.

- **규칙 평가 엔진**: JSONLogic 생성(`views.py:152-244`) · 역파싱(`views.py:251-435`) · 평가(`views.py:3827-3846`)
- **제약 유형 체계**: 호환/금지/필수동반 3종 템플릿(`views.py:139-149`)
- **계층 추론**: 공정 상세옵션의 상위 상속 walk(`views.py:1352-1361`), 카테고리 레벨 자동 도출(`admin.py:978-986`)
- **무결성 캐스케이드**: 활성 서브트리 + 외부 사용 판정 fail-closed(`admin.py:786-827`)
- **범위 대수**: 마스터 경계와 상품 오버라이드의 병합·좁히기 검증(`views.py:2491-2521`)

**결함**: 이 심볼릭 규칙들이 **선언되지 않고 절차로 흩어져 있다**. 예를 들어 "참조차원"이라는 개념은 5곳에 각기 다른 형태(var 매핑 / 모델 매핑 / 라벨필드 / impact 매핑 / DB 트리거)로 존재하며, 어디에도 "차원이란 무엇인가"의 단일 선언이 없다.

### (3) 지식/온톨로지 — **거의 비어 있음**

기초코드 테이블(`t_cod_base_codes`)은 온톨로지가 **아니다**. 근거:

- 코드와 이름만 있고 **의미 역할(role) 컬럼이 없다**. 그래서 "표지"라는 개념이 `SEMI_ROLE.02` 라는 **문자열 리터럴로 코드에 박혀야만** 작동한다(`admin.py:1508`, `1526`).
- 계층은 자기참조 FK(`upr_cod_cd`, `upr_proc_cd`, `upr_mat_cd`, `upr_cat_cd`)로 표현되나 **관계 유형이 없다** — 모두 "상위"일 뿐, is-a인지 part-of인지 구분 불가(`admin.py:93-97`).
- 개념 간 제약(예: "판형은 사이즈의 부분집합")은 관계가 아니라 **불리언 플래그 + 코드 필터**로 표현된다(`impos_yn='Y'`, `views.py:1472-1476`).
- 상품 유형·자재 유형·선택 유형이 모두 같은 한 테이블에 접두어로 섞여 있고, 분리는 `BASE_CODE_GROUP` 파이썬 dict가 한다(`basecodes.py:8-25`). 즉 **분류 체계의 정의가 DB 밖에 있다**.

결론: 값 사전(vocabulary)은 있으나 온톨로지(개념·관계·공리)는 없다.

### (4) 월드모델(행동→결과 예측) — **세 개의 미완성 싹**

예측을 지향하는 구조가 세 곳에 존재한다. 모두 **"예측"이 아니라 "표시" 또는 "사후 통보"** 단계다.

| 싹 | 무엇을 하는가 | 근거 | 왜 월드모델에 못 미치는가 |
|---|---|---|---|
| **옵션 선택 미리보기** | 옵션그룹 설정 → 고객 화면이 라디오/체크박스로 어떻게 보일지 렌더 | `views.py:3068-3151` | 렌더링 결과만 예측. 선택의 **결과(가격·제조 가능성)** 는 예측하지 않음. "보기 전용 — DB를 변경하지 않는다"(views.py:3071) |
| **검증 미리보기** | 임의 선택 조합을 넣으면 어느 제약에 막히는지 반환 | `views.py:3799-3848` | 방향은 정확히 월드모델(행동→결과). 그러나 ① 사용자가 조합을 **직접 입력**해야 함(탐색 없음) ② 평가 실패는 통과 처리(fail-open) ③ 가격 결과는 포함 안 됨 |
| **사용처(impact) 배지** | 이 차원행을 참조하는 곳의 개수를 행마다 표시 | `views.py:3681-3742`, `views.py:1207-1208` | "이걸 지우면 무엇이 깨지는가"의 원시형. 그러나 ① `v_cfg_ref_impact` 뷰에 의존 ② **CONSTRAINT 레그는 `ref_dim_cd=NULL`이라 차원행 단위 매칭 불가**(views.py:3685-3686, 3760-3762)라 예측이 구조적으로 불완전 ③ 개수만 알려주고 영향의 **성격**은 모름 |

**추가 근거 — 사후 통보 구조**: SKU 선택값 저장 후 제약을 평가해 경고를 세션에 넣고 리다이렉트한다(`views.py:4081-4114`). 저장을 막지 않는다. 즉 **"저장하면 무슨 일이 생기는가"를 저장 전에 알려주지 못하고, 저장 후에 알려준다.**

**최종 판정**

| 계층 | 상태 | 근거 강도 |
|---|---|---|
| 뉴로 | 부재 (이 범위 내) | 실측 |
| 심볼릭 | 강함, 산재 | 실측 |
| 지식/온톨로지 | 거의 부재 — 값 사전 수준 | 실측 |
| 월드모델 | 싹 3개, 모두 미완성 | 실측 |

**비어 있는 것**: 이 영역에 결정적으로 없는 것은 **③지식/온톨로지 계층**이다. 심볼릭 규칙은 이미 충분히 많은데 그것들이 참조할 개념 모델이 없어서, 규칙마다 코드 리터럴을 다시 적는다. 그리고 온톨로지가 없기 때문에 ④월드모델의 세 싹이 자라지 못한다 — "이 자재를 지우면 무엇이 깨지는가"를 답하려면 자재·용도·공정·가격의 관계가 선언되어 있어야 하는데, 지금은 `v_cfg_ref_impact` 라는 단일 뷰가 부분적으로 대신하고 있고 그마저 CONSTRAINT를 못 잡는다.
