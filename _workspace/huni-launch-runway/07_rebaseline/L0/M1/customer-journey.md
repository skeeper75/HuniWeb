# M1 — 고객 여정 전수 (customer-journey)

> 위젯이 **고객에게 무엇을 시키는가**. 단계마다 「무엇이 필수 / 무엇이 선택」인가.
> 근거: 앱 내장 매뉴얼 2종 · SDK 개발가이드 · **라이브 데모 실동작 관찰**(주문 직전 정지) · 코드.

---

## 0. 전체 흐름 — 고객이 밟는 단계

```
[1] 카탈로그 · 상품 목록          GET /catalog        (시작가·design_cnt 표시)
      │
      ├─ design_cnt ≥ 1 ─▶ [1-a] 디자인 고르기 페이지   GET /designs
      │                          └─ 고른 디자인의 고정 사양이 [2]에서 잠김
      ▼
[2] 주문 페이지 = 위젯            GET /widgets/{wgt_cd}   ← 게시본만
      │
      ├─ [2-1] 사양 선택(차원·옵션·후가공)  ─▶ POST /price   (300ms 디바운스, 서버 계산)
      │                                    └▶ POST /validate (제약 검증)
      ├─ [2-2] 수량 · 페이지수 · 건수 입력
      ├─ [2-3] 제작물 제목 입력
      ├─ [2-4] 원고 —  파일 업로드  ─▶ POST /upload/presign ─▶ S3 직접 PUT
      │              └ 또는 편집기 ─▶ POST /editor/resolve + /editor/token ─▶ Edicus
      ▼
[3] 「장바구니 담기」              POST /handoff   ← ★최종 관문(전체 재검증) → 서명 token
      │
      ▼  ── 여기부터 쇼핑몰(자사몰) 영역 ──
[4] 후니 항목 보관소               POST /cart/items  (S2S) → item_id
[5] 샵바이 장바구니                POST /cart        (optionInputs 2칸 + orderCnt=총액÷10)
[6] 장바구니 화면                  POST /cart/items/fetch (S2S, ≤50건)
[7] 수량 변경(선택)                PUT  /cart/items/{item_id} {qty|copies}
[8] ★결제 직전 갱신(필수)          PUT  /cart/items/{item_id} (수량 생략)
[9] 결제 → 주문 생성               (샵바이)
[10] 주문 등록(필수)               POST /order/register → t_ord_orders
      │
      ▼  ── 여기부터 M3(생산) 영역 ──
```

> **[1]~[3] = 위젯(후니) 담당. [4]~[10] = 쇼핑몰 담당.** 이 경계가 M2 계약의 실체다.

## 1. 단계별 필수/선택 표

### [2-1] 사양 선택

| 입력 | 필수 여부 | 미충족 시 `reasons` 문구 | 근거 |
|---|---|---|---|
| 차원(사이즈·자재·인쇄옵션 등) | **필수** — 값이 정해져야 가격이 나옴 | `"사이즈 선택"` / `"내지종이 선택"` | 라이브 `huni:state` 캡처 |
| 기본값이 있으면 | 자동 선택됨 | — | 상품설정 `dflt_yn` 또는 위젯 `dflt_val`(**위젯 우선**) |
| 컨트롤 숨김 항목 | 고객에게 안 보이지만 **기본값 강제 적용** | — | 매뉴얼 `COMMON_PROPS` |
| 옵션그룹 | 그룹 마스터의 단일/다중 설정에 따름 | 그룹명으로 안내 | 매뉴얼 |
| 후가공(공정) | **필수 공정은 해제 불가** · 나머지 선택 | — | 매뉴얼 컴포넌트 「후가공」 |
| 비규격 치수 | 상품 `비규격여부=Y` 일 때만 | `bad_dim_precision`(소수 자릿수 초과) | SDK 가이드 §15 |

**라이브 실측** (`WGT_000288` 무선책자, 아무것도 안 고른 초기 상태):
```json
"reasons": ["내지 원고 파일 업로드", "표지 원고 파일 업로드", "사이즈 선택",
            "제작물 제목 입력", "내지종이 선택", "가격 계산 대기/불가"]
```
> 셋트는 미충족 문구 앞에 **구성원 역할명이 붙는다** — `"내지 원고 파일 업로드"`.

### [2-2] 수량 · 페이지수 · 건수

| 입력 | 필수 | 규칙 출처 | 오류 코드 |
|---|---|---|---|
| **수량**(`qty`) | 필수 | 상품 `min_qty/max_qty/qty_incr/dflt_qty` + **사이즈별 수량규칙**(있으면 우선) | `bad_qty` |
| **부수**(`copies`) | 셋트만 | 셋트 `qty_rule` (라이브 실측 무선책자: min 2, max 1000, incr 1, 단위 「권」) | `bad_copies`·`set_not_supported` |
| **페이지수**(`pages`) | 페이지룰 있는 인쇄옵션이면 필수 | 상품 페이지룰 (라이브: min 24, max 300, incr 2) | `bad_pages`·`pages_required` |
| **건수**(`case_cnt`) | 선택 (기본 1) | **컴포넌트 `props.min/max` 가 유일 출처** — 상품 마스터 개념 없음 | `bad_case_cnt`·`case_cnt_not_allowed`(셋트) |

> [HARD] **유효 수량은 `min + incr×n` 이지 `qty % incr` 가 아니다** (SDK 가이드 §14 `requote`).
> 건수 = 사양·수량 동일, **원고만 다른 반복 벌수**. 청구식 = **건당 계산결과 × 건수** (추가상품은 곱해지지 않음).

### [2-3] 제작물 제목

| 항목 | 값 |
|---|---|
| 필수 여부 | **기본 필수** (`props.required !== false` — 속성을 한 번도 안 건드린 항목은 필수) |
| 최대 길이 | **UTF-16 코드유닛 100** — 이모지는 2로 셈 |
| 왜 | **MES 동일 필드가 `nvarchar(100)`** — SQL Server 는 문자 수가 아니라 코드유닛 수 |
| 가격 영향 | **없음** — 주문 정보로만 넘어감 |
| 오류 | `bad_order_title` · `order_title_not_allowed`(컴포넌트 없는데 값 전송) |

근거: 렌더러 `widget_renderer.js:52` · 서버 `widget_api.py:1351` (한 벌로 유지 — 「한쪽만 바꾸면 화면 통과·주문 422」)

### [2-4] 원고 — **파일 업로드와 편집기는 「둘 중 하나」**

| 위젯 구성 | 미충족 시 문구 |
|---|---|
| 파일 업로드 **+** 편집기 | `"원고 업로드 또는 편집기로 만들기"` ← **한 벌로 묶여 둘 중 하나만 하면 통과** |
| 파일 업로드만 | `"원고 파일 업로드"` |
| 편집기만 | `"편집기로 원고 만들기"` |
| 업로드 진행 중 | `"원고 업로드가 끝나기를 기다리는 중입니다"` |
| 업로드 실패 | `"업로드에 실패한 원고가 있습니다 — 다시 시도해 주세요"` |

**라이브 실측**(핀버튼 WGT_000005, 파일업로드+편집기 둘 다 배치):
`reasons: ["원고 업로드 또는 편집기로 만들기"]` — 매뉴얼 기술과 일치 확인.

- **편집기는 「저장」을 해야 충족.** 열어보고 닫기만 하면 미충족.
- **전송이 끝난 파일만** 원고로 인정(업로드 중·실패는 미충족).
- 원고를 나중에 받는 상품이면 담당자가 해당 항목을 **선택 항목으로 설정**해 이 검사에서 뺄 수 있다.

### [3] 「장바구니 담기」 = 주문 인계(handoff)

**클라이언트 판정 → 서버 재검증, 2겹**

| 층 | 무엇을 보나 | 실패 시 |
|---|---|---|
| 브라우저 | `canOrder` + `reasons[]` — **네트워크 왕복 0회** | 버튼 비활성 + 사유 표시. `submit()` 을 억지로 불러도 `{ok:false, code:"incomplete", reasons}` 즉시 반환 |
| 서버 (`POST /handoff`) | 가격·제약·원고·수량규칙·조합템플릿·책등 **전부 재검증** | 422 (fail-closed) |

**서버 재검증 순서** (코드 `widget_api.py:_quote()` 실행 순서):
1. 사용중지 선택값 관문 (`_off_sel_err`)
2. 제작물 제목 (`parse_order_title`)
3. 디자인 존재·소속·**고정사양 일치**(`design_spec_mismatch`)
4. 책등 재계산 (`SW.resolve_ctx`) — **클라가 보낸 spine 값은 색상 하나 빼고 전부 무시**
5. (셋트) 구성원 정제 → 셋트 가격 → 셋트 제약
   (단일) 차원 정제 → 치수 정밀도 → 수량규칙 → 건수 → 페이지수 → 후가공 상세 → 제약 → 가격
6. 단가 갭 (`price_gap` — **언더차지 차단**)
7. 추가상품 재계산 (`_addons_strict`)
8. 부가세 정산 → **10원 배수 검사**(`price_unit_mismatch`)
9. 원고 필수 검사 (`_check_artwork`) + **S3 키 모양 검증**
10. 옵션 전개 (`_expand_opt_sels`) — MES 전달용
11. **조합 템플릿 → 자재 확정** (`TC.resolve_all`, 미등록 = `tmpl_combo_gap` 422)
12. 책등 payload 적재/거절 판정
13. **HMAC 서명 → token** (유효기간 **3600초**)

**성공 응답**
```json
{ "ok":true, "token":"eyJ…", "payload":{…}, "expires_in":3600,
  "handoff_id":"550e8400-…", "qty_rule":{min,max,incr,dflt} }
```

> [HARD] `submit()` 은 **절대 throw 하지 않는다** — 실패도 항상 resolve.
> ⚠ **중복 제출 가드가 위젯에 없다** — 버튼 연타로 handoff 가 여러 번 서명될 수 있다.
> 호스트가 `disabled` 로 막아야 한다 (SDK 가이드 §5 「알려진 요철 ③」).

## 2. 이벤트 계약 (호스트가 붙잡는 지점)

| 이벤트 | 언제 | detail |
|---|---|---|
| `huni:ready` | 로드·첫 렌더 완료 | `{widgetId, product, widget:{wgt_nm,ver_no}, reasons[]}` |
| `huni:change` | 고객이 선택을 바꿈 | `{state{…}, summary[{label,value}], reasons[]}` |
| `huni:priced` | 가격 계산 성공 | `{total, ok}` |
| `huni:state` | **주문가능 상태 변화** (ready 직후 1회 보장) | `{canOrder, reasons[], price\|null}` |
| `huni:submit` | 핸드오프 성공 | `{ok:true, token, payload, handoff_id, summary, expires_in}` |
| `huni:editor` | 편집기 버튼 클릭 (**취소 가능**) | `{item, mbr, product, widgetId}` |
| `huni:error` | 가격/검증/핸드오프/편집기 실패 | `{message, code?, cause?}` |

**발화 순서 계약**: `ready → state(초기 1회 보장) → 이후 상태가 실제로 바뀔 때만`. 같은 상태 연속 발화는 억제.

### `state` 객체 실측 (라이브 캡처)

**단일 상품** (핀버튼):
```json
{ "kind":"single",
  "selections":{"siz_cd":"SIZ_000548","bdl_qty":"4"},
  "qty":2, "addons":[], "procSels":[], "files":[], "editors":[],
  "caseCnt":null, "orderTitle":null, "pages":null, "spineColor":null }
```

**셋트 상품** (무선책자):
```json
{ "kind":"set", "copies":3,
  "members":[
    {"sub_prd_cd":"PRD_000290","role":"SEMI_ROLE.02","role_nm":"표지","inst":1,
     "label":"무선책자-표지","siz_cd":"SIZ_000632","mat_cd":"MAT_000074",
     "print_opt_cd":"POPT_000001","procs":[{"proc_cd":"PROC_000004","detail":{}}]},
    {"sub_prd_cd":"PRD_000289","role":"SEMI_ROLE.01","role_nm":"내지","inst":1,
     "label":"무선책자-내지","siz_cd":"SIZ_000250","print_opt_cd":"POPT_000002","pages":24}],
  "addons":[], "setSelections":{}, "setProcs":[], "files":[], "editors":[],
  "orderTitle":null, "spineColor":null,
  "memberSpecs":{"무선책자-표지":"무선/PUR책자 표지A5, 백색모조지 220g, 단면, 디지털인쇄",
                 "무선책자-내지":"A5세로 (148x210mm), 양면, 24페이지"} }
```

> ⚠ **`state` 는 위젯 내부 표기(camelCase)이고 `payload` 는 서버 표기(snake_case)다.**
> `procSels`↔`proc_sels`, `caseCnt`↔`case_cnt`, `orderTitle`↔`order_title`.
> **둘을 같은 것으로 취급하면 안 된다** — `state` 는 화면 정보, `payload` 는 서명된 사양이다.

## 3. 호스트가 고를 수 있는 3가지 모드

| 모드 | 속성 | 효과 |
|---|---|---|
| 기본 | — | 위젯 내장 「장바구니 담기」 버튼 + 미충족 사유 안내 |
| 자체 버튼 | `hide-submit` | **버튼 한 줄만** 숨김. 사유 안내는 위젯 안에 남음. `huni:state` 로 호스트 버튼 동기화 필요 |
| 완전 자체 UI | `hide-submit hide-reasons` | 사유도 위젯이 안 그림. 호스트가 `reasons[]` 로 전부 그림 |
| 편집기 가로채기 | `huni:editor` + `preventDefault()` | 위젯 오버레이 미표시. 끝나면 `el.setEditorResult(item, {prjid})` 로 결과 반영 **필수** |
| 디자인 잠금 | `design="DSN_000001"` | 고정 사양(사이즈·페이지수 등) 잠김 + 배너 표시 |

## 4. 결제 이후 — 담당 경계 (SDK 가이드 §10)

| 구간 | 담당 |
|---|---|
| 위젯으로 사양 선택 · 원고 업로드 | **위젯(자동)** |
| 장바구니 담기 · 결제 직전 재견적 | 쇼핑몰 |
| 주문 생성 | 쇼핑몰 |
| **주문 등록 호출 1개** | 쇼핑몰 |
| 원고 파일 보관·이동 | **후니** |
| 파일 오류 검사 · 고객 재업로드 안내 | **후니** |
| **생산 시스템(MES) 접수** | **후니** |
| 주문상태 변경 · 송장번호 등록 | **후니** |
| 생산 진행에 따른 고객 알림 | **후니** |

**쇼핑몰이 만들면 안 되는 것 3가지** (가이드 §10 「주의할 것」):
1. 쇼핑몰 관리자에서 **주문 상태를 손으로 바꾸지 마라** — 취소 가능/불가 경계가 어긋난다.
2. **별도의 주문취소 기능을 만들지 마라** — 취소 정책은 주문상태로 강제된다.
3. **가상계좌 입금기한은 3~7일** — 원고 임시 보관이 30일이라 그보다 길면 입금 전에 원고가 사라진다.

취소 경계: `입금대기·결제완료` = 즉시 취소 가능 / `상품준비중`부터 = 취소요청 후 담당자 승인.

## 5. 보관 기간 — 「가장 짧은 것」을 따른다

| 부속물 | 보존 기간 |
|---|---|
| 원고 파일 (S3 임시버킷) | **30일** — 확인됨 |
| 편집기 프로젝트 (Edicus) | **미확인 — 후니가 Edicus 담당자에게 확인 중** |
| 샵바이 장바구니 | **미확인 — 쇼핑몰이 알려줘야 함** |
| 후니 항목 보관소 | 30일 (위에 맞춤) |
| 주문 토큰 | **1시간** (재견적 필요) |

> [HARD] 기간은 **「처음 담은 시각」부터** 센다. 결제 직전 갱신을 아무리 자주 불러도 30일은 연장되지 않는다(`payload.orig_ts` 가 불변이라 그렇다).
> ⚠ **알려진 구멍**(코드 주석 `widget_api.py:3237`): 「S3 수명주기로 원고가 이미 삭제된 장바구니 항목도 **재견적은 통과**한다 — 결제·승격 단계에서 잡아야 한다」

## 6. 라이브 관찰에서 발견한 이상 (관찰 사실 · 원인 미확인)

### 6.1 셋트 위젯 `summary` 의 후가공 라벨이 전부 「디지털인쇄」

라이브 `WGT_000288` `huni:change` 캡처:
```json
"summary":[ …, {"label":"표지코팅","value":"디지털인쇄"},
                {"label":"박가공","value":"디지털인쇄"},
                {"label":"형압","value":"디지털인쇄"} ]
```
표지 구성원에 후가공 컴포넌트가 3개 배치돼 있는데(표지코팅·박가공·형압), 고객이 아무것도 고르지 않은 초기 상태에서 **세 라벨 모두 필수공정 `디지털인쇄`(PROC_000004) 를 값으로 표시**한다.

- **관찰 사실**: 위와 같다. 라이브 데모에서 재현됨.
- **원인 미확인**: 요약 생성 로직이 「구성원의 선택된 공정 전체」를 컴포넌트마다 반복 표시하는 것으로 보이나, 코드로 확인하지 않았다.
- **영향 범위 미확인**: 이 `summary` 는 **샵바이 `huni_order` 텍스트 옵션(셀러어드민 주문 상세)에 그대로 실린다.** 담당자가 읽는 문자열이 틀리면 오생산 유발 가능. 단, 서명 payload 의 `procs` 자체는 정상이므로 **가격·생산 데이터에는 영향 없음**으로 보인다(미검증).
- **분류**: 표시 결함 후보. **재현 절차가 있으므로 개발 전달 대상.**

## 7. 미확인

1. **실제 자사몰(huni-skin-shopby) 화면에서의 고객 여정** — 관찰한 것은 후니가 만든 데모 스토어(`/sdk/demo/`)다. 자사몰 실화면은 보지 않았다.
2. **디자인 고르기 페이지의 실동작** — 라이브 카탈로그의 게시 위젯 중 `design_cnt ≥ 1` 인 상품이 없어(전부 `dsn=0`) 관찰 불가.
3. **편집기(Edicus) 실제 오픈 동작** — 데모에서 편집기 버튼을 누르지 않았다(외부 SaaS 호출·프로젝트 생성이 발생할 수 있어 읽기전용 원칙에서 보류).
4. **파일 업로드 실동작** — presign 발급이 실제 S3 오브젝트를 만들 수 있어 수행하지 않았다.
5. **제약 규칙이 걸린 위젯의 UI 동작**(`block_typ_cd` 비활성/숨김) — 관찰한 두 위젯 모두 `constraints.rules = []`.
6. **`huni:submit` 실제 payload** — 장바구니 담기를 누르지 않아 실물 미관측. payload 스키마는 코드·SDK 가이드 근거.
7. **게스트(비회원) 구매 성립 여부** — M2 영역.
