# 위젯 가격 오류 차단 — 계층 가드 설계 (개발자 요청서)

> 목표(운영자 원문): 「최종적으로 위젯에서 가격이 세지않고 정확하게 나오게하는 최선의방법」
> 작성 근거: 2026-08-28 실측. 코드는 `raw/webadmin/` 직독(읽기전용), 라이브는 SELECT 만.
> 인용 원칙 — **읽지 않은 가드는 서술하지 않았다.** 측정하지 않은 수치는 「미측정」으로 표기했다.

---

## 0. 결론 한 장

오늘 적발된 결함 7종은 **전부 `ok=true` 로 통과했다.** 원인은 가드의 부재가 아니라 **가드가 보는 축이 하나뿐**이라는 데 있다:
현행 가드는 전부 「엔진이 값을 만들어냈는가(`is not None`)」만 본다. **「그 값이 권위 엑셀의 값인가」를 보는 가드는 코드 어디에도 없다.**

그래서 설계의 축은 두 개다.

| 축 | 질문 | 현행 | 제안 |
|---|---|---|---|
| **산출 가능성** | 값이 나오는가 | 있음(strict·`_price_gap_errors`·`verify_zero_quote`) | 구멍 3개 메우기 |
| **산출 정확성** | 나온 값이 권위값인가 | **전무** | 신설(L1·L2·L4) |

최고 레버리지는 **L2 구조 시점 가드(공식 구성 저장 시점)** 다 — 7종 중 3종(①·⑤·④)이 「단가를 잘못 입력해서」가 아니라 **「구성요소를 잘못 엮어서」** 생겼고, 이 시점은 고객 노출 이전이며 검사 비용이 쿼리 몇 개다.
다만 **첫 배포는 L1(적재 시점) 0원·이상치 가드**여야 한다 — 20줄이고 오늘 당장 나간다.

## Part A — 현행 가드 실측

각 항목은 실제로 읽은 코드다. 「무엇을 검사하는가」는 코드가 하는 일만 적었고, 「7종 판정」은 그 검사로 잡히는지 여부다.

### A-1. `price_grid_save` — 단가표 그리드 저장 (`price_views.py:1411-1520`)

전 검사 항목 전수(errors.append 8곳, `:1460`·`1468`·`1473`·`1480`·`1487`·`1490`·`1495` + `:1509` 전체삭제 방지):

| 검사 | 위치 | 내용 |
|---|---|---|
| 공정 상세 파라미터 타입 | `:1460` | int/number 캐스팅 실패 |
| 적용일 형식 | `:1468` | `yyyy-MM-dd` |
| **단가 숫자 파싱** | `:1473` | `Decimal(...)` 파싱만. **부호·범위·0 검사 없음** |
| 차원 int 캐스팅 | `:1480` | |
| 차원 numeric(8,2) 정규화 | `:1487` | |
| 공정 소속 검사 | `:1490` | 하위공정 아닌 `proc_cd` 거부 |
| 페이로드 내 자연키 중복 | `:1495` | 같은 (적용일·차원·상세) 2행 |
| **전체 삭제 방지** | `:1505-1510` | 유효행 0인데 기존행 존재 → 422 |

`:1473` 이 결정적이다. `Decimal("0")` 도 `Decimal("-5000")` 도 유효한 파싱이다 — 저장된다.
그리고 이 뷰는 **full-sync**(`:1411` docstring: 「그리드에 보이는 행이 곧 이 구성요소의 전체 단가표」)라, DB 에만 있는 키는 **말없이 삭제**된다. 「전체가 비었을 때」만 막고, **「52행 중 2행이 사라졌을 때」는 막지 않는다.** 이것이 결함 ④(폼보드 A1 소실)가 통과한 자리다.

- 판정: ③·④ **미탐지**. ①②⑤⑥⑦ 범위 밖.

### A-2. `pricing.evaluate_price` strict 모드 (`pricing.py:604-720`)

- 소스 우선순위 `TEMPLATE_PRICE → PRODUCT_PRICE → FORMULA → NONE` (`:604-650`).
- **strict 차단 조건은 정확히 두 갈래뿐**:
  1. `_FATAL_ERRORS`(`:73-75`) 에 속한 구성요소 오류 — `ambiguous_combo`·`duplicate_rows`·`below_min_qty`·`above_max_size`·`no_tier_row`·`no_plate_pansu`. 판정은 `_is_fatal`(`:78-80`), 차단은 `:664-667`.
  2. 공식인데 `included` 구성요소가 **0건**(`:671-675`), 또는 소스 자체 부재(`:657-661`).
- **`_FATAL_ERRORS` 에 「순수 no-match」가 없다.** `pricing.py:799-811` 에서 `m["row"] is None` 이면 `data_gap` 만 기록하고 **경고조차 내지 않는다**(코드 주석: 「무관 공정 등 정상 no_match 포함이라 시끄럽지 않게」). 즉 구성요소 1개가 통째로 빠져도 나머지가 1개라도 매칭되면 strict 통과.
- 0원: `:614`·`:634` 는 `unit_price is not None` 만 본다. `Decimal(0) * qty = 0` → `source=TEMPLATE_PRICE`, `ok=True`, `final=0`.

- 판정: ③ **미탐지**(설계상 0은 유효값). ①②④⑤ 미탐지. 잡는 것은 「구간행 없음」·「동시매칭」·「중복행」 뿐.

### A-3. `widget_api._price_gap_errors` (`widget_api.py:719-786`)

유일하게 「단가행 갭」을 고객 주문 경로에서 fail-closed 로 막는 가드. 배선은 표시 `:2029-2033`(→ `ok=false`, `code=price_gap`), 서명 `:2918-2921`(→ 422).

입력이 엔진의 `data_gap` 이므로 **엔진이 gap 으로 기록한 것만** 본다. 구멍 셋(전부 코드에 명시적으로 주석돼 있다):

| 구멍 | 위치 | 내용 |
|---|---|---|
| `proc_cd` 제외 | `:756-757` | 공정 다중선택 합산 모델이라 오탐 폭발 회피 — 의도적 |
| 가족형 쌍 면제 | `:744-751` (`covered` 집합) | 형제 구성요소가 그 (차원,값)을 **명시 행**으로 커버하면 면제 |
| 셋트 경로 미적용 | `:728` docstring 「단일상품 경로 전용」 | `_filter_set` 은 이 가드를 안 탄다 |

★ **가족형 쌍 면제가 결함 ①을 정확히 통과시킨다.** 캔버스행잉포스터는 같은 나무봉 단가를 가진 구성요소가 둘이므로, 한쪽이 값을 커버하는 순간 다른 쪽의 공백은 「가족 분담」으로 면제된다. 가드는 이 상태를 **정상으로 판정한다.**

- 판정: ①②③④⑤⑥⑦ 전부 **미탐지**. 잡는 것은 「고객이 고른 값에 해당하는 행이 아예 없음」 한 종류.

### A-4. `_addons_strict` / `_compute_addons` (`widget_api.py:1592-1625`, `:1862-1874`)

- `strict_none=True`(서명 경로)면 `amount is None` 인 추가상품에서 즉시 422(`:1619-1620`, `:1869-1872`).
- 표시 경로는 `strict_none=False` — `amount=None` 을 항목에 남기고 합계에서 `or 0`(`:1851`) 로 **0 취급**.
- **`amount == 0` 은 `None` 이 아니므로 두 경로 모두 통과한다.**

- 판정: ③ **미탐지**. 나머지 범위 밖.

### A-5. `_filter_set` vs `_filter_single` — 비대칭 (`widget_api.py:1832` / `:1876`)

```python
1833:    ok = bool(res.get("ok")) and res.get("final_price") is not None   # 단일
1877:    ok = res.get("final_price") is not None                            # 셋트 — res["ok"] 를 안 본다
```
셋트는 엔진이 `ok=False` 를 냈어도 `final_price` 만 있으면 `ok=true` 로 나간다. 여기에 A-3 의 셋트 미적용까지 겹쳐 **셋트 경로가 단일보다 두 겹 약하다.**

### A-6. 게시 흐름 (`widget_views.publish_widget:467-518`, `publish_gate.js`)

`publish_widget` 본체가 하는 검사 전수: **위젯 항목 0건**(`:501` `EmptyWidgetError`) + **같은 site×prd 게시 겹침**(`:503` `PublishConflictError`). **가격 검사 0건.**

클라이언트 관문 `publish_gate.js` 의 5개 판정 중 가격 관련은 `startPriceWarn`(`:89-101`) 하나뿐이고, 이것도 **차단이 아니라 `confirm()`** 이다(파일 헤더 `:8` 「막지 않는다 — 확인만 받는다」). 판정 재료는 `_start_price_brief`(`widget_views.py:521-530`) → `auto_amt` 또는 `man_amt` 가 **존재하는가**뿐. 값의 정확성은 보지 않는다.

- 판정: ⑥ **미탐지**. 게시 관문에 「이 상품 가격이 권위와 맞는가」를 묻는 자리 자체가 없다. 131건 일괄 게시가 가능했던 구조적 이유다.

### A-7. 시작가 배치 (`start_price.py`, `tools/recalc_start_prices.py`)

- 대상 판정(`start_price.py:targets`, `:53-79`): 게시+활성버전+미삭제·미중지+상품 `use_yn='Y'`. **운영자의 스코핑 규칙과 이미 일치한다** — 재사용할 선례.
- 계산: 렌더러 하네스(`tools/start_price_collect.js`)로 **기본값 1조합**만 만들고 `_price_core` 로 평가.
- 실패는 `fail_rsn` 에 기록, `auto_amt` 는 NULL 로 지움(fail-closed).
- `recalc_start_prices.py:44-46`: 상품별 실패는 **exit 0**. 「상시 실패 80건」 때문에 의도적으로 완화된 상태 — 즉 **이 배치의 실패 신호는 현재 사실상 꺼져 있다.**

- 판정: 「기본 조합에서 가격이 안 나옴」만 탐지. ①②③④⑤ 미탐지(0원도 값이므로 성공 처리).

### A-8. 이미 존재하는 회귀 도구 두 개 [중요 — 신규 개발 이전에 배선부터]

**`tools/verify_zero_quote.py`** — 읽기전용 0원 견적 전수 적발기. 헤더 전문 정독함.
- 검출 4종: `ZERO_FINAL` / `NO_SOURCE` / `UNDERCHARGE`(엔진 `_FATAL_ERRORS` 로 제외된 구성요소 존재) / `ENGINE_ERROR`.

**`tools/audit_published_prices.py`** — 게시 위젯 전수 가격계산 점검. **활성 버전 스냅샷**(`t_wgt_widget_versions.cfg`, `act_yn=Y`) 기준, 조립은 렌더러 재사용, 평가는 `api_price` 미러(`_price_gap_errors` 포함).

## Part B — 도메인 리서치

벤더 마케팅과 확립된 실무를 구분해 적었다. 원리만 흡수하고 도구는 답습하지 않는다.

### B-1. 승인 테스트(Approval / Characterization / Golden Master) — **확립된 실무**

Michael Feathers 계보의 기법으로, 명칭만 넷일 뿐 같은 기법이다(regression / characterization / golden master / snapshot). 정의가 우리 문제에 정확히 맞는다: 「코드의 **올바른** 동작을 검증하지 않는다. 작성 시점에 **관측된** 동작을 검증한다」 — 즉 **변경 탐지기**다.

우리에게 주는 원리:
- 가격 엔진의 「정답」을 코드로 서술하려 들면 실패한다(공식 118개·차원 12종). 대신 **관측 출력을 고정**하고 **차이만** 띄운다.
- 「승인(approval)」이라는 이름이 핵심이다 — 스냅샷 갱신은 사람이 승인하는 행위다. 결함 ④(개편 중 소실)는 **승인 없이 스냅샷이 갱신된 것**과 같은 사건이다.

### B-2. 재조정(Reconciliation) — 검증(validation)과 다른 통제 — **확립된 실무**

MDM 실무에서 재조정은 「데이터가 시스템 간 이동 후에도 완전·정확·일관한가」를 보는 별도 통제로, 데이터 품질 검증과 구분된다. 기법 계층이 명시적이다: **레코드 수 → 키 대조 → 해시 비교 → 속성(셀) 단위 비교**. 인용하자면 「counts, keys, hashes 를 비교하라 — 아니면 golden record 는 금칠일 뿐이다」.

우리 상태 대입:
- `diff.py` 는 **레코드 수 단계에서 멈춰 있다.** 그 단계만으로 9/26 이 걸렸다.
- 셀 단위 비교로 내려가야 회전(②)이 잡힌다.
- 「반복되는 불일치는 임계값이 아니라 **검증 규칙으로 승격**한다」는 운영 원리도 그대로 쓸 수 있다.

### B-3. 가격 가드레일 — 앵커 / 코리도 / 승인 계층 — **확립된 실무(CPQ 딜데스크)**

세 층으로 정리돼 있다:
1. **구조** — 참조가(list/anchor), 세그먼트별 **밴드(corridor)**, 가이던스 플로어와 절대 플로어. 단일 숫자가 아니라 **구간**으로 잡는다.
2. **승인 아키텍처** — 자율 구간 / 위임 승인 / 예외 승인의 3티어. 「위임은 트리거 기반이고 팀 간 일관돼야 한다 — 아니면 판매자가 승인자를 쇼핑한다」.
3. **집행 수단** — 시스템 통제(「승인 ID 없이 가이던스 플로어 미만 견적 생성 자체를 막는다」) + 예외율 대시보드 + **사후 표본 검증**.

우리에게 주는 원리: 결함 ②(회전)는 **개별 행이 전부 그럴듯했다**. 밴드(같은 구성요소·같은 축의 이웃 값 대비 이상치)는 「그럴듯한 개별값」을 잡는 유일한 값-무관 신호다. 다만 **밴드는 경고이지 차단이 아니다** — 차단은 권위 대조가 한다.

### B-4. 4-eyes / maker-checker — **확립된 실무(금융권 규제 요건)**

「각 거래에 최소 2인이 필요하다」. 민감 필드를 지정해 그 필드가 바뀌면 **다른 사용자의 검증 대기 상태로 플래그**하는 형태가 마스터데이터에 적용된 표준형이다(SAP S/4HANA 민감필드 패턴). 자기 자신의 변경을 자기가 승인할 수 없다.

우리에게 주는 원리: 결함 ⑥의 131건은 **maker 만 있고 checker 가 없었던 상태**다. 전면 도입은 과하지만, **「게시」라는 단 한 지점**에 「가격 검토자 서명」을 요구하는 것은 최소 비용의 4-eyes 다. 이미 `ver_note` 라는 자리가 존재하고, 거기에 「가격 미검토」라고 **자기 신고까지 돼 있다.**

### B-5. 벤더 주장으로 분류하고 채택하지 않은 것

- 「CPQ 도입으로 가격 오류 45% 감소」류의 수치 — 출처가 벤더 블로그이고 방법론 미공개. 원리(규칙 기반 승인 워크플로)만 취하고 수치는 인용하지 않는다.
- MDM 스위트의 「적응형 품질 개선」 — 제품 기능 서술. 우리는 규칙 승격 원리만 취한다.

### L1. 적재 시점 (담당자가 그리드에 값을 입력하는 순간) — **첫 배포 대상**

#### G1-1. 0원·음수 저장 규율 (`price_views.py:1473` 직후)
- **검사**:
  - `price < 0` → **무조건 거부**.
  - `price == 0` **AND** `note` 가 비어 있음 → **거부**. `note` 가 있으면 통과(무료 사유가 감사 기록으로 남는다).
- **왜 「0 금지」가 아닌가**: 라이브에 0원 행 12건이 실재하고, 의도된 무료인지 미입력인지 **코드로 구분 불가**(A-10). 하드 금지는 12건을 즉시 저장 불가로 만든다. 사유 강제는 스키마 변경 없이 의도를 데이터에 새긴다.
- **실패 문구**:
  - `단가는 음수일 수 없습니다. 행을 지우려면 그리드에서 행 자체를 삭제하세요.`
  - `단가 0원은 '비고'에 무료 사유를 적어야 저장됩니다 (예: 기본 포함 · 프로모션). 값을 아직 모르면 행을 비워 두세요 — 0원은 '가격 미입력'보다 나쁩니다(고객에게 0원으로 노출되고 주문까지 통과합니다).`
- **비용**: 극소(≈15줄). **오탐 위험**: 12건 재저장 시 사유 입력 요구 — 의도된 마찰.
- **잡는 것**: ③(부분 — 구성요소 단가 축)

#### G1-2. 템플릿 직접단가 0원 거부 (`price_views.py:1685` 저장 경로)
- **검사**: 추가상품 템플릿 직접단가 `== 0` → 거부.
- **근거**: 라이브 0건(A-10)이므로 합법 사례가 없고, 0원 행은 상품가 fallback 을 **영구 차단**하면서 422 도 통과한다(엔진 정본 §4).
- **실패 문구**: `추가상품 템플릿 단가에 0원은 넣을 수 없습니다. 무료로 두려면 「삭제」로 행을 지우세요 — 0원 행은 상품 가격으로의 자동 대체를 막고 0원 주문이 통과합니다.`
- **비용**: 극소. **오탐 위험**: 0(합법 사례 없음). **잡는 것**: ③

#### G1-3. Full-sync 삭제 미리보기 (`price_views.py:1505-1510` 확장)
- **검사**: 이번 저장으로 **삭제될 기존 행 수** `D` 와 남는 행 수 `K` 를 세어, `D > 0` 이면 저장을 **1차 거부**하고 삭제 대상 목록(적용일·차원값·단가)을 돌려준다. 클라이언트가 목록을 보여주고 `confirm_delete: true` 재전송 시에만 실행.
- **왜**: 결함 ④의 발생 형태가 정확히 이것이다 — 구성요소 축 개편 저장 한 번에 A1 20,000원 행이 흔적 없이 사라졌다. 현행은 「전멸」만 막는다(`:1505`).
- **실패 문구**: `이 저장으로 기존 단가행 {D}개가 삭제됩니다. 아래 목록을 확인하세요. — {적용일} {차원} {단가}원 …  삭제가 맞으면 [확인 후 저장]을 누르세요.`
- **비용**: 소(서버 20줄 + 그리드 확인 모달). **오탐 위험**: 0(정보 제시형). **잡는 것**: ④

#### G1-4. 이웃 이상치 경고 (비차단)
- **검사**: 저장 직전, 같은 `comp_cd` 의 같은 축 이웃 행과 비교해 **비단조**(사이즈가 커지는데 값이 작아짐) 또는 **10배 이상 점프**를 경고로 표시.
- **왜**: 결함 ②(회전)는 개별 행이 전부 그럴듯했다. 회전은 대체로 **단조성을 깨뜨린다** — 값-무관 신호로는 이것이 유일하다.
- **실패 문구**(경고): `⚠ 사이즈가 커지는데 단가가 내려갑니다 (600mm 20,000 → 800mm 6,000). 값이 밀려 들어갔는지 확인해 주세요.`
- **비용**: 소. **오탐 위험**: **중** — 구간 정책상 정당한 역전이 있을 수 있어 **반드시 경고(비차단)**. **잡는 것**: ②(부분·확률적)

### L2. 구조 시점 (공식 구성요소 구성이 저장될 때) — **최고 레버리지**

이 계층이 최고 레버리지인 이유: 7종 중 ①·④·⑤ 셋이 **값이 아니라 구성**에서 생겼고, 검사가 순수 DB 위상 질의라 싸며, 고객 노출 이전에 **저장 자체를 거부**할 수 있다.

#### G2-1. 중복 단가 벡터 탐지 [결함 ① 정면]
- **검사**: 한 공식(`frm_cd`)에 물린 구성요소들에 대해, 각 구성요소의 (차원조합 → 단가) 집합을 정규화한 **지문(fingerprint)** 을 만들고, **두 구성요소의 지문이 동일**하면 저장 거부.
- **왜 잡히는가**: 캔버스행잉포스터는 나무봉 부과금을 담은 구성요소가 둘이고 **단가 격자가 같다.** A2 에서 두 값이 20,000 으로 일치해 단일 사이즈 점검이 통과했지만, 지문은 사이즈 전체를 보므로 **한 사이즈의 우연 일치에 속지 않는다.**
- **실패 문구**: `공식 '{frm_nm}' 안에 단가표가 완전히 같은 구성요소가 2개 있습니다: '{A}' · '{B}'. 같은 비용이 두 번 더해집니다 — 하나를 빼거나, 한쪽 단가표를 실제 값으로 고치세요.`
- **비용**: 소~중(구성요소당 단가행 조회 1회). **오탐 위험**: 낮음. 「의도적으로 같은 값인 서로 다른 항목」은 존재할 수 있으므로 **강한 경고 + 확인** 등급이 안전(위험 회피형 팀이면 차단).

#### G2-2. 고아 구성요소 감사 [결함 ①의 나머지 절반]
- **검사**: `t_prc_price_components` 중 살아 있으나 **어느 `t_prc_formula_components` 에도 물리지 않은** 것을 나열. 특히 **단가행을 보유한** 고아를 상단에 올린다.
- **왜**: 결함 ①의 본품 구성요소는 「올바른 값을 가진 채 아무 데도 안 물린」 상태였다. 엔진 정본 §6 은 이 유형을 **9개 / 172행**으로 기록(2026-08-28, 재실측 필요).
- **위치**: 공식 저장 시 경고 + `tools/` 감사 리포트
- **실패 문구**(경고): `⚠ 단가가 등록돼 있는데 어느 공식에도 연결되지 않은 구성요소가 {n}개 있습니다: {목록}. 이 상품 것이라면 공식에 추가하세요 — 지금은 가격에 전혀 반영되지 않습니다.`
- **비용**: 극소(쿼리 1). **오탐 위험**: 낮음(의도적 보류분이 있을 수 있어 경고 등급).

#### G2-3. 다중 옵션그룹 구성요소 차단 [결함 ⑤ 정면]
- **검사**: 한 공식 안에서 `use_dims` 에 `opt_cd` 를 쓰는 구성요소들의 **소속 옵션그룹이 2개 이상**이면 저장 거부.
- **근거**: `_workspace/pricing-principles/component-split-rule.md` §7 의 규칙 **C1** 이 이미 이 형태로 서술돼 있고, 전수 118공식 중 위반 **2건**(`PRF_POSTER_BANNER_N`·`PRF_POSTER_BANNER_M`)으로 측정돼 있다. 런타임 근거는 `selections.opt_cd` 가 스칼라이고 렌더러가 첫 그룹만 싣는 것(`widget_renderer.js:4250-4266`).
- **실패 문구**: `이 공식은 서로 다른 옵션그룹({A}·{B})의 옵션에 값을 매기는 구성요소를 함께 갖고 있습니다. 위젯은 옵션을 하나만 서버로 보내므로 한쪽은 반드시 과금에서 빠집니다. 공식을 나누거나, 한쪽을 다른 차원(자재·공정)으로 옮기세요.`
- **비용**: 소(조인 1). **오탐 위험**: 낮음 — 다만 기존 2건이 즉시 저장 불가가 되므로 **선(先)교정 후(後)차단** 순서 필수.

#### G2-4. 축 개편 커버리지 diff [결함 ④ 구조 쪽]
- **검사**: 공식의 구성요소 집합이 바뀌는 저장에서, **변경 전 공식이 커버하던 (사이즈·옵션) 조합 집합**과 **변경 후 집합**을 비교해 **사라진 조합**을 나열.
- **왜**: 폼보드 A1 은 단가행 삭제가 아니라 **구성요소 축 교체**의 부수 효과로 사라졌다. G1-3(행 삭제 미리보기)만으로는 안 잡힌다.
- **실패 문구**: `이 변경으로 다음 조합의 가격이 사라집니다: A1(594x841mm). 의도한 것이면 [확인]을 누르고, 아니라면 새 구성요소에 해당 행을 먼저 넣으세요.`
- **비용**: 중. **오탐 위험**: 낮음(정보 제시형).

### L3. 게시 시점 (위젯 버전이 라이브로 올라갈 때)

#### G3-1. 가격 검토 서명 요구 [결함 ⑥ 정면 · 4-eyes 최소형]
- **검사**: `publish_widget`(`widget_views.py:467`) 진입 시, 대상 `prd_cd` 의 **가격 검토 기록**이 (a) 존재하고 (b) 현재 단가표 상태의 해시와 일치하는지 확인. 불일치·부재면 **`ver_note` 에 검토자 서명 없이는 게시 거부**.
- **최소 구현**: 새 테이블 없이 `ver_note` 규약으로 시작한다 — 「가격검토: {이름} / {단가표해시 앞 8자}」 형식. 해시는 그 상품 공식에 물린 전 `t_prc_component_prices` 행의 정렬 다이제스트.
- **왜 이 형태인가**: 131건이 이미 `ver_note` 에 「가격 미검토」라고 **자기 신고**를 남겼다. 그 필드를 판정 재료로 승격시키면 신규 개발이 거의 없다.
- **실패 문구**: `이 상품의 가격이 아직 검토되지 않았습니다(또는 검토 이후 단가표가 바뀌었습니다). 가격뷰어에서 값을 확인한 뒤 게시 메모에 「가격검토: 이름」을 적고 다시 게시하세요.`
- **비용**: 소~중. **오탐 위험**: 낮음. **잡는 것**: ⑥ (그리고 ①②④가 검토 없이 라이브에 도달하는 경로를 닫는다)

#### G3-2. 게시 전 권위 대조 게이트 (비동기·차단형)
- **검사**: 게시 요청 시 그 상품에 대해 L4 재조정(아래)을 **1상품만** 돌리고, 셀 불일치가 있으면 게시 거부.
- **왜 비동기가 아니라 차단인가**: 게시는 드문 이벤트고 1상품 대조는 저렴하다. 반면 `start_price` 재계산은 **의도적으로 비동기 best-effort** 로 돼 있다(`widget_views.py:534-549`) — 그 자리에 무거운 검사를 넣으면 게시 응답이 멈춘 것처럼 보인다. **권위 대조는 게시 요청 경로에, 시작가 재계산은 지금처럼 백그라운드에** 둔다.
- **잡는 것**: ①②④ — **고객이 보기 전 마지막 관문**

#### G3-3. 셋트 경로 대칭화 (`widget_api.py:1877`)
- **검사**: `_filter_set` 의 `ok` 를 `_filter_single`(`:1833`)과 동일하게 `bool(res.get("ok")) and final_price is not None` 로. 그리고 `_price_gap_errors` 를 셋트 경로에도 배선(`:728` 의 「단일 전용」 해제).
- **비용**: 극소(2줄) + 셋트 gap 오탐 검증. **오탐 위험**: 중 — 셋트 구성원 gap 의 정상 패턴을 먼저 측정해야 한다(§미확정 3).

### L4. 회귀 (주기 실행 — 권위 ↔ 라이브 재조정)

#### G4-1. 셀 단위 권위 대조 [결함 ②·④ 정면 · 이 설계의 심장]
- **검사**: `_workspace/postersign-audit/parse_excel.py` 를 **전 19시트로 일반화**하고, `diff.py` 를 개수 비교에서 **셀 단위 값 비교**로 올린다. 산출 3분류:
  - `MISSING` — 엑셀에 있는데 라이브에 없음
  - `EXTRA` — 라이브에 있는데 엑셀에 없음
  - `VALUE_MISMATCH` — 키는 같은데 값이 다름 ← **회전이 여기서만 잡힌다**
- **[HARD] 스코핑 규칙 인코딩**: 분모는 **라이브 기준**이다. 엑셀에 있는데 라이브에 없으면 **미출시이지 결함이 아니다.** 구체적으로:
  - 상품: `t_prd_products.use_yn='Y' AND coalesce(del_yn,'N')<>'Y'`
  - 게시 도달: 활성 게시 위젯(`t_wgt_widgets.sts_typ_cd='WGT_STS_TYPE.02'` + `t_wgt_widget_versions.act_yn='Y'`)이 있는 상품만 `MISSING` 을 결함으로 승격, 나머지는 `INFO`
  - 이 판정은 **`start_price.targets`(`start_price.py:53-79`)와 `verify_zero_quote` 의 분모 판정을 그대로 재사용**한다 — 렌즈를 새로 만들지 않는다.
  - 논리삭제 행(`del_yn='Y'`)은 라이브 쪽 집계에서 제외.
- **위치**: `tools/reconcile_authority.py`(신규) — `--sheet` 로 시트 지정, `--json`, 결함 시 exit 1
- **비용**: 중(시트별 파서 규칙이 시트마다 다름 — 포스터사인 파서가 이미 검증된 템플릿)
- **오탐 위험**: **중~고**, 그리고 **여기가 이 설계 전체의 최대 위험 지점**이다. 완화는 세 가지: 스코핑 규칙 강제 · 시트 1개씩 순차 도입(포스터사인 → 나머지) · 첫 실행은 **경고 전용 모드**로 며칠 돌려 오탐 카탈로그를 만든 뒤 게이트에 물린다.

#### G4-2. 견적 스냅샷 승인 테스트 [결함 ④ 시계열 · B-1 원리]
- **검사**: 활성 게시 위젯 전 상품에 대해 대표 조합 N개의 `_price_core` 응답(`supply`·구성요소별 `subtotal`)을 스냅샷으로 커밋. 매 실행에서 **차이가 있으면 실패**하고, 사람이 **승인해야** 스냅샷이 갱신된다.
- **왜 이게 ④를 잡는가**: 폼보드 A1 소실은 「어떤 값이 틀렸다」가 아니라 「어제는 나오던 값이 오늘 안 나온다」는 사건이다. 정답을 몰라도 **변화**는 탐지된다.
- **구현 재사용**: 조합 생성·평가는 `tools/audit_published_prices.py` 가 이미 렌더러 재사용 + `api_price` 미러로 하고 있다. 출력 직렬화 + 스냅샷 비교만 얹으면 된다. **새 도구를 만들지 말 것.**
- **비용**: 소(기존 도구 확장). **오탐 위험**: 낮음 — 단, 의도적 가격 개정 때 스냅샷 갱신이 **일상 작업**이 되므로 승인 흐름을 가볍게(파일 커밋 1회) 유지해야 한다.

#### G4-3. 기존 두 도구 CI·크론 배선
- `tools/verify_zero_quote.py` — **야간 크론 + 게시 전 해당 상품만**. exit 1 을 알림으로.
- `tools/audit_published_prices.py` — 야간 전수, 결과를 관리자 화면 대시보드로.
- `tools/recalc_start_prices.py:44-46` — 현재 상품별 실패가 exit 0. **완화를 되돌리지 말고**(양치기 방지 판단은 옳다) 대신 **실패 건수 추세**를 알림 기준으로 삼는다(전일 대비 증가 시 알림).
- **비용**: 극소. **이것이 신규 개발 대비 가장 높은 즉시 수익이다.**

### D-4. 문구 원칙

실패 문구는 **무엇이 틀렸는지 + 무엇을 하면 되는지 + 그대로 두면 무슨 일이 생기는지** 셋을 담는다. 세 번째가 중요하다 — 0원과 대량 게시를 만들어 낸 것은 「해도 되는 줄 알았다」이지 부주의가 아니다.
